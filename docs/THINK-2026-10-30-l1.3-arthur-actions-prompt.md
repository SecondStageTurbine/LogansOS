# THINK: L1.3, Arthur's actions in image A behind a WM permission prompt

**Seat B, 2026-10-30.** Dispatch: `Plans/DISPATCH-2026-10-30-lanes-L1-L2-L7.md` (Seat B, L1.3). Gap map:
`docs/THINK-2026-10-30-playbook-gap-map.md` L1 (3) and decision 4. This THINK fixes the shape before code, because
L1.3 adds a protocol opcode, moves the grant authority from neo-shell to the WM, and is the base L2.1–L2.4 build on.

## 1. What exists, and what image A has

- **Actions** (`userland/neo-arthur`): the A1–A3 grammar (`agentic_action_logic.rs`), tiered R/T/L/X/U
  (`agentic_effect_tier`), postures (default Yolo, ADR-069), typed confirm for L/X, copy-before-write undo
  (`arthur-reversibility`, `reversibility_logic.rs`) and user stakes policy (`stakes.json`). Every action goes
  through `libneo::action::execute_action_with` against Arthur's in-process mirror of the caps it was granted.
- **Grants** (ADR-060): `grants.json` v1 (`libneo/src/grant_store.rs`) is a record, never the authority. neo-shell
  reads it, derives file caps from its own root and `sys_grant`s them to Arthur after spawn; `/revoke` revokes the
  derived cap (transitively, through the cap graph) and rewrites the record. `GrantDecision {Session, Always, No}`
  and `apply_grant_decision` ("Always" → a record entry) are built and host-tested but never wired.
- **Confirm** is the next chat line (`ConversationState`, a 2-turn TTL). There is no trusted channel: the
  model's own output and the user's answer arrive the same way.
- **Image A** has none of this. Its Arthur (`desktop-session`, `desktop-home`, …) is chat plus `list /` (the Lens);
  `run_desktop_session` calls `respond_to_input` without the action executor, so the action features don't even
  compile there. The WM spawns Arthur with the session channel and its memory directory; there is no shell.
  Kernel: no `file-caps`, no `net-dial-cap`, no `cap-rooted-open`.

## 2. The one dependency that bounds the claim

Until **L1.1** (`cap-rooted-open` after K1b, seat A) is in image A, any process, Arthur included, can open any
root path itself. So in image A before L1.1, a grant limits what Arthur's **action path** does (the mirror, and the
kernel cap it holds for a granted path), but it does not stop a compromised Arthur from calling `SYS_OPEN` directly.
L1.3 turns on `file-caps` (the grants become real kernel caps, derivable, revocable) and says this plainly in the
PR and the ledger; **L1.1 is what makes the boundary a kernel boundary**. Nothing in L1.3 depends on L1.1's order:
when L1.1 lands, Arthur's root cap is narrowed to its own subtree, and the prompt below is then the only way it
gets anything outside it.

## 3. Decisions

**D1. The WM is the grant authority on the desktop.** It already owns the session, holds `/`, and is the only
writer of `.system/`. It takes neo-shell's role: it reads the grant record, derives each cap from its own root and
lends it over the client's channel (`grant_over`, the same O/R/grant/A exchange the LaunchCap uses).
*As built (L1.3a):* lending is **on demand**, per action, not at launch. Arthur holds no file grant of its own and
sends `OP_PERMISSION` for each action. A path and action the record already holds is lent with no prompt, anything
else prompts. A file handle has no seek, so a cap kept between reads would read on from its end; a fresh cap per
action avoids that and keeps the lending path single.

**D2. The record moves to the WM-only store.** `/neofs/.system/arthur-grants.json` (the `system-store` cap, #224),
same v1 format (`grant_store`), **not** `/neofs/.arthur/grants.json`: that directory is Arthur's own, so a record
there would let Arthur grant itself on the next boot. ADR-060 already says the file is never the authority; on the
desktop it also can't be written by the party it governs. The serial/shell path keeps its file (unchanged).

**D3. `OP_PERMISSION` (opcode 12), Arthur → WM, a parked request like `OP_LAUNCH`.** The fixed message carries the
identity, the action kind (`u16`: 1 read, 2 list, 3 write; the A1/A2 kinds only, D6) and the path length (the scope
follows from the kind). The 72-byte message has no room for a path, so **the path follows as one raw
message** on the same channel (at most 255 bytes, normalized and checked by the WM: absolute, under `/neofs`, not
under `.system/`). Arthur stays parked for the reply, as in `OP_LAUNCH`, while the WM serves its own loop.

**D4. The prompt is a WM-owned trusted view, the lock screen's pattern.** WM focus (HANDOFF, the queue discarded),
the client held, only the WM's frames composited. Text: "Arthur wants to **read** /neofs/notes.txt" with three
answers: **Allow once**, **Always**, **Deny** (keys 1/2/3, Enter = Allow once, Esc = Deny; pointer clicks on the
three buttons). The text is built by the WM from the kind and the checked path, never from Arthur's words. The lock
outranks the prompt: if the lock engages, the prompt is answered Deny and the request refused (nothing is decided
behind a lock). A second `OP_PERMISSION` while one is up is refused (`BadState`).

**D5. What each answer does (the authority, not just a reply).**
- **Allow once:** the WM derives the cap for that path with the action's rights and lends it; Arthur performs the
  one action and sends `OP_PERMISSION_DONE`; the WM then **revokes** the derived cap (so the lending is enforced by
  the cap graph, not by Arthur forgetting it). A client that never sends DONE loses it at its next request or the
  session's end. *As built, every lent cap is revoked at DONE*, Always included: the record, not a held cap, is what
  makes Always last.
- **Always:** as Allow once, and the WM writes the record entry (grants.json v1, `granted_by: "wm-prompt"`), so later
  requests for it, this session and after a reboot, are lent with no prompt.
- **Deny:** nothing is lent; the WM remembers the denial for the session (the THINK-06-18 D4 rule: no re-prompt
  storm), and later requests for the same path and kind are refused without a prompt until the session ends.

**D6. Image A turns on A1 and A2 only.** Read, list, change directory, status, and (in write mode, D7) write. The A3
kinds (kill, spawn, external send, model load, trash, move) run against stub syscalls today
(`AgenticA3Syscalls`) and stay out of image A; the confirm-typed path stays out with them. Reversibility
(copy-before-write undo) comes in with writes.

**D7. Read-only is the default; write mode is one switch (J.c.'s open decision 4).** A WM mode with two values:
- **Read-only (default):** only R-tier actions can be asked for. A T-tier action (write) is refused before any
  prompt, with Arthur saying so ("I can only read for now"). Reads inside a grant run; reads outside one prompt.
- **Write:** T-tier actions are allowed through the same prompt (the prompt then says "change"), with undo armed.
The mode is a neo-init feature for now (`arthur-actions-write`, off), so the product image builds read-only and a
scenario builds the other. When J.c. decides, it either flips that feature or becomes a WM-only setting
(settings-core's WM-only keys, #222's split). Both modes are gated by scenarios from the first PR.

**D8. Kill-switch.** `arthur-actions` (neo-init + neo-arthur, product image) off ⇒ today's image A exactly: no opcode
handled, no record read, no caps lent, Arthur chat plus `list /`. A scenario proves the off build's behaviour is the
previous layer's (the `desktop_lens_boot` / `login_*` expectations unchanged).

**D9. L2 hooks in here.** L2.1's action log lives in `.system/` and only the WM writes it, so the WM is where log
entries are made: every prompt and answer, every grant lent, revoked or recorded, and (from `OP_PERMISSION_DONE`,
which carries the outcome) every action Arthur ran with a prompt-granted cap. Actions inside a standing grant need a
report too: L2.1 adds `OP_ACTION_REPORT` (Arthur → WM, fire-and-forget, the intent text in a following raw message).
L1.3 does not build the log; it keeps the WM as the single point the log will hook.

## 4. Slices (each its own PR, each with its scenario)

1. **L1.3a, the prompt and the authority, read-only.** Kernel `file-caps` in image A (pairing assert). The WM: the
   record in `.system/`, launch-time lending, `OP_PERMISSION` + the trusted view + D5's three answers + `DONE` and
   the revoke. Arthur on the desktop: the A1 executor wired into `run_desktop_session`, the prompt on a miss.
   Scenario `desktop_arthur_permission`: a read outside the grants prompts; Allow once reads and the cap is revoked
   after (a second read prompts again); Always writes the record and a reboot lends it (no prompt); Deny refuses and
   doesn't re-prompt; a write in read-only mode is refused with no prompt; the lock during a prompt answers Deny.
   Controls: the revoke skipped (the second read runs unprompted); the record in `.arthur/` (Arthur's own write to
   it takes effect next boot).
2. **L1.3b, write mode.** `arthur-actions-write`: writes through the prompt, copy-before-write undo, "undo" in chat.
   Scenario: Allow once a write, undo restores the bytes.
3. **Product image:** `arthur-actions` in image A's feature lists with the pairing asserts, after (1) gates.

## 6. Found while building L1.3a

- **`file-caps` without `cap-rooted-open` breaks directory inheritance.** With `file-caps`, `sys_open` adds the owner
  meta bits (`DERIVE`/`GRANT`) to the handle, and spawn without `cap-rooted-open` admits only a directory whose rights
  are *exactly* LOOKUP|READDIR (`is_spawn_inheritable_dir`). So the WM's spawn of Arthur with its memory directory
  failed (`EPERM`, neo-init exit 61). L1.3a works around it in the WM: Arthur is handed a derived child with exactly
  those rights (`plain_dir`). The kernel rule itself is seat A's area (L1.1 turns on `cap-rooted-open`, whose arm
  admits a directory carrying GRANT); noted for them, not changed here.
