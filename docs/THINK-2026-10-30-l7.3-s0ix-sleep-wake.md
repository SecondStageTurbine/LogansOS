# THINK: sleep and wake on the Zenbook (S0ix), L7.3 part 2

**Status:** design THINK, seat C, 2026-10-30. Asked for by `Plans/DISPATCH-2026-10-30-lanes-L1-L2-L7.md` (L7.3: "then,
as a design THINK first, sleep/wake (S0ix) on the Zenbook"). Nothing here is built. §9 lists the decisions for J.c.

**Sources.**
- The Zenbook's own firmware: `fixtures/acpi/zenbook-s14-ux5406aa-303/`, firmware UX5406AA.303, disassembled with
  `iasl -d` for this THINK. Object paths below are AML paths, so they don't depend on the disassembler's line numbers.
- The kernel on `main` at `e2483b29`.
- Prior art, read for principle (§7).

## 1. The short answer

- **The Zenbook is a Modern Standby machine.** Its FADT has `LOW_POWER_S0` set (flags `0x20c4f5`). It has the Intel
  power-engine device `\_SB.PEPD` (`INT33A1`, compatible `PNP0D80`), which offers the Intel and the Microsoft
  low-power `_DSM`s, and an LPIT. This is the S0ix path Windows uses on it.
- **"Asleep" has to be measured, not assumed.** The LPIT names two hardware counters:
  - package C10 residency, MSR `0x632`;
  - the PMC's SLP_S0 residency, a 32-bit counter in memory at `0xFE00193C`, 8197 Hz.

  Only a rising SLP_S0 count proves the platform reached S0ix. A screen-dark, halted kernel without it is just an idle
  laptop draining its battery. **The first rung is the instrument (§5, Z0 and Z1)**, read on screen before and after.
- **We are several dependencies away from real S0ix, and two of them are deep:**
  1. **The display.** The SoC can't reach SLP_S0 with the display engine scanning out. We draw through the firmware's
     GOP framebuffer and have no display driver for this GPU, so nothing of ours can turn the pipes off.
  2. **AML at runtime.** The `_DSM` notifications the firmware expects go to the embedded controller (EC), which
     needs the in-kernel interpreter with EC operation regions (OT-86 rungs L4, L6, L7, L9). Wake by power button and
     lid comes through the EC and an SCI as well, and the kernel has no SCI handler today.

  The rest is ordinary kernel work we already know how to do:
  - MWAIT idle instead of `sti; hlt`;
  - stopping the 100 Hz tick, whose 10 ms period is under the LPIT's 30 ms minimum residency;
  - device quiesce and resume, which OT-90 P3b builds for shutdown;
  - putting the NPU and IPU into D3.
- **ACPI S3 is not the shortcut it looks like.** `_S3` is there (SLP_TYP 5), but the firmware is built for Modern
  Standby, and Windows never exercises its S3 path on this machine. S3 also needs `_PTS`/`_WAK` (AML), the FACS
  waking vector (the FACS isn't in the dump), a 16-bit resume trampoline, and a full re-initialization of every
  device, the IOMMU and the APs. §4 recommends against it as the product path.
- **Recommendation.** Build the measurable, dependency-free rungs now: the instrument, MWAIT idle, tickless sleep
  and the quiesce/resume split. Each one pays off on its own: MWAIT alone cuts idle power, and the instrument tells us
  where we are. Gate true S0ix on two decisions for J.c.: a display path (§9, D1) and the OT-86 runtime-AML rungs
  (D2). Until both land, the product claim is **"screen-off idle"**, and it's labelled as that, not as sleep.

## 2. What the Zenbook's firmware asks for

| Item | The firmware | What it means for us |
|---|---|---|
| FADT flags | `0x20c4f5`: `LOW_POWER_S0` (bit 21) set, `HW_REDUCED` (bit 20) clear, `PWR_BUTTON` (bit 4) and `SLP_BUTTON` (bit 5) set | Modern Standby. Bits 4 and 5 set mean neither button is a fixed-feature button: the power button is a control-method device (`PNP0C0C`), so its press arrives through the EC and a GPE, not the PM1 status bit. |
| Sleep packages | `\_S0` (0), `\_S3` (5), `\_S4` (6), `\_S5` (7), all constant `Name`s at root scope | S3 exists on paper. §4 weighs it. |
| `\_PTS`, `\_WAK` | `_PTS` calls `EC0.EC0S`, `LPCB.LPTS`, `TPM.TPTS`, `MC.NPTS`, `RPTS`; `_WAK` calls the matching `*WAK`/`EC0W` | S3 needs both. They touch the EC, so they need EC regions. |
| `\_SB.PEPD._DSM`, Intel UUID `c4eb40a0-6cd2-11e2-bcfd-0800200c9a66` | Function 0 returns `0x7F`, so functions 1-6 are offered: 1 the device constraints (`DEVY`, 118 entries), 2 crash dump, 3 display off (`GFX0.HPMS`, EC command `0xB7`, LEDs), 4 display on (EC `0xB8`), 5 LPI entry (EC `0xAE`), 6 LPI exit (EC `0xAF`) | Functions 3-6 send EC commands. The body ignores the revision argument (`Arg1`). |
| `\_SB.PEPD._DSM`, Microsoft UUID `11e00d56-ce64-47ce-837b-1f898f9aa461` | Function 0 returns `0x0381`, so only functions 7 (sleep entry: `ECEN`, `EC0.ST9A`), 8 (sleep exit: `ECEX`, `EC0.ST9B`) and 9 (display-on intent) are offered. Functions 3-6 of this UUID are **not** offered | Call only what function 0 advertises. Linux and FreeBSD call by the mask; a caller that assumed the usual Microsoft 3-6 set would invoke undefined functions. |
| LPIT entry 0 | MWAIT hint `0x60` (FFH, bit offset 2), minimum residency 30 000 µs, latency 3 000 µs, counter MSR `0x632` (package C10), frequency 0 (the TSC) | The idle state to enter, and a residency floor our tick currently breaks. |
| LPIT entry 1 | Same trigger and residency; counter in memory at `0xFE00193C`, 32-bit, 8197 Hz | The SLP_S0 counter: the PMC base `0xFE000000` plus offset `0x193C`. 8197 Hz is the 122 µs tick Linux's PMC driver uses for this counter on the client parts (cross-check, §7). |
| LPIT entry 2 | Disabled | Ignore. |
| Lid, power, EC | `PNP0C0D` (lid, `_LID`), `PNP0C0C` (power button), `ACPI0003` (AC adapter), `PNP0C09` (EC0, with `_GPE`), an ECDT | Wake events that come through the EC need an SCI handler, a GPE dispatch, EC queries (`_Qxx`) and AML. |
| FACS | `FIRMWARE_CTRL` `0x5CB63000`, `X_FIRMWARE_CTRL` 0. The table is not in the Windows dump | Only S3 needs it (the waking vector). Capture it with a Linux dump if S3 is ever pursued (§9, D3). |
| CPU | Panther Lake, Core Ultra 9 386H (`provenance.json`) | Linux's Panther Lake PMC support puts the NPU (`0xb03e`) and IPU (`0xb05d`) into D3 itself, because without drivers they block package C-states (§7). We have drivers for neither. |

## 3. What the kernel has, and lacks

| Needed for S0ix | On `main` | Gap |
|---|---|---|
| A deep idle state | Idle threads `sti; hlt` (`sched/scheduler.rs`, `idle_thread_entry`): C1 at best | MWAIT with the LPIT hint (`0x60`) on every CPU, after checking CPUID leaf 5 |
| A long, quiet interval | A 100 Hz periodic tick (PIT, or the LAPIC timer under `lapic-timer`), and `tick-sleep` naps on it | During sleep, stop the tick and arm one far deadline, or none. The LAPIC timer may stop in deep C-states unless CPUID.6:EAX[2] (ARAT) is set, so the wake source can't be the LAPIC timer without ARAT. |
| Devices quiet, in D3, with their DMA stopped | Nothing for sleep. OT-90 P3b (next in L1.4) designs a per-driver quiesce for shutdown | Make P3b's hook a **quiesce/resume pair** from the start (§8), plus D3 for the NPU and IPU |
| The display off | GOP framebuffer only; no display driver for this GPU | Deep (§9, D1) |
| The `_DSM` notifications | No AML at runtime. `third_party/acpi-loganfy` runs only in the host grade tool | OT-86 L4 (UUID compare above 4 bytes), L6 (the mediated region seam), L7 (the step budget), L9 (EC regions) |
| A wake source | The i8042 keyboard IRQ (the Zenbook's keyboard is `PS2K`) and our own device IRQs | Power button and lid need the SCI, GPE dispatch and EC queries. Once function 7 has put the EC in its standby mode, it's unproven whether a keypress still raises IRQ 1 (§6, F6). |
| CPU power policy | `hwp-performance` sets HWP to performance in image A | Restore the energy-performance preference before sleep and set it again on wake. |

## 4. Three meanings of "sleep", compared

| Option | What it is | Needs | Battery effect | Risk on the Zenbook |
|---|---|---|---|---|
| **A. Screen-off idle** | Every CPU in MWAIT C10, the tick stopped, devices quiesced, the framebuffer blanked to black (the panel stays lit unless the backlight is turned off, §9 D1) | Z0-Z5 of §5. No AML, no display driver | Package C-states rise, SLP_S0 stays 0. Better than today's `hlt` loop, nowhere near Windows' standby | Low: no firmware call, and nothing outside the kernel's own control |
| **B. S0ix (s2idle)** | Option A, plus the display engine off, the `_DSM` notifications, SCI wake, and SLP_S0 residency rising | A, plus the display path (D1) and OT-86 L4/L6/L7/L9 plus an SCI/GPE/EC-query handler | Real standby: the firmware's design point | Medium. AML runs firmware code on the EC. OT-86's two standing constraints (mediated regions, the step budget) are what bound it |
| **C. ACPI S3** | The PM1 write with SLP_TYP 5, firmware-held DRAM, resume through the FACS waking vector | `_PTS`/`_WAK` (AML, EC), the FACS, a 16-bit trampoline, a full re-init of every device, the IOMMU (VT-d) and the APs | If the firmware's S3 works, the best of the three | **High and unknown.** Windows uses Modern Standby here, so this firmware path may be untested or stubbed. A failed resume means a forced power-off, so test it only as a probe (D3) |

**Recommendation: build toward B, through A.** Every rung of A is also a rung of B, and the instrument tells us
which one we've reached. C duplicates most of B's dependencies (AML, EC, device resume), adds the riskiest path,
and the firmware wasn't designed around it.

## 5. The ladder

Each rung is a separate PR with its own kill-switch, which must be bit-identical to the previous layer when off. Costs
are given as dependencies, cycles and gates (CLAUDE.md). "Zenbook run" means a joint J.c. run under
`docs/runbook-baremetal-zenbook-s14.md`, with photos of the fb console as the evidence, and the write guard on.

| Rung | What | Depends on | Kill-switch | Iterations / uncertainty | Gate |
|---|---|---|---|---|---|
| **Z0** | **The LPIT parser**: pure logic in `acpi/lpit_logic.rs`, with a host KAT whose byte oracle is the Zenbook's own `lpit.dat`, hand-decoded (entry 0: MSR `0x632`; entry 1: `0xFE00193C`, 32-bit, 8197 Hz; entry 2 disabled) | none | not compiled into the kernel | 1 (mechanical) | push CI |
| **Z1** | **The instrument.** On the fb console: CPUID leaf 5 (the MWAIT sub-states), CPUID.6 ARAT, and the deltas over a fixed idle window of the LPIT counters, `MSR_PKG_C2..C10_RESIDENCY` and `MSR_CORE_C6/C7` | Z0 | feature `power-residency-probe`, off in image A until J.c. asks for it | 1-2 (MSR access on this CPU family is the uncertainty) | QEMU (it must read 0 and not fault; QEMU has no PMC page, so the probe must handle an absent or unmapped counter) + **one Zenbook run**: the baseline, expected to show SLP_S0 at 0 and PC10 at about 0 |
| **Z2** | **MWAIT idle**: idle threads `monitor/mwait` with the deepest LPIT hint when CPUID leaf 5 allows it, else `hlt`. A wake IPI stays a wake | Z1 for the measurement | feature `mwait-idle`; off ≡ `sti; hlt` | 2-3. The CP-19..CP-28 AP-idle and wake-handoff class applies. Cross-family AAG, since this is SMP core | 4-shard QEMU + a Zenbook run: PC-state residency rises over Z1's baseline |
| **Z3** | **Tickless sleep**: `power::sleep_enter` stops the periodic tick on every CPU and arms one far deadline. TSC-deadline needs ARAT, otherwise none: then the wake is a device IRQ. Ticks are re-synchronized from the TSC on wake, so time doesn't jump | Z2 | feature `sleep-tickless` | 3+. Timekeeping across the gap is the new seam: `TICKS`, the scheduler's deadlines, `net-tick`, `tick-sleep`. Pitfall bank: CP-19..CP-28 and the timer classes | 4-shard QEMU (enter, keypress, wake, time continuous) + a Zenbook run |
| **Z4** | **The quiesce/resume pair** for each driver image A runs: NVMe (or VMD), i8042, the touchpad, `rtl8125` if bound. Plus the NPU and IPU forced to D3 by PCI ID, as Linux does on Panther Lake | OT-90 P3b's quiesce (§8) | per driver, and feature `sleep-quiesce` | many: one driver at a time, each its own small loop. NVMe power states and APST are the deepest | QEMU per driver + Zenbook runs |
| **Z5** | **Screen-off idle (option A) in the WM**: a Sleep item behind the same confirm as Shut down (L1.4 P5); the framebuffer blanked to black; a keypress wakes and redraws | Z3, Z4, L1.4 P4 (`SYS_POWER`) | feature `power-sleep-idle` | 2 | QEMU + a Zenbook run: SLP_S0 stays 0 and is reported honestly; PC10 rises |
| **Z6** | **The `_DSM` notifications**: Intel 3/5 on entry and 6/4 on exit, Microsoft 7/8/9, each only if function 0 advertises it, in FreeBSD's and Linux's order (§7) | OT-86 L4, L6, L7, L9 merged, and the in-kernel interpreter | feature `sleep-lps0-dsm` | many (firmware code on the EC). The capture is the per-call result and the EC status | Zenbook runs |
| **Z7** | **SCI, GPE and EC queries** for the power button and the lid as wake sources, and the lid as a sleep trigger | Z6's interpreter, plus an SCI handler | feature `sci-gpe` | many | Zenbook runs |
| **Z8** | **The display path** (§9, D1): pipes off and panel power down | J.c.'s D1 decision | its own | unknown-depth: a from-scratch display driver for this GPU, or a firmware route | Zenbook runs: **SLP_S0 > 0 is the S0ix acceptance proof** |

Z0-Z3 and Z5 need nothing that isn't on `main` or in L1.4. Z4 rides on P3b. Z6 and Z7 wait on OT-86. Z8 waits on D1.
**The acceptance bar for "S0ix works"** (CLAUDE.md: merge bar vs acceptance bar) is the SLP_S0 delta on the Zenbook,
read through Z1's instrument, over a sleep of at least a minute, followed by a clean wake.

## 6. Failure modes and discriminators (blind hardware: the Zenbook has no serial port)

Pre-seeded from prior art and this firmware, not from first principles. Every run prints the Z1 block before
and after, so a failure reads off one photo.

| # | How a run fails even when the rung's own change is right | Discriminator (on screen) |
|---|---|---|
| F1 | PC10 or SLP_S0 stays 0 because some IP never idles: the NPU or IPU without a driver (Linux's PTL fix-up), the display engine, an LTR from a PCIe device, or a USB controller | Z1 prints per-rung residencies (PC2 through PC10) to localize the depth reached. Z4 prints each device's D-state before entry. Reading the PMC's IP-blocker status (Linux reads it at offset `0x2004` on these parts) is a later capture, in Z1's second iteration, if F1 hits |
| F2 | The LAPIC timer stops in C10 and the wake deadline never fires | Z1 prints CPUID.6 ARAT. Without ARAT, Z3 doesn't arm the LAPIC deadline, and the PIT/HPET are the only timer wake |
| F3 | The tick keeps running (some path re-arms it) and residency stays under the LPIT's 30 ms | Z3 counts timer interrupts per CPU across the sleep, and the count must be 0 or 1 |
| F4 | MWAIT is advertised but the hint is wrong for this CPU (C-state hints are model-specific) | Z1 prints CPUID.5 EDX, the sub-state counts. Z2 uses the LPIT's hint and falls back to the deepest one CPUID lists |
| F5 | A wake IPI is lost because an AP armed MONITOR on a line the waker doesn't write | Z2's AP-idle scenario at NEO_SMP=4 (the CP-19..CP-28 class), with a wake-latency count per CPU |
| F6 | After Microsoft `_DSM` 7 (Z6), the EC stops raising IRQ 1 for keypresses and routes them as SCI events instead | Z6 logs whether a keypress raised IRQ 1, an SCI, or neither. Z6 doesn't ship without Z7 if it's an SCI |
| F7 | Time jumps or stalls after wake (`TICKS` versus the TSC) | Z3 prints the TSC and `TICKS` deltas across the sleep, and the scheduler's deadlines must not fire early or late |
| F8 | A device loses its state across D3 (NVMe queues, the touchpad's HID descriptor) | Z4's resume re-probes and prints each driver's resume verdict. A failed resume degrades that driver; it doesn't panic |
| F9 | The run writes the Windows NVMe | Impossible by construction: every block write goes through the write guard (PR #85/#88), and sleep doesn't write disks. Z4's NVMe quiesce only issues admin commands to the guard-armed disk |

## 8. What this asks of other lanes

- **OT-90 P3b (L1.4, mine, next).** Shutdown needs only a per-driver *quiesce*. Sleep needs quiesce *and* resume.
  P3b will define the hook as a pair, `quiesce()` and `resume()`, with `resume()` unimplemented (and refused) for
  drivers until Z4 fills them in. That costs nothing now and avoids a second pass over every driver.
- **OT-86 (ACPI/AML).** Z6 and Z7 are a concrete consumer for L4 (UUID `_DSM`s), L6 (mediated regions), L7 (the step
  budget) and L9 (EC regions, `_REG`). The `PEPD._DSM` calls (Intel 3-6, Microsoft 7-8) are worth adding
  to the corpus probes, so the grade measures them on the host before Z6 needs them in the kernel.
- **The pitfall bank.** Z2 and Z3 touch the AP-idle and wake-handoff class (CP-19..CP-28) and the timer seams. Their
  dispatches carry the pitfall table, and their merges a cross-family AAG lens (SMP core).

## 9. Decisions for J.c.

- **D1, the display path for real S0ix.** Pick one:
  - (a) a display driver for this GPU's display engine: unknown depth, from scratch;
  - (b) leave the display on, and ship option A only, honestly labelled "screen-off idle";
  - (c) investigate whether the firmware's `_DSM` 3 (`GFX0.HPMS`) plus a GOP-level blank is enough for the PMC. The
    PM's prior is that it isn't, but Z1 and Z5 will measure it.

  **Recommendation: (b) now, and measure (c) at Z5.**
- **D2, priority of the OT-86 runtime-AML rungs (L4, L6, L7, L9).** Z6 and Z7 can't start without them, and they serve
  other lanes too (the touchpad and touchscreen `_DSM`s, the EC).
- **D3, an S3 probe.** One Linux live-USB run on the Zenbook: `/sys/power/mem_sleep`, an `rtcwake -m mem` test, and a
  FACS dump. It would show whether this firmware's S3 path works at all. It writes no disk, but it needs a
  Linux stick (the Kingston is the image stick now). **Recommendation: not needed.** §4 recommends B over C either
  way, so do it only if D1 rules out B.
