# OT-61 C2.4 survey: the Stylo closure, and where layout really sits

**Seat:** D. **Date:** 2026-10-30. **Status:** survey for the ladder's second rung (`Plans/DISPATCH-2026-10-30-seat-d-browser.md`,
"Stylo / layout closure: the same method, extended to style and layout"). Nothing here is built. The build follows
on `claude/ot61-c2.4-stylo`, stacked on C2.3b (#245).

**The one-line finding.** Stylo can close now, by C2.3b's method: about 120 pure-Rust crates, every licence
permissive or MPL-2.0. **Servo's layout cannot close before C3.** `servo-layout` 0.7.0 links `servo-script`, and that
brings in `mozjs_sys` (SpiderMonkey's C++), `harfbuzz-sys`, `freetype-sys`, webrender and servo-media: 444 linked
crates. So this rung is **Stylo**, and Servo layout moves to just after C3, where the C++ runtime and the C font stack
it needs exist.

## 1. Method

- Scratch crates outside the repo depend on each candidate. Cargo resolves them against crates.io, and `cargo tree
  --target x86_64-unknown-none -e normal` gives what links. `x86_64-unknown-none` stands in for our target: it has
  no `unix` and no `windows` family, same as ours.
- Nothing was built or run. Per J.c.'s C2.3b decision, the closure's first build runs on the CI runners.
- Licences are from each crate's metadata. A repository's last commit comes from a shallow, blob-less clone
  (`git log -1`), read 2026-10-30.

## 3. Stylo on our target: what breaks (from reading the sources; *verify* items need the build)

1. **`rayon` + `num_cpus` (unconditional dependencies).** Stylo sizes its style thread pool as
   `max(num_cpus::get() * 3/4, 1)` (`global_style_data.rs`), and `num_cpus` falls back to a portable count on
   an unknown OS. With one thread there is **no pool**: Stylo styles sequentially on the calling thread. That is
   correct, just not parallel. A parallel pool later needs `std::thread::available_parallelism` (our PAL leaves it
   unsupported) or a `num_cpus` arm. That's an optimisation, not this rung. rayon's threads would be `std::thread`,
   which C1.3 already provides.
2. **`libc`** is pulled by `num_cpus`. On an OS libc doesn't know, it compiles to an empty module (`libc/src/lib.rs`:
   "non-supported targets: empty"). No break. *Verify.*
3. **`parking_lot`** is used throughout Stylo (`RwLock`, `Mutex`). C2.3b's parker patch applies unchanged; this
   rung reuses that patched copy.
4. **`std::env::var`** appears in `stylo/context.rs` (debug options) and `rayon-core` (`RAYON_NUM_THREADS`). In a
   sealed process our environment is empty, so these return `NotPresent` and the defaults apply. No break.
5. **`url`** names `std::net` types but opens nothing. Its IDNA path goes through `icu4x` (Unicode-3.0 data).
   No OS surface.
6. **`encoding_rs`** and `simdutf8` have compile-time SSE2 paths only. No break. `core_detect` reads CPUID; the same
   OSXSAVE rule C2.3b fixed in the kernel covers it.
7. **The build script runs Python.** `stylo/build.rs` generates the property code from Mako templates by running
   `python3` (it finds it on `PATH` or through `PYTHON3`). It is new: C2.3b's build-time code was Rust only. The CI
   runners need `python3`. The Mako sources are inside the published crate (vendored with it), so nothing is fetched.
   The Python it imports is bundled in the crate (`properties/vendored_python/`): Mako 1.3.10 (MIT, a wheel),
   toml 0.10.2 (MIT, a wheel; its repository's last commit is 2023-10-11 ⚠) and MarkupSafe (BSD-3-Clause, one
   source file from pallets/markupsafe `1251593`). Hashes and last commits are in `VENDORED.md`.
   **Decided (J.c., 2026-10-31; CLAUDE.md on `main`, `69550a3c`):** build-time Python is allowed, as long as it
   fetches nothing over the network. Its first run is on the CI runners, under the C2.3b ruling: the closure
   workflow's `stylo-build` job (`cargo xtask ot61-closure-build --stylo`), with `PIP_NO_INDEX=1` so a pip lookup
   would fail rather than fetch.
8. **Allocation.** Stylo's `servo_arc`, `thin-vec` and `hashbrown` go through std's global allocator, which is
   `neo-std-pal`'s `SyscallHeap`. Styling a real page allocates far more than parsing does; the smoke runs under
   the same mem-quota budget, so an overrun is a measured number, not a crash.

## 3b. Trap mining: Stylo's thread paths (Chad #219)

Read from the vendored sources (`third_party/ot61-browser/vendor`), since none of it has been built yet. Each trap gets
the observation that tells it apart when the C2.4 smoke runs.

1. **On our target Stylo builds no thread pool, by default.** `STYLE_THREAD_POOL` (`stylo-0.22.0/global_style_data.rs`)
   takes the `layout.threads` pref (default `-1`, `stylo_static_prefs`), else `max(num_cpus::get() * 3 / 4, 1)`, capped at
   6, and builds a pool only for more than one thread. `num_cpus` 1.17.0 has no branch for our `target_os` and returns
   **1** (`src/lib.rs`, the `not(any(...))` arm). So styling runs sequentially on the caller's thread and no Rayon
   worker exists. That's the safe default, and the smoke should assert it (`STYLE_THREAD_POOL.num_threads == None`), so
   that a later `num_cpus` or std change that turns the pool on is seen, not inherited.
2. **With `layout.threads` ≥ 2, the pool spawns through std.** Rayon calls Stylo's `thread_spawn`, which uses
   `std::thread::Builder` with a 256 KiB stack (`STYLE_THREAD_STACK_SIZE_KB`, `parallel.rs`; our std's minimum is also
   256 KiB) and so reaches `SYS_THREAD_CREATE`. That's gated on the process's BrowserRuntime `THREAD_SPAWN` right. Without
   it the spawn fails, `ThreadPoolBuilder::build()` returns `Err`, and Stylo keeps `pool = None` silently: sequential,
   with `num_threads` still `Some(n)`. **Discriminator:** `num_threads.is_some()` with no pool means a refused spawn,
   not a sequential choice.
3. **Idle workers spin, then sleep.** `rayon-core`'s `sleep/mod.rs` yields (`thread::yield_now`) for 32 rounds, then
   parks on a std `Mutex`/`Condvar` (our futex). The spin is bounded and yields into the kernel each round, so it doesn't
   need a tick. APs have none (the fact recorded in CP-86), and an unbounded spin there would never be preempted. The
   count is in rounds, not time (CP-80's class); with `yield_now` each round is one scheduler pass, not a `PAUSE`.
4. **Rayon's sleep protocol (CP-14).** Rayon's own counters (`sleep/counters.rs`) plus the condvar under its mutex are
   its lost-wake guard. It is upstream's design and isn't re-proven here; on our side it rests on std's `Condvar` over
   `SYS_FUTEX_WAIT`/`WAKE` (C1.1/C1.3, `std_threads`).
5. **Stylo's `parking_lot` locks.** `RwLock` in `rule_tree/core.rs` and `Mutex`/`RwLock` in `global_style_data.rs` park
   through the patched `parking_lot_core` (C2.3b: std `Mutex` + `Condvar` on the futex), not the generic `spin_loop()`
   parker. Same guard as C2.3b, same discriminator (its 8-contender sleeping-holder check).
6. **Thread-locals with destructors.** `rayon-core`'s `WORKER_THREAD_STATE` (no destructor) and `crossbeam-epoch`'s
   per-thread handle (a destructor that unregisters it) run on std's key-only TLS (C1.2). Workers exit only at
   `StyleThreadPool::shutdown()`, which joins them, so the destructors run on a clean exit.
7. **Process exit with workers parked (CP-95, CP-98).** If the content process exits or is killed with the pool alive,
   its workers are parked in the futex or Ready in a syscall. That's the kernel's kill/exit teardown of parked and
   in-syscall threads, guarded by those entries and their scenarios (`kill_at_exit`, `std_threads`' abort case).
8. **Panics.** Rayon catches a job's panic and re-raises it in the caller, or aborts if there's no handler. Our target
   is `panic=abort`, so any panic in a style worker ends the whole content process. That's per-process containment, the
   ADR-078 model.
9. **Rayon's global pool.** A `rayon::join` outside Stylo's pool would build Rayon's global registry, sized from
   `RAYON_NUM_THREADS` (unset: the sealed environment is empty) or `available_parallelism()`, which our std reports as
   unknown, so **1**. Stylo itself only uses its own pool.

**CP rows** (the standing pitfall-bank consult, for the build that turns the pool on):

| CP | Stylo's path | Introduce / guard / N-A | Discriminator |
|---|---|---|---|
| CP-86 (no AP tick; a running thread is never preempted) | Rayon's idle spin; `parking_lot` waits | guarded: the spin yields each round and is bounded at 32; `parking_lot` parks on the futex | C2.3b's contended `parking_lot` check; the smoke's pool-on leg (when built) completes with the pool at N ≥ 2 |
| CP-80 (a wait counted in spins) | Rayon's 32-round idle spin | guarded: each round is a `yield_now` syscall, not `PAUSE` | as above |
| CP-14 (lost wake) | Rayon's sleep/wake; `parking_lot` unpark | guarded upstream (Rayon's counters + condvar; C2.3b's parker holds its mutex from `unpark_lock` to `unpark`) | the pool-on leg finishes every job; C2.3b's condvar wake-and-timeout check |
| CP-95, CP-98 (kill/exit with threads parked or in a syscall) | content process exit with live workers | guarded by the kernel (#204, OT-98) | `kill_at_exit`; a pool-on leg that exits without `shutdown()` |
| CP-106 (a runtime that can't see the program's threads) | none: Stylo is Rust only; no C stdio | N/A | none needed |

Not dispatched as a build until J.c. answers §3.7; these rows go into the C2.4 build's PR with their legs.

## 5. The plan for the build (C2.4)

- Vendor the new crates into `third_party/ot61-browser/vendor/` (the same tree, one `VENDORED.md`), with `stylo`'s
  `default-features = false` plus `servo`, whichever set the smoke needs.
- **The smoke:** style a parsed document. Take C2.3b's page, add a stylesheet with cascade, specificity,
  inheritance, `!important`, a media query and `var()`, run Stylo's traversal over the html5ever tree, and check
  computed values (`color`, `display`, `font-size` in px, `margin` in px) against values derived by hand from the
  CSS cascade rules, the same oracle discipline as C2.3b's selector counts.
- The embedder side is Stylo's `TElement`/`TNode`/`TDocument` traits over our DOM. That is the work Servo's
  `script` does; our version stays in the smoke crate.
- Same kill-switch (one standalone crate, opt-in scenarios), the same CI closure-build job, and the same QEMU
  scenario shape (FXSAVE and XSAVE kernels).

## 6. The alternative not taken, for the record

A Blitz-shaped engine (html5ever + Stylo + taffy + parley, then Vello or SWGL to draw) could render pages **without**
SpiderMonkey or Servo's C dependencies. That would mean a usable no-JS page renderer before C3. It is a second layout
engine, though, and ADR-078 §2.1 chose Servo-embed. Switching would be J.c.'s call, not this seat's. This survey
records it because the cost difference is large (138 linked crates against 444 plus C++), and because it is the one
lever that could put a rendered page on the Zenbook before the SpiderMonkey rung lands.
