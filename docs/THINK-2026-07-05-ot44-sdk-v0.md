# THINK: OT-44 H1 — SDK-v0 design (what we honestly offer a LogansOS programmer today)

**Date:** 2026-07-05

**Status:** **RATIFIED (PL, 2026-07-05) — all four points as recommended:** (1) the ABI tier list (STABLE syscall numbers/errno, STABILIZING versioned structs, EXPERIMENTAL AI/network surfaces); (2) the versioning policy (leading `version: u32` on every ABI struct, removals forbidden — successor structs instead; `NetStatsV1` gains its field on next touch); (3) WASM DEFERRED to H3-if-ever; (4) the "contrib module" model as H1's distribution story, install-an-app deferred to the H2 G1/G2 kernel build. ## Executive summary

The cross-compilation SDK that a third-party programmer needs **mostly already exists** in this repo. What's missing is formalization: an honest ABI-stability promise, versioning discipline, a template app, and documentation that doesn't assume insider knowledge. This THINK inventories the real surface from code, classifies its stability with evidence from the `KernelObservabilityV1` v1->v2 bump (the only live ABI break at the time this THINK was ratified; OT-9 later bumped the same family to v3), traces the load-bearing gap in third-party app installation, sketches the capability-manifest direction for H2, assesses WASM as an early-app substrate, and proposes a costed SDK-v0 formalization plan.

**Verdict:** SDK-v0 is a **docs + template + versioning discipline** build (~1 week). No new kernel code. The critical path gap (no exec-from-file syscall) is named but out of scope — it's the H2/H3 frontier, not H1.

## D2 — The ABI-stability promise (truthful tier list from real evidence)

### 2.1 The live case study: `KernelObservabilityV1` v1->v2->v3 bump

This is the only ABI struct family that has evolved since introduction. Commit `3e3263f` (2026-07-04, "instrument arthur ipc-frequency counts") added 6 new `u64` fields (syscall counters) to `KernelObservabilityV1`, bumping `KERNEL_OBSERVABILITY_V1_VERSION` from 1 to 2. OT-9 then merged the aggregate scheduler/memory/trace slice on 2026-07-08 (`027d91c`), bumping the same family from 2 to 3.

**What changed:**
- 6 x `u64` fields inserted after `heap_alloc_failures`: `syscall_total`, `syscall_ipc`, `syscall_file`, `syscall_ai`, `syscall_net`, `syscall_other`
- v3 added the fixed trace-ring shape: `trace_capacity`, `trace_count`, and 16 `TraceEventV1` records
- Version constant currently reads `KERNEL_OBSERVABILITY_V1_VERSION = 3` in both `kernel/src/observability.rs` and `userland/libneo/src/lib.rs`

**What this required on each side:**
- **Kernel:** Added 6 atomic statics, 3 helper functions (`record_syscall_counter()`, `syscall_domain_counter()`, `fill_syscall_snapshot()`), updated struct definition in `observability.rs`
- **libneo:** Mirrored the 6 fields at the exact same offset, bumped version constant, updated `empty()` impl — all in `lib.rs`
- **Syscall number:** Unchanged (`SYS_OBSERVE = 22`)
- **Dispatch:** Unchanged — already passes `size_of::<KernelObservabilityV1>()` as buffer length

**Safety mechanism that caught the break:** The kernel's `sys_observe_impl` validates `out_len == size_of::<KernelObservabilityV1>()` (exact match). A v1 or v2 userland binary calling against a v3 kernel would pass the old size and get `EINVAL`. This is the **load-bearing ABI guard**: buffer-size validation at the syscall boundary. The 2026-07-09 Rule-4 host KAT added an independent field-order/byte-offset oracle for the same-size-reorder gap that exact-size validation cannot catch.

**Naming convention:** The struct name remained `KernelObservabilityV1` (not renamed to `V2`). The "V1" suffix identifies the *syscall family*, not the version within that family. Versioning is carried by the separate `KERNEL_OBSERVABILITY_V1_VERSION` constant. This is a deliberate pattern: **syscall number + struct name are stable; the version field inside the struct tracks layout revisions.**

### 2.2 Syscall number stability

**49 syscalls defined in kernel, 48 exposed in libneo.** Complete alignment except `SYS_TENSOR_WRITE` (0x104) which is kernel-only with no libneo wrapper (internal use by the tensor sharing gate).

**Numbering history: Zero renumberings.** Every syscall has kept its original number since introduction. Additions are strictly monotonic within reserved ranges:
- Base range: 0–23 (process, IPC, file, memory, status) — 24 slots used, 232+ slots of headroom before 0x100
- AI range: 0x100–0x17F (tensors, models, inference) — Bible Article 6.1 formally reserved
- Network range: 0x180+ (sockets, TCP, DNS, TLS) — Phase 4 owned
- Utility: 0x190+ (CSPRNG)

**Fallback:** Unknown syscall numbers return `ENOSYS` (-38) via the `_ => ENOSYS` catch-all in the dispatch match. This doubles as a feature-detection mechanism (e.g., `sys_getrandom` checks for ENOSYS when `kernel-rng` is disabled).

### 2.3 ABI struct versioning inventory

All structs crossing the kernel/userland boundary are `#[repr(C)]` with duplicated definitions on both sides:

| Struct | Version constant | Current version | Has `version` field? |
|--------|-----------------|-----------------|---------------------|
| `ProcessSnapshotV1` | `PROCESS_SNAPSHOT_V1_VERSION` | 1 | Yes (first field) |
| `SysStatV1` | `SYSSTAT_V1_VERSION` | 1 | Yes (first field) |
| `KernelObservabilityV1` | `KERNEL_OBSERVABILITY_V1_VERSION` | **3** | Yes (first field) |
| `SchedulerStatsV1` | (none — nested) | inherits parent | No |
| `TraceEventV1` | (none — nested) | inherits parent | No |
| `NetStatsV1` | (none) | N/A | **No** — only V1-named struct without version field |
| `MountRequestV1` | `MOUNT_REQUEST_V1_VERSION` | 1 | Encoded as first 4 bytes of request buffer |

**Convention:** All versioned output structs place `version: u32` as the very first field. This allows the kernel to read the version from the first 4 bytes before interpreting the rest — a standard forward-compatible pattern. `NetStatsV1` is the one exception (no version field).

### 2.4 Error code stability

**19 errno constants, 100% aligned.** Kernel (`kernel/src/errno.rs`) and libneo (`userland/libneo/src/lib.rs:136-154`) define identical constants with identical values. Values match Linux/POSIX for recognizability.

**Error flow:** Raw `i64` returns — no conversion layer. Syscall impls return `i64` directly; negative = error, zero or positive = success. Libneo's `raw3()` wrapper returns the raw RAX value; higher-level wrappers interpret sign (`if r < 0 { Err(r) }`).

**Stability caveat:** The kernel explicitly documents at `errno.rs:7-8`: "they are not ABI-stable beyond Phase 1.x and may extend / re-curate when Phase 2 capability errors land." No automated test verifies kernel/libneo errno alignment — they're maintained manually.

### 2.5 The truthful tier list

Based on the evidence above, here is the honest ABI classification for SDK-v0:

| Tier | Surface | Promise | Evidence |
|------|---------|---------|----------|
| **STABLE** | Syscall numbers (0–23, 0x100+, 0x180+) | Will never change handler or number. New syscalls are additive only. | Zero renumberings in entire history. Reserved gaps provide forward headroom. |
| **STABLE** | Syscall signatures (arg count, types) | `fn(ptr, len) -> i64` convention is fixed. ENOSYS fallback for unknown numbers. | All 49 syscalls follow the same `(u64, u64) -> i64` or `(u64, u64, u64) -> i64` pattern. |
| **STABLE** | Errno values (current 19) | Will not change value. May add new errno constants. | 100% kernel/libneo alignment. POSIX-compatible values. |
| **STABILIZING** | Versioned ABI structs (`ProcessSnapshotV1`, `SysStatV1`, `KernelObservabilityV1`) | Struct name and syscall number stable. Layout may evolve with version bump. Kernel guards with exact-size check. | `KernelObservabilityV1` v1->v2->v3 proved the evolution path works: size mismatch -> EINVAL, version field lets userland detect revision; the Rule-4 host KAT now pins same-size field order too. |
| **EXPERIMENTAL** | AI syscalls (0x100–0x17F) | Surface is active under development. Expect additions and struct layout changes. | Tensor/model/inference syscalls added across Phase 5–8. `SYS_TENSOR_WRITE` is kernel-only (ABI gap). |
| **EXPERIMENTAL** | Network syscalls (0x180+) | Surface stabilized through Phase 4 but may evolve with new protocols. | TCP/DNS/TLS stack is functional; new transport modes may add syscalls. |
| **BREAKS FREELY** | libneo internal helpers (`encode_mount_request_v1`, `parse_dirent_v1`) | These are convenience wrappers, not ABI guarantees. | Implementation detail, subject to change. |

### 2.6 Versioning policy proposal

Adopt the **`.neom`-style version-gate precedent** for ABI structs:

1. **Every ABI struct** that crosses the syscall boundary MUST have a `version: u32` as its first field
2. **Version constant** is defined on both kernel and libneo sides (e.g., `KERNEL_OBSERVABILITY_V1_VERSION`)
3. **Kernel validates buffer size** at entry: reject with EINVAL if `out_len != size_of::<Struct>()`
4. **Adding fields:** Bump version constant, insert fields, update both sides simultaneously
5. **Removing fields:** NEVER — this is a breaking change that would invalidate old binaries. Add a successor struct (V2) instead if removal is unavoidable
6. **New syscalls:** Always additive. Never reuse a number. Use reserved gaps.

Fix the one exception: add `version: u32` to `NetStatsV1` on next touch.

## D3 — What IS a third-party app, mechanically, today? (the load-bearing trace)

### 3.1 Binary format

**ELF64 x86_64, statically linked, pinned at 0x400000.** All userland binaries use the same linker script (`userland/neo-init/linker.ld`):
- `OUTPUT_FORMAT(elf64-x86-64)`, `ENTRY(_start)`
- Three PT_LOAD segments: `.text` (R+X), `.rodata` (R), `.data`/.bss (R+W)
- W^X enforced by the kernel ELF loader — refuses segments with both PF_W and PF_X
- No dynamic linking, no relocations, no PT_INTERP, no PT_TLS

The kernel ELF loader (`kernel/src/loader/elf.rs`) validates: ELF64 magic, `EM_X86_64`, type in {EXEC, DYN}, all vaddrs in user half, W^X compliance, entry RIP inside a loaded segment.

### 3.2 How binaries get onto the system today

**Limine boot modules only.** During ISO assembly, xtask copies each binary's ELF into `staging/modules/`. Limine loads them at boot and exposes them via `ModuleResponse`. The kernel provides `find_module_by_path_suffix()` to retrieve module bytes by name.

**There is NO mechanism to load a binary from NeoFS after boot.** The kernel comment at `process.rs:1389` states: "All ELF data comes from Limine modules; Phase 3+ NeoFS will add disk-backed paths."

### 3.3 The spawn path

`sys_spawn_impl(name_ptr, name_len, handles_ptr, handles_count)` takes:
1. A UTF-8 **name** string (max 64 chars) — NOT a file path
2. An array of handle indices to inherit (max 16)

The kernel resolves the name to `/neo-<name>` and looks it up in Limine modules. If not found: `ENOENT`. The spawned child starts with ONLY the explicitly inherited handles — no ambient authority. Inheritance filter:
- Handles with `GRANT` meta-right → inheritable (fresh CapId, parent link recorded)
- Directory file handles with exactly `LOOKUP|READDIR` → inheritable (own-directory exception)
- Non-directory file handles → `EPERM` (never inherited)

### 3.4 The gap list (what a third-party developer needs that doesn't exist)

| # | Gap | Severity | Blocked on |
|---|-----|----------|------------|
| **G1** | No exec-from-file syscall — `sys_spawn` resolves Limine module names, not file paths | **Critical** | New kernel syscall (`SYS_SPAWN_PATH` or similar) |
| **G2** | No post-boot binary installation — binaries are baked into ISO at build time | **Critical** | G1 + NeoFS write conventions |
| **G3** | No dynamic linking — all binaries must static-link against libneo | High | ELF loader extension OR ABI stability guarantee for static linking |
| **G4** | No CPU-time isolation — a pathological process can consume all CPU slices | High | OT-15 (scheduler QoS) |
| **G5** | No capability grant UX for third-party apps — no "app declares caps → user grants" flow | Medium | OT-18 generalization, OT-22 multi-principal |
| **G6** | No app lifecycle manager — no service manager or daemon supervisor | Medium | General init redesign |
| **G7** | No on-box build toolchain — cross-compilation from host is the only path | Low (cross-compile works) | OT-44 H3 |

**The critical insight:** Gaps G1 and G2 are the same problem — there's no syscall to load an ELF from disk and spawn it. This is a **kernel build**, not an SDK-v0 deliverable. SDK-v0 can exist without it by targeting developers who want to contribute binaries that get baked into the image (the "contrib module" model).

For H1, the honest answer is: **a third-party app today is a Rust crate that static-links libneo, builds with our target spec, and produces an ELF64 that gets added to the xtask build list.** It's the "contributing to the repo" model, not the "installing an app" model. That's fine for SDK-v0 — it's what we can honestly offer. The "install an app" story is H2.

## D4 — The capability-manifest sketch (H2 preview, design-only)

When OT-22 multi-principal work opens, third-party apps will need to declare what capabilities they require. Sketch:

```json
{
  "name": "my-app",
  "version": "0.1.0",
  "capabilities": [
    { "kind": "file", "scope": "/data/my-app", "rights": ["read", "write"] },
    { "kind": "network", "scope": "outbound", "protocols": ["tcp"] },
    { "kind": "ai", "scope": "infer", "models": ["*"] }
  ]
}
```

This maps onto the existing grant machinery:
- `capabilities[].kind` → `Grant` enum variant (OT-18)
- `scope` + `rights` → attenuated cap derivation at spawn (`derive_handle` with `CapRights`)
- Owner grants via shell UX → `ipc::grant` to the child process at spawn time

**Why it waits for OT-22:** The current grant system (OT-18) is single-principal — the owner grants to Arthur. Multi-principal generalization requires: per-app identity, a grant-approval UX that presents the manifest to the owner, and revocation that works across app boundaries. All of these are OT-22 pillars.

**Naming:** `app-manifest.json` (provisional). Deferred to OT-22 ratification.

## D5 — The interpreted-substrate question (WASM assessment)

### 5.1 Prior art: WASM runtimes for no_std Rust

| Runtime | no_std support | ROM footprint | Dependencies | Status |
|---------|---------------|---------------|--------------|--------|
| **wasmi** | Yes (`std` feature optional) | ~150 KB binary (core engine) | `bumpalo` allocator, `hashbrown` (no_std) | Actively maintained, pure Rust interpreter |
| **wasmtime** | Partial (`no_std` crate exists but requires significant host support) | ~2+ MB (cranelift + runtime) | `cranelift`, `libc` (for syscalls), `memfd` | Production-grade but heavy; not embedded-friendly |
| **wasm3** | Yes (C runtime, FFI from Rust) | ~40 KB | None (self-contained C) | Minimalist, fast interpreter, no GC |
| **wax** | Yes | ~50 KB | `bumpalo` | Rust-native, designed for embedded |

### 5.2 Fit assessment for LogansOS

**Question:** Does a sandboxed WASM runtime add anything our capability model doesn't already give a native binary?

**Analysis:**
- **Security:** LogansOS already provides per-process address space isolation + capability-bounded syscalls. A native Rust binary in its own address space with zero capabilities is already sandboxed. WASM adds memory safety *within* the process, but Rust already provides that at compile time. The marginal security benefit of WASM over a Rust binary on LogansOS is **near-zero**.
- **Distribution:** WASM's value is "no native compiler needed on the target." But SDK-v0 is cross-compilation-only — the native compiler lives on the dev PC, not on-box. A third-party distributing a WASM module still needs a host-side compiler. The distribution advantage only materializes if we ship a JavaScript/WASM ecosystem toolchain on-box, which we won't.
- **Performance:** WASM interpretation adds 2-10× overhead vs native. On our scalar CPU path (no SIMD for WASM), this is significant for anything compute-bound (AI inference, crypto).
- **Implementation complexity:** Integrating a WASM runtime into the kernel means either (a) running it in userland as a host process (adds a layer but no security benefit over native), or (b) embedding it in the kernel (massive surface area increase for marginal gain).

**Recommendation: DEFER.** WASM does not add value at the H1 stage. The capability model + address space isolation already provides the sandbox. Cross-compilation from the host is the day-one story. Revisit at H3 only if there's a concrete use case that native binaries can't serve (e.g., untrusted AI-generated code that we don't want to compile natively).

**Exception path:** If H3's "AI-native development" requires Arthur to generate and run code on-box without a native compiler, WASM becomes the obvious substrate. But that's an H3 question, not H1.

## D6 — The formalization plan + verdict

| ISC | Deliverable | Size | Verification |
|-----|-----------|------|--------------|

| **ISC-2** | `userland/template-app/` — minimal "Hello, LogansOS" app | ~100 lines | Builds with `cargo build --target ../x86_64-neoplutarch-user.json`. Demonstrates: `.cargo/config.toml`, `build.rs`, `linker.ld`, `main.rs` with one syscall. |
| **ISC-3** | `docs/SDK-GUIDE.md` — cross-development quickstart | ~150 lines | Step-by-step: "clone repo → build template → add to xtask → run in QEMU." Assumes dev PC with Rust nightly. |

### 6.2 Cost estimate

| Item | Effort | Notes |
|------|--------|-------|
| SDK-ABI.md | 2 hours | Grep-verifiable against live code; the tier list is this THINK's D2 |

### 6.3 Explicit non-promises

SDK-v0 explicitly does NOT promise:
- **On-box toolchain** — cross-compilation from host is the story (OT-44 H3)
- **POSIX personality** — not in scope; that's an OT-22 pillar decision
- **App installation after boot** — requires G1/G2 kernel builds (H2 frontier)
- **ABI stability for EXPERIMENTAL tier** — AI and network syscalls may evolve
- **WASM runtime** — deferred per D5 assessment

### 6.4 Verdict

**ADOPT as Phase-8 consolidation slice.** SDK-v0 is a low-cost, high-signal formalization of what already exists. It makes the repo accessible to external contributors (human or AI) without changing any kernel code. The ABI tier list is honest: stable where proven (syscall numbers, versioned structs with size guards), experimental where active (AI surface), and freely-breaking where internal (helper wrappers).

**Ratification points for PL:**
1. Approve the ABI tier list as the published stability promise
2. Approve the versioning policy (§2.6) as binding for future ABI struct changes
3. Approve WASM deferral (D5) — no interpreted substrate in H1
4. Confirm that the "contrib module" model (third-party apps baked into ISO) is acceptable as the H1 distribution story, with "install after boot" deferred to H2
