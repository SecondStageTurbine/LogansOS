# OT-61 C2.3b spike: the html5ever + Stylo `selectors` dependency closure (no gate)

**Seat:** S4. **Date:** 2026-10-29. **Status:** findings for J.c.'s supply-chain decision. Nothing here is
merged code, and no build of the closure ran (see §1).

**What this answers.** The C2 gate's last item (ADR-078 §3; `docs/RESEARCH-2026-07-22-ot61-servo-host-closure-spike-FINDINGS.md`,
"The first prototype") is to "parse a fixed HTML fragment with upstream html5ever and run one upstream
Stylo selector/style unit". C2.3a (#199) built everything else. Before C2.3b builds this one, the PM asked
for the closure (2026-10-29): every crate, its licence, its last commit, and what breaks on our target. The
choice between fetching from the registry at build time and `cargo vendor` goes to J.c. once this list
exists, and this document doesn't make it.

## 1. Method, and what was not done

- **The crate set.** A throwaway crate in the S4 scratchpad, outside the repo, depends on:
  - `html5ever 0.40.1`, the HTML parser;
  - `selectors 0.41.0`, Stylo's selector matching, published from `servo/stylo`;
  - `cssparser 0.38.0`, the CSS tokenizer `selectors` parses with;
  - `neo-std-pal`, for the allocator.

  Cargo resolved it against crates.io for `x86_64-unknown-neoplutarch`. `cargo tree` gives the closure, and
  `-e normal,no-proc-macro` separates what is linked into the binary from what only runs on the build host.
- **Not built.** I tried to build the closure for our target and the session's permission classifier refused
  it: building runs third-party build scripts and proc macros on the build machine. That refusal is itself
  input to the decision (§4). So "what breaks" below comes from **reading the sources** (`cfg` arms,
  target-gated dependencies, the std APIs each crate reaches), not from a compile. Any item marked *verify*
  needs the real build to confirm.
- **Dropped:** `markup5ever_rcdom`. The published release is `0.39.0+unofficial` (upstream no longer
  publishes it), and it pulls a second, older `html5ever 0.39` plus `xml5ever` and `serde`. A port writes
  its own `TreeSink`, which is what Servo's DOM is anyway.
- **Metadata.** Licences come from each crate's `Cargo.toml` and crates.io. Release dates come from the
  crates.io API. Last commits are each repository's HEAD date, from a shallow, blob-less clone; the GitHub
  API returned 403 through the session proxy. All data was read on 2026-10-29.

## 4. Build-time code execution (supply-chain input for J.c.)

Building this closure runs third-party code on the build machine:
- **Build scripts:** `web_atoms` (generates the atom tables with `string_cache_codegen` and
  `phf_codegen`), `parking_lot_core` (`rustc_version` probe), `proc-macro2` and `quote` (compiler probes).
- **Proc macros:** `cssparser-macros`, `derive_more-impl` and `phf_macros`, which run inside rustc.

This is true whichever way the sources arrive. `cargo vendor` pins and reviews the *source*, but the
scripts still run at every build. The session's permission classifier refused exactly this step for the
cloud seat, so the C2.3b build also needs a decision on **where** it runs: CI's runners, J.c.'s machine, or
the cloud seat with an explicit permission rule.

## 5. What breaks on our target (static reading; *verify* items need the build)

Our target spec (`userland/x86_64-unknown-neoplutarch.json`) sets `os = "neoplutarch"` and **no
`target-family`**, so `cfg(unix)` and `cfg(windows)` are both false.

1. **`parking_lot_core`: a hang, not a compile error.** Its `thread_parker` picks a backend by
   `target_os`/`target_family`, and ours falls to `generic.rs`. There `park()` is a pure `spin_loop()`
   busy-wait that never yields or blocks. `string_cache`'s global atom table is a set of
   `parking_lot::Mutex` buckets, so two threads interning atoms can contend.
   - **The risk:** APs get no timer tick (the CP-86 note). A thread parked behind a lock holder on the
     same AP spins forever, and the holder never runs again.
   - **Fix options**, the C2.3b build's job and not decided here:
     - a `neoplutarch` arm in `parking_lot_core` that parks on `SYS_FUTEX`, as std's sync already does
       (C1.3). This means a `[patch]` fork or an upstream PR;
     - keeping html5ever and the atom table on one thread for the smoke, which is not a fix.

   It compiles either way: no `libc` is pulled, because that dependency is `cfg(unix)`-gated.
2. **memchr's AVX2 path (*verify*).** memchr chooses SSE2 or AVX2 at run time with
   `is_x86_feature_detected!`. That is only safe if what CPUID and XCR0 report to user code matches what
   the context switch saves. The kernel's AVX handling depends on its `xsave-fpu` build and on per-CPU
   XCR0 (`ai/ops/qk_matmul.rs`'s census). A kernel that advertises OSXSAVE and YMM but saves only FXSAVE
   state would corrupt the upper halves of the YMM registers across switches. This is the same question
   for any std program using AVX; check it on the C2.3b build's kernel config.
3. **html5ever's tokenizer SIMD:** compile-time `target_arch = "x86_64"` SSE2 paths. No break.
4. **`selectors`:** pure. It needs the embedder's `Element` and `SelectorImpl` implementations, a few
   dozen lines in the smoke, and uses `servo_arc`, `smallvec`, `cssparser`, `precomputed-hash` and `phf`.
   No OS surface.
5. **`log`, `tendril`, `smallvec`, `rustc-hash`, `scopeguard`:** no break.
   - Their `thread::spawn` calls are in tests (`tendril`, `smallvec`, `rustc-hash`), and the `std::fs` hit is
     a doc comment (`scopeguard`).
   - What remains on a linked path uses std features our PAL already provides: `rustc-hash`'s per-thread
     seed is a `thread_local!`, and `scopeguard` calls `thread::panicking()`.
   - `log`'s `kv` module names `std::net` address types but never opens a socket.
6. **Allocator:** the closure allocates through `std`'s global allocator, which is `neo-std-pal`'s
   `SyscallHeap`. html5ever runs fine on one thread; if C2.3b moves parsing onto a thread, #199's
   multi-region heap fix (CP-94) is needed.
7. **No `getrandom`, no `libc`, no `SystemTime::now` on any linked path that I found.** `fastrand`, the
   one RNG crate, is host-only.
