## 0. The one-paragraph thesis (read this first)

We are **not** at zero, but the ground truth is sharper — and more uncomfortable — than "builds on the Phase-6 Intel bring-up" suggests. **Phase-6 brought up exactly one of the iGPU's three subsystems: the compute (GPGPU) pipeline on the render engine.** The **display engine** (modeset / scanout / page-flip / vblank) and the **3D/render pipeline** (the fixed-function + shader path WebRender actually paints through) are **greenfield — literally zero lines in the tree** (grep-confirmed). So the honest architecture is a **three-rung ladder keyed to *which GPU subsystem each rung needs*, not to "how accelerated" it feels**: **Rung 0** is a *real* software pipeline — WebRender on `swgl` (Servo's own software-GL) for the browser, tiny-skia/Vello-CPU for the compositor — composited into Limine's framebuffer through the existing `fb::blit_rgba`, **needing no new GPU code at all**; **Rung 1** brings up the **display engine** (scanout + flip + optional 2D blitter) for *accelerated present* — tear-free vsync and hardware surface composition — which is **the rung that delivers the desktop's first real pixels and the browser's smooth present**, and is a genuinely new but *bounded* bring-up; **Rung 2** is hardware raster, and here the honest fork is that **WebRender-over-GL needs the 3D pipeline (Mesa-scale, disjoint from everything Phase-6 built), whereas a compute-first renderer (Vello) maps onto the GPGPU substrate we have already silicon-proven** — so the wgpu/Vello convergence route is not merely "kept open," it is the route that *reuses our actual asset*. The whole ladder is governed by one kill-switch (`accel-*` off ≡ Rung 0 software path, bit-for-bit) and by an I-14 model where the GPU's **already-proven per-context PPGTT + cross-tenant fault isolation** is the hardware backing for cap-gated GPU submit, and where I-14(c) for the highest-bandwidth device is solved by **IOMMU domain isolation (c2), not swiotlb bounce-fencing (c1)**.

## ISC-1 — the CURRENT GPU state (ground truth, surveyed firsthand)

Everything below was read from the tree (`docs/ADR-032`, `kernel/src/drivers/accel/*`, `kernel/src/drivers/fb/mod.rs`, `kernel/src/drivers/dma_arena.rs`, `kernel/src/drivers/iommu/mod.rs`), not assumed.

### 1.1 What hardware, what gen
**Intel UHD 630, Gen9.5 (Kaby-Lake-R iGPU), PCI `00:02.0`, device IDs `0x9bc8/0x9bc5/0x3e92/0x3e98`**, on the OptiPlex 7080 bare-metal box. GTT-mapped **system RAM, no discrete VRAM** — the simplest memory model, and the one in hand. This is the box the release runs on; there is no second GPU target in scope.

### 1.2 What is silicon-proven today (the asset)
The Phase-6/7 arc (ADR-032) landed a **compute-only** driver, end-to-end on real silicon:

- **PCI probe → forcewake → GGTT mapping → legacy render ring → `STATE_BASE_ADDRESS` → stateless-A64 indirect-data payload → EU dispatch.** Add `[1,2]+[3,4]=[4,6]`, matmul, and GELU all retire on the UHD 630 EUs, byte-exact / within-tolerance (BUILD-4a/4b-1/4b-2, Phase-6 closed `2026-06-07`).
- **GuC-free execlist / LRC submission works** (BUILD-4X-1 PASS): a context submitted via the ELSP runs, CSB posts switch-in→idle, seqno retires. This is a *big* asset — execlist is the modern submission model every further GPU subsystem needs.
- **Per-context PPGTT with tensor-data isolation** (BUILD-4X-2 PASS, `select=PPGTT`): a tenant's buffers resolve through *its own* 48-bit page tree, cleared from GGTT.
- **Cross-tenant negative + RO-on-write enforcement** (BUILD-4X-3 PASS): a second tenant's access to the first's tensor *page-faults* on silicon (`RING_FAULT`, `select=PPGTT`, fault VA = the victim's VA); an RO-shared page is hardware-unwritable by the grantee. **The GPU's own page tables are a proven hardware isolation boundary between mutually-distrustful principals.** Hold this thought — it is the security foundation for cap-gated GPU submit (ISC-3).
- An **offline EU-kernel toolchain** (`tools/intel-gen9-finalizer/`, pinned IGC/ocloc) that deterministically compiles checked-in OpenCL-C to provenance-pinned Gen9 blobs, with `ocloc disasm` as an independent byte oracle.
- A discipline record worth its weight: **every command-buffer byte is asserted against hand-computed PRM values** (D7), and every blind bare-metal iteration carried a failure-mode/discriminator table. The `0x9e1` ring-fault saga (iter4–8) resolved to a NEO-vs-i965 thread-payload GRF-layout difference — read from `compute-runtime` source, not guessed. That rigor is the template every GPU rung below inherits.

### 1.3 What does NOT exist — the gap that defines this whole design
This is the load-bearing finding, and it is easy to under-state:

- **No display engine.** grep for `vblank|modeset|scanout|page_flip|DSPSURF|PLANE_SURF|display_pipe` across `kernel/src` returns **0 lines.** Phase-6 explicitly decided (**ADR-032 D8/C4**) to treat the framebuffer as **expendable** during a compute run — "do **not** modeset or fight the scanout." The iGPU drives the **Limine-handed GOP framebuffer**, and we never touch the display controller. Scanout, pipes, planes, transcoders, PLL/mode-set, the flip queue, the vblank interrupt — **none of it is brought up.**
- **No 3D / render pipeline.** Phase-6 uses the render engine (RCS) **only** for GPGPU (`PIPELINE_SELECT` = GPGPU, `MEDIA_VFE_STATE` → `GPGPU_WALKER`). The 3D state (`3DSTATE_*`, vertex fetch, the strip/fan, the rasterizer, the pixel/fragment shaders, blend/depth/stencil, the sampler/texture units at scale) — the pipeline **WebRender actually paints through** — is untouched.
- **No GPU interrupt.** Completion is **polled** (ADR-032 D5: "poll a seqno first … the GPU interrupt as a later optimization"). There is no GT interrupt handler, no vblank ISR.
- **The GPU is outside the DMA-fence discipline.** `dma_arena.rs` states it plainly: "Existing DMA users (**GPU**/NVMe/AHCI/virtio) are untouched and outside the arena." And VT-d (`iommu/mod.rs`) puts "the proven substrate (**GPU**/NVMe/AHCI/virtio) into **identity domains (GPA==HPA)**" — i.e. the GPU today has **passthrough DMA, no IOMMU containment.** RMRR parsing exists (`acpi/dmar.rs`) — the reserved-region handling integrated graphics needs — but the iGPU is not yet in a translated/fenced domain. **The highest-bandwidth DMA device we will ever have is currently the least contained.** (ISC-3 owns this.)

### 1.4 What the framebuffer path provides (the software floor's foundation)
`kernel/src/drivers/fb/mod.rs`: a **Limine linear framebuffer**, 32-bit BGRA, guarded by a single `spin::Mutex`. Software primitives: `clear`, `plot`, `fill_rect`, **`blit_rgba` (row-major RGBA8888 with alpha blend — the exact hand-off a userland renderer produces)**, `draw_glyph`/`draw_string` (8×16 bitmap font). The header comments are prophetic and correct: *"double-buffering arrives with the userspace compositor"*; *"Phase 2 will replace it with a userspace driver via a capability-gated IPC port."* **There is no double-buffer, no vsync, no tear protection beyond the mutex.** This is the surface both consumers currently composite into, and it is exactly enough for Rung 0.

### 1.5 The two consumers, and what each already has designed
- **The Atrium compositor (OT-52, design-complete through G1).** Ratified as an **own, cap-native, software compositor** (not X11, not a Wayland clone). The G1 synthesis (`docs/THINK-2026-07-10-g1-compositor-SYNTHESIS.md`) fixes **exactly two new kernel object kinds** — a **shared pixel-buffer object** (immutable descriptor, `BorrowedBuffer` Pmap ownership, Arc-pinned, **compositor mappings hardware RO/NX**) and an **`InputFocus` object** (kernel-routed, atomic focus transfer) — with **composition via the existing `fb::blit_rgba`** and **software-measured present fences**. Kill-switch: compositor-off ≡ v1 console bit-for-bit. **The compositor's accel need is not "a GPU" — it is (a) tear-free double-buffered present and (b) hardware composition of N surfaces, to replace the software `blit_rgba` when surface count/size makes CPU composition the bottleneck.**
- **The browser (OT-61, ratified release-gating).** Servo paints via **WebRender 0.69 + `surfman` + `glow` + platform GL/ANGLE** (the FINDINGS corrected the earlier "wgpu" assumption; wgpu is only Servo's *WebGPU web API*). The port task is stated verbatim: *"implement a supported GL/context/present route **or** fund a WebRender backend port."* Acceleration is a **release-gate performance/compatibility prerequisite, not a first-pixel prerequisite** ("Blitz has a CPU renderer and the compositor can begin in software"). Honest program cost: **34–58 person-months LogansOS-specific, of which graphics/compositor is 8–14.**

**The through-line:** both consumers have *already ratified a software-first path*, and both are blocked on the *same* next thing — a real present/compositor surface that today is a bare Limine framebuffer with no flip and no fence backing. That is what this accel path builds, smallest-first.

## ISC-2 — the accel architecture (the three-rung ladder)

The organizing principle — my central independent claim — is that **"accelerated" is the wrong axis to slice on; "which GPU subsystem" is the right one.** Sliced that way, the layers fall out cleanly and the cost estimates stop lying.

```
   consumer            renderer (userland)         present surface            GPU subsystem used
 ┌──────────┐   ┌───────────────────────────┐   ┌──────────────────┐   ┌────────────────────────────┐
 │ Atrium   │   │ tiny-skia / Vello-CPU      │   │                  │   │ RUNG 0: none               │
 │ (OT-52)  │──▶│ (surfaces)                 │──▶│ software compose  │──▶│  (Limine FB + fb::blit_rgba)│
 ├──────────┤   ├───────────────────────────┤   │ → Limine FB       │   └────────────────────────────┘
 │ Browser  │   │ WebRender 0.69 on **swgl** │──▶│                  │
 │ (OT-61)  │   │ (Servo's software GL)      │   └──────────────────┘
 └──────────┘            │                            ▲
                         │                            │  RUNG 1: DISPLAY ENGINE
                         │                    ┌───────┴────────┐  scanout + double-buffer flip + vblank
                         │                    │ HW present:     │  + optional 2D blitter (BLT engine)
                         │                    │ flip + blitter  │  → tear-free vsync, HW N-surface compose
                         ▼                    └────────────────┘
              ┌────────────────────────────────────────────────────────┐
              │ RUNG 2: HARDWARE RASTER — the fork                       │
              │  2a WebRender-over-GL  → the 3D/render pipeline (Mesa-   │
              │     scale; DISJOINT from all Phase-6 compute work)        │
              │  2b Vello-on-compute   → the GPGPU pipeline we ALREADY   │
              │     proved on silicon (execlist+PPGTT+EU dispatch)        │
              └────────────────────────────────────────────────────────┘
```

### Rung 0 — the software floor (real pipelines, zero new GPU code)
Two distinct floors, and the distinction matters — this is where I most expect to differ from a first-principles design:

- **Compositor floor = tiny-skia / Vello-CPU rasterizing surfaces, composed by the userland compositor into Limine's FB via `fb::blit_rgba`.** This is *precisely the G1 slice-1 design already ratified*. No GPU. The kill-switch target.
- **Browser floor = WebRender **on `swgl`**, not a hand-rolled CPU rasterizer and not tiny-skia.** `swgl` ("software WebGL/GL") is **Servo/Mozilla's own software implementation of the exact GL subset WebRender uses** — it is what Firefox ships on machines with blocklisted GPUs, and it lives in the WebRender tree. **The strategic point: running WebRender on `swgl` exercises the *real* `surfman`/GL present contract Servo binds to — the same code path a hardware GL backend would later replace — so it de-risks the Servo port far more than a toy raster ever could, and it can itself pass the release battery's correctness (not speed) requirements.** A tiny-skia floor proves the compositor; a `swgl` floor proves the *browser's graphics contract*. Blitz/Vello-CPU (the OT-60 HTML-reader route) remains the **explicitly-limited** interim reader — never the release gate — but the ship-target browser's floor should be `swgl`, because it is the pipeline we intend to *accelerate*, run in software.

**Why Rung 0 is the honest first build:** it unblocks the desktop's first Workfield pixels *and* the browser's correctness battery with **no display-engine or 3D bring-up on the critical path at all**, and it is bit-for-bit the kill-switch. Everything above it is a performance upgrade to a *working* system, not a prerequisite to a *booting* one.

### Rung 1 — the display engine (the accelerated-present rung; the desktop's real first pixels)
This is the rung I want to argue is **under-valued** if we frame the roadmap as "software floor → GL → GPU-accel WebRender" (the dispatch's default sequence). That sequence skips the single highest **value-per-unit-risk** step: **bringing up the display controller for tear-free, double-buffered, vsync-paced present.**

What Rung 1 brings up (all NEW, all display-engine — none of it is 3D or GL):
- **Scanout ownership**: take the display pipe from Limine's static GOP framebuffer to a driver-owned front/back buffer pair in GGTT, program the plane surface address (`PLANE_SURF`/`DSPSURF`-class registers), and **flip** on vblank.
- **The vblank interrupt** (the GPU's *first* interrupt in the whole system — Phase-6 was polled): the two-level Gen9 GT interrupt tree (master `GTIER`/`GTIIR` → the display `DE_*` interrupt registers), delivering a real "the flip completed / the scanline is in vblank" signal. **This is the hardware backing for the compositor's present-fence** — replacing G1's *software-measured* fence with a *real* one (honest liveness gets more honest).
- **Optional: the 2D blit engine (BLT/BCS)** for hardware surface composition — copy-with-blend N client surfaces into the back buffer without CPU cycles. This is the "hardware compositing" OT-52 named as the later upgrade.

**Cost is moderate and bounded** (mode-set is the historically nasty part — see the trap-mining pass; but we can often *inherit Limine's already-configured mode* and only take over the flip + plane-address, deferring full mode-set), and **the payoff is the desktop feeling real** (no tearing, vsync-locked, measured-becomes-real present). **Rung 1 is where "the GUI is where the PL lives on boot, and it must be beautiful" (OT-52's framing) actually lands** — a torn, single-buffered framebuffer is not beautiful, and the design-language work (OT-45: "latency-is-beauty," "the only shadow is the Undo Shadow," honest motion) presumes a flip/fence surface underneath.

### Rung 2 — hardware raster (the fork, stated honestly)
Only here does "GPU-accelerated" mean hardware pixel-pushing, and here the two consumers **pull apart**, which is the crux the panel must resolve:

- **2a — WebRender over hardware GL** is what the *browser* nominally wants, and it needs the **3D/render pipeline**: `3DSTATE_*` programming, vertex/fragment shaders through the Gen9 shader cores, the rasterizer, blend units, the sampler/texture machinery, and a GL/GLES front-end (a `surfman` "device" + a `glow`-compatible GL context, i.e. a from-scratch Gen9 GL driver, or ANGLE-over-something). **This is disjoint from every line Phase-6 wrote** — Phase-6 never issued a single 3D command. It is the **Mesa-scale** cost (the FINDINGS' 8–14 person-months for graphics is *this*). Our proven assets that *do* carry over: execlist/LRC submission, GGTT/PPGTT, forcewake, the byte-oracle discipline, the offline shader-compile toolchain. The *pipeline itself* does not.
- **2b — Vello on our compute substrate** is the route that **reuses what we already proved on silicon.** Vello is a **compute-shader renderer** — it rasterizes via compute kernels, not the fixed-function 3D pipeline. Its architecture is the same shape as `GPGPU_WALKER` + EU kernels that we have *running on this exact UHD 630*. The mainstream Vello runs on `wgpu` (needs a Vulkan/Metal/GL/DX driver we don't have), but **Vello's *model* — tiled compute rasterization — is portable onto our native EU-compute path** the way Phase-6 ported matmul/GELU. This is speculative and large, but it is the *only* Rung-2 route where our silicon-proven work is the foundation rather than a bystander.

**My recommendation on the fork (and I flag it as a bet, not a proof):** **do not commit Rung 2 in this THINK.** Build Rungs 0–1, ship the desktop and the browser's *correctness* battery on `swgl`, and let the *measured* Rung-0/1 performance data decide 2a-vs-2b. But **design Rung 1's present/fence/buffer contract so that either 2a or 2b can plug in behind it** — the compositor and browser should see "a surface, a buffer, a present-fence, a damage rect," never "a GL context" or "an EU kernel." If the seam is renderer-agnostic (it is, in the G1 design), Rung 2 is a swap-in, and the 2a/2b choice is deferred to evidence. The `wgpu`/WebGPU-web-API path (Servo's separate `wgpu-core`) rides on whatever Rung-2 substrate wins and is not on the release-gate critical path.

### The GL-context seam (the one concrete thing the browser port needs, stated precisely)
Servo needs a `surfman`-shaped **rendering context** exposing: create-context, make-current, a GL function loader (`glow`/`gl_generator`), a swap-chain/present surface, and a fence/sync. **Rung 0 provides this over `swgl`** (swgl *is* a GL implementation — `surfman` has a software/`swgl` device path upstream). So the browser's *first* GL/context/present route is **not new graphics work — it is wiring Servo's existing `swgl` device to our present surface.** Hardware GL (2a) later replaces `swgl` behind that same `surfman` device seam. This is the "implement a supported GL/context/present route" option from the FINDINGS, taken via `swgl` first — the cheapest correct answer.

## ISC-3 — the driver + capability + DMA model (I-14, mandatory)

This is a device-driver-class build, so the governance fault-containment analysis is required. I take each I-14 vector against **each rung** (the vectors bind differently at Rung 0 vs Rung 1 vs Rung 2), because a blanket "the GPU is contained" would be exactly the hand-wave the rule exists to catch.

### I-14(a) — Lock isolation: the GPU IRQ/ISR path acquires NO AI-governance lock
- **Rung 0:** trivially satisfied — no GPU interrupt exists; the only lock is `fb::FB`'s leaf `spin::Mutex`, which touches no governance state. **N-A / holds by construction.**
- **Rung 1 (the vblank ISR — the first real GPU interrupt):** this is where (a) becomes a *live obligation*, not a freebie. The vblank/flip-complete ISR must touch **only** the display unit's MMIO (ACK the `DE_IIR`), a leaf present-fence atomic, and the flip-queue — and **acquire no `INFLIGHT`/`RECENCY`/`ARENA`/`TABLE`/scheduler-inner lock.** This is the same discipline the VT-d fault path already proves (`iommu/mod.rs`: "the fault path acquires NO AI-governance lock … the VT-d state lock is a leaf `SwitchMutex`, never nested under the ordered AI band, ceiling `USB_CORE=31`"). **Guard:** the GPU display lock gets a **lockdep level below the AI band** (extends I-5/CP-1 lockdep — see ISC-4 CP-1), and a grep-gate asserts the ISR body references no governance lock. **Discriminator:** a runtime assertion `in_gpu_isr → !holds_any_ai_lock`.
- **Rung 2:** the completion ISR (render-done) has the same rule; identical guard.

### I-14(b) — Liveness: a GPU fault/hang DEGRADES, never stalls or corrupts governance
The kill-switch *is* the liveness backstop, and it is layered:
- A GPU **hang/TDR** (the EU wedges, the flip never completes) must **fall back down the ladder**: Rung 2 fault → Rung 1 software-compose-to-flip; Rung 1 flip-timeout → **Rung 0 (`fb::blit_rgba` to the Limine framebuffer)**. Rung 0 is pure CPU and depends on no GPU liveness at all, so *the display never dies as long as the CPU runs.* This mirrors Phase-6's proven graded fallback (`exec::run_with_driver` routes an `Unsupported`/failed GPU op to `accel_cpu`, "completes, never fails").
- **The present-fence must be bounded-wait, never an unyielding spin** (ADR-030 contract; CP-2/CP-3 — see ISC-4). A wedged GPU that never fires the fence must **time out** and degrade, not hang the compositor thread. The compositor is a *userland* tenant (G1), so even its total death degrades to "no composition," never a governance stall — but the fence-timeout keeps it from *reaching* that death on a transient hang.
- **Governance is never on the GPU's liveness path.** The AI residency daemon, the ledger, the inference scheduler run on the CPU and hold no GPU dependency. Even if the display engine is wedged solid, I-1…I-13 stay live (the residency daemon degrades to P4b synchronous reclaim as always). **Discriminator:** a fault-injection test (feature-gated) that wedges the flip and asserts (i) the display degrades to Rung 0 and keeps painting, (ii) the governance ledger checksum is unchanged across the wedge.

### I-14(c) — Memory isolation: GPU DMA, the highest-bandwidth-device stress test
This is the hard one, and the honest answer **differs from the connectivity-driver answer** — which is the single most important I-14 point in this document.

**The naïve reading of the dispatch** — "GGTT/PPGTT buffers must route through `dma_arena::fence(...)`" — **is wrong for the GPU, and following it would wreck it.** `dma_arena` (I-14(c1)) is the **swiotlb / restricted-DMA-pool bounce pattern**: a small pre-registered contiguous region, and every DMA buffer is *allocated from it*. That is correct for a NIC's ring descriptors (kilobytes). **It is catastrophic for a scanout framebuffer + WebRender's texture/tile working set (tens to hundreds of MB, updated every frame):** you cannot bounce-copy a 4K framebuffer through a fixed arena at 60 Hz, and you cannot size the arena to hold the GPU's entire working set without it stopping being an "arena."

**The correct I-14(c) model for the GPU is (c2) — IOMMU domain isolation — not (c1) bounce-fencing.** Concretely:
1. **Move the iGPU out of its current VT-d identity domain into a dedicated *translated* domain** (`iommu/mod.rs` today: GPU is in an identity domain, GPA==HPA, passthrough — the least-contained device). The GPU's translated domain maps **only** the physical frames of its legitimate buffer set (scanout front/back, command rings, WebRender's tiles/textures, the per-client surfaces) — so a **misbehaving GPU (or a compromised command stream) physically cannot DMA outside that set; the IOMMU faults.** This is exactly the fence-domain treatment `iommu/mod.rs` already gives connectivity devices, applied to a *large, dynamically-managed* domain instead of a tiny fixed one.
2. **Honor RMRR.** The integrated graphics stolen-memory / reserved regions (`acpi/dmar.rs` already parses RMRRs) **must be identity-mapped within the GPU's translated domain** or the display engine faults on its own legitimate scanout of the pre-boot framebuffer. This is the documented iGPU-under-VT-d trap (trap-mining, ISC-4).
3. **The two translation layers are distinct and both matter.** The iGPU emits *graphics* virtual addresses → **GGTT/PPGTT** translates them to physical (this is *our* Phase-6-proven layer, and it is already an isolation boundary — BUILD-4X-3 proved cross-tenant PPGTT faults on silicon) → **VT-d** then translates/validates physical (this is the c2 layer). **The GPU's isolation is therefore *belt-and-suspenders*: PPGTT contains what the GPU's own contexts can address, VT-d contains what the GPU device can physically reach.** Both are needed; neither alone is I-14(c)-complete for a device this powerful.
4. **The command-buffer *programming* boundary still gets a witness-type gate**, adapted. We keep the `FencedDmaAddr`-style discipline for the *addresses the driver programs into GGTT PTEs / ring descriptors* — the driver should not be able to install a GGTT/PPGTT entry pointing outside the GPU's domain without going through a validating constructor. This is `dma_arena`'s **construction-proof pattern** (private fields, one gate) reused for GPU page-table entries, *without* the bounce-buffer allocation. So: **fence the *address programming* (c1-style witness), isolate the *device reach* (c2 IOMMU domain)** — the two halves of I-14(c) split cleanly by mechanism.

**Discriminators:** (i) a negative test that the GPU in its translated domain **faults** on a DMA to a physical address outside its buffer set (the c2 boundary, silicon — the BUILD-V precedent: "fenced NVMe out-of-arena DMA faulted"); (ii) a host oracle that a GGTT/PPGTT entry cannot be constructed for an out-of-domain physical frame (the witness gate); (iii) RMRR coverage asserted (the display engine's scanout of the reserved region does *not* fault).

### The capability-sandbox for the accel surface (who can submit / allocate)
This is where the Phase-6 asset pays its biggest dividend, and it ties directly to OT-61's ratified `NetDialCap` lesson ("kernel-enforced authority, not a UI grant").

- **The surface/buffer cap model is *already ratified* by G1** and I adopt it wholesale: a **`SurfaceCap`** (an IPC channel — the session), a **shared pixel-buffer object** (client-RW, **compositor RO/NX**, immutable descriptor, Arc-pinned), a **`PresentFenceCap`** (one-shot present signal), an **`InputFocus`** object (kernel-routed). **A client (browser renderer, Atrium Workfield) allocates a *surface and a pixel buffer* — it never gets raw GPU submit.** It writes pixels into its own RO-to-the-compositor buffer; the *compositor* (a thin trusted userland tenant) is the only party that presents. **A hostile browser renderer that scribbles corrupts only its own pixels — structurally (C4 of the G1 synthesis).**
- **When Rung 2 makes GPU submit real, the submit authority is a separate, scarcer cap** — call it a **`GpuSubmitCap`** — and it is **NOT held by page-rendering clients.** Only the compositor and the (single, trusted) render-service hold it. A browser content process that wants hardware raster does so **by handing its surface + a command *description* to the render service across the cap boundary**, which validates and submits — the renderer never touches the ring/ELSP. **The hardware backing for this is already proven:** BUILD-4X-2/4X-3 showed **per-context PPGTT isolates a tenant's GPU memory and cross-tenant access faults on silicon.** So even *if* a future design lets a semi-trusted client submit, it submits **into its own PPGTT context**, and the hardware page tables — which we have *validated on this exact silicon* — contain it. **This is a genuine differentiator: a capability-confined GPU by construction, with hardware (not just policy) isolation between GPU principals, proven before the browser ever runs.**
- **The seam that must NOT leak** (the `SYS_NET_DIAL`-is-ambient lesson): there must be **no ambient "submit to the GPU" or "map scanout" syscall** that bypasses the cap. Every GPU-submit and every scanout-plane program is reachable only through a held cap. Grep-gate + the G1 "structural no-snoop" property extended to GPU submit.

## ISC-4 — the pitfall bank (CP-*) + Intel-GPU trap-mining

### Part A — concurrency pitfall bank (`docs/concurrency-pitfalls.md`, normative; I authored it, OT-62)
The GPU path is cross-CPU / interrupt / DMA code, so I map each relevant CP-* to **introduce / guard / N-A + discriminator**. The pattern to hold onto: **Rung 0 touches almost none of these (no GPU IRQ, no cross-CPU GPU state); Rung 1's vblank ISR + present-fence lights most of them up.** That is another reason Rung 1, not Rung 0, is the concurrency-risk inflection point.

| CP | Trap | GPU exposure | Introduce/Guard/N-A + discriminator |
|----|------|--------------|-------------------------------------|

## ISC-5 — build slices, kill-switch, honest sequencing

### The slices (smallest-first, host-testable where possible; each names its GPU subsystem)

**Slice G-0 — the software floor (NO new GPU code; the kill-switch baseline).**
- Wire the **G1 compositor slice-1** (create-surface → map buffer → commit → `fb::blit_rgba`) — this is *already the ratified G1 first slice*, so G-0 is largely "land G1 slice 1," not new invention. Adds nothing to ring 0 beyond G1's two object kinds.
- Bring up **WebRender-on-`swgl`** as the browser's software floor behind Servo's `surfman` device seam (host-first: prove WebRender paints a page to an in-memory buffer under `swgl` on the *host*, before any target port).
- **Kill-switch = this slice.** Everything above reduces to G-0 bit-for-bit when `accel-display` is off.
- **Gate:** host-testable (compositor model + `swgl` paint are host code); the framebuffer-integration bit is the one kernel-touching, QEMU-gated step (G1 already scopes it as slice-7's `atrium_g0` scenario). **Unblocks: the desktop's first Workfield pixels AND the browser's correctness battery.**

**Slice G-1a — display-engine flip + vblank (the accelerated-present rung; the desktop's *real* first pixels).**
- Take over **scanout**: driver-owned front/back buffers in GGTT, plane-surface flip, **inheriting Limine's trained mode** (defer full mode-set — trap T2).
- Bring up the **vblank interrupt** (the system's first GPU IRQ): the two-level GT interrupt tree, ACK-before-EOI (CP-7/T4), delivering a **real flip-complete present-fence** to replace G1's software-measured one.
- **This is the first genuinely-new, blind-hardware GPU bring-up of this program** ⇒ **the blind-hardware failure-mode/discriminator-section rule applies to its dispatch** (expected failure modes: wrong plane address = shifted scanout; lost vblank = no flip; forcewake wedge; watermark underrun). Bare-metal on the OptiPlex.
- **Kill-switch:** `accel-display`-off ⇒ no flip/no vblank ⇒ G-0 (`blit_rgba` to Limine FB) bit-for-bit.
- **Gate:** kernel-touching + blind-hardware ⇒ QEMU gate (where expressible — vblank is hard to fixture in TCG; much of this is OptiPlex-only, so the discriminator bank must make the blind run conclusive) + the AAG (concurrency lens on the new ISR/fence).

**Slice G-1b — hardware 2D composition (the BLT/blitter engine).**
- Use the 2D blit engine to compose N client surfaces into the back buffer without CPU cycles — the compositor's `blit_rgba` upgrade for high surface-count/large-surface cases.
- **Kill-switch:** off ⇒ software `blit_rgba` compose. **Gate:** kernel-touching, QEMU where possible + OptiPlex.

**Slice G-2 — hardware raster (the deferred fork; NOT built in this THINK's horizon).**
- **Design the Rung-1 present/buffer/fence seam to be renderer-agnostic now** (it is, per G1), so 2a (WebRender-over-GL / the 3D pipeline) or 2b (Vello-on-compute) plugs in later behind the same seam.
- **The 2a-vs-2b decision is made on measured Rung-0/1 data**, not now. My bet: 2b (compute-Vello) reuses our silicon-proven substrate and is the lower-risk route to *some* hardware raster; 2a is the higher-fidelity-but-Mesa-scale route the release *battery* may ultimately force for full WebRender/WebGL/canvas coverage. **This THINK does not commit it** — it commits to *not foreclosing either*.

### The kill-switch (Rule-1 compliance, explicit)
- Feature flags mirror the existing pattern (`accel-intel`, `vtd`, `wifi` are all default-off): **`accel-display`** (Rung 1), **`accel-raster`** (Rung 2), each default-off, each reducing to the rung below.
- **The provable equality:** `accel-display`-off ≡ the G-0 software path (compositor `blit_rgba` to Limine FB) **bit-for-bit** — the same discipline G1 already commits ("compositor-off ≡ v1 console bit-for-bit") and Phase-6's `accel-intel`-off ("CI unaffected"). The kill-switch regression is a *unit-test equality where expressible* (the composited framebuffer bytes are identical with the flip path stubbed), a *behavioral* equality on silicon.
- **Complexity is bounded because it is switch-off-able at every rung** (the governance Rule-1 thesis): a wedged display engine, a suspect blitter, a half-built raster — each falls back to a *proven* lower rung, down to pure CPU.

### Honest sequencing against the roadmap
- **G-0 unblocks BOTH first-pixel needs and is on nobody's critical-path-below-it** — it is the immediate, low-risk build, and it is *mostly already-ratified G1 work* plus the `swgl` wiring. **This is the first thing to build.**
- **G-1a (display flip + vblank) is the desktop's *real* first pixels** (tear-free, vsync, honest fence) and the browser's *smooth* present — the rung that makes "where the PL lives on boot, and it must be beautiful" (OT-52) true. It is the **highest value-per-risk** step and the one the default "software → GL → GPU-WebRender" sequencing skips. **Build it second.**
- **The browser's *acceleration* (Rung 2) is genuinely the long pole to 1.0** (OT-61: "first-ship gates on the browser ⇒ the browser + its GPU prerequisite are the long pole"), but its *correctness* battery runs on G-0's `swgl` floor — so **the browser is not blocked on Rung 2 to make progress**, only on Rung 2 to hit release *performance*. The 34–58 person-month browser program overlaps G-0/G-1, it does not queue behind them.
- **The OT-59 gating dependency (from the CP-14/15/16 map):** the GPU present path is the *same wake-race family* OT-59 is fighting on `main` right now. **G-1a (the first GPU ISR + present-fence wake) must not land until OT-59 is closed** — otherwise it inherits a live cross-CPU wake race into a brand-new interrupt path. G-0 (no GPU IRQ) has no such dependency and can proceed in parallel. **This is a real sequencing constraint, not a nicety.**
- **Runner/contention note:** G-0 is largely host-testable (light CI). G-1a/G-1b are kernel-touching + blind-hardware ⇒ they consume the contended 4-shard QEMU gate + an OptiPlex run; stagger them per the CI-capacity discipline, and do not open a GPU kernel lane concurrently with two other kernel-touching QEMU gates.

### Blind-hardware note (the standing rule, pre-acknowledged)
Every bare-metal GPU slice (G-1a onward) is a **blind hardware run** (OptiPlex, MMIO/breadcrumb observability only — no JTAG). So each such **dispatch** (not this THINK) must carry the expected-failure-mode + discriminator section and capture-before-you-need-it instrumentation — pre-seeded from the trap bank (ISC-4 Part B). Phase-6's saga is the proof this works: the `0x9e1` fault was only conclusive because the fault-address capture was added *before* the run that needed it. Rung 1's dispatch inherits that discipline directly (plane-address / vblank-count / forcewake-well / watermark discriminators, captured before the first flip).
