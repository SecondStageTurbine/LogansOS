# Complexity Governance — the invariant ledger and the rules that keep LogansOS maintainable

**Status:** Normative (PM-maintained). **Created:** 2026-06-10.
**Trigger:** an external review of the project verdict'd the engineering "elite-tier… extreme discipline" with exactly one named risk — *the Complexity Trap*: "when you build a system so complex that it requires a 'discriminator discipline' just to understand why a test failed, you run the risk of the system becoming too heavy to maintain." This document is the project's mechanical answer. Maintainability here is not a habit or a virtue — it is a **falsifiable property with named gates**, governed the same way correctness is.

One correction to the reviewer, recorded because it changes the risk calculus: **the discriminator machinery is not the complexity — it is the payment *against* complexity.** Without it, a concurrent-residency race is an unreproducible hang that costs a week; with it, BUILD-P4a's five gate failures each self-localized in a single run. Instrumentation that makes failures conclusive has *negative* net maintenance cost. The genuine weight risk is elsewhere: the **invariant surface** — the set of properties every future build must preserve — grows faster than the feature list. The day that surface can no longer be enumerated on one page is the day the trap has closed. This document IS that page, and its overflow is the alarm.

**2026-07-09 Rule-4 update (post-A1/A2/v1/3B/OT-43/OT-49/OT-9/B1/OT-19):** the live

## 1. The invariant ledger (the one page)

Every load-bearing invariant in the AI subsystem, with the mechanism that guards it. **A build that touches a row must keep its guard green. A build that adds a row must justify the addition (§2 Rule 2).** If this table no longer fits the page, stop adding and consolidate (§2 Rule 4).

| # | Invariant | Stated where | Guarded by |
|---|-----------|--------------|------------|
| I-1 | **Result-invariance (the byte-oracle).** Placement, eviction, retention, migration and (OT-34) the matmul's thread count change *where* or *on how many cores* work runs, never the bytes computed. | ANSPEC §9.9–§9.12; ADR-070 | The byte-oracle assertion in every gate scenario, P1→P4b, over the full NEO_SMP stress loop; the threaded matmul partitions only the output axis (`ot34_threaded_matmul_column_partition_is_byte_identical` KAT + `threaded_matmul_parity` at NEO_SMP=4). |

Under any failure the system collapses to a simpler, already-proven core. | ANSPEC §9.9–§9.12 | Unit-test equality (e.g. `W=0` ≡ P2) + the full prior-layer regression family run on every build. |
| I-3 | **Single-mutator, relaxed-and-re-proven.** The executor pass was the only mutator of its value table (P1–P3); P4a relaxed this for the daemon path *only* via the migration reservation — a referenced tensor is never claimable, an arriving accessor parks-and-re-resolves, swap+accounting commit in one critical section. | `kernel/src/ai/evict.rs` coherence note; ANSPEC §9.12; ADR-039 | The P4a NEO_SMP stress gate + its standing discriminators: storage generation counter, parked-count quiesce, migrate-owner uniqueness. |

kernel's **static-lock surface is 71 production lock statics** (the method:
`static` items typed as a lock primitive -- `SwitchMutex` / `IrqSafeMutex` /
`spin::Mutex` / `Mutex<...>` -- under `kernel/src`, excluding the 19 NEO_TEST
`test_harness.rs` locks, which are counted separately for a 90 grand total). The
count remains honest and screen-enumerable; **13 production call sites carry
machine-checked ordering (I-5) at lockdep levels <= 31, and 58 production locks
are leaf/unordered by design**. The USB band still occupies the top of the
documented `1..=31` lockdep domain (`USB_DEVICE`=29 / `USB_XHCI`=30 /
`USB_CORE`=31, above every AI level by I-14(a)) -- the ordered band fits, with
the ceiling still reached: a future lock needing to order *above* USB would
require widening the domain, though interior slots remain free. Of the AI

host-testable** (`*_policy.rs`, `*_logic.rs`, `predictor.rs`, `watermark.rs` --
5,608 physical lines pure vs 11,438 total), rising to **59.8%** counting the
CPU/quant op kernels (`ai/ops/` -- 8,687 pure+ops physical lines vs 14,517
total) -- the variety lives in the cheap-to-maintain tier by construction, as
designed.

## 2. The rules (each one mechanical, not aspirational)

**Rule 1 — The kill-switch is a required deliverable.** Every policy/substrate build ships (a) a disabled mode and (b) a regression proving *disabled ≡ the previous layer, bit-for-bit* (unit-test equality where expressible, the full prior-gate family otherwise). Complexity you can provably switch off is bounded complexity. A dispatch without the kill-switch ISC is mis-specified — same standing as a blind-hardware dispatch without a discriminator section.

**Rule 2 — The invariant budget.** The default for a new build is to **preserve** the ledger's rows. A build that needs a genuinely **new cross-cutting invariant** (one future builds must also preserve) is a yellow flag: the dispatch must name the new row explicitly, justify why no existing row covers it, and add its guard *in the same build* (capture-before-you-need-it). Relax-and-re-prove (the P4a pattern: relax one row, re-prove it under a stress gate, update the row) is the honest way to change a row — silently weakening one is the trap. **If the ledger outgrows one page, feature work pauses for consolidation.**

**Rule 3 — Complexity placement (the tier rule).** New decision logic goes in the **pure, kernel-free, host-testable tier** (`*_policy.rs` / `*_logic.rs`) unless it physically cannot; kernel glue stays thin and mechanism-reusing (`Tensor::migrate`, the reservation, the park primitive — never a parallel path); anything needing new `unsafe` or a new lock primitive is its own dispatch with its own gate, never a rider. (This is why RCU/seqlock was declined in P4: the contention it would save is negligible at our scale, and a hand-rolled lock-free primitive in a young kernel is precisely the unmaintainable kind of cleverness. Revisit only on a *measured* contention finding.)

**Rule 4 — Scheduled consolidation (the no-feature build).** The forward-momentum culture only ever adds; mature systems also digest. Cadence: **one consolidation build per ~3–4 feature builds** (the policy layer P1→P4b run ends in one). A consolidation build ships zero features and gates on: duplication collapsed, dead scaffolding deleted, module docs/ADR pointers reconciled with the code, the ledger above re-verified row-by-row and re-measured, and — the legibility test — the layering still explainable to a fresh reader from the module docs alone. The byte-oracle (I-1) and the regression family (I-2) are what make consolidation *safe*: the entire stack sits behind exact equivalence, so refactoring is fearless by construction.

**Rule 5 — Discriminators are paid-down debt; keep them armed.** Gate instrumentation (generation counters, quiesce hooks, the lockdep, delta assertions) is never removed as "test-only weight" — it is the standing guard column of the ledger and stays compiled into the gates permanently. The P4a precedent is the proof: five failures, five one-run diagnoses, including the lockdep catching a bug in itself.

## 3. The alarm conditions (when to stop and consolidate)

Any one of these is a hard signal that the trap is closing — feature dispatches pause, a consolidation build (Rule 4) dispatches instead:
1. The §1 ledger no longer fits one page, or a build lands that cannot say which rows it touches.
2. A gate failure that the standing discriminators **cannot localize** in one run (the P4a standard regresses).
3. A kill-switch regression fails — some layer no longer collapses cleanly to its predecessor.
4. A new contributor (or a cold re-read) cannot reconstruct the layering from module docs + this ledger without spelunking `git log`.

## 4. Performance falsifiability — the latency oracle and the performance budget

The project has, until now, made **two** properties falsifiable: *correctness* (the
byte-oracle, I-1 — every layer's output is bit-identical to a reference) and
*maintainability* (this document — the invariant ledger and its gates). It has **not**
made *cost* falsifiable. That is the one honest gap: the policy layer is proven to be
**correct** and **switch-off-able**, but its **orchestration tax has never been
measured.** Every governance decision — a placement, a `mint`, a capability check, an
accounting update — adds indirection between an opaque buffer and a kernel-managed
tensor. If that tax ever exceeds the value the governance buys, the system is a
performance disaster *that the correctness gates would still pass green.* The byte-oracle
cannot see a regression that is purely a slowdown.

The answer is symmetric with everything else here: **a performance property, measured
against a named budget, the same way correctness is measured against a reference.**

### The latency oracle (the instrument to build)
A host + QEMU micro-benchmark harness that measures the **hot-path orchestration
operations** in isolation and asserts each against a budget — the cost counterpart to the
byte-oracle. The hot path, by operation:

| Operation | What it costs | Budget — **now measured (QEMU TCG / host i9-9900K, 2026-06-14; numbers in §5)** |
|---|---|---|
| `mint` (`guarded_clone`) | atomic refcount inc + generation compare + one short `ARENA` critical section; **no syscall, no park** on the uncontended path | O(1); bounded to a small constant of atomics + one uncontended lock acquire; **zero** allocation — **HOLD** (in-kernel, no ring transition) |
| `sys_tensor_query` (metadata) | capability lookup + copy of **cached** `meta` | **never touches tensor bytes**; cost independent of tensor size — **HOLD** (flat across a 4096× size sweep). *(Correction: the shipped `sys_tensor_query_impl` DOES `mint` to read `meta` — an O(1) `Arc` bump; "never mints" should read "never copies tensor bytes." See ADR-052.)* |
| Capability check | the cap-derivation walk (`tensor_handle_lookup_in`) | O(derivation depth), bounded; no tensor data touch — **HOLD** |
| Placement decision (`decide`) | pure function over the device-candidate set | O(devices), no I/O, no lock beyond the §9.5 snapshot — **HOLD** (linear in device count) |
| Per-op orchestration total | placement + mint + accounting around one dispatched op | **bounded to a small constant fraction of the op's own compute** — the load-bearing budget: the tax must be *amortizable*, i.e. negligible against any real op — **HOLD** (≤3‰ of a 16×16 matmul, <1‰ of 48×48) |

### The budget, stated as a thesis to be defended
The project's value rests on the **necessity** axis (governance userspace cannot
provide), not the speed axis — so the performance bar is **not** "faster than
PyTorch+CUDA." It is the weaker but essential claim: **the orchestration tax is small
enough that the governance is not paid for in unacceptable latency.** Concretely, the
budget the oracle defends:
1. **No hot-path syscall** for in-kernel residency operations (mint/claim resolve in
   kernel, not via a round trip).
2. **Metadata-cheap:** existence and queries never scale with tensor *size* (the I-4
   cached-meta property — handles name slots, they don't carry bytes).
3. **Amortizable per-op tax:** the governance overhead around a dispatched op is a small
   constant relative to that op's compute, so it vanishes on any real workload and the
   CPU-fallback thesis (correctness first; the accelerator is the optimization) holds with
   the tax *included*.
4. **Indirection is paid once, not per-byte:** O1's `mint` is per-*use*, never per-element
   — a forward pass mints an operand once, not once per weight.

### The discipline (the rule this establishes)
Once the oracle exists, it joins the gate family: **a policy/substrate build that adds
indirection to the hot path measures the delta against the budget**, the way the
kill-switch (I-2) proves correctness-equivalence. A change that blows the budget is a
*defect*, surfaced at the gate — not discovered in production. **The oracle now exists
(BUILD-LO, ADR-052):** the four claims are **measured (QEMU/host, 2026-06-14)**, not
"designed-for." Performance claims for the instrumented ops must now cite §5 (the measured
numbers), not assert; an op not yet in §5 is still "designed-for, not measured" and must be
stated that way until it is added.

### Tracked commitment — **DISCHARGED (BUILD-LO, 2026-06-14, ADR-052)**
**Built:** the hot-path latency oracle + the per-operation micro-benchmark (Tier A host +
Tier B QEMU), with the first measured numbers recorded in §5 below. All four budget claims
**HOLD under measurement** (no budget blown). One banked follow-on: a **bare-metal re-read**
on the next OptiPlex boot for real constant-rate-TSC magnitudes (QEMU TCG cycles are
virtualized, not silicon — §5 labels them so). With this, cost is a **named, tracked,
falsifiable property** alongside correctness (I-1) and maintainability (this doc); every
future hot-path build measures its tax against §5 instead of asserting it.

## 5. The performance row — the latency oracle's first reading (the measured budget)

The §4 budget, **measured** (BUILD-LO, 2026-06-14, ADR-052). The instrument is the host
micro-bench (`tools/ai-ops-tests`, Tier A) + the `neo-test-ai-latency-oracle` QEMU scenario
(Tier B). **The Tier-B (QEMU TCG) cycle counts are virtualized and NOT silicon** — the
in-guest TSC is not constant-rate under TCG, the magnitudes are inflated ~100–1000× and are
not additively consistent; **only the SHAPE and RELATIVE results are conclusions.** A
bare-metal re-read for real magnitudes is banked for the next OptiPlex boot.

**Tier A — host (Intel Core i9-9900K @ 3.6 GHz, native rdtsc):**

| Op | Measured | Budget verdict |
|---|---|---|
| `decide` | 1→286 … 128→6169 cyc/iter over the device sweep | **HOLD** — O(devices) (16× input ⇒ 11× cost; quadratic would be ~256×); no allocation |
| `attributed_resident_bytes` | ~51–72 cyc/iter, flat 256 B…1 TiB | **HOLD** — independent of tensor size |
| `total_resident_bytes` | 1/4/16/64 principals → 91/124/402/1231 cyc/iter | O(principals) |
| generation compare (`key_matches`+`bump`) | 120 cyc/iter | O(1) |

**Tier B — QEMU TCG on the i9-9900K (in-guest rdtsc — inflated, not silicon):**

| Op | QEMU TCG cycles (median) |
|---|---|
| `mint` (lookup + gen compare + guarded_clone) | 173,914 |
| `guarded_clone` (slot-level clone alone) | 50,848 |
| cap check (`tensor_handle_lookup_in`) | 37,918 |
| `sys_tensor_query` metadata core | 333,848 |
| query size sweep 256 B / 4 K / 64 K / 1 M | 363,730 / 210,866 / 216,872 / 314,416 → **flat (no size trend)** |
| orchestration (decide + mint + accounting) | 117,588 |
| matmul 16×16 / 48×48 (CPU fallback) | 32.86 M / 902.72 M → orchestration is **3‰ / <1‰** of the op |
| indirection (8-op × 2-operand pass, 4096 elems each) | **16 mints / 65,536 elements** (paid per use, not per element) |

**The four budget claims — all HOLD:** (1) no hot-path syscall (mint resolves in-kernel);
(2) metadata-cheap / size-independent (query flat across 4096×); (3) amortizable per-op tax
(orchestration ≤3‰ of even a tiny matmul, falling as the op grows — the load-bearing claim);
(4) indirection paid once per operand-use, never per element.

**The gate rule (the discipline this establishes).** A future policy/substrate build that
adds indirection to the hot path **measures its delta against this table**, the way the
kill-switch (I-2) proves correctness-equivalence: a change that blows a budget is a *defect
surfaced at the gate*, not discovered in production. Re-measure this row at every consolidation
build (Rule 4), and replace the QEMU magnitudes with bare-metal numbers when the banked
re-read lands.
