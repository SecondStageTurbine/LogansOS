# DISPATCH: Scheduler idle thread — fix the "ready queue empty" panic OT-43 fix v2 exposed (OT-49) → Oracle

**Date:** 2026-07-07
**From:** PM (Claude)
**To:** Oracle (main-tier coder; idle, and this unblocks your own OT-16 B1 + the whole cascade). **Branch:** `codex/scheduler-idle-thread-oracle` off `origin/main` HEAD.
**Status:** DISPATCHED — **an intermittent kernel panic is live on `main` and is the new critical-path blocker.** Root cause (confirmed at source): **NeoPlutarch has no per-CPU idle thread.** Four park sites in `kernel/src/sched/scheduler.rs` (`:915`, `:974`, `:1033`, `:1094`) do `s.ready.pop_front().expect("ready queue empty — no thread to switch to")` — with comments literally reading *"Phase 1.5 has no idle."* The scheduler was designed assuming there is ALWAYS a runnable thread when a thread parks. That held only because the virtio-blk polling completion worker (`loop { poll; yield_now }`) was permanently in the ready queue as a de-facto always-ready fallback. **OT-43 fix v2 retired that worker** (IRQ-driven completions), removing the accidental fallback → now, when the **last runnable thread on a CPU parks on I/O and the ready queue is empty, the scheduler panics** instead of going idle. Intermittent/timing-dependent: it slipped fix v2's own gate (green) and the 3B gate (green), but Janus's OT-9 gate hit it (`arthur_memory_forgetting`, shard 3: *"virtio-blk inline poll missed → park → panic scheduler.rs:1108"*). It will keep randomly redding gates until fixed.

## The fix (ISC-1) — a proper per-CPU idle thread
Give the scheduler what every real OS has: a **per-CPU idle thread/context that is always available to switch to.** When a park site finds the ready queue empty, switch to the idle context instead of panicking; the idle loop **enables interrupts and `hlt`s** until an interrupt (the OT-43 completion IRQ, a timer, an IPI) makes a thread runnable, then resumes normal scheduling. This is the canonical fix — the panic must become "go idle and wait for the wake."
- **All four park sites** (`:915` exit, `:974` block_current_into, `:1033` block_current_into_with_guard, `:1094` block_current_with_token_and_guard) must use the idle fallback — not just the one that panicked (they share the deficiency; fix them uniformly or via a shared helper).
- **The wake path must work from idle (LOAD-BEARING, ties to OT-43):** submitter parks → no ready thread → switch to idle → `sti; hlt` → the virtio-blk used-ring MSI fires → its ISR wakes the parked thread (makes it ready) → idle's next loop picks it up (or the ISR/return path reschedules). Verify a parked I/O waiter that goes idle is genuinely woken by the completion IRQ and does not sleep forever. This is exactly the OT-43 scenario, now through the idle path.
