## The thesis to sharpen (frame the dive)
v1 is RATIFIED as **conversation + `neo>` shell, no GUI** (OT-26). The five-year-old THINK proved the conversation surface is intuitive-by-construction. But an AI-native OS that is *only* easy is not the goal — the PL's frame (the Linux Mint article) is **"perfect for beginners AND power users… deep in the OS, not just relying on Arthur."** The macOS lesson (P1, verified): beginners never see the terminal, power users live in it, and it's *one substrate, two views* — the CLI and GUI edit the same truth. LogansOS's analog: **the transcript and `neo>` are two views over one capability-secured substrate**, and `neo>` must be a first-class power surface in its own right — not a fallback, not a raw Unix clone, not a place where you disarm the OS to get power. This dive makes "excellent for power users" as concrete and gate-able as the five-year-old test made "excellent for beginners."

## What to determine (real source — HCI + real shell/CLI prior art; cite the real work, byte-oracle-acquisition rule for exact claims)
- **Q1 — What makes a POWER surface excellent (the `neo>` design standard).** From real prior art — the macOS "full Unix underneath" model (P1), and modern shell design (PowerShell's object pipeline, fish/nushell discoverability + structured data, the composability/predictability canon). What are the properties a *capability-native deterministic* shell must have to be a joy for a power user: composability, predictable/stable commands (P2 — never self-morphing), discoverability (help/completion as first-class, recognition-over-recall applied to the CLI), structured not-stringly output, and **determinism as a feature** (the `neo>` path is the reproducible/scriptable counterpart to Arthur's non-deterministic forward pass). It is NOT a POSIX personality (that's a bounded kill-switched concession, OT-44/OT-22 — decided elsewhere); it's a from-principles capability-native shell. Deliver the handful of properties `neo>` must satisfy.
- **Q2 — The promotion affordance: the transition from layer 1 to layer 2 (P3, the load-bearing seam).** Shneiderman's multi-layer interfaces + Apple's disclosure model (both verified P3): the power path must be **visible-but-quiet from the beginner surface**, and stepping up must not be a cliff. Design the concrete pattern: how does a transcript user *discover* `neo>` exists (Arthur naming the deterministic equivalent — *"I've done that; you can also run it yourself with `neo> …`"* is our disclosure button); how does the first-boot affordance introduce both layers without overwhelming; how does a user move fluidly between "ask Arthur" and "type the precise command" in one session (the PL's own framing: *"talk to Arthur, drop to `neo>` when you want precision"*). This is where beginner-friendliness and power-depth either reinforce or fracture.
- **Q3 — Power-is-not-a-jailbreak, operationalized (P5, the verified ChromeOS lesson).** The anti-pattern to structurally forbid: making power users *disable protections* to get power (the "developer mode posture downgrade" — trains the most capable users to run the least protected systems). In LogansOS, **depth = more granted capabilities, never fewer enforced invariants.** Design how this shows up in `neo>` UX: the shell is a capability tenant like Arthur; a power command that needs authority surfaces an OT-18 grant (not a "sudo, all protections off"); there is no mode that turns the cap-check off. Contrast explicitly with the Windows registry (P4/verified: the power-config path carries a "reinstall your OS at your own risk" warning — the anti-pattern of power-through-danger).
- **Q4 — The never-adaptive rule on the power surface (P2, verified measured).** Findlater & McGrenere: system-driven self-morphing UI is measurably slower + disliked; users prefer explicit control. Apply to `neo>`: the command set and shell behavior stay **stable and predictable**; Arthur may *suggest* a shortcut, the shell never silently rearranges itself. Power users especially depend on muscle memory — design the line between helpful (opt-in aliases the user sets) and hostile (auto-adapting command behavior).
- **Q5 — The unified-substrate view (P1, OT-50 tie-in — design the PRINCIPLE, not the store).** The transcript and `neo>` must operate over one truth: Arthur saying *"I've turned that off, sir"* and `neo> config get` must show the same key; a file Arthur created is the same object `neo> ls` lists. Design the *interaction principle* (two views, one substrate, never divergent state) at the UX level — the concrete OT-50 config-store SHAPE is gated on the first config-surface build (don't design the store here; design the two-views-one-truth UX contract the store must later satisfy).
