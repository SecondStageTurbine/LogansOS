**Status:** DISPATCHED — **kernel-touching Phase-7.5 driver build.** PL directive: **"We ship correct. Never with a crutch."** The baked WiFi *channel* is a crutch — a real distro takes SSID + password and **scans, finds the AP on any channel, and joins**; it never asks the user for the channel. We baked it only because the mt7601u wedges on channel-switching and our **scan path still runs `CAL_BW` on every hop** (your merged fix, `87b635a`, deferred `CAL_BW` only on the *targeted single-channel tune* — the scan/survey path was untouched, so it still wedges ~ch6-7). This build **removes the crutch**: extend the same `CAL_BW`-defer to the scan path so a full 14-channel sweep completes without wedging → the driver joins with **SSID + password only (`CHANNEL=0`)**. **Supersedes the channel-baked WiFi-ISO staging relay.** Build to the trap-mine FINDINGS as authoritative.

## Root cause recap (from `Plans/RESEARCH-2026-07-22-mt7601u-channel-switch-trapmine-FINDINGS.md`)
The wedge is `MCU_CAL_BW` (inside `set_bw_filter`), fired on every channel change. Your merged fix defers it on the **targeted** tune (`TunePath::Targeted`) and recalibrates post-association — proven correct in the AAG. But the **survey/scan path calls `inline_cal_bw(TunePath::Survey)` hardcoded `true`** (confirmed in the merge AAG), so every scan hop still runs `CAL_BW` → the sweep wedges around ch6-7 (BUILD-W1 reached only ~ch1-6 on silicon). That is exactly why a full scan can't be trusted and the channel was baked.

## Scope — what to build
1. **Extend the `CAL_BW`-defer to the scan/survey path.** Make `inline_cal_bw(TunePath::Survey, ...)` **defer** `CAL_BW` on each scan hop (the same mechanism as your targeted-tune fix), so the full `reg_start..reg_num` sweep completes **without wedging**. Keep the per-hop RF programming that a scan genuinely needs — **freq-plan regs 17-20 + LNA gain + VCO cal + TX power are still set on each hop** (per the trap-mine: enough for beacon RX + management-frame TX); only the wedging bandwidth-filter MCU round-trip is deferred. **Recalibrate `CAL_BW` after association** on the operating channel — reuse your existing post-assoc `calibrate_bw` path (the `deferred_cal_pending` flow), which already fires after the assoc-resp on both open + WPA2 paths.
2. **Remove the channel requirement — `CHANNEL=0` (scan) is the shipping path.** With the scan no longer wedging, `configured_target()` with `CHANNEL=0` does a full sweep, finds the AP by **SSID**, selects its BSSID/channel, and joins — **SSID + PASSPHRASE only, no channel.** Set the `mt7601u_assoc_baremetal` scenario / `configured_target()` shipping shape to `CHANNEL=0` (the driver discovers the channel). The user provides SSID + password; that's it (that part IS normal — a distro asks for those).
3. **Do NOT regress the targeted path.** Your merged `TunePath::Targeted` fix stays as-is (a station *can* still be told a channel, e.g. for a fast known-AP join), but it is **no longer required** for correctness — `CHANNEL=0` scan-and-join is the default/shipping behavior.

## Blind-hardware failure-mode / discriminator bank (mandatory — the real proof is silicon, and this run tests MORE unproven surface at once)
**Honest framing:** skipping the channel crutch means the first bare-metal run tests **two** unproven things together — (a) the full scan *without* `CAL_BW` doesn't wedge, and (b) the assoc/4-way/DHCP path. The discriminator bank MUST separate them so a failure is localizable. Carry the trap-mine's 6-mode bank + add scan-specific modes, each mapped to serial breadcrumbs + the NVMe sink:
- **Scan still wedges mid-sweep** → per-hop `set_channel`/CAL breadcrumb: which channel wedged, and did `CAL_BW`-defer actually apply on scan hops (`cal_bw=false` on the hop log)? Distinguishes "defer didn't take on the survey path" from "a *different* MCU op wedges on scan."
- **Scan completes but the AP's SSID is NOT found** → `scan complete — N BSSID(s)` + the BSS list: is the AP's channel in the swept range, and is RX sensitivity sufficient without `CAL_BW` (beacons heard)? Distinguishes "scan RX too weak uncalibrated" from "AP not in range/wrong band."
- **SSID found + selected, assoc fails** → `assoc attempt`/`authenticated`/`assoc result` breadcrumbs localize auth vs assoc-reject (this is the assoc-path unknown, independent of the scan fix).
- **Assoc OK but post-assoc `CAL_BW` recal wedges** → a breadcrumb before/after the deferred recal; if the link comes up then the recal kills the MCU, that's a *different* fix (skip `CAL_BW` entirely, or recalibrate differently).
- **4-way / DHCP** → your existing breadcrumbs (M1..M4, DORA) — the LINK-UP close.
