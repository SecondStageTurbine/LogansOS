## Section 309: Janus, #8 (P4: the PowerControl cap and SYS_POWER)
**MODEL** GPT-6.1-Sol, **EFFORT** high: a new syscall and a new capability on the shutdown path, after your #6/#7
reviews. Head `9121fba2`.
1. Only the session root (neo-init) holds `PowerControl`; it has USE only (no DERIVE, no GRANT), so no other
   process can obtain it by derivation, grant, inheritance at spawn, or a reused handle slot.
2. `SYS_POWER` returns EPERM without the cap, EINVAL for a bad action or flags, EBUSY while a shutdown runs; two
   concurrent calls (two CPUs) can't both start a shutdown.
3. The syscall number and action values come from one source (`acpi/power_abi.rs`) shared with libneo; the
   SDK-ABI entry matches, with a byte/number oracle independent of the code.
4. The kill-switch: `power-cap` off gives ENOSYS and the previous behaviour.
5. The PR body's prior-art/CP section is present and holds (it defers K4/K6 analysis to #6/#7; check nothing new
   crosses CPUs).

## Section 310: Jarvis, #14 (P5: Shut down and Restart from Home, behind a confirm)
**MODEL** GPT-6-Luna, **EFFORT** high: contained userland UI over #8's syscall. Head `73453e31`.
1. `shut down` / `restart` at Home opens the confirm card; nothing powers off without an explicit confirm, and Esc
   or any other key cancels.
2. Only neo-init calls `SYS_POWER`; Arthur's text can't trigger it (a model reply containing "shut down" does not).
3. Kill-switch: `power-menu` off sends those lines to Arthur as before; the product image pairs `power-menu` with
   `power-cap` and the check enforces it.
4. The `ot90_power_menu` scenario's ordered serial checks and the QMP power-off check would fail if the confirm
   were skipped or the order changed.
