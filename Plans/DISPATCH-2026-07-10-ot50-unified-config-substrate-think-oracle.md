## The one idea (frame everything around it)
**There is ONE config store.** Arthur saying "I've turned that off, sir" and `neo> config get <key>` must **provably read the same key** — no hidden second registry, no "Arthur's settings" vs "system settings." Arthur, the `neo>` power path, and the future Atrium GUI are all **VIEWS over one typed, capability-gated store**; depth for a power user = *more keys visible*, never *a different mechanism*. The verified prior art (read it firsthand): macOS `defaults` — the GUI and the CLI edit the same per-domain typed key-value store. The notorious negative case: Windows's split-brain (registry vs two Settings surfaces). Today's small surfaces (`grants.json`, `stakes.json` — owner-readable files Arthur mediates) already conform; the THINK generalizes that pattern into the substrate every future config rides.

## ISCs — the design (recommend a shape; the PL ratifies)
- **ISC-1 — the store shape.** Propose the concrete substrate: **typed** (what type system — a fixed scalar/record schema? per-key declared types?), **capability-gated** (read/write gated per key or per namespace via I-15 write-caps — a surface can only read/write keys its caps admit), **file-backed** (extend the `grants.json`/`stakes.json` owner-readable-file pattern, or a dedicated store?). State the one-store invariant precisely and how it's enforced (what structurally prevents a second registry from ever appearing).
- **ISC-2 — the VIEWS model (the load-bearing part).** Show how Arthur, `neo> config`, and a future Atrium surface are all views over the ONE store: the read/write API each uses, and the falsifiable property — "Arthur turned it off" ⇒ `neo> config get` shows the same value, always. No surface caches a divergent copy; no surface has a private store. This is where the anti-split-brain guarantee lives.
- **ISC-3 — the four banked lenses, embodied (not just cited).** Show the store design *enforces* them: **never-adaptive-surface** (the store never self-morphs the UI; Arthur suggests, only the owner rearranges — Findlater/McGrenere CHI 2004), **promotion-affordance** (layer-2 keys are visible-but-quiet from layer-1 via disclosure states on ONE surface, never two parallel surfaces), **explain-never-vanish** (a declined/failed config write gets a stated reason + pointer in the butler register, never a silent redirect), **power-is-not-a-jailbreak** (more visible keys = more granted capabilities, never fewer enforced invariants; no "developer mode" posture downgrade).
- **ISC-4 — the seams (compose, don't collide).** (a) **OT-51 rollback seam** — a whole-system A/B rollback (OT-51, Cerebro's parallel THINK) must NOT silently lose or corrupt the config store; state whether config lives *inside* the rolled artifact, *beside* it as recorded reversible deltas, or spans both, so "roll back the system" and "keep my settings" have a defined interaction. (b) **OT-17 memory** — the config store is NOT Arthur's memory substrate; delineate the boundary (settings vs learned context). (c) **grants/stakes** — the existing small surfaces are the seed; the store generalizes them, it does not replace their semantics.
- **ISC-5 — format + byte-oracle.** If the store has an on-disk byte layout, the standing rule applies: it needs an **independent hand-laid byte-oracle**, not just round-trip. Propose the format + a worked byte example, or explicitly defer the byte-layout to the build with a note that the build owes the oracle.
- **ISC-6 — smallest-first path + kill-switch.** Today's `grants.json`/`stakes.json` already conform — so the migration is *additive*, not a rewrite. Sequence: the first real config-surface build (what's the smallest one — an Arthur-toggle + its `neo> config get` mirror?), then generalization. Kill-switch discipline: default-off ≡ today's scattered small surfaces, bit-for-bit.
- **ISC-7 — honest forks + PL ratification.** The store shape is explicitly *gated on PL ratification* (per the OT-50 row). State the genuine forks (dedicated store vs generalized-files; type-system strength; per-key vs per-namespace caps) with your recommendation + reason for each.
