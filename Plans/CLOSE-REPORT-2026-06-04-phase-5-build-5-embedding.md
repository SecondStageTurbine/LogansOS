## Summary

BUILD-5 adds the final Layer-2 op, `Embedding` (OpCode 9): a rank-1 I32 index tensor gathers rows from a rank-2 F32 table into a rank-2 F32 output. This is the first I32 consumer in the inference executor, so the arm validates input dtypes individually instead of sending the indices through the existing F32-only path.

No `.neom` format or validator changes were made. The existing opcode 9 format support is consumed by executor dispatch, the op kernel, `valid_embedding.neom`, and the `infer_embedding_forward` QEMU scenario.

## Byte oracle

The forward scenario gathers indices `[2, 0, 3]` from a `[4, 3]` F32 table. Expected output bits:

```text
[0xbf800000, 0xc0000000, 0xc0400000,
 0x3f800000, 0x40000000, 0x40400000,
 0x3dcccccd, 0x3e4ccccd, 0x3e99999a]
```

Expected bytes, little-endian:

```text
00 00 80 bf 00 00 00 c0 00 00 40 c0
00 00 80 3f 00 00 00 40 00 00 40 40
cd cc cc 3d cd cc 4c 3e 9a 99 99 3e
```

The host test asserts these bytes directly, and the QEMU scenario compares the kernel-produced tensor bytes against the same exact oracle.

## Bounds safety

The kernel rejects any index with `idx < 0 || idx >= vocab` before computing or reading the table row. The host suite covers OOB and negative indices in `embedding_rejects_oob_and_negative_indices_before_read`, plus wrong index dtype and unsupported ranks.

The QEMU safety scenario `infer_embedding_oob_rejected` loads `valid_embedding.neom`, creates I32 inputs `[4]` and `[-1]`, and requires both `SYS_INFER_RUN` calls to return `EINVAL`.
