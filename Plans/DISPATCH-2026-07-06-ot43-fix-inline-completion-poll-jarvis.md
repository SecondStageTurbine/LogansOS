**Status:** DISPATCHED — **the OT-43 hang is LOCALIZED** (Prometheus trap-mining + PM code verification converged). Root cause: the virtio-blk **completion worker is a bare polling kthread with no priority boost and no IRQ** — `virtio_blk_completion_worker` = `loop { poll_all_completions(); yield_now(); }` (`virtio_blk.rs:920`). The submitter parks via `block_current_with_token_and_guard` and depends **entirely** on that worker getting a scheduler slice to call `wake_thread_token`. Under memory-scenario contention (many user processes doing crypto + block I/O — `forget` does the most: key-burn + overwrite + truncate), the worker is **starved**: the op completes instantly in TCG (device posts to the used-ring) but nobody polls it → the submitter stays parked → post-spawn hang with "repeated virtio-blk completions" visible. Intermittent because the starvation window is timing/contention-dependent (passed Oracle's consolidation gate 14:04, hung all retries of Cerebro's). **This is Prometheus's ranked Pattern C (× A); confirmed at source.**

## The fix (ISC-FIX-1) — poll-inline-after-notify (the Linux blk-mq hybrid-poll pattern)
Restructure `submit_pending_and_wait` (`virtio_blk.rs:507`) so the submitter does **not** commit to parking before observing completion:
1. Submit + `notify_queue` to get the op on the wire (as today).
2. **Immediately poll the used-ring inline** (bounded spin — a small fixed number of `poll_used()` attempts, or a short bounded loop). Under TCG the op is almost always already complete here.
3. **If `poll_used()` returns `Some(completion)`** → process it inline, `wake`/return the result, **never park**. The hang is structurally impossible on this path.
4. **Only if still not complete after the bounded inline poll** → park via the existing `block_current_with_token_and_guard` token mechanism (the completion worker remains the backstop for the genuinely-slow case).

**Safety — the single-claim invariant that makes this race-free (do not break it):** both the inline poll and the completion worker retire via `poll_used()` → `self.in_flight.take()` under the same inner lock. `take()` is the atomic single-winner claim: whichever acquires the lock first gets the `Completion`, the other sees `None` and no-ops. **The inline poll MUST use the same `take()`-based `poll_used()` under the same lock** — never a second parallel completion path. Verify there is exactly one `in_flight.take()` claim site reachable per completion; a double-take would double-wake / double-free the rendezvous.
