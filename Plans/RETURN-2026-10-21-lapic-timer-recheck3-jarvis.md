## Finding: R4-P2 — late PIT edge is accepted as a full calibration window

**Location:** `kernel/src/acpi/timers_logic.rs:204-218`; consumed at `kernel/src/arch/x86_64/refclock.rs:244-256`.

**Reproduction:** A temporary host test imported the unchanged production `timers_logic.rs`. With `low_timeout=10`, `high_timeout=10`, an OUT2 trace of HIGH, then LOW only after the injected clock moved from 0 to 100, then HIGH, returned `true`. A second trace observed LOW immediately, moved the clock from 0 to 100, then first observed HIGH; it also returned `true`. Both tests passed as *reproductions of the bug*. The transition-setting read makes the loop condition false, so neither `now()`/timeout check at lines 206 or 213 executes for that late edge. The checked-in `pit_one_shot_needs_both_edges` KAT holds the old level beyond the deadline and therefore exercises the timeout body; it misses an edge on the first read after the deadline.

With a gated, absent, or misbehaving channel-2 path that yields a stray late transition, `measure_pit` reports the fixed 10 ms duration anyway. If PIT is the only working reference, `choose_rate` can promote the resulting sample to `Calibrated` without a second check (`lapic_timer_logic.rs:222-233`). Check elapsed time when each edge is observed, including the iteration that observes the new level. An early LOW→HIGH transition also passes immediately and is assigned the full duration; the helper proves ordering and an upper bound only, not the expected rate.

## Dispatch questions and other diff review

- **R1 remaining paths.** `calibrate_lapic` at `lapic_timer.rs:290-303` uses an estimated TSC for its approximately 10 ms measurement window when there is no crystal or independent clock. This is outside the fixed tick-verification budgets, but disproves the unqualified “never sizes a wait” claim. `start` also accepts `Estimated` at 409-410 and `plan` uses it for a TSC-deadline *period* at `lapic_timer_logic.rs:120-124`; that period is not a verification timeout. A wrong leaf-0x16 estimate can yield a wrong tick rate even though first-tick liveness passes. The prior review already identified the unverified estimate fallback. The no-verify control uses the bound at `lapic_timer.rs:508`. At a real 1 GHz TSC, the bound means 0.5 s for each 100 Hz first-tick demotion and 5 s for PIT verification; this costs boot time but does not make a healthy 100 Hz tick fail early.
- **R2 firmware and routing.** `refclock::discover` runs before BSP scheduler initialization (`refclock.rs:89-102`), so stopping a firmware-running HPET does not interrupt an established kernel clock. Clearing legacy replacement selects the standard route under [HPET 1.0a §2.4.2](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/software-developers-hpet-spec-1-0a.pdf); it cannot create physical 8254/PIC wiring on platforms that omit it. The fallback's first-tick check will name that failure. Disabling `Tn_INT_ENB_CNF` also inhibits comparator interrupt delivery in FSB mode; the [HPET spec §2.3.8](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/software-developers-hpet-spec-1-0a.pdf) says that bit is required for timer interrupts. No extra FSB bit has to be cleared for this polling use.
- **R2-P3 specification nit:** `timers_logic.rs:176-179` writes every set interrupt-status bit back. [HPET 1.0a §2.3.6](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/software-developers-hpet-spec-1-0a.pdf) says write-1-clear for a **level-triggered** comparator, but to ignore an **edge-triggered** comparator's status and always write 0 to that bit. A register image with comparator 0 edge mode (config bit 1 clear) and status bit 0 set produces an illegal status write of `1`. I did not establish a resulting interrupt failure; mask status writes to level-mode comparators.
- **R3 other consumers.** The timer lane's FADT output is only `TimerHardware.pm_timer` (`acpi/mod.rs:264-281`), then `refclock::discover`/`read_free_running` (`refclock.rs:130-133,167-180`). No second fixed-hardware read in this lane bypasses the flag check.
- **R4 hardware behavior.** The [Intel 8254 mode-0 description](https://www.scs.stanford.edu/25sp-cs212/pintos/specs/8254.pdf) says OUT is LOW after the control word, stays LOW to terminal count, then HIGH. A real programmed PIT should expose LOW almost immediately; the 3-million-cycle short timeout at `refclock.rs:59-61` is generous at common TSC rates. An incorrectly fast LOW→HIGH trace still passes and the outer cross-check only rejects it when a second independent rate exists. No real gated PIT or firmware-configured HPET was exercised here.
- **Coverage.** The four-shard/scenario gate exercises QEMU's normal HPET/PIT state and the named mode/fallback controls. The source wires `timer_not_lapic`, `no_tick_source`, `no_tick_after_unverified_mode`, and `apic_mode_not_x2apic` at `test_harness.rs:18465-18479,18515-18527`; `pit-gated` masks IRQ0 in `scheduler.rs:373-378`, rather than injecting a channel-2 port trace. Host KATs exercise register images and stuck-level PIT traces. Neither covers late edge timing, a real gated channel 2, or firmware's HPET state. These are coverage limits, not claimed QEMU failures.
