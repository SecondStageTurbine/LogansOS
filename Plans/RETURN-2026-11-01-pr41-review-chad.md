# Relay 251: design read of PR #41

Reviewed PR head: `6bc1a74dbfbad1189fe10ee6bc76b00c221ccec2` (`pr41`).

- **PASS — Decode boundary.** The concrete boot path gives the viewer a derived USE-only READ cap and puts reading/decoding in that process (`docs/THINK-2026-11-01-l2d-images-in-the-desktop.md:160-180,298-319`). The later user-chosen path uses `OP_PERMISSION`; the WM opens and derives the cap in `permission.rs:225-238`, then lends and revokes it in `permission.rs:444-474`. No proposed path sends image bytes through the WM decoder or kernel.
- **FAIL — Per-image/per-session enforcement is overstated.** The 16 MiB decoded cap and 32 MiB encoded cap bound the proposed viewer input (`docs/THINK-2026-11-01-l2d-images-in-the-desktop.md:310-321,417-422`), and a budgeted child can be hard-limited when `mem-quota` is enabled (`:470-480`). But the desktop build does not enable `mem-quota`; the document itself says the image scenario must enable it and product defaults remain off (`:480-483`). Further, the 64 MiB is the viewer's frame account, while the WM is explicitly “unlimited root” (`:461-468`), so it is not an enforced whole-session ceiling. Concrete case: launch the proposed image viewer in the product desktop with `mem-quota` off; repeated hostile-file decode allocations have no stated hard account ceiling. Make the feature and per-session accounting an explicit prerequisite or narrow the claim to the test scenario and viewer process.
- **FAIL — The quota discriminator does not prove the stated cause.** The test says a 2048² decode under 32 MiB must fail with `ENOMEM` (`docs/THINK-2026-11-01-l2d-images-in-the-desktop.md:615-617`), but the decoder is also instructed to reject any image above the 16 MiB decoded cap (`:417-422`). Thus the same input can fail as `TooLarge` before quota exhaustion. Concrete input: a 2048×2048 RGBA PNG (exactly 16 MiB) is at the cap boundary; use an image whose decoded size is within the cap but whose measured peak allocations exceed the test budget, and assert the error is `ENOMEM` after a successful size check.
- **PASS — First build and visual gate.** A one-image viewer exercises file cap → app decode → G1 → WM composite, and is a useful first consumer with no protocol addition (`docs/THINK-2026-11-01-l2d-images-in-the-desktop.md:647-651`). The independent Python decoder plus scene oracle and exact client/full-frame digests distinguish the image from the no-image scene (`:572-598,602-608`), so a passing oracle demonstrates the decoded pixels reached the framebuffer.
- **FAIL — One spawn citation is not the claimed file-cap template.** The viewer row and boot steps cite `desktop_session.rs:5440-5490` for a spawn-with-cap layout (`docs/THINK-2026-11-01-l2d-images-in-the-desktop.md:641,561-563`). That code actually opens and passes the Lens directory with LOOKUP|READDIR using `sys_spawn` (`desktop_session.rs:5461-5484`); it does not derive or pass a file READ cap and does not use `sys_spawn_budgeted`. Cite `permission.rs:225-238` for the derived USE-only cap and `sys_spawn_budgeted`'s API separately, or label the Lens code only as an fd-slot layout example. The image design's actual cap recipe is correctly written in its own pseudocode (`:298-304`).
