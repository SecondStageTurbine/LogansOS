# RETURN — relay #105: OT-87 R4.1, device identity and the install claim (PR #163)

Reviewer: Muse (Gwen), a separate model family, reviewing Claude-authored code. Files read from the repo at the reviewed SHA. Pasted by the PL on 2026-10-27; banked verbatim by the PM.

Reviewed SHA: `cec200af` (PR head `d1aa3a89` plus a merge of main). Gate batch 8, run 40477098079, all green. Scope per the dispatch: claim machinery only, no installer writes yet (those are R4.3).

1. **The claim is the only path past the guard, and it's narrow — PASS, with one named limitation.** `GuardedDevice::write_block` (`kernel/src/drivers/block/mod.rs:484`) is guard-checked; the only other inner write path is `claimed_write` (`mod.rs:503`), which requires the device's `claimed` flag (Acquire load) and is reachable only from `install_claim`'s `KernelTarget::write` (`kernel/src/drivers/block/install_claim.rs:89`). The claim holds `Arc<GuardedDevice>` (`claim_logic::Claim`, `kernel/src/drivers/block/claim_logic.rs`), so a registry change cannot redirect it; `Claim` has no Clone derive and no API to swap its target or clear `stopped` (sticky via `get_or_insert`), so a stopped claim cannot be re-armed or moved. One claim at a time per device: `claim()` swaps `claimed` to true before validation and restores it on failure unless it was already set (`install_claim.rs`, `claim` function). Limitation to close in R4.3: the registry does not consume the enumeration token — after a `ClaimedWriter` drops (which clears `claimed`), the same `Enumerated` row can claim again, since the generation is unchanged while the device stays alive. A fresh claim re-runs every refusal check, so this is not a guard bypass, but "expires after one install" does not yet hold across writer lifetimes. With `installer` off, none of this compiles: `claim_logic` and `install_claim` are `#[cfg(feature = "installer")]` (`mod.rs:14–20`), as are `MediaState`, `MediaTracker`, the `claimed` field and `claimed_write`; `installer = []` (`kernel/Cargo.toml:1027`) is not in the default set, and the guard path is today's.
2. **Tokens can't be forged or reused — PASS.** In R4.1 tokens never cross the syscall boundary: no syscall takes a token, and there is no indexed caller of `install_claim::enumerate` or `install_claim::claim` outside the module itself — the API is kernel-internal, for the future installer. (If a future syscall accepts a token, forgery becomes a design question for R4.3; it is not one in R4.1.) A token from before a death is refused twice over: `current_generation` (`install_claim.rs`) bumps the slot's generation when the device is dead (counted once) before comparing, so the token mismatches (`StaleToken`), and the `alive()` check refuses with `DeviceDead` regardless. Re-registration gets a new slot (`register_device` pushes, never reuses), so an old slot's token still names the old device object — which is exactly what the claim holds. A token from before a reorder or removal is likewise refused by the generation comparison (`claim_logic.rs:389`).
3. **The pre/post `media_generation` checks — PASS.** `Claim::write` (`claim_logic.rs`, `write` method) reads `media_generation()` and `alive()` before submission — a mismatch means `target.write` is never called (`MediaChangedBefore`) — then reads both again after completion, and any mismatch stops the claim for good (`MediaChangedAfter`, sticky; later writes return `Stopped`, as does `boundary()`). `flush()` has the same before/after checks, and `KernelTarget::write` re-checks `media_state()` between its 64 KiB chunks. Ordering: the pre-read is an Acquire load of the tracker generation (`MediaTracker::state`, `mod.rs:175ff`, AcqRel bumps) or, for NVMe/AHCI, an MMIO status-register read, in program order before the submission; NVMe submission itself is synchronous with a Release fence before the doorbell write and an Acquire fence after the completion entry is observed (`nvme.rs`, queue `submit`), so the post-check genuinely runs after completion, not after a fire-and-forget doorbell. Caveat, which is item 6's stated limit rather than an ordering defect: the post-check can only see events the driver has already processed into the tracker; a swap the driver has not yet reported is invisible to both checks.
4. **Driver reporting — FAIL.** Per driver, against THINK §2a item 5's list (removal, reset, namespace/config change, fatal status):
   - NVMe: removal → dead (CSTS all-ones, `nvme.rs` `media_state` ~473ff); fatal → dead (CSTS_CFS, CSTS_NSSRO, RDY-down). **Namespace-change notices: not implemented — there is no AEN processing anywhere in `nvme.rs` (the interrupt handler only counts interrupts), and no async-event queue is ever armed. Reset notices: not implemented as notices** — a reset is visible only if a `media_state()` poll happens while CSTS_RDY is down, in which case the device is declared dead; a reset that completes between two polls leaves no trace in the generation.
   - AHCI: removal → dead (PxSSTS.DET not present+PHY, `ahci.rs` `media_state` ~395ff); exchange → changed (PxSERR.DIAG.X); PhyRdy change → changed (PxSERR.DIAG.N), counted once and cleared write-1-to-clear for only those two bits; the command path also notes X/N before clearing PxSERR (~477ff). Port-reset status has no dedicated poll — it is covered only indirectly via DIAG.N when the PHY re-establishes.
   - Virtio-blk: config change → changed (`config_generation` move, `virtio_blk.rs` `media_state` ~714ff); NEEDS_RESET/FAILED → dead. Removal has no virtio-blk notification in this driver; FAILED covers device failure.
   Concrete FAIL sequence for NVMe: enumerate an NVMe disk and take a destructive claim; the host detaches namespace 1 and attaches a different namespace with the same serial and capacity (a twin image) while the controller stays ready throughout. No generation bump occurs (no AEN path exists to produce one) and `alive` stays true, so the next `ClaimedWriter::write` pre-check passes and the write lands on the wrong medium. The step-boundary identity check does not catch it (serial, model and capacity all match), and the fingerprint check catches it only if the twin's sampled windows differ outside what the current step overwrites — the item 6 masked case. The THINK relies on this reporting: §2a item 5 calls reliable driver reporting "a prerequisite, not something the installer can supply," and lists "NVMe namespace or reset notices" as part of the R4 work. The fix is NVMe AEN processing for namespace-change notices plus reset-notice handling — or, with explicit PM sign-off, moving NVMe namespace-change into the stated unreported limit. Scope note: no installer writes exist yet in R4.1, so nothing can exploit this today, and the claim machinery itself (items 1–3) is sound; the failure is in driver event coverage, not in the claim logic.
5. **"Identity unavailable" fails closed — PASS.** `DriverIdentity::available()` (`claim_logic.rs`) requires a serial non-empty after trimming and printable ASCII; `ascii_field` strips NULs and spaces from both ends and returns empty if any interior byte is non-printable, so an empty, blank or non-printable serial can never pass. A destructive claim on such a disk is refused with `IdentityUnavailable` (`claim_logic.rs`, `claim` function); a Fresh claim is allowed by design (a blank or INCOMPLETE disk has nothing to lose). The kernel's identity re-reads are live: NVMe re-issues Identify Controller + Namespace (`nvme.rs:441ff`), AHCI re-issues IDENTIFY DEVICE (`ahci.rs:361ff`), virtio-blk re-issues GET_ID (`virtio_blk.rs:685ff`, refusal or a zeroed buffer → empty serial → unavailable). A same-serial twin is not treated as the same disk: the claim-time identity comparison covers the full `DriverIdentity` including capacity and sector size, the claim-time window comparison refuses before the first write (`ChangedSinceEnumeration`), and the boundary check refuses later (`FingerprintMismatch`/`IdentityChanged`) — except for the masked case, which is item 6's stated limit.
6. **The stated limit is honest — PASS.** The masked-swap KAT (`masked_unreported_swap_is_not_detected`, `tools/install-claim-logic-tests/src/tests.rs:412ff`) asserts the limit on purpose: an unreported replacement with the same identity and the same last MiB, whose first MiB differs only inside the sectors the next step writes, is swapped in before that step, every boundary passes, and the test asserts `c.boundary() == Ok(())` with the comment "the limit: not detected" and "a later claim of a stronger bound must fail it." `claim_logic.rs`'s header states the same limit in words ("What it cannot decide"). The PR claims no stronger bound.
7. **Memory — PASS.** Enumeration keeps only digests: `Fingerprint::read` (`claim_logic.rs`) hashes the two windows chunk-wise (64 KiB buffer) and `enumerate()` (`install_claim.rs`) stores the resulting 64-byte `Fingerprint` per row — no path keeps per-row bytes. Only the live claim holds the 2 MiB of expected bytes (`Claim.expected: Windows`, two 1 MiB windows, or the whole device if smaller), and only one claim per device can be live (`AlreadyClaimed`). Step-boundary comparison is chunk-wise (`Windows::matches`, 64 KiB buffer), not a second full copy. Failed allocation and failed reads fail closed: `DmaBuffer::alloc_zeroed` failure in `KernelTarget::write` returns false → the claim stops with `Io`; a window read failure makes `Windows::read` return None → `Io` refusal at claim time; a fingerprint read failure makes `enumerate()` skip the row (logged "unreadable"). One note: the 2 MiB window allocation itself is an infallible `Vec` allocation (kernel-wide OOM policy applies, as for every `Vec` in the kernel); the graceful fail-closed paths are the ones listed above.
8. **Test-only items stay out of the product — PASS, with one verification limitation.** `neo-test-install-claim = ["neo-test", "installer"]` (`kernel/Cargo.toml:877`); `installer` itself is absent from `PRODUCT_IMAGE_KERNEL_FEATURES` at this SHA (`tools/xtask/src/main.rs:5219ff`, full list contains no `installer`, `neo-test*` or `neofs-partition` entry). No `neo-test-install-claim` cfg gates or swap hooks were found in the driver files — swaps are modelled in the host KATs, not by kernel hooks. Limitation, stated plainly: the QEMU leg `install_claim_identity` in `kernel/src/test_harness.rs` could not be read — the file is 1,583,197 bytes, over the read tool's limit, and the repo is private, so the raw download returns 404 without the token the tool redacts. Its gating was therefore not independently verified; this item's verdict rests on the Cargo feature gating and the product list above.
9. **Coverage — gaps to name.** Real NVMe/AHCI media-change events (QEMU cannot hotplug these in the gate); a SATA disk behind a port multiplier (the AHCI port registers describe the port, not the PM device behind it); the NVMe AEN gap (item 4, a FAIL, not just a gap); the token-reuse-after-drop limitation (item 1); `PROTECTED_SERIALS` is empty by design until a lane needs it (the VMD/layer-5 table); the `test_harness.rs` leg unread (item 8); no end-to-end installer exists yet (R4.3), so the claim has never driven a real install; NVMe CSTS RDY-down declares the device dead permanently (no revive in `MediaTracker`) — fail-closed, but a transient not-ready observed by any poll makes the disk unclaimable for the rest of the boot; and virtio `config_generation` is a u8, so 256 config changes between two polls would wrap undetected.

**Overall verdict: FAIL.** Item 4 fails on NVMe namespace-change and reset notices, which the THINK lists as required R4 driver reporting and relies on as a prerequisite. Items 1, 2, 3, 5, 6, 7 and 8 pass. Per the dispatch type (revert-first on a confirmed FAIL), this should be resolved by NVMe AEN/reset-notice handling, or by an explicit PM decision to move NVMe namespace-change into the stated unreported limit, before the claim is relied on for a real install.
