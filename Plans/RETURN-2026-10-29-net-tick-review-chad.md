# RETURN: relay #175, periodic net tick (#215)

Reviewed `46dcda0e` (stat, diff, enclosing callers), PR #215's body/CP table, and the same paths at `8c1b7a1d`. Citations below are at `8c1b7a1d`; net implementation is unchanged from the squash. Requested GPT-6.1-Sol/high, one session throughout the bundle. RAG health was healthy (Ollama/Qdrant true); the discovery query returned no hits, so direct reads supplied the evidence. **FAIL for the universal IF-off rule, allocation-free registries, bounded work, and strict off equivalence.** No production changes.

- **1 FAIL - the tick is IF-off, but not every harness taker is.** `kernel/src/net/periodic.rs:57` wraps both tick and pump; syscall SFMASK clears IF (`kernel/src/arch/x86_64/syscall.rs:608`), and `release_net` wraps closes (`kernel/src/sched/process.rs:1726`). The new harness also wraps its net operations (`kernel/src/test_harness.rs:41680`). IF-on takers still include `run_phase4_tcp_connect_stream_close` (insert at `test_harness.rs:36786`, tick at `:36833`), `run_phase4_dhcpv4_ipv4_udp` (send at `:36696`, ARP injection at `:36709`), and the real-DHCP harness (demux/tick at `:17587`/`:17590`). These plain TCP/socket/ARP/DHCP locks do not mask on acquire. Concrete configuration/schedule: `neo-test-phase4-tcp-connect-stream-close,net-tick`; preempt the IF-on harness holding CONNECTIONS with the timer, then schedule the IF-off tick on that CPU. Its snapshot at `kernel/src/net/tcp.rs:888` spins forever. This is a source interleaving, not a reproduced hang. The driver bring-up callers (`rtl8125.rs:1258`, `usb/boot_eth0.rs:121`) precede scheduler/tick startup (`main.rs:842`, `:893`, `:906`), so they are not concurrent product exceptions. `mt7601u/mod.rs:5269` is another harness-only tick caller. `net-rx` is not on this main snapshot; the separately inspected `origin/claude/ot96-wire-rx` (`dfa051ca`) wraps service/delivery/flush in `without_interrupts`, but that is not post-merge evidence. This confirms the documented OT-97 follow-up rather than establishing the dispatch's universal condition.
- **2 FAIL - IRQ-safe types and print placement pass; the no-allocation condition does not.** The device and identity registries are `IrqSafeMutex` (`kernel/src/drivers/net/mod.rs:27`, `kernel/src/net/identity.rs:67`). Registration prints occur after the guards end (`drivers/net/mod.rs:58`, `identity.rs:100`); no explicit park occurs inside either guard. However the device Vec pushes under its guard (`drivers/net/mod.rs:55`), and identity registration allocates the name, clones it and grows the Vec under its guard (`identity.rs:90`, `:94`, `:92`). Tick itself allocates its ID snapshot under the identity guard (`identity.rs:153`); `name` and `snapshot_links` also allocate there (`:186`, `:213`). Concrete input: first device/identity registration, or a tick with `interface-identity` enabled and at least one registered interface. The heap allocation occurs while REGISTRY is held. IRQ masking solves CP-37; it does not make these sections allocation-free.
- **3 PASS - no reverse net-lock ordering found in the tick call chain.** `kernel/src/net/mod.rs:63` finishes each protocol tick before the next. ARP/NDP age only their own cache (`arp.rs:214`, `ndp.rs:268`); DHCP tick only changes its own client (`dhcpv4.rs:184`, `:313`). TCP releases TIME_WAITS before snapshotting listeners/connections (`tcp.rs:880`, `:883`, `:888`); retransmit extraction releases socket.inner before enqueue (`:890`, `:1105`). Loopback and wire drains release OUTBOUND before injection/transmit (`:909`, `:1361`). Identity releases its registry before device lookup and re-acquires only to store (`identity.rs:153`, `:155`, `:159`). In particular the receive-side socket.inner -> TIME_WAITS nesting (`tcp.rs:1081`) has no tick-side TIME_WAITS -> socket.inner counterpart. This is a lock-order pass, separate from items 1/2/4.
- **4 FAIL - no fixed work bound per tick.** TCP snapshots the entire global tables (`kernel/src/net/tcp.rs:883`, `:888`), and `flush_wire_egress` drains until empty (`:1360`). The loopback pump's 128 outer rounds do not bound its inner drain (`:905`, `:908`); OUTBOUND producers have no queue cap (`:1347`). ARP and NDP insert unbounded keys and age the whole map (`arp.rs:74`, `:84`; `ndp.rs:90`, `:100`). Concrete inputs: N distinct ARP sender addresses, or N unacknowledged TCP connections/outbound segments, followed by one tick; its work grows with N. A concurrent producer can also keep an inner drain nonempty. There is no post-bring-up wire receive on this snapshot, so the external-peer ARP growth example describes the protocol seam, not a claim of a live product wire path. The local TCP tables/egress already lack a tick budget. A per-listener backlog cap does not bound the global work. Add cache/queue capacities and a per-invocation batch budget before calling this bounded.
- **5 FAIL for strict unchanged-kernel wording; PASS for absence of the periodic thread.** The module and startup are cfg(net-tick) (`kernel/src/net/mod.rs:20`, `kernel/src/main.rs:905`). With it off the new thread is absent. The two registry conversions and moved prints are unconditional (`drivers/net/mod.rs:27`, `identity.rs:67`). Concrete build: `desktop` or image A with net-tick off still takes the new IRQ-safe registry paths. PR #215 explicitly records desktop/image-A +384 bytes .text and usb-host +64, while default .text is unchanged. Those measurements are the author's, not a fresh binary comparison here. This is an intentional fix to the prior mixed-IF registries, but it is an exception to strict off equivalence.
- **6 PASS by source and attributed negative-control evidence.** `kernel/src/test_harness.rs:41670` requires two thread ticks; disabling startup reaches `thread_not_ticking` at `:41672`. The scenario requires missing bytes before the final leg (`:41742`), then neither ticks nor pumps while waiting (`:41747`); removing retransmission leaves it at `no_retransmit` (`:41760`). PR #215 records both controls (plus removing the pump), with the latter two receiving only 64240/143080 bytes. The scenario feature itself enables net-tick (`kernel/Cargo.toml:628`), so the runnable disabled-thread control is removal of startup, not claiming a feature-off scenario binary still contains this test. No fresh QEMU run was made.
- **7 FAIL for the CP table's universal claims; PASS for its presence.** PR #215 has CP-37, CP-56, I-14(a) and simultaneous-ticker rows. CP-37's statement that every taker is IF-off is too broad for item 1's harness combinations; the bank itself acknowledges such combinations (`docs/concurrency-pitfalls.md`, CP-37 third instance). CP-56's no-last-Arc-under-lock rationale is consistent with copying connection Arcs out before processing. Its absence of prints does not establish allocation-free registries (item 2). Existing regression passes cannot prove the uncovered mixed-IF configuration safe.
