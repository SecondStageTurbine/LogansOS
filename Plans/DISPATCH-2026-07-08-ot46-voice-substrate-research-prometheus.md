## The stakes (frame the dive)
Voice is **bidirectional**, and STT-in matters MORE than TTS-out for Article 1.5: a five-year-old **speaks before they type** — the primary interface for the youngest/least-technical user is *talking to Arthur*, so speech→text is the load-bearing half. But voice is a **NEW model type** (encoder-decoder / conv-frontend STT; VITS/flow TTS) unlike our decoder-only Qwen forward — so it raises the **same substrate question OT-16 raised for DeltaNet**: does it need a new ring-0 forward, a userland inference process, or a classical DSP path that skips the neural substrate entirely? And it introduces **audio devices** (mic capture + speaker output, with DMA) — the Phase-7.5 connectivity lane's cousin, so I-14 fault-containment is in play. The load-bearing NON-NEGOTIABLE, bake in from day zero: **voice input is push-to-talk / local-only, NEVER always-listening-cloud** — done our way, voice REINFORCES sovereignty; done the surveillance way it is exactly what Article 23.1 forbids.

## What to determine (real source — the actual model repos/papers, model cards, on-device benchmarks; byte-oracle-acquisition rule for exact claims — read the real thing, never a summarizing fetch)
- **Q1 — STT (speech→text): the load-bearing half.** Survey the on-device options and their real costs: **Whisper-class** (whisper.cpp — proven on-device, but encoder-decoder transformer + a conv/mel frontend, architecturally very different from our decoder-only Qwen path), the **smaller/faster** end (distil-whisper, Moonshine, Vosk/Kaldi classical HMM/DNN), and any tool-use-oriented small STT. For each: model size / on-device latency (real numbers where they exist), accuracy for conversational commands (not dictation-perfect — "good enough to run an OS by voice"), and — decisively — **does it need a NEW ring-0 forward, or can it run as a userland inference process?** Cite measured numbers.
- **Q2 — TTS (text→speech): the output half + the real fork.** **Neural** (Piper/VITS, Kokoro — high quality, a new flow/GAN forward) vs **classical/formant** (eSpeak-NG-style — tiny, deterministic, no neural forward at all, lower quality). The classical path **skips the neural substrate entirely** — a genuine fork worth stating plainly. Which fits the understated-butler voice AND our substrate constraints? Is "good classical" acceptable for v-first, with neural as an upgrade — or does the butler persona need neural warmth from the start? Recommend, and name the fork.
- **Q3 — The substrate-integration call (the OT-16 parallel — THE decision the row gates on).** For the recommended STT/TTS: **new ring-0 forward** (Whisper's encoder-decoder would be an OT-16-class kernel change — does voice RIDE the OT-16 data-driven-forward-graph generalization, or is it a separate forward?), **userland inference process** (a separate ring-3 model runner — cleaner isolation, the likely-right answer?), or **classical DSP** (no neural forward). Give the measured/estimated cost of each and a recommendation. This directly parallels the DeltaNet "new forward vs config-swap" call.
- **Q4 — Reference availability for the parity oracle (the OT-30 / DeltaNet-Q1 discipline).** For any neural model chosen, is there a **correct reference implementation** to anchor a parity oracle against (the exact question that un-parked DeltaNet)? whisper.cpp is a real C++ reference; Piper/VITS have reference repos. Confirm — a chosen model with no correct reference is a parked candidate, like Gemma-4 was.
- **Q5 — The privacy architecture + the audio-device dimension (bake in from day zero).** Design the **push-to-talk / local-only** mechanism: a physical key or explicit gesture, NOT a wake-word (a wake-word requires always-listening — the forbidden model). Confirm the whole path is on-device (no audio ever leaves the machine). And the **device dimension**: STT needs mic capture, TTS needs speaker output — new device classes (USB-audio / HDA-AC97), with DMA ⇒ the **I-14 fault-containment vectors** the eventual build must address (mic DMA through the fenced arena; a mic/audio driver fault cannot stall governance). State which I-14 vectors audio touches (research-level; the full containment analysis is the build's job). Note what the target hardware (the OptiPlex / typical laptop) actually presents for audio.
