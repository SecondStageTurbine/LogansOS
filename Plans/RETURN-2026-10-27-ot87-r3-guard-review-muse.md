# RETURN — relay #101: OT-87 R3, the write guard's partition rule and parser move (PR #160)

Reviewer: Muse (Gwen), a separate model family, reviewing Claude-authored code. Files read from the repo at the reviewed SHA. Pasted by the PL on 2026-10-27; banked verbatim by the PM.

Reviewed SHA: `7c771c0b` (PR head `2c342585` plus a merge of main). Gate batch 6, run 40457391685, all green.

1. **The parser move changes no decision — PASS.** The differential KAT (`tools/block-guard-logic-tests/src/lib.rs`, differential module ~897ff) compares the new `judge()` and `read_table()` against `legacy::judge()`/`legacy::read_table()` as Debug text (same claims, extents, blocked count, table name). The legacy file's header states it is `write_guard_logic.rs` exactly as on main at `e0a59501`, frozen and test-only. The corpus includes `windows` built by `windows_gpt(cap)` — the same builder as `windows_gpt_disk_never_arms` (`lib.rs:455`) — plus windows+markers, windows primary only, oracle 512/4096, disagreeing copies (and primary wiped), protective-MBR-only, 4K GPT, unreadable primary, whole-disk NeoFS and empty. The mutation sweep flips each byte of the primary header, the first two primary entries and the backup header, one at a time, across 5 bases, asserting `mutants > 2000`. The differential uses `judge()` (the feature-off path), which is the right comparison for this item.
2. **A Windows or foreign GPT never arms — PASS.** `partition_claims` (`kernel/src/drivers/block/write_guard_logic.rs:466ff`) skips every entry whose type GUID is not `LOGANSOS_NEOFS_TYPE_GUID` (`kernel/src/drivers/block/gpt_logic.rs` ~44, stored byte order, asserted equal to `uuid!().to_bytes_le()` by `logansos_type_guid_bytes` in `partition_guard_tests.rs`). A Windows disk with a NEOFSv1-looking block planted at a partition start arms nothing (`superblock_alone_arms_nothing`: the entry re-typed to a Linux FS GUID arms nothing; a superblock planted at the ESP's start arms nothing). A byte-swapped type GUID does not equal the stored-form constant, so it is skipped, not mistaken for the NeoFS GUID. The seal on the superblock is a BLAKE3 checksum anyone can compute, which is why the type-GUID gate — not the seal — is the load-bearing check for a Windows disk, and it holds.
3. **All five conditions are required — PASS.** Each single condition and each set of four is covered: type GUID alone (`type_guid_alone_arms_nothing`), superblock alone or with a broken seal (`superblock_alone_arms_nothing`, `unsealed_edit_arms_nothing`), a superblock claiming past its partition (`superblock_past_its_partition_arms_nothing`: BLOCKS+1 and u64::MAX/4096 arm nothing; BLOCKS or fewer arm the whole partition extent, not the volume), and INCOMPLETE set (`incomplete_partition_arms_nothing`). Note: the dispatch's "five" is GPT validates, type GUID, valid superblock, volume fits, INCOMPLETE clear; the THINK §4.2 lists four (INCOMPLETE arrived with the §4.7 incomplete-install rule) and a comment in `block/mod.rs` still says "four conditions" — the code checks five, and the comment is stale, not the code.
4. **The armed range is exact — PASS.** `oracle_disk_arms_partition_2_only` probes one sector before the partition, one sector after, a range crossing the end, the ESP start, LBA 0, both headers and both entry arrays — all refused by `Arming::allows` (`write_guard_logic.rs:131`, which requires one claim extent to contain the whole range). `PartitionDevice` (`kernel/src/drivers/block/partition.rs`) `new` requires the entry to be in the validated GPT with checked arithmetic and end ≤ the device's block count; `map()` requires a multiple of the logical block size and delegates to `partition_lba` (`gpt_logic.rs` ~235), which returns None when blocks == 0, when end > lba_count, or when `first_lba + lba` overflows — a crossing request is refused, never truncated. `PartitionDevice` wraps the `GuardedDevice` as inner, so its writes are judged against the whole disk again.
5. **Parser robustness — FAIL.** Five of the six bullets pass: count/size overflow (saturating_mul, then the MAX_ENTRY_BYTES bound, plus array == 0 rejected); entry array past the disk end (checked_add plus the ≤ last_lba + 1 bound); `first_lba > last_lba` (per-entry check); header CRC valid with a bad entry-array CRC (the array CRC is compared against header field 88); a backup header pointing at the primary (my_lba must equal the LBA being validated, and `read()` locates the backup at the last LBA, never via the primary's alternate field). No panic or out-of-bounds read: header reads index a fixed 512-byte buffer, entry reads use `chunks_exact(entry_size)` with entry_size ≥ 128, and allocation is bounded by MAX_ENTRY_BYTES. But **overlapping entries are not rejected**, and that bullet fails. Concrete disk layout: a valid GPT (both copies, all CRCs re-sealed) with usable range starting at LBA 34; entry 1, type ESP GUID, [2048, 1050623]; entry 2, type LogansOS NeoFS GUID, [2048, 1050623], INCOMPLETE clear; a valid sealed NEOFSv1 superblock at LBA 2048 whose total_blocks × 4096 fits the span. `validate()` (`gpt_logic.rs` ~183–203) checks each entry only against the usable range (`last < first` or either end outside usable rejects the copy); there is no pairwise overlap check anywhere in `gpt_logic.rs` or `partition_claims` (grep for "overlap" in `gpt_logic.rs` returns nothing). `partition_claims` therefore arms [2048·ss, 1050624·ss) for entry 2, and a `GuardedDevice` write to any byte of that span — including the ESP's FAT boot sector at LBA 2048 — passes `write_range_allowed`. The armed span is also a foreign partition's span, which breaks the R3 rule as stated ("arms exactly that partition") and item 5's "overlapping entries → arms nothing." Entry-over-table overlap IS covered (entries must lie in the usable range while headers and arrays lie outside it; `partition_over_the_tables_arms_nothing` covers a partition extending into either array or header) — the gap is entry-vs-entry only. Exposure scope, stated plainly: a real Windows disk never has overlapping entries (Windows Disk Management will not write them), so the Zenbook's actual Windows disk is not exposed by this; the failure is a crafted-disk, malformed-input case, exactly what item 5 tests. It is also why the differential sweep did not catch it: single-byte flips of a valid table cannot construct a second overlapping entry plus a sealed superblock. The fix is small: reject the table (or skip the overlapping entries) when any two non-zero entries overlap, in `validate()`.
6. **The judgement still reads only — PASS.** The `Disk` trait (`gpt_logic.rs:24`) exposes only `capacity`, `sector_size` and `read` — the judgement cannot write by construction. `GuardReader` (`block/mod.rs:176ff`) implements only reads (64 KiB chunks). `partition_claims` and the `boot-neofs` probe (`find_neofs_partition`, `fs/mod.rs` ~811–890: first LogansOS-typed partition without INCOMPLETE whose NeoFS probe passes, skipping the rest with logged "incomplete"/"probe" reasons) issue only reads before the arming decision. The #120 judgement-wait discipline is unchanged: `arming()` (`block/mod.rs`) uses `Once` plus `wait_for_judgement`, which waits with interrupts on and yields each round (CP-82); this PR only selects `judge` vs `judge_with_partitions` at `block/mod.rs` ~313–318.
7. **The test-only items stay out of the product — PASS.** The frozen legacy guard and the oracle live only in `tools/block-guard-logic-tests`, a host test crate, not in the kernel. `neofs-partition` is defined as `[]` (`kernel/Cargo.toml:1002`) and is not in the default feature set (`:77`). `PRODUCT_IMAGE_KERNEL_FEATURES` at this SHA (`tools/xtask/src/main.rs:5161ff`, 26 entries) contains no `neofs-partition` and no `neo-test*` entry.
8. **Coverage — gaps to name.** Real NVMe/AHCI with 4Kn sectors; a disk hot-removed during judgement; a GPT written by Windows Disk Management rather than the fixtures; the entry-vs-entry overlap case (item 5, a FAIL, not just a gap); and the differential sweep's single-byte-flip limit (it cannot construct multi-byte crafted tables such as the overlap layout).

**Overall verdict: FAIL.** Item 5 fails on the overlapping-entries bullet, with the concrete layout above. Items 1, 2, 3, 4, 6 and 7 pass. Per the dispatch type (revert-first on a confirmed FAIL), this FAIL should be resolved by the pairwise overlap rejection in `validate()` before the relaxation is relied on; the failure is narrow, crafted-input-only, and does not expose a real Windows disk.
