## 1. Why SC-4 now

SC-3C closed Q7 (per-CPU CR3 cache + IPI TLB shootdowns). The kernel is now SMP-correct for address-space mutations but **not yet SMP-correct for capability operations**. Substrate evidence:

- `kernel/src/sched/process.rs` line 53-56: `BUILD-1 uses a single global atomic because cap allocation is not a hot path; Phase 2 SMP work may switch this to per-CPU banks without changing the API surface.` — explicitly defers SMP cap-allocation work.
- `kernel/src/sched/process.rs` lines 165-172: per-process `handles: Mutex<HandleTable>` and `derivations: Mutex<BTreeMap<CapId, Option<CapId>>>` use `spin::Mutex` (single-CPU semantics, no IRQ-off discipline, no preempt-safe holding).
- `kernel/src/sched/process.rs` line 305-308: `PROCESSES: Lazy<Mutex<BTreeMap>>` registry uses `spin::Mutex`. Every cross-process operation (revoke walk, complete_grant, terminate, on_thread_reap) takes this lock multiple times in sequence — under SMP, concurrent operations can race in ways the single-CPU code is blind to.
- `kernel/src/sched/process.rs` `terminate` function: `Phase 1.5b limitation (ADR-007 §Q3): only Ready-state threads can be killed. If the yank fails, the target is Blocked in IPC (Phase 2 work to support).` — explicit Q8.c entry point.
- `kernel/src/ipc/mod.rs` `close_peer`: `mem::replace(&mut guard[peer_idx], EndpointState::Closed)` extracts PEER side; then `guard[my_side.idx()] = EndpointState::Closed` overwrites MY side **silently dropping any parked `Box<Thread>` on my side**. Under multi-threaded user processes (Phase 1.5+) or under forced-kill of a process with a thread blocked on its own channel side, this leaks the thread.
- SC-3C 4c verification report: `q7c_process_exit_during_thread_run` PASS with mechanism marker `q8c_deferred=true` — the existing exit path was preserved through SC-3C precisely because the Q8.c work was scoped out. Q8.c replaces that marker with implementation.

The pre-SMP capability machinery is functional for BUILD-1's single-CPU test scenarios. It is incorrect for SMP under specific race patterns enumerated in §3. SC-4 closes those races.

## 2. Substrate inventory (from OBSERVE)

### 2.1 Capability data model (canonical, ratified by ADR-004 / ADR-007)

```text
CapId(u64)              kernel-unique opaque cap identifier; CapId(0) reserved as null sentinel
CapRights {             8-bit meta rights + 8-bit semantic rights
    meta: u8            USE / DERIVE / GRANT / REVOKE (meta_rights module)
    semantic: u8        per-cap-type: SEND/RECV/CLOSE (channel) | KILL/WAIT/INSPECT (process)
}

Handle::Channel { channel: Arc<Channel>, side: EndpointSide, cap_id: CapId, rights: CapRights }
Handle::Process { target: ProcessId,                          cap_id: CapId, rights: CapRights }

HandleTable {
    entries: Vec<Option<Handle>>,        // lowest-free-index allocation per ADR-004 §Q2
}

Process {
    pid: ProcessId,
    name: &'static str,
    pmap: Option<Arc<Pmap>>,
    handles: Mutex<HandleTable>,         //  Q8.a target — single-CPU spin::Mutex
    derivations: Mutex<BTreeMap<CapId, Option<CapId>>>,    //  Q8.a target — single-CPU spin::Mutex
    exit_code: AtomicI32,
}

PROCESSES: Lazy<Mutex<BTreeMap<ProcessId, Arc<Process>>>>   //  Q8.b target — single-CPU spin::Mutex
COMPLETED_EXIT_CODES: Lazy<Mutex<BTreeMap<ProcessId, i32>>> //  Q8.b target — single-CPU spin::Mutex

NEXT_CAP_ID: AtomicU64                   // already SMP-safe; per-CPU banks deferred per line 53 comment
NEXT_PID: AtomicU32                      // already SMP-safe
```

### 2.2 Capability operations (hot paths)

All operations currently wrap their bodies in `without_interrupts(|| { ... })` to make them safe against same-CPU preemption. None acquire locks across `without_interrupts` boundaries except where noted.

| Operation | Locks taken (in order) | Cross-process reach |
|---|---|---|
| `install_cap(proc, handle, parent)` | `proc.handles` → `proc.derivations` | single |
| `derive_handle(pid, h, child_rights)` | `proc.handles` (read) → `proc.handles` + `proc.derivations` (via `install_cap`) | single |
| `revoke_handle(pid, h)` | `caller.handles` (read) → snapshot `PROCESSES` → loop: each `proc.derivations` (read) → loop: each `proc.handles` (write) + each `proc.derivations` (write) | **multi** — walks every process |
| `complete_grant(grantor_pid, ..., recipient_pid, ...)` | `grantor.handles` (read) → `recipient.handles` (write via `install_cap`) | dual |
| `register(proc)` | `PROCESSES` (write) | global |
| `get(pid)` | `PROCESSES` (read) | global |
| `cr3_for_thread(pid)` | `PROCESSES` (read) | global |
| `processes_snapshot()` | `PROCESSES` (read) | global |
| `name_of(pid)` / `any_user_process()` | `PROCESSES` (read) | global |
| `on_thread_reap(pid)` | `PROCESSES` (clone) → `proc.handles` (drain) → call `close_channel_peers` (touches channel mutexes) → `PROCESSES` (remove) → `COMPLETED_EXIT_CODES` (write) | global + cross |
| `terminate(pid)` | `PROCESSES` (read for staleness) → `scheduler::kill_thread_by_pid` → `PROCESSES` (remove) → `proc.handles` (drain) → call `close_channel_peers` | global + cross |
| `record_exit_code(pid, code)` | `PROCESSES` (read) | global |
| `take_completed_exit_code(pid)` | `COMPLETED_EXIT_CODES` (write) | global |

### 2.3 Existing SMP discipline (from SC-3B)

SC-3B introduced `SwitchMutex` for IPC channel state. The discipline rules per ADR-018/ADR-019:

- **`SwitchMutex`** = preempt-safe spinlock holding the runqueue's lock-owner field; safe to hold across context switches via `context_switch_with_release`. Used for IPC channel `state: SwitchMutex<[EndpointState; 2]>`. Irq-off acquisition required for IPC fastpath per SC-3B Phase D.
- **`IrqSafeMutex`** = preempt-safe + IRQ-off by construction (ADR-019); used for primitives that must be safe against IRQ-handler reentry on the same CPU. Heap allocator is the canonical use site.
- **`spin::Mutex`** = single-CPU spinlock; safe under `without_interrupts` only; UNSAFE to hold across context switches.
- **Hpw (Hold-Preempt-While)** discipline (Bible Article 8.5.4): preempting while holding a lock + IRQ-off same-CPU waiter is the canonical kernel-deadlock failure mode; `without_interrupts` around lock-acquire-to-release is the discipline.

Q8.a/b retrofit selects which lock type fits each capability table. See §4.

## 3. Race enumeration (the design problem)

### 3.1 Q8.a races (per-process handle table + derivations under SMP)

**R1: Concurrent install on different CPUs, same process.**
Two CPUs execute `derive_handle` against the same process at the same time. Each calls `install_cap`, which takes `proc.handles.lock()` separately. The `Vec<Option<Handle>>` lowest-free-index allocation may give both installers the same index if they hit slots out-of-order, OR — more likely under spin::Mutex — they serialize correctly but the lock acquisition is unsafe to hold across the context-switch boundary if the install path ever needs to allocate (Vec::push may grow the underlying buffer).

Severity: serialization is correct under spin::Mutex on x86 (no out-of-order TSO concerns for the slot scan), but the lock type is wrong — spin::Mutex doesn't compose with the rest of the kernel's preempt-safe discipline. If `install_cap` ever takes the lock and then a context switch happens before release (which can happen if the heap allocator (`IrqSafeMutex`) blocks), the holder thread blocks with the spin::Mutex held → deadlock.

**R2: Revoke walk vs concurrent install/derive.**
CPU A executes `revoke_handle(pid, h)`. CPU A: snapshots PROCESSES, then iterates each process's derivations (lock-acquire-drop per process), accumulating the revocation set. CPU B: concurrent `derive_handle` on some process in A's walk, inserting a new child cap whose parent is in A's revocation set.

Failure mode: depending on B's interleave with A's walk:
- B's insert happens BEFORE A reaches that process: A sees the child, includes it in revocation set, removes correctly.
- B's insert happens AFTER A passes that process but before A's terminal cleanup pass: A's revocation set is incomplete; B's child survives the revoke. Linux's capability revocation has the same general race and resolves it via per-process revoke generation counters + retry; seL4's CDT (Capability Derivation Tree) uses a global revoke-in-progress lock.

Severity: **correctness violation**. Revoke must be observably-complete from the caller's perspective; surviving children break the security model.

**R3: Cross-process complete_grant vs target-process exit.**
CPU A executes `complete_grant(grantor_pid, ..., recipient_pid, ..., max_rights)`. CPU A: looks up grantor via `get(grantor_pid)`, reads grantor's handle by cap_id, computes intersection rights, then calls `get(recipient_pid)`. CPU B: concurrent `terminate(recipient_pid)` or `on_thread_reap(recipient_pid)`.

Failure modes:
- B removes recipient from PROCESSES before A's `get(recipient_pid)`: A returns `RecipientGone` correctly. ✓
- B removes recipient AFTER A's `get` but BEFORE A's `install_cap` on recipient: A installs a cap into a Process that is mid-tear-down. Recipient's handle table may have been drained already; the install lands but the Process Arc is about to be dropped. The Arc keeps the Process alive (A holds a clone), but the grant lands on a Process no one can use. Resource leak — the channel side held by the grant payload is never released until everyone drops their Arc.

Severity: not strictly incorrect (Arc lifetime keeps things sound), but a resource-management hazard. Linux/seL4 handle this with grant-completion-failure on target-tearing-down state, which requires a per-Process "exiting" flag visible to grant rendezvous.

**R4: Concurrent revokes on different CPUs.**
CPU A: `revoke_handle(pid_a, h_a)`. CPU B: `revoke_handle(pid_b, h_b)`. Both walk PROCESSES.

Without a strict lock-acquisition order, the per-process locks (derivations, handles) can deadlock: A holds proc_x.derivations and waits for proc_y.derivations; B holds proc_y.derivations and waits for proc_x.derivations.

Severity: **liveness violation** (deadlock). Lock-ordering rule required.

**R5: Handle table operations vs handle table drain (during process exit).**
CPU A: `derive_handle(victim_pid, h, child_rights)`. CPU B: `terminate(victim_pid)` or `on_thread_reap(victim_pid)` mid-drain.

Failure mode: A reads parent handle from `proc.handles.lock()`, computes child rights, calls `install_cap` which re-acquires `proc.handles.lock()`. Between A's two lock-acquisitions, B's drain runs: parent handle no longer exists in the table; child install lands in a drained-then-installed-into table whose Process is being torn down.

Severity: similar to R3 — Arc lifetime soundness preserved, but child cap lands on a dying Process and is immediately unreachable.

### 3.2 Q8.b races (PROCESSES + COMPLETED_EXIT_CODES under SMP)

**R6: `on_thread_reap` double-lock interleaving.**
The on_thread_reap path has FIVE separate `without_interrupts` blocks each acquiring PROCESSES, handles, or COMPLETED_EXIT_CODES, with the load-bearing comment noting that single-acquisition "interacts subtly with the rendezvous Drop chain". Under SMP, another CPU executing `terminate` on the same pid could remove the Process between any two of the five blocks → ESRCH-shaped staleness halfway through cleanup.

The current single-CPU code is correct because no concurrent terminate is possible. Under SMP it's not.

Severity: **correctness violation**. Either the natural-exit path or the forced-kill path must observably win and the other must observe the loss cleanly.

**R7: Process registry walk vs concurrent registration/removal.**
Any function calling `processes_snapshot()` (currently only `revoke_handle`) takes PROCESSES, clones the values into a Vec, releases PROCESSES. Under SMP another CPU may insert or remove a process between snapshot-time and walk-time. The walk operates on the snapshot, which may not reflect current state.

Severity: this is INTENTIONAL eventually-consistency for revoke walks (Linux capabilities have the same property). The snapshot's correctness is bounded by R2's design: as long as the revoke walk reaches a fixed point on the snapshot's derivation closure, late-arriving processes that miss the walk also miss any caps derived from the revoked root (because the root was already invalidated in CPU A's caller before the snapshot). The implementation needs explicit ordering proof but the design is sound.

**R8: COMPLETED_EXIT_CODES growth without bound.**
Independent of SMP: every exited process's exit code accumulates in COMPLETED_EXIT_CODES until consumed by `take_completed_exit_code`. Phase 1.5b has at most a handful of processes; Phase 2+ multi-process needs a `sys_wait`-driven consumer. Not strictly an SMP race but a Q8.b cleanup-discipline question — should the SC-4 retrofit address this?

### 3.3 Q8.c races (blocked-thread-kill walk)

**R9: `terminate` on a Blocked-in-IPC target returns EINVAL.**
Current code:
```rust
if !scheduler::kill_thread_by_pid(target_pid) {
    return EINVAL;
}
```
`kill_thread_by_pid` only yanks Ready-state threads. A target with thread parked in a Channel endpoint state (SendBlocked / RecvBlocked / GrantBlocked / RecvGrantBlocked) is not killable.

Severity: this is the explicit Phase 1.5b limitation, and the ADR-007 §Q3 design acknowledged it would be Phase 2 work. Q8.c lifts it.

**R10: `close_peer` silently drops MY-side parked `Box<Thread>`.**
Current code:
```rust
let mut guard = self.state.lock();
let extracted = core::mem::replace(&mut guard[peer_idx], EndpointState::Closed);
guard[my_side.idx()] = EndpointState::Closed;   // ← drops Box<Thread> on my side
```
The `mem::replace` extracts PEER side and produces `EndpointState::Closed` in peer slot, capturing the extracted state in `extracted` for the wake path. But the immediately-following `guard[my_side.idx()] = EndpointState::Closed` overwrites MY side WITHOUT capturing what it overwrites. If MY side was holding a parked `Box<Thread>` (e.g., in `SendBlocked { ..., waiter: Box<Thread> }`), that Box is dropped without waking the thread — the thread is leaked / lost-forever.

Phase 1.5b has only single-threaded user processes, so this can't fire in practice: a single-threaded process's only thread can't be in close_peer because close_peer is called from on_thread_reap or terminate, which means the process is exiting; if the process's only thread is blocked on the channel side being closed, that thread IS the dying thread and the close_peer call would be operating on an inconsistent process. Phase 2+ multi-thread breaks this assumption.

Severity: **latent thread-leak bug**, ratcheting from latent to live the moment multi-threaded user processes ship. Q8.c fixes proactively.

**R11: `terminate` for a target with mixed Ready+Blocked threads (Phase 2+).**
Hypothetical Phase 2+ multi-threaded process: terminate must yank ALL of the target's threads, not just one. Some Ready, some Blocked-in-IPC. Q8.c needs to enumerate threads-by-pid (not just one thread) — the substrate `scheduler::kill_thread_by_pid` is single-thread-focused.

Severity: Phase 2+ blocker. Q8.c either: (a) handles only single-thread case explicitly with a forward marker for Phase 2+ multi-thread, or (b) does the multi-thread walk now while we're in the area.

PM lean: (a). Multi-threaded user processes are not a Phase 2 BUILD-3 deliverable; the discipline + machinery should compose to support it but the test surface doesn't justify implementing it now.

### 3.4 Cross-cutting: lock ordering across handles, derivations, PROCESSES, channel state

Any SC-4 retrofit must specify a strict global lock-acquisition order. PM proposal (to ratify in D-table):

1. `PROCESSES` (registry) — outermost
2. Per-process locks (handles, derivations) — by ascending `ProcessId.0`
3. Within a single process: `handles` before `derivations`
4. Channel state — innermost (matches existing SC-3B SwitchMutex ordering)

Held-across-context-switch property required for: channel state (already SwitchMutex). Q8.a/b decides: do per-process and global registry locks need switch-safe holding, or is irq-off + non-preemptible holding sufficient?

## 4. Design space — Q8.a (per-process handle table + derivations SMP retrofit)

### 4.1 Lock-type alternatives for `Process.handles` and `Process.derivations`

**L1. `SwitchMutex<HandleTable>` and `SwitchMutex<BTreeMap<CapId, Option<CapId>>>`.**
Same as SC-3B IPC channel retrofit. Holds across context switch if needed; preempt-safe. Requires the handle-table install path to be safe across context switches if the install ever allocates (Vec::push grow).

Pros: composes with existing SC-3B discipline; ADR-018/019 machinery applies; preempt-safe by construction.
Cons: SwitchMutex has higher per-acquisition overhead than spin::Mutex (per ADR-019 6000ns vs 50ns native-hardware target); cap operations are not as hot as IPC fastpath but are not infrequent either.

**L2. `IrqSafeMutex<HandleTable>` and `IrqSafeMutex<BTreeMap>`.**
ADR-019 sub-phase A primitive — preempt-safe + IRQ-off by construction. Holds across context switch only if explicitly released by `context_switch_with_release` (heavy machinery).

Pros: IRQ-handler safe; consistent with heap allocator discipline; reduces the `without_interrupts` boilerplate that currently wraps every capability operation (the lock provides the irq-off).
Cons: not designed for held-across-context-switch by default; capability operations that may yield (alloc that hits IrqSafeMutex heap path) would deadlock without explicit release. Most cap ops are short and don't yield, but install_cap can alloc (Vec::push) and grow the BTreeMap.

**L3. Hybrid: `IrqSafeMutex` outer + per-operation short critical sections.**
Use IrqSafeMutex but structure operations so the lock is never held across alloc. Acquire, snapshot state, drop lock, allocate, re-acquire, install. Two-phase pattern.

Pros: avoids the allocate-while-locked failure mode; keeps lock acquisitions short; aligns with how Linux `cap_set` works (RCU-style: read-side lock-free, write-side double-buffer).
Cons: more complex; race-prone in the "snapshot then install" window (R2/R5 races become live).

**L4. RCU-style read-side lock-free + write-side serialization.**
Most cap operations are reads (lookup by index, lookup by cap_id). Reads use atomic loads of pointers/indices; writes serialize through a per-process "writer's lock" (any of L1/L2/L3).

Pros: maximizes read throughput; capability lookups are very hot (syscall fastpath).
Cons: requires a `Mutex<Arc<HandleTable>>` or similar; every write produces a new table; old tables must be reclaimed via epoch-based reclamation or RCU-call. Substantial complexity for what may be a non-bottleneck.

**PM lean for Q8.a (D-table item D1):** L1 (SwitchMutex) for both handles and derivations. Rationale: capability operations are not IPC-fastpath hot, so the 6000ns vs 50ns gap is acceptable; preempt-safe holding simplifies install_cap (no two-phase pattern needed even if Vec::push grows); composes with SC-3B/SC-3C discipline. L4 (RCU) is the right Phase 2+/Phase 3 answer if profiling shows cap-lookup as a bottleneck — file as forward marker.

### 4.2 Handle-table data structure

Current: `Vec<Option<Handle>>` with lowest-free-index allocation. Under SMP retrofit options:

**S1. Keep `Vec<Option<Handle>>` under SwitchMutex.**
No data-structure change. Lock serializes all access. Simplest.

**S2. Switch to `BTreeMap<u32, Handle>` keyed by handle index under SwitchMutex.**
Same single-lock structure but BTreeMap reads/writes O(log n) instead of O(n) for the Vec lowest-free scan. Phase 1.5b has at most ~10 handles per process; not meaningful. Phase 2+ multi-cap-type may grow; still not large.

**S3. Sharded handle table (per-thread or per-CPU shards).**
Different threads in a multi-threaded process get different shards; cross-shard lookups need a second hop. Massively complex; only justified if cap-lookup is profiled as a bottleneck.

**PM lean (D2):** S1. Vec<Option<Handle>> with SwitchMutex. Capability-table cardinality is bounded; Vec scan is acceptable; preserves ADR-004 §Q2 lowest-free-index ABI.

### 4.3 Derivation log data structure

Current: `BTreeMap<CapId, Option<CapId>>` mapping child to parent. Used by `revoke_handle` walk.

Under SMP, the BTreeMap is fine; the question is lock granularity.

**G1. One lock for the whole derivation log per process.**
Current shape; lock serializes all derivation reads/writes for the process. Simple.

**G2. Lock-free / split-lock per-CapId.**
Each entry has its own atomic; insertion/removal is lock-free. Complex; capability derivations have low per-entry contention, so the per-entry locking is unwarranted.

**PM lean (D3):** G1. Single SwitchMutex per process for derivations.

## 5. Design space — Q8.b (PROCESSES + cross-process operations)

### 5.1 PROCESSES registry lock type

Same alternatives as §4.1 (L1-L4). PROCESSES is read by every cross-process operation: `cr3_for_thread` (called on every cross-process context switch — VERY HOT), `get`, `name_of`, `any_user_process`. Writes are much rarer (register, remove).

**PM lean (D4):** Read-write structure. Either:
- L1' SwitchRwLock (parallel to SwitchMutex but reader-writer) — would need to be designed if not present (verify in OBSERVE-2).
- L4 RCU-style: `AtomicPtr<BTreeMap>` with epoch-based reclamation for the snapshot pattern.

Trade-off: every CR3 reload currently takes the PROCESSES lock. Under SMP with N CPUs, N concurrent cross-process context switches contend on this single lock. That's a real bottleneck.

PM lean refinement: **L4 (RCU-style with AtomicPtr<Arc<BTreeMap>>)**. Reads via atomic pointer load; writes via copy-on-write of the BTreeMap inside the writer's lock. Old tables retired via a simple epoch counter or via leaving the Arc to Drop naturally (the registry is updated by replacing the pointer; old readers retain their Arc clones until they're done).

This is more complex than L1 but Phase 2 SMP cross-process context switches are exactly the bottleneck case where the complexity earns its keep. **Flag for Cerebro deep-research dispatch** (D-decision D5): prior art on per-CPU process-table caching, Linux `rcu_read_lock`-protected task_struct lookup pattern, seL4 thread state vs Linux pid_namespace tradeoffs.

### 5.2 Revoke walk concurrency

R4 (concurrent revokes) requires strict lock ordering. PM proposal:

**O1. Strict by-ProcessId ordering.**
All multi-process operations acquire per-process locks in ascending `ProcessId.0` order. Revoke walks must hold the snapshot's `Vec<Arc<Process>>` sorted by pid; per-process locks acquired in ascending pid. Two concurrent revokes either start at the same pid (one wins each per-process race; both make progress) or start at different pids and meet in the middle — by-pid ordering prevents the AB-BA deadlock.

**O2. Single global revoke-in-progress mutex.**
Only one revoke can run at a time. Simple; defends against R4 unconditionally. Cost: revokes are rare but a global serialization point is a scalability cap.

**PM lean (D6):** O1 (strict by-ProcessId ordering). Document in revoke_handle as a load-bearing invariant. Phase 2+ may revisit if revokes become hot.

### 5.3 Grant rendezvous vs target-process tear-down (R3)

Two design options:

**T1. Add `Process.exiting: AtomicBool` flag.**
`terminate` and `on_thread_reap` set this before draining handles. `complete_grant` checks the flag after `get(recipient_pid)` and before `install_cap`; if exiting, return RecipientGone instead of installing. Tear-down ordering: set flag → drain handles → remove from PROCESSES.

Pros: cheap (one atomic load per grant); narrow race window closed.
Cons: requires explicit flag check at every install_cap site (currently centralized; manageable).

**T2. Use Arc weak-reference pattern.**
`PROCESSES` stores `Weak<Process>` and `Process` keeps its own self-Arc until exit. complete_grant's `get(recipient_pid)` returns an upgraded Arc; if upgrade fails, RecipientGone.

Pros: lifetime-elegant; no explicit flag.
Cons: invasive refactor; every PROCESSES.lock().get() becomes Weak::upgrade.

**PM lean (D7):** T1 (exiting flag). Lower-touch; explicit; matches the kernel's existing exit_code = EXIT_CODE_RUNNING sentinel pattern.

### 5.4 `on_thread_reap` and `terminate` SMP-safety

The five-block `on_thread_reap` and four-block `terminate` need to be transactional under SMP. Options:

**X1. Outer lock per process (Process.exit_lock: SwitchMutex<()>).**
Both natural-exit and forced-kill paths acquire this lock at the top of their respective functions; the lock serializes the two paths. Whichever acquires first wins; the other observes the process already-removed via the existing check and returns its standard error.

**X2. CAS-based exit-claim.**
`Process.exit_state: AtomicU8` with states { RUNNING, EXITING_NATURAL, EXITING_FORCED, EXITED }. Both paths CAS RUNNING → their state. The CAS-winner proceeds; the CAS-loser bails. Simpler synchronization; no held lock.

**PM lean (D8):** X2 (CAS-based exit-claim). Avoids holding a process-scoped lock across the entire exit path (which currently spans channel mutex acquisitions, scheduler operations, frame audit prints). The single AtomicU8 CAS is the synchronization point.

The CAS-loser handling is the subtle part:
- If A wins (natural-exit) and B loses (forced-kill arrives later): B observes EXITED state (or in-progress), returns ESRCH or EALREADY.
- If A wins (forced-kill) and B loses (natural-exit thread reaches reap path): B observes its own state was forced-killed, skips natural-exit cleanup (already done by terminate).

## 6. Design space — Q8.c (blocked-thread-kill walk + my-side awareness)

### 6.1 Find-blocked-thread strategy

When `terminate(target_pid)` is called and `scheduler::kill_thread_by_pid` returns "not in Ready queue", the target's thread is parked inside a Channel endpoint. Q8.c must find where.

**F1. Walk target's handle table; for each Channel handle, lock and inspect.**
For each Handle::Channel { channel, side, .. } in target's drained-handle-table, acquire `channel.state.lock()`, check if `state[side.idx()]` is `*Blocked { waiter: Box<Thread> }`. If so, extract.

Pros: works without scheduler-side enumeration; mirrors close_peer's existing pattern; lock ordering matches SC-3B.
Cons: requires holding multiple channel locks in sequence; lock ordering with other operations needs care.

**F2. Scheduler-side: enumerate all blocked threads by pid.**
The scheduler maintains a registry of blocked threads (parked in IPC); terminate queries by pid. Requires the scheduler to track this — currently parked threads live INSIDE endpoint states, not in a scheduler-side queue.

Pros: scales better if many handles; doesn't require channel-state inspection.
Cons: would require restructuring how blocked-thread parking works; significant refactor.

**PM lean (D9):** F1. The handle-table walk is the natural shape — terminate already drains the handle table; integrating the blocked-thread extraction into that drain costs little.

### 6.2 `close_peer` my-side awareness (R10 fix)

Two structural options:

**M1. Two-stage close: extract both sides, wake both if needed.**
Replace the current `close_peer` body:
```rust
let extracted_peer = core::mem::replace(&mut guard[peer_idx], EndpointState::Closed);
let extracted_my = core::mem::replace(&mut guard[my_idx], EndpointState::Closed);
drop(guard);
wake_if_blocked(extracted_peer, EPIPE);
wake_if_blocked(extracted_my, ???);   // What return value?
```

The "What return value" is the design question: if my-side is blocked because my own process is exiting, what does the thread observe on wake? Options:
- EPIPE (peer-side semantics; the thread was blocked waiting for peer; peer is functionally gone from this thread's perspective since its own process is dying)
- EINTR (interrupted; the thread should observe its own process is exiting and proceed to exit cleanup)
- EKILLED (new errno; explicit "your process was killed")

PM lean (D10): EINTR. The thread isn't being told "peer is gone"; it's being told "your own context is being torn down". EINTR is the closest POSIX analogue.

**M2. Add a separate `close_self` method.**
Keep `close_peer` as-is (peer-side close); add `close_self(my_side)` that extracts and wakes my-side. Both methods called during process exit.

Pros: clearer naming; explicit pairing.
Cons: two methods instead of one; close_self semantics overlap with close_peer.

**PM lean (D11):** M1. The single method "close this entire endpoint" is what process-exit needs; the peer is already getting closed; my side getting closed is symmetric.

### 6.3 Blocked-thread wake errno

Linked to D10. The thread, on wake, observes a syscall return value. Currently:
- Peer-side close → wake with EPIPE.
- Q8.c my-side close → wake with ??? (PM lean: EINTR).

For the **forced-kill from `terminate`** case: the thread is being woken because its OWN process is being killed. The thread should not continue execution — it should be reaped, not resumed. Q8.c needs to wake the thread and then immediately push it to the zombie queue, not let it return to userspace.

**W1. Wake with EINTR, then push to zombie.**
After extracting the Box<Thread>, set its return value to EINTR (so if it ever runs again it sees the EINTR), but actually move it directly to zombie queue.

**W2. Don't wake at all; just push to zombie.**
The thread never runs again. Its `Box<Thread>` is recycled by the reaper. No syscall return value matters because the thread isn't returning.

**PM lean (D12):** W2. The thread won't run again; no return value to set. Push to zombie directly. The `wake_thread` semantics imply "will run again with this return value"; for kill we want "will not run, free its resources".

This implies a new function: `sched::zombify_thread(Box<Thread>)` that takes a parked thread and puts it directly on the zombie queue without invoking the wake path. Parallel to `wake_thread` and `wake_thread_on_current_cpu`.

## 9. Verification model (SC-4 D14/D17 analogues)

SC-4 mirrors SC-3C's D14 missing-shootdown-detection discipline. Two new negative-feature scenarios:

- **`q8a_concurrent_install_revoke`** + **`neo-test-missing-cap-lock-negative`**: under negative feature, the install path skips the new SwitchMutex acquisition. Test creates two threads on two CPUs; thread A repeatedly derives caps; thread B repeatedly revokes. Without the lock, the revocation set is incomplete or the install corrupts the Vec. Test PASSES when the failure is detected; this confirms the gate works.
- **`q8c_blocked_kill_walk`**: spawn worker child, have it block in IPC on a channel inherited from parent. Parent sys_kills the worker. Test verifies: (a) worker thread enters zombie queue; (b) channel state observable post-kill is Closed on both sides; (c) frame audit clean after worker pmap drop.

Both follow the SC-3C 4c verification report pattern (event labels with mechanism + detected condition + negative_feature gating).
