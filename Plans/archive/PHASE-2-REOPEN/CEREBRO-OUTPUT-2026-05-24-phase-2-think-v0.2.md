## Q1 — `sys_close` use case and semantics

**Ratified question (verbatim):** *ADR-010 reserved the CLOSE semantic bit pending a use case. Today, channel close is implicit at process exit via the `close_channel_peers` shared helper (now structurally pid-aware per F-005's unified `extract_parked_if_owned`). Does Phase 2 surface an explicit `sys_close(handle)` use case distinct from process-exit cleanup — for example, application-level "I'm done with this channel" semantics for long-lived processes that hold many channels — and if so, what are its semantics? Specifically: does `sys_close` wake the peer with `-EPIPE` mirroring exit-time cleanup, how does it interact with the survive-exit cap lifetime invariant (a closed channel cap still held by a third process), and is the CLOSE semantic bit gated as "enforcement, not theatre" per ADR-010 Principle 2? If no use case surfaces, the disposition is: ship `sys_wait` and `sys_inspect`; defer `sys_close` to the phase where a use case emerges, leaving the CLOSE bit reserved.*

**Recommended disposition: DEFER `sys_close`. Ship `sys_wait` + `sys_inspect`; CLOSE bit stays reserved.** The use-case search (RAG-first, per dispatch §2) found no Phase-2 driver: the only processes that exist are short-lived test cohorts and `neo-init` (PID 1), none of which hold many channels long enough that implicit-close-at-exit is a problem. No "I'm done with this channel" pattern appears anywhere in the project's accumulated design notes — the top RAG hits are the question itself, ADR-010's survive-exit section, and the audit's `INV-CAP-12` ("sys_close not shipped"). The genuine driver is **Phase 4** (network sockets = many channels per long-lived server process) and **Phase 7** (multi-tenant inference serving) — both out of Phase-2 scope.

**Reasoning.** ADR-010 note 8 itself frames CLOSE as "ships Phase 2 BUILD-2 or later, **once a use case appears**" — explicitly use-case-gated, not calendar-gated. Shipping `sys_close` with no consumer would be reserved-bit activation for its own sake, violating the project's own "no mechanism without a real correctness/security/accounting property" discipline (ADR-010 note 9). Deferral leaves the CLOSE bit reserved (zero ABI cost per Principle 2), so the future activation is non-breaking.

**Should a use case be forced into scope, the semantics are:** `sys_close(handle)` gates on `semantic & CLOSE != 0` (enforcement, not theatre — ADR-010 Principle 2); it routes the my-side endpoint through the **same** unified `close_channel_peers` / `extract_parked_if_owned` machinery F-005 hardened, waking a blocked peer with `-EPIPE` exactly as exit-time cleanup does; survive-exit is unaffected because close operates on *this handle's* endpoint, and a third process's derived cap to the same Channel keeps the `Arc<Channel>` alive — that holder's subsequent invocation simply returns `-EPIPE` (gone peer), the established survive-exit outcome. So the mechanism is *already built*; only the syscall wrapper + CLOSE gate would be new.

**Alternative considered — ship `sys_close` now for ABI completeness.** Ruled out: activating a reserved bit with no consumer adds a syscall surface to test and maintain for zero current benefit, and the bit's reserved status already guarantees a clean future activation. The cost of waiting is nil; the cost of shipping-unused is a permanent surface.

**Revisit trigger:** Phase 4 network-socket handles, or any long-lived process whose channel count makes hold-until-exit a resource concern.

## Q2 — `sys_wait(handle)` semantics and FM-D14 retirement

**Ratified question (verbatim):** *ADR-007's "Future Phase 2 hardening" names `sys_wait` returning the target process's exit code, and FM-D14 records that `COMPLETED_EXIT_CODES` grows unbounded without a wait/consume consumer. The design surface: (a) blocking semantics … (b) handling targets that have already exited … (c) multiple waiters … (d) interaction with D13 single-thread-per-process and D8 `exit_state` CAS … (e) FM-D14 retirement: does landing `sys_wait` fully retire the unbounded-growth concern, or only bound it …*

The consumer surface already exists in source: `process.rs` has `exit_state: AtomicU8`, `exit_code: AtomicI32`, `record_exit_code()`, and `take_completed_exit_code(pid)` (removes from `COMPLETED_EXIT_CODES`). `on_thread_reap` already CAS-claims `exit_state` and inserts the code into `COMPLETED_EXIT_CODES`. `sys_wait` is the missing caller + the blocking case.

**Recommended dispositions, sub-question by sub-question:**

- **(a) Blocking semantics — blocking by default, with a `WNOHANG`-style non-blocking poll flag.** ADR-007 specifies "blocks until the target exits"; the canonical use is the supervisor (`neo-init` waits for a worker). The blocking case parks the caller's Thread (the established rendezvous-block mechanism) and the reaper wakes it. The poll flag returns immediately with a "still running" indicator for callers that can't block. *Alternative — poll-only:* ruled out as the default because it forces userspace busy-polling, contradicts ADR-007, and weakens FM-D14 (a poller that never polls leaves codes accumulating). The poll flag is retained as an option, not the default.
- **(b) Already-exited target — return the cached exit code immediately and free the slot via `take_completed_exit_code`.** This is the FM-D14 retirement mechanism: the consumer that frees `COMPLETED_EXIT_CODES` entries. If `exit_state` reads Exited/Zombie and a code is cached, return it without blocking and remove the map entry.
- **(c) Multiple waiters — first waiter consumes the code; subsequent waiters get `-ESRCH`.** This is POSIX-faithful (`wait()` single-consumer; others get `ECHILD`/`ESRCH`), which userspace authors expect, and it keeps `COMPLETED_EXIT_CODES` bounded (consumed on first wait). Multi-waiter is constructible in Phase 2 (a parent can `sys_grant` a `ProcessHandle` to a sibling — grant shipped in BUILD-1), so the question is real. At reap, one parked waiter wakes with the code; any other parked waiters wake with `-ESRCH`. *Alternative — broadcast + handle-presence-gated slot lifetime* (all holders see the code; slot freed when the last `ProcessHandle` drops): more cap-composable and the cleaner full-FM-D14-retirement, but it needs a per-target handle refcount the cap system doesn't currently expose. Deferred unless a multi-reader use case surfaces (see (e)).
- **(d) D8/D13 interaction — `sys_wait` observes `exit_state` externally; it does NOT participate in the CAS.** D8's `exit_state` CAS serializes *who performs cleanup* (natural-exit vs forced-kill); `sys_wait` is a *reader of the outcome*, not a cleanup actor. It loads `exit_state` (Acquire) and reads `exit_code` (already Release-stored by `record_exit_code`). Clean producer/consumer split: the reap path (CAS owner) is the sole producer of the cached code; `sys_wait` is the consumer. The parked-waiter wake fires inside `on_thread_reap` *after* the code is recorded, so a woken waiter always sees a consistent code. Under D13 (single thread per process) the thread reap *is* the process exit, so there is exactly one wake point.
- **(e) FM-D14 retirement — landing `sys_wait` BOUNDS the growth; it does not fully retire it.** With first-consumer semantics, a code is freed when waited. But a code for an exited process whose handle-holder never calls `sys_wait` still accumulates — the residual. Full structural retirement requires tying slot lifetime to **handle-presence** (free when the last `ProcessHandle` is dropped/revoked, so no future waiter is possible). Recommend Phase-2 close land `sys_wait` (the practical bound) and record the handle-presence-gated free as a follow-on if churn measurement shows residual growth. Honest framing matches the question: "only bound it."

**Reasoning (overall).** `sys_wait` is the named ADR-007 Phase-2 hardening item and the FM-D14 consumer; the storage (`exit_code`, `COMPLETED_EXIT_CODES`, `take_completed_exit_code`) is already in place, so the work is the syscall wrapper + the blocking parking/wake wiring. The one genuinely new mechanism is the blocking parking site (a per-Process waiter wake from `on_thread_reap`) — see §9, the only real "new mechanism in close" cost.

**Prior art:** POSIX `waitpid` (WNOHANG, single-consumer ECHILD); seL4 `Notification` (signal-and-wait, but seL4 has no exit-code semantics — NeoPlutarch's ProcessHandle+exit_code is closer to POSIX); Plan 9 `await`/`wait` (parent reads a status string from an exited child, single-consumer). The first-consumer + WNOHANG shape is the well-trodden one.

## Q3 — `sys_inspect(handle)` surface

**Ratified question (verbatim):** *The INSPECT semantic bit is reserved per ADR-010. What process or thread state is inspectable through it, and how does the design stay inside Bible 12.2's no-ambient-authority discipline? … Is INSPECT useful enough without cap-passing (Phase 4) to justify shipping in Phase 2 close, or does it await Phase 4's cap-passing-over-IPC to become operationally meaningful?*

**Recommended disposition: SHIP `sys_inspect` in Phase 2, scoped to a thin scalar status snapshot.**

- **Inspectable-state set:** run-state (`exit_state` enum: Running / Exited / Zombie), cached `exit_code` if exited, `thread_count` (always 1 under D13 — but the field future-proofs for multi-thread), open-channel-handle *count*, and `name`. Returned as a **fixed value-type snapshot struct passed by value** — never any `Handle`, `CapId`, or pointer field.
- **No-ambient-authority enforcement (Bible 12.2):** the anti-leak property — "INSPECT lets you observe state but never derive a usable cap from observation" — is **structurally enforced by the return type**: the snapshot contains only scalars (enums, counts, an i32 code, a `&'static str` name), so there is no cap-typed value an inspector could turn into authority. Explicitly **excluded**: the target's cap inventory identities (CapIds/rights of its handles) — a count is observable, the identities are not, because the identities are the ambient-authority leak the discipline forbids.
- **Phase-2-vs-Phase-4 meta:** **ship in Phase 2.** INSPECT does not need Phase-4 cap-passing to be useful — the `ProcessHandle` minted at `sys_spawn` already carries INSPECT, so the **parent-inspects-child** supervisor pattern works today (`neo-init` asks "is my worker still running? what code did it exit with?" without killing or blocking).

**Reasoning.** Activating INSPECT completes the reserved-bit ABI trio cheaply (a read-only syscall, no new mechanism), and it is complementary to `sys_wait`: `sys_wait` blocks-and-consumes; `sys_inspect` is the non-blocking, non-consuming peek. The supervisor introspection use is real in Phase 2 via the spawn-minted handle.

**Alternative considered — defer `sys_inspect` alongside `sys_close`.** Honest tension: under D13, `thread_count` is always 1, and `exit_state`+`exit_code` overlap `sys_wait(WNOHANG)`, so the *marginal* Phase-2 inspectable surface (handle-count, name) is thin. PM may reasonably defer it with `sys_close` and ship only `sys_wait`. I recommend shipping because the cost is near-zero (read-only, reserved bit) and it gives the supervisor a clean non-consuming status read that `sys_wait(WNOHANG)` only partially covers — but this is the closest of the seven to a coin-flip, and §9 flags it as a reasonable either-way for PM. (Note THINK v0.1 Q1's own fallback pairs "ship sys_wait and sys_inspect; defer sys_close," which this recommendation matches.)

## Q4 — Bible Article 16.4 performance-regression harness

**Ratified question (verbatim):** *Article 16.4 mandates per-commit tracking of boot time, syscall latency, context-switch cost, and scheduling fairness (Redox `schedrs`-adapted) "from Phase 2 onward." No such harness currently exists. Phase 2 close stands one up. The design questions: (a) reference environment … (b) measurement methodology … (c) integration with CI … (d) composition with ADR-019's deferred 50ns native bench … (e) regression policy …*

This is the most design-dense question. The core insight that resolves the apparent environment conflict: **separate regression-*gating* from absolute-*characterization*, and assign each to the environment that can actually serve it.**

- **(a) Reference environment — TIERED, not single.** Three environments, three roles: **QEMU TCG** runs **deterministic structural proxies** per-commit (context-switch counts, CR3-write counts, allocation counts, scheduling-decision counts for a fixed workload) — TCG absolute timing is fiction, but these *counters* are deterministic and reliably catch algorithmic regressions (an O(n)→O(n²) change moves a counter). **Bare-metal OptiPlex 7080** captures **absolute-latency characterization** (boot time, syscall latency ns, context-switch ns, fairness) during PL hardware sessions — real numbers, but cannot run per-commit. **VMware-VM** is the **reproducible middle tier** for relative trends/fairness when bare-metal sessions aren't available. Load-bearing for *gating* = the TCG proxies; load-bearing for *absolute characterization* = bare-metal. **This is a PL-confirms operational choice — flagged in §9 per the dispatch directive.**
- **(b) Methodology — n-trial median + IQR for absolute metrics; deterministic single-shot for the TCG proxies.** Absolute metrics (bare-metal/VMware): report median over n trials with IQR (or MAD) as the spread; flag a regression only when the median shift exceeds a margin tied to the measured spread (e.g. >2× baseline IQR, or a per-metric % threshold set during a one-time baseline characterization). The TCG proxies are deterministic, so single-shot suffices and *any* change is signal. (Prior art: criterion-style median + outlier rejection; for fairness specifically, the Redox `schedrs` weighted-share methodology Bible 16.4 names — see `PM-NOTE-2026-05-10-redox-dwrr-prior-art.md` for the project's own triage that motivated the 16.4 fairness enumeration.)
- **(c) CI integration — proxies every push (gating); absolute characterization periodic (tracking, not gating).** The deterministic TCG proxies run on every push as part of the existing CI (cheap, deterministic, no flake). Absolute-latency characterization runs nightly on a dedicated runner if one exists, otherwise at phase boundaries during PL bare-metal sessions. Per-push *gates* only on the proxies; absolute trends are *tracked*, not gated (they're environment-sensitive and can't run per-push on real hardware).
- **(d) ADR-019 50ns native bench — SUBSUMED, not orthogonal.** The IrqSafeMutex lock/unlock-cycle micro-bench is exactly the kind of context-switch-adjacent micro-measurement Bible 16.4 wants; fold it in as one of the harness's bare-metal micro-benchmarks, retiring the standalone ADR-019 deferral (`Q9-EXPLORATION` §5.3 already suggests capturing it opportunistically during a bare-metal session). One harness, one place; orthogonality would duplicate infrastructure.
- **(e) Regression policy — three tiers.** (i) A deterministic-proxy change (a structural counter that should be invariant for a fixed workload moves) = **CI BLOCKER** — it's deterministic, so any change is a real algorithmic change demanding explanation. (ii) An absolute-latency regression beyond the noise margin on the characterization tier = **WARNING + investigation** — not an auto-blocker, since absolute numbers are environment-sensitive. (iii) A sustained/large regression across multiple characterization runs = **requires an ADR justifying the regressing change** (Bible 1.2: performance is third, so a regression accepted for correctness/coherence is fine — but it must be *justified in writing*, not silent).

**Reasoning (overall).** Bible 16.4 mandates the four metrics "from Phase 2 onward"; the binding constraint nobody can wish away is that you cannot run bare-metal per-commit (no PL hardware session per push) and TCG absolute numbers are meaningless. The tiered split honors both: deterministic proxies give per-commit regression *gating* that's actually trustworthy under TCG, while bare-metal gives the *real* numbers Bible 16.4 ultimately wants, captured at a sustainable cadence. This also extends the project's established environment-anchoring discipline (ADR-019 bench, HANDOFF-2026-05-11 §8.4 environment triplet).

**Alternative considered — single reference environment.** Pure-bare-metal: can't gate per-commit (hardware sessions don't scale to every push), so regressions land between sessions. Pure-QEMU-TCG: can't characterize absolute latency at all (timing is fiction), so Bible 16.4's actual metrics are never measured. Either single-environment choice fails half of 16.4's intent. The tiered approach is the only one that gates continuously *and* characterizes truthfully.

**Open dependency:** (a) the PL-confirms environment choice (§9).

## Q5 — ADR-019 sub-phases B/C scope and pairing with audit (b) tests

**Ratified question (verbatim):** *ADR-019 sub-phase A landed at `27d1b99`. Sub-phase B migrates mixed-context `SwitchMutex` callers to `IrqSafeMutex`; sub-phase C migrates `Channel.state` `without_interrupts(...)` sites and removes the manual wrappers. The questions: (a) standalone defense-in-depth subphase, or pair with the audit (b) tests touching the same Channel.state surface (INV-IPC-5, INV-SYNC-5)? (b) per-sub-phase verification gate …? (c) is B before C the right order …?*

**Recommended dispositions:**

- **(a) Pair sub-phase C with `INV-IPC-5` only; route `INV-SYNC-5` to Q7/A2 — DIVERGENCE from the PM read, with reasoning.** The PM read pairs both audit (b) Channel.state tests with B/C. But the two tests touch *different* lock surfaces: `INV-IPC-5` (`ipc_rendezvous_translate_fault`) is on the **Channel.state / rendezvous** surface — that IS sub-phase C's surface, so pair them. `INV-SYNC-5` (`sched_ready_queue_capacity_pressure`) is on the **scheduler ready-queue** surface — that is **Q7/A2's** surface, and A2 is literally its structural fix (see Q7(c)). Pairing `INV-SYNC-5` with ADR-019 C would put a ready-queue test in a Channel.state subphase. So: ADR-019 B/C + `INV-IPC-5` = one defense-in-depth subphase; `INV-SYNC-5` rides the A2 subphase.
- **(b) Per-sub-phase gate — C gets the SC-3B 200/200 `NEO_SMP=4` gate; B gets a lighter gate (full suite green + the ADR-019 micro-bench).** Gate proportional to risk. Sub-phase C migrates `Channel.state` — the exact lock surface SC-3B's Hpw mechanism lived on (`e2b3f4f`); a regression there is catastrophic and the 200/200 stress gate is the established bar for that surface. Sub-phase B migrates non-Channel.state `SwitchMutex` callers; that's a type-preserving change at lower-risk sites, so full-suite-green plus the IrqSafeMutex acquire/release micro-bench (ADR-019 Q4) suffices.
- **(c) B before C — confirmed.** B establishes `IrqSafeMutex` usage broadly at the mixed-context `SwitchMutex` callers, proving the type in place; C then migrates the highest-risk `Channel.state` `without_interrupts` sites onto the now-established type and removes the manual wrappers. C-first would migrate `Channel.state` while other mixed-context callers still use the old pattern — a more heterogeneous, harder-to-audit intermediate state. (No double-migration risk either way: B and C touch disjoint locks — `SwitchMutex` instances vs the `Channel.state` `spin::Mutex` — so the Q5(c) "migrate twice" worry doesn't arise; the order is about coherence, and B-first is cleaner.)

**Reasoning.** ADR-019's own sub-phase numbering and the risk gradient both point to B→C; the divergence on (a) is a real surface-matching correction that keeps each audit (b) test with the BUILD that actually touches its lock. This is not a live correctness fix (INV-SYNC-1 manual discipline is TESTED) — it's structural enforcement of the Hpw discipline, so the value is defense-in-depth, which is exactly why it's in the close set per the §1.1 ratification.

**Alternative considered — single combined "lock-discipline" subphase (B+C+both tests at once).** Ruled out: it bundles the catastrophic-risk Channel.state migration with lower-risk work under one gate, forcing the whole subphase to the 200/200 bar and conflating a ready-queue test with a Channel.state migration. Splitting B (light gate) from C (heavy gate) and routing INV-SYNC-5 to A2 keeps risk and surface aligned.

## Q6 — Bare-metal multi-CPU verification protocol

**Ratified question (verbatim):** *Bible Article 13's bare-metal multi-CPU mandate is the open Phase 2 close-gate. The OptiPlex 7080 boot smoke is single-CPU UEFI boot only … (a) acceptance bar … (b) core count … (c) evidence shape … (d) hardware target … (e) procedure shape …*

**Recommended dispositions:**

- **(a) Acceptance bar — the SC-3B/3C/4 SMP-specific scenario set must PASS on real hardware:** `smp_cross_cpu_rendezvous_stress` (the SC-3B 200/200 gate), `q7c_*` (TLB shootdown: missing-shootdown-detection + concurrent-munmap), `q8a/b/c_*` (cap-table-SMP + blocked-kill walk), the `cap_*` suite under SMP, and `ipc_heap_kill_smoke`. Rationale: bare-metal's value *over* QEMU `-smp 4` is real LAPIC IPI delivery, real cache coherency, and real TSC — so the must-pass set is exactly the scenarios whose correctness depends on those (cross-CPU rendezvous, IPI shootdown, cross-CPU revoke/kill). Single-CPU-only scenarios add no bare-metal signal beyond the existing OptiPlex boot smoke.
- **(b) Core count — ≥4 logical CPUs minimum, plus the target's full count.** 4 gives apples-to-apples comparability with the established `NEO_SMP=4` dev gate; additionally running at the hardware's full logical-CPU count validates `MAX_CPUS` scaling beyond 4 and surfaces any 4-hardcoding or SMT-specific issues. Don't mandate a specific high number (hardware-dependent) — mandate "≥4, and the target's full logical-CPU count."
- **(c) Evidence shape — mirror the QEMU PASS vocabulary plus AP-bringup evidence:** full serial-log capture of the run, frame-audit-clean post-run, zero `KERNEL PANIC` / `BUG:` lines, per-AP GS-base sentinel PASS (the AP-bringup-specific evidence that only matters on real multi-core), and per-scenario PASS sentinels. This is the established PASS vocabulary (`PROCEDURE-2026-05-11-vmware-hypervisor-vm-verification.md` §5 "What constitutes a PASS") extended with the per-AP sentinels.
- **(d) Hardware target — OptiPlex 7080 required; cross-vendor (AMD) a non-blocking stretch.** *(PL ratifies the specific hardware — open dependency.)* OptiPlex 7080 is the established bare-metal target (Phase-3 boot smoke runs on it) and is Intel; Bible Article 13 requires "at least one bare-metal target," which a single Intel machine satisfies. A cross-vendor AMD run would additionally validate vendor-specific APIC/INVLPG behavior (relevant to the Q7.c shootdown path) but is not mandated.
- **(e) Procedure shape — a formal procedure document modeled on the VMware procedure, authored pre-BUILD, executed in-BUILD.** The protocol (boot steps, scenario list, evidence-capture instructions) is pre-BUILD planning (PM/Cerebro authors it, as with the VMware procedure for PL direct execution); the execution + evidence capture is the BUILD's verification deliverable. This matches the VMware precedent (PL executes a written protocol; PM consumes the evidence).

**Reasoning.** The acceptance bar should target precisely what bare-metal tests that QEMU can't (real IPI/coherency/TSC), not re-run the whole suite for its own sake; the evidence vocabulary should match the project's established PASS criteria so results are directly comparable to the QEMU gate; and the procedure-doc-then-execute split matches the proven VMware-verification workflow.

**Open dependencies (PL-operational, §9):** (d) the specific hardware target + whether cross-vendor is in scope; (e) who executes (PL hardware session, per the VMware precedent — the dispatch flags (d)/(e) as benefiting from PL operational input).

## Q7 — ADR-016 A2 implementation shape

**Ratified question (verbatim):** *Per §1.4 of the PL ratification, ADR-016 A2 (decouple scheduler from global heap; replace `VecDeque<Box<Thread>>` ready/zombie queues with bounded/pre-allocated storage) is Phase 2 conformance work … (a) intrusive linked list … fixed-capacity per-CPU ring buffer, or another structure …? (b) where does the bounded capacity come from …? (c) does this compose with audit (b)'s `sched_ready_queue_capacity_pressure` (INV-SYNC-5) …? (d) sequencing relative to ADR-019 B/C …?*

ADR-016 §Decision 1 explicitly defers the A2 implementation structure to "Cerebro in a follow-up A2 design dispatch." This is that substrate; the recommendation is load-bearing for A2's implementation. ADR-016's hard constraints: spawn fails gracefully (no panic) at a configurable per-CPU limit (provisional default 64); the Box-pointer-stability invariant must be preserved (`scheduler.rs` doc lines 16–20: storage is `VecDeque<Box<Thread>>` *not* `VecDeque<Thread>` because a captured pointer into the Thread — the `rsp` slot — must survive enqueue/dequeue); and scheduler ops must reach no `alloc`/`dealloc` while holding `PerCpuScheduler.inner`.

**Recommended dispositions:**

- **(a) Structure — fixed-capacity per-CPU ring (circular-array deque) of `Box<Thread>`.** Two rings per CPU (ready, zombies), each `[Option<Box<Thread>>; N]` with head/tail indices, pre-allocated at scheduler init. Enqueue/dequeue = move a `Box` into/out of a slot + index arithmetic (O(1) at both ends, supporting `push_ready` back-insert and `wake_thread_front` front-insert); arbitrary removal for `kill_thread_by_pid` is O(N≤64) under a briefly-held lock, no worse than today's `VecDeque` retain.
- **(b) Bounded capacity — a per-CPU limit equal to the ring size, default 64 (ADR-016's provisional default), configurable at scheduler init via a `PerCpuScheduler` field.** `spawn`/`push_ready` check the count and return an error (`-EAGAIN`) when the ring is full — the fallible-spawn ADR-016 requires. **Per-CPU, not global:** it matches ADR-013's per-CPU scheduler topology and composes with FM-D5's retirement of `PROCESSES` from the hot path (the bound lives in the per-CPU scheduler, never touching the global registry).
- **(c) Composes with `INV-SYNC-5` — SAME BUILD; A2 *is* the structural fix.** Today the `VecDeque` (READY_INITIAL_CAPACITY=8) can reallocate under the scheduler lock when >8 threads are ready — the `INV-SYNC-5` release-build hazard (debug-only `debug_assert!` catches it; release silently allocates-under-lock, violating Bible 8.5.3). The fixed ring *cannot* reallocate — it's a fixed array; over-capacity returns `-EAGAIN` instead. So `sched_ready_queue_capacity_pressure` becomes A2's **acceptance test**: drive threads to the per-CPU bound and assert graceful `-EAGAIN` with no realloc/alloc-under-lock/panic. They are one BUILD, not sequential.
- **(d) Sequencing — A2 before ADR-019 B/C.** A2 settles the *structure* the scheduler lock protects; ADR-019 B/C migrates the lock *type*. Landing A2 first means the lock-type migration rebases onto a settled queue structure (one re-touch), whereas B/C-first would migrate lock types and then A2 would re-touch the same queue code. They're otherwise largely orthogonal (different concerns: storage vs lock-type), so the only constraint is "do the bigger structural change first."

**Reasoning — why the ring over the canonical intrusive list.** The textbook kernel answer is an **intrusive doubly-linked list** via per-Thread `next`/`prev` fields (Linux `list_head`, FreeBSD `TAILQ`, seL4 scheduler lists), which needs *zero* container pre-allocation because each Thread's own `Box` is the node. It preserves pointer-stability perfectly (the Thread never moves) and matches NeoPlutarch's mutually-exclusive thread states (Running/Ready/Zombie/Blocked — one `next`/`prev` pair suffices). **But it forces `unsafe` raw-pointer plumbing** (`NonNull<Thread>`, `Box::into_raw`/`from_raw` on every enqueue/dequeue to reconcile Rust ownership with intrusive links) **into scheduler control flow — and Bible Article 4.2 confines `unsafe` to hardware boundaries (asm, MMIO, page tables, MSRs), reviewed line-by-line.** A scheduler-data-structure intrusive list is squarely *not* a hardware boundary. The fixed-capacity ring of `Box<Thread>` achieves every ADR-016 constraint — bounded-by-construction, pre-allocated, zero-alloc-under-lock, fallible spawn, and Box-pointer-stability (the ring stores the owned `Box`, so moving a slot moves only the 8-byte owning pointer; the Thread heap allocation and its captured `rsp` never move) — **entirely in safe Rust.** The ring's only cost is ~1 KB/CPU of pre-allocated slots (128 pointers × 8 bytes × 64 CPUs ≈ 64 KB total at MAX_CPUS), trivially within budget. Structure-over-discipline is ADR-016's own thesis; the ring delivers it without spending the project's tightly-rationed `unsafe` budget on scheduler logic.

**Alternatives considered:**
- **Intrusive doubly-linked list** (ruled out above): canonical and zero-pre-alloc, but injects `unsafe` into scheduler logic against Bible 4.2. Revisit only if a future phase needs unbounded ready queues or O(1) arbitrary-position removal the ring can't give — D13 (single-thread-per-process) + the 64/CPU bound make a fixed ring sufficient through Phase 2.
- **Pre-reserved `VecDeque<Box<Thread>>` + a spawn-time bound check** (the minimal change): keep the existing container, `reserve` to the bound at init, and refuse spawn past the bound so it never reallocates. Ruled out because it's *disciplinary, not structural* — a missed bound check silently reallocates under the lock (the exact INV-SYNC-5 hazard), and `VecDeque` exposes no "fail if this push would realloc" guarantee. ADR-016's whole point is to make heap-independence *structural*; the fixed array makes "cannot grow" a type property, not a code-review obligation.
