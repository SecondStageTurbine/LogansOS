## Section 385 checklist

1. **PASS — never the internal drive, by the unchanged guard rule.** The design adds no marker and no rule. The partition arm is the existing `partition_claims`: it requires the LogansOS NeoFS type GUID, INCOMPLETE clear, a sealed NEOFSv1 superblock at the partition's first block, and the volume fitting the partition (`kernel/src/drivers/block/write_guard_logic.rs:466-511`). `judge_with_partitions` appends those claims after the ordinary marker judge (`:515-519`); a Windows GPT has no LogansOS-typed entry, and a valid marker inside a Windows partition is dropped by the table filter (`:609-616`). The existing KAT `windows_gpt_disk_never_arms` (`tools/block-guard-logic-tests/src/lib.rs:460`) passes. R3's `usb_persist_never_internal` (a Windows-shaped NVMe with a planted whole-disk NEOFSv1 superblock in a data partition, a refused-write line, and a host-side image hash) is the right proof.

   Caveat: the design's census and mount rule need the armed **extent**, the table name and the stick's write-protect state; the block API exposes only a boolean (`kernel/src/drivers/block/mod.rs:651-657`). See F3.

2. **FAIL — the layout is not yet sound in three places.** The placement and the DD/rewrite story are right, but the creation path has no verified partition entry, the `persist=off` selection has no kernel mechanism, and the boot-device match falls back to guessing.

   (a) **The appended entry and both GPT copies are not established.** The ISO's GPT is xorriso's, with the ESP from `--efi-boot-part` (`tools/xtask/src/main.rs:10637-10658`); the design appends partition 3 with a GPT type GUID and says "verify in R3" (`docs/THINK-2026-11-10-ot100-usb-persistence.md:94-99`). Its fallback is "rewrite the one entry's type GUID and recompute both CRCs" (`:98-99`). That does not name rewriting the **backup** header and entry array, which the append moves and which a firmware/Windows repair can promote; R3's oracle as written does not say it checks the backup copy. Concrete input: build the image on the dev container's xorriso and dump LBA 1, LBA 2, the last LBA and the last 33 LBAs; if partition 3 is absent, non-consecutive, or the backup's entry array/CRCs do not carry the same entry, the image is not ready for R3.

   (b) **`persist=off` is not wired.** The design gives the image two Limine entries and says the try entry passes `persist=off` on the kernel command line (`:114-124`), but `boot/limine.conf` has one `/NeoPlutarch` entry (`boot/limine.conf:17`), `write_limine_conf` only injects modules into that entry (`tools/xtask/src/main.rs:24452`), and there is no kernel command-line parser anywhere in `kernel/src` (the only `cmdline` reference is the Limine file-struct offset comment, `kernel/src/limine_file_logic.rs:12`). The product boot always calls the read-write mount (`kernel/src/main.rs:921`; `kernel/src/fs/mod.rs:1152-1185`), so "mounts the area read-only" (`THINK:120-122`) needs a named readonly branch and a parser. The setup menu's "Try" button also needs a named one-shot store for the next boot. Concrete input: boot the try entry with a persistence area present; assert the stick image hash is unchanged **and** the mount reports read-only. As written there is no path that reads the flag.

   (c) **The boot-device match can fall back to the wrong stick.** `boot_disk_guid()` returns `None` when Limine's GPT disk UUID is zero (`kernel/src/limine_file_logic.rs:38-42`), and the design then falls back to "today's first LogansOS partition on any device" (`THINK:207-210`). With two LogansOS sticks attached, that is the wrong area, mounted read-write. Concrete input: QEMU with two LogansOS sticks, the boot stick's Limine UUID zero; assert the persistence volume selected is the boot device's (by ESP/kernel-file partition, not by registry order), or refuse the RW mount rather than guessing.

3. **FAIL — the MSC write path cannot be built as written.** The core data-out stage is missing from the design and the code it reuses.

   `msc_logic::command` hard-codes the CBW direction bit to device-to-host (`encode_cbw(tag, data_len, true, ...)`, `kernel/src/drivers/usb/msc_logic.rs:391`) and only performs a data-in stage via `pipe.bulk_in(data)` (`:402-413`). The `Pipe` trait has no bulk-out data method (`:325-334`), and the binding's `bulk_out` carries only the 31-byte CBW through `small` (`kernel/src/drivers/usb/msc.rs:209-219`). The THINK says to copy the caller's data into the `bounce` buffer (`THINK:151-156`) but never adds a data-out `Pipe`/`command` stage; §5.1 CP-77/78 says "Leave. The OUT TRBs use the same ring code as today's bulk-in" (`THINK:261`), which is not true: today there is no bulk-OUT data TRB, only the CBW. R2 would have to change the pure protocol module, every `Pipe` implementation and its KATs. The existing KAT even states that `WRITE(10)` is refused before the pipe is touched (`tools/usb-msc-logic-tests/src/lib.rs:560-563`).

   The write split is also unnamed. `MAX_READ_BLOCKS`/`next_read` are read-only (`msc_logic.rs:44-45`, `:302-311`); there is no write chunk helper and no explicit >32-bit LBA refusal. The design says "A larger stick is refused writes with a line, not mis-addressed" (`THINK:139-140`) but does not name the check; a 3 TB stick would have to reject a write at LBA > `u32::MAX` before the CBW. `MscDisk` currently implements only `read_block`/`write_block` (`msc.rs:279-364`); `supports_flush`/`flush` are trait defaults (`kernel/src/drivers/block/mod.rs:139-145`). The design says the probe will set them, but the overrides and their `PartitionDevice` forwarding (`kernel/src/drivers/block/partition.rs:133-139`) are not named.

   The trap bank itself (§8.1, `THINK:306-323`) does cover the known `unusual_devs`/write-cache-lies classes with a discriminator per trap (F2, F3, F4, F10, F13); that part passes. The path that would exercise it does not.

4. **PASS — crash consistency relies on the right NeoFS contract, but "goes read-only" is not implemented (F2).** NeoFS writes copy-on-write data/inode/directories/free-map, then superblocks only after a flush (`kernel/src/fs/neofs/commit_logic.rs:1-22`, `:68-80`; `kernel/src/fs/neofs/cache.rs:1015-1075`), and a writable mount is refused without a flush (`kernel/src/fs/neofs/mount.rs:62-70`; `cache.rs:1121-1137`). A pulled stick or a cut leaves an older superblock naming an intact generation, which is the mountable-volume contract the dispatch asks for. The design says the device must honour SYNCHRONIZE CACHE and that every NeoFS commit point flushes (`THINK:160-167`, `:200-202`). That is correct.

   The weakness is the failure transition. `NeoFsState.writable` is an immutable `bool` (`kernel/src/fs/neofs/inode.rs:111`, `:229-231`), and the writeback kthread exits `Failed(2)` on the first drain error (`cache.rs:710-712`). There is no path that flips the mount to read-only on DATA PROTECT, a failed flush or `DeviceGone`; the design's F2/F3/F11 lines (`THINK:330-339`) assume a state transition the design does not specify and the code cannot currently make. See F2.

5. **PASS — I-14 containment.** The write path holds `MscDisk.transport` and takes xHCI's `EVENT`/`EP_ROUTES` per poll, exactly as reads do (`kernel/src/drivers/usb/msc.rs:304-340`, `:139-155`); the I-14 note is at `msc.rs:11-17` and the xHCI event path's no-governance-lock claim at `kernel/src/drivers/usb/xhci.rs:19`, `:856`. `Flush` and `write_block` are entered from the NeoFS drain kthread with IF=1, and the design's debug assert is the right discriminator (`THINK:346-363`). Every OUT transfer must use the fenced `bounce` buffer; the design says so (`THINK:359-363`), but that is part of the missing data-out path (F1). The proposed grep check "`msc.rs` names no governance lock" is brittle (the file names `DmaBuffer`/`dma_arena`); scope it to the actual governance locks, not the string `ARENA`.

6. **PASS with a named contradiction — missing area is read-only only when no other LogansOS volume exists.** With no persistence partition, `partition_claims` returns empty, `find_neofs_partition` returns `None`, and the boot mount logs `NoValidSuperblock` and carries on (`kernel/src/fs/mod.rs:1000-1095`, `:1151-1185`); nothing hangs. But the design keeps "today's first LogansOS partition on any device" as the fallback (`THINK:207-210`), and today's product path is a **read-write** mount (`kernel/src/main.rs:921`). A second LogansOS stick or an installed LogansOS disk would therefore be mounted read-write on a no-area boot, contradicting the unconditional "boot carries on read-only" in the dispatch. On the Zenbook (Windows NVMe only) the single-stick case is fine. See F6.

7. **PASS — each code rung has a gate, kill-switch and oracle; the image kill-switch needs a byte-level check.** R2 (`THINK:372`), R3 (`:373`) and R4 (`:374`) name a gate, an off-state and an oracle; R1/R5 are the read and hardware rungs and have no kill-switch by nature. The R2 off-state (allowlist KAT, `write_block` `Unsupported`, `supports_flush` false) is testable. The R3 off-state says "`xtask iso` without `--persist-mib` yields today's image with no LogansOS entry" — that should be a byte-for-byte image identity check (same commit, same xorriso, off vs on), not only the absence of one entry, because a changed xorriso argument list or a changed kernel can still alter the image. R4's "quick tier unless it touches the SMP core" is a PM call, but a new kthread plus a new file write path is a new seam, not just a test scenario.

   The §8.2 blind-hardware table (`THINK:325-344`) gives every failure a line visible on screen or in the stick log, including F9's `nvme... armed=none` and F13's boot counter. That satisfies the discriminator requirement.

8. **FAIL — the prior-art survey has no date for Tails, the primary precedent.** The dispatch asks for licences **and dates**; the Tails row says "Last commit (checked): **Not checked:** `gitlab.tails.boum.org` refused (403)" (`THINK:290`). Every other row that is used has a date (Ventoy `74cff34240dc`, 2026-10-22; Linux `b3dfbde62cf1`, 2026-11-09; Haiku `f4e3fd5e6ab9`, 2026-11-09; TinyUSB `26adc208a2bf`, 2026-11-09), and the THINK already knows a Tails version ("LUKS2 with Argon2id since Tails 5.13", `THINK:268`). This is the same class as the #99 bounce (one survey row's date/SHA). Concrete input: add the Tails release/commit or the docs page's last-updated date, or a pinned Tails version, to the Tails row. Redox is explicitly "Not read" (`THINK:296`), which is honest; if the row is kept, give it a date too.

## High-risk findings (hypothesis + named test)

### F1 (high) — the data-out path is absent, so R2 cannot issue WRITE(10)

**Hypothesis.** If R2 reuses `msc_logic::command` as-is, the CBW for a WRITE(10) has `bmCBWFlags` bit 7 set (device-to-host) because `encode_cbw(..., true, ...)` is hard-coded (`kernel/src/drivers/usb/msc_logic.rs:391`), and the driver waits for a bulk-IN data stage that the device will not send (or sends a phase error). The first `usb_msc_write` scenario fails with `Outcome::Reset { reason: Phase(...) }` or a CHECK CONDITION, and the raw image hash after QEMU is unchanged.

**Named test.** `usb_msc_write_cbw_direction` (host, new): build a WRITE(10) CDB, run it through the new write command with a recording `Pipe`, assert (i) the CBW byte 12 is `0x00`, not `0x80`; (ii) the data stage is a bulk-OUT of exactly the pattern bytes; (iii) the CSW residue is 0. Then the QEMU `usb_msc_write` scenario writes a pattern across 128-block and 64-block boundaries, flushes, reads it back, and xtask hashes the raw image after exit. Production `command()` must take a direction/out-slice, and the `Pipe` trait needs the OUT data method.

### F2 (high) — the mount cannot "go read-only" on DATA PROTECT, a failed flush or `DeviceGone`

**Hypothesis.** A write-protected stick, a pulled stick, or a flush that returns an error does not flip the mount: `NeoFsState.writable` is a plain immutable `bool` (`kernel/src/fs/neofs/inode.rs:111`, `:229-231`), and the drain worker exits `Failed(2)` on the first error (`kernel/src/fs/neofs/cache.rs:710-712`). The VFS keeps reporting the mount writable (`is_writable()` is used as the mutation guard at `inode.rs:1941`, `:2042`, `:2072`, `:2106`; `mount.rs:112`, `:142`, `:165`), so later writes can be accepted into the cache with no drain worker to commit them; F11's `persist: volume lost; read-only` line never prints. Data loss is silent until the next boot.

**Named test.** `usb_persist_unplug_midwrite` (R3 QEMU): boot read-write, start a multi-block write, QMP `device_del` the usb-storage device, then (a) attempt a second write and an fsync, (b) assert every mutation returns a `ReadOnly`/`BlockDevice` error and `NeoFs::is_writable()` is false, (c) assert the `persist: volume lost; read-only` line printed once. Add a host KAT for the DATA PROTECT sense path (`Unit Attention`/`Data Protect`) that asserts the same latch. If the intended contract is "writes fail per-call, mount stays writable until reboot", say that explicitly and drop the F2/F3/F11 "read-only" claims.

### F3 (medium) — the mount/census conditions have no observable state

The design's read-write rule needs "the stick's probe reported `wp=no` (or unknown)" and "the armed extent equals the partition's span" (`THINK:213-218`); the census needs `armed=<extent>` and `table=<t>` (`THINK:243-248`). `MscDisk` has no `write_protected` field (`kernel/src/drivers/usb/msc.rs:270-277`) and the `BlockDevice` trait has no write-protect query (`kernel/src/drivers/block/mod.rs:139-145`); `block::writes_allowed` returns only a bool (`:651-657`), and `Arming.claims`/`table` are not exposed past `GuardedDevice`. Test: a boot scenario with a second claim on the same disk (a sealed log-sink header overlapping the partition) must refuse the RW mount unless the armed extent is exactly the partition. Add the read-only accessors first.

### F4 (medium) — the bind-time probe sends SYNCHRONIZE CACHE to every MSC device before the guard

`bind_inner` runs before `register_device`/`GuardedDevice` (`kernel/src/drivers/usb/msc.rs:383-569`). The §3.4 probe adds MODE SENSE, TEST UNIT READY and SYNCHRONIZE CACHE at bind (`THINK:192-198`), i.e. to any USB mass-storage device, including a foreign one the guard would never arm. A cache flush can commit the device's own cached data; it is not a data write, but it breaks the runbook's "the only medium we write is the Kingston stick" posture. Hypothesis: plugging a foreign write-back USB disk flushes it before any guard judgement. Named test: QEMU with a second usb-storage disk backed by a write-back model; assert no SYNCHRONIZE CACHE is sent until the device is armed (or move the probe to the first read-write mount, not bind).

### F5 (medium) — the VM/one-disk layout checks assume the boot disk has no NeoFS volume

`check_vm_layout` requires `boot.raw` to be the ISO bytes and rejects a NeoFS superblock at the boot disk's own offsets (`tools/xtask/src/vm_image.rs:156-177`); `check_one_disk` expects entry 2 to be the NeoFS partition (`:107-109`), and `check_boot_disk_partitions` only requires an ESP (`:203-233`). The new image appends a LogansOS NeoFS partition to the boot ISO. If `xtask vm-image` uses a `--persist-mib` ISO, the kernel's "boot device first" rule (`THINK:207-210`) would mount the boot disk's persistence partition instead of `data.raw`, and the installer/VM invariants in `vm_image.rs` are no longer true. Test: build the two-disk and one-disk VM layouts from a persistent ISO; assert `check_vm_layout` passes and the kernel selects `data.raw` for the installer, not the boot area; or state that `vm-image` always builds without `--persist-mib`.

### F6 (medium) — no-area boot is not unconditionally read-only (see item 6)

Test: boot a no-area stick with a second LogansOS volume attached; the design's fallback mounts the second volume read-write. Either drop the fallback under `usb-persistence` (refuse RW when the boot device cannot be identified) or state that the "read-only" guarantee is conditional on no other LogansOS volume.

## Smaller notes

- `THINK:27-28` cites `block/mod.rs:705-731` for the guard and `:383-395` for lazy arming; the guard construction is at `705-731`, and lazy arming is `383-427` (`arming` plus `writes_allowed`). The first citation is right; the second should end at 427.
- `THINK:49-53` says the product boot mount "takes the first LogansOS partition on any device"; the actual product call is read-write (`kernel/src/main.rs:921`), not read-only. "As today" in §0 (`THINK:20-23`) should say "read-only when no volume exists; the product still mounts a found volume read-write."
- `THINK:121-122` says "With `persist=off`, the kernel never calls `writes_allowed()` on the stick"; the §5 census calls `writes_allowed()` on every device (`THINK:243-248`). The judgement is reads-only, so this is harmless, but the sentence is false as written. Say "never issues a write to the stick."
- `THINK:139-140` says the current reads "stop at a 32-bit LBA"; `next_read` returns `None` at the boundary and `read_block` then copies a short `out` into full caller buffers (`kernel/src/drivers/usb/msc.rs:311-356`), which would panic rather than refuse. For the 512 MiB v1 area this is unreachable; the later >2 TiB step needs the explicit refusal.
- The runbook needs an R3/R5 update: `docs/runbook-baremetal-zenbook-s14.md:59-60` says Image A's only writes are to NeoFS volumes it finds and "none exists on this machine". With the persistence partition, the boot stick now carries one and Image A writes it by design. The hard rule (never the internal NVMe) is unchanged; the "Preparing the stick" and "If it does not boot" sections should say the stick is now a data medium, not only a boot medium.
- `THINK:372` R2's kill-switch "the product ELF must not contain the new probe's line" is a weak proxy; the allowlist KAT and the `write_block`/`supports_flush` assertions are the real checks.
