# DISPATCH: CI hygiene — hermetic QEMU tests + artifact-storage discipline → Cerebro

**Date:** 2026-06-18
**From:** PM (Claude)
**To:** Cerebro (W2 is silicon-gated — cycles free; `phase4_https_fetch` is net-stack, adjacent to the connectivity lane). New branch off `origin/main` HEAD: `codex/ci-hygiene-hermetic-tests-cerebro`.
**Status:** DISPATCHED. **A green CI gate is a falsifiable safety property — and right now it's lying twice.** The CSPRNG 10.3 QEMU gate went red on shard 3 with **`phase4_https_fetch` (code=85, 4× retries)** — a failure that (PM-verified) has **nothing to do with 10.3** (10.3 is clean-additive, doesn't touch net/TLS; the net path doesn't consume the kernel RNG; `phase4_https_fetch` passed green on `main` at `6c13773`). It's an **environmentally-fragile test**. And separately, the **GitHub artifact storage quota is exhausted**, so any failing shard's log-upload *also* fails, compounding the red. Both are CI-infra, both block real merges. Fix both.

## 0. The decision this build makes
Make the QEMU gate **stable, hermetic, and trustworthy** so kernel-touching builds can merge again: (0) the **exit-137 process kills under load** must stop reddening the gate (the priority — it blocks every kernel merge); (1) `phase4_https_fetch` must not flake on external network state; (2) an artifact-upload failure must never redden a shard whose *tests* passed, and the storage bloat is curtailed. **No product code** — test-harness + CI-workflow hygiene. **This build is the prerequisite for re-gating CSPRNG 10.3 (code already PM-verified clean) and every subsequent kernel build.**

## 1. Context (the evidence)
The shard-3 failure (run `27786586587`, job `82231763273`): `NEO_TEST/1 event=FAIL name=phase4_https_fetch reason=https_fetch_exit_nonzero code=85` (×4). The artifact step failed *downstream* (`##[error]Failed to CreateArtifact: Artifact storage quota has been hit … recalculated every 6-12 hours`) — it only ran because the test step had already failed (`Upload … on failure` is `if: failure()`). 22 scenarios PASSED in that shard; only `phase4_https_fetch` failed.

## 2. ISCs
- **ISC-0 — Diagnose + mitigate the exit-137 process kills under CI load (NEW — the priority; it blocks *every* kernel gate).** A 2026-06-18 re-gate (`27793940047`) hit **exit 137 (SIGKILL)** on host-checks + QEMU shards 2 & 3 — a *different* failure mode than ISC-1's `code=85`. **First, confirm what the 137 is:** SIGKILL is also the **cancel** exit code, and that run was canceled — so check the runner's **OOM/dmesg logs + the per-job kill timestamps vs the cancel time** to distinguish a genuine **resource (OOM) kill** from cancel-induced 137s. **Key clue — the host has 128GB RAM, so a genuine host-RAM OOM is implausible** (6 concurrent build+QEMU+Docker jobs ≈ 30–40GB, well under 128). So the 137 is almost certainly **NOT real RAM exhaustion** — it is one of: **(a) cancel-induced** (SIGKILL is the cancel exit code; that run *was* canceled — if the 137s landed *after* the cancel, there may be no OOM at all and run 2 is simply inconclusive, leaving run 1's `phase4_https_fetch` external flake as the only confirmed failure); or **(b) an ARTIFICIAL cap firing far below 128GB** — the prime suspects: the **`altimitneo-wsl` runner is WSL2**, which has its own `.wslconfig` `memory=` cap (a fraction of host RAM regardless of the 128GB; shard 2 ran there), **Docker Desktop's WSL2-backend memory cap**, or a **docker-compose `mem_limit`**. **Check these first — do NOT conclude "add RAM."** The likely fix is raising/removing a config cap (`.wslconfig memory=`, the Docker backend limit, or a compose `mem_limit`) and/or capping job concurrency so heavy jobs don't pile onto one runner (`max-parallel` on the shard matrix). State clearly which 137s were cancel vs a real cap, and which cap fired. **Ops dimension:** if a config cap is the cause, the PL can raise it directly (a `.wslconfig`/Docker-settings change, not new hardware) — flag the exact knob.
- **ISC-1 — Diagnose + de-flake `phase4_https_fetch` (the hermetic-test fix).** Root-cause `code=85`: **does this scenario depend on a live external HTTPS endpoint?** If yes (the likely cause — it passed on `main` and fails here with no related code change ⇒ external state, not determinism): make it **hermetic** — serve the fetch from an **in-VM / loopback TLS endpoint** (a local test fixture with a known cert + response) so the scenario tests the *TLS/net stack* deterministically with no internet dependency. If the scenario's *value* is genuinely testing real external egress (not just the stack), then **reclassify it as a network-gated scenario excluded from the standard QEMU shards** (the BUILD-W1 `mt7601u_scan_baremetal` exclusion precedent) — run it only where real network is guaranteed, never in the gating shards. **Principle: a gating QEMU scenario MUST be hermetic** — no scenario in the 4-shard gate may depend on the live internet. Pick the right fix and state why.
- **ISC-2 — An artifact-upload failure must not redden a tests-passed shard.** Set the `Upload neo-test serial logs on failure` step to **`continue-on-error: true`** — a storage-quota/upload failure is infra, never a test verdict; it must not flip a shard whose tests passed to red. (Today it can't mask a real failure either way, but it *can* turn a future green-tests/storage-full run red — close that.)
- **ISC-3 — Curtail the artifact storage bloat.** Reduce the serial-log artifact `retention-days` (currently 14 → **3**, enough to debug a recent failure) and confirm uploads only fire on failure (they do). **The one-time prune of the exhausted quota is an ops action** (delete old workflow-run artifacts via the API / Actions UI) — note it in the RETURN for PL/PM to action; this dispatch fixes the *recurrence* (retention + continue-on-error), not the existing backlog.
- **ISC-4 — Standards.** No product code; test-harness + `.github/workflows/ci.yml` only. The de-flaked `phase4_https_fetch` must pass **hermetically** in the QEMU shards. `fmt`/`clippy` clean (if any Rust test-harness/fixture code changes). No new invariant/`unsafe`. Add a one-line note to the CI section / a guard: **gating scenarios are hermetic.**
