# DISPATCH: File-capability unification — bring `Handle::File` into the CapRights graph (I-15) → Cerebro

**Date:** 2026-06-19
**From:** PM (Claude)
**To:** Cerebro (main-tier; security-core kernel work). New branch off `origin/main` HEAD: `codex/file-cap-unification-i15-cerebro`.
**Status:** DISPATCHED. **The prerequisite OT-18 E1b is blocked on (found by Genesis's E1b STOP, PM-verified against the code).** File handles are a parallel rights system (`FileRights`) that never entered the `CapRights` derivation/grant graph: `Handle::File::rights()` returns `CapRights::new(0,0)` (process.rs:503), so `derive_handle` (needs `DERIVE`, line 877) and grant-install (needs `GRANT`, line 986) **EPERM on every file handle**, and `with_cap` on a `File` **ignores** the passed rights (line 532, `let _ = rights;`). The `FileRights::GRANT_RESERVED (1<<24)` / `DERIVE_RESERVED (1<<25)` bits (fs/mod.rs:51-52) were reserved for exactly this and never wired. **PL-ratified 2026-06-19: build the unification before E1b.** This is the keystone-preserving path (Article 29.3): without it, a delegated file cap cannot be narrowed or kernel-enforced.

## 0. The decision this build makes
Make `Handle::File` a **first-class capability** in the derivation/grant graph — derivable (attenuated), grantable, inheritable — exactly like `Handle::Channel`/`Process`/etc., with file-rights subset-checking. After this, OT-18 E1b's "neo-shell derives a narrow read-only file cap and grants it to Arthur" works and the kernel cap is genuinely Arthur's boundary. **This is the only build that touches the file-handle capability semantics; E1b is the consumer (a separate build).**

## 2. ISCs
- **ISC-1 — `Handle::File` carries real meta-rights.** `Handle::rights()` for `File` must surface meta bits (at minimum `DERIVE` and `GRANT`) derived from the file handle's stored rights, so `has_meta(DERIVE)`/`has_meta(GRANT)` gate file derivation/granting exactly as for other handle kinds. Pick the cleaner representation (map `FileRights::{GRANT,DERIVE}_RESERVED`→`CapRights` meta while keeping `FileRights` authoritative for the semantic file ops; OR fold file semantic rights into `CapRights` — file semantic ops fit in 8 bits). **Document the exact `FileRights ↔ CapRights` mapping as a table in the ADR and assert it in a KAT (the mapping is the oracle — hand-write it, don't round-trip).**
- **ISC-2 — `with_cap` attenuates file rights (the bug Genesis flagged).** `with_cap` on a `File` must **attenuate**, not ignore: the resulting handle's `FileRights` must be the requested subset of the original (child ⊆ parent). A `FileRights::READ` derivation of a `READ|WRITE` parent yields a **read-only** handle.
- **ISC-3 — `sys_open` roots the file's derivation tree.** The opener of a file is the root owner of that file capability, so `sys_open` grants the returned handle the `DERIVE`+`GRANT` meta-rights (plus the requested semantic rights). Without this, a freshly-opened handle (e.g. neo-shell's) holds nothing to derive/grant from. (Mirror how a process spawn roots authority over its child.)
- **ISC-4 — `derive_handle` / `ipc::grant` / spawn-inheritance work on files with FileRights subset-checking.** File derivation attenuates `FileRights` (child ⊆ parent) and carries meta per the existing derivation rules; granting/inheriting a file cap works and `revoke_handle` cascades through the file's derivation subtree exactly as for other handles. No bypass — the meta-gating + subset-check is the boundary.
- **ISC-5 — I-15, the new invariant (budget rule: name + justify + guard, all in this build).** **I-15: "File handles are first-class capabilities — a derived/granted file handle's `FileRights` is a subset of its parent's, and `DERIVE`/`GRANT` meta-rights gate file derivation/granting as for every other handle kind (no file-handle bypass of the capability graph)."** Add it to `docs/complexity-governance.md` with a **grep-checkable + runtime-assertion guard** (e.g. an assert in the file-derive path that `child.file_rights ⊆ parent.file_rights`, and a test that no `Handle::File` path reaches derivation without the meta-check). Justify it in the ADR (it's the prerequisite for OT-18's kernel-enforced Arthur boundary).
- **ISC-6 — Standards + kill-switch + KATs.** **Kill-switch `file-caps` default-OFF ⇒ `Handle::File::rights()` returns `CapRights::new(0,0)`, `with_cap` ignores rights, `sys_open` sets no meta bits ≡ today bit-for-bit** (ship the equality regression proving disabled == the current layer). Default-ON ⇒ I-15 active. No new `unsafe` (rights logic). `fmt`/`clippy --workspace --all-targets -D warnings` via Docker (kernel clippy blocking). SPDX. New ADR (file-capability unification) + the I-15 ledger row.

## 3. Gate
- **Host KATs:** (a) the `FileRights↔CapRights` mapping table (hand-written oracle); (b) **attenuation** — derive `READ` from `READ|WRITE` → child is read-only; (c) **subset enforcement** — derive exceeding parent → EPERM; (d) **meta-gating** — a file handle without `DERIVE` can't be derived, without `GRANT` can't be granted/inherited; (e) **revoke cascade** on a granted file cap; (f) **kill-switch equality** — `file-caps` off ⇒ rights()==(0,0), no derivation, byte-for-byte today.
- **QEMU scenario `file_cap_derive_grant`:** a process opens a file (gets DERIVE+GRANT), derives a read-only cap, grants it to a child; the child **reads OK but writes → EPERM** (live attenuation against the real kernel); a non-granted file → EPERM. At **NEO_SMP=4**. (This is the live proof E1b will rely on.)
