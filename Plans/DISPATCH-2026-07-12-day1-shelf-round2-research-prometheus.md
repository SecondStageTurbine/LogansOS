## The framing (three realities, plus one NEW axis this batch forces)
Round 1's three rules still bind: (1) "recompile as a cap-native client" has a prerequisite ladder (`no_std` libneo → the `std`-analog target → GUI backend); (2) **purity is verified from the real dependency tree, never assumed** ("written in Rust" is a claim to audit — read each repo's own `Cargo.toml`/`Cargo.lock`/`cargo tree`; any load-bearing `*-sys`/C binding disqualifies or flags); (3) the AI-native twist — **prefer the library/substrate wired into Arthur/a Workfield over a ported windowed app** where it serves the need better.

**NEW axis (chat forces it, but it applies broadly): LEGAL / ToS feasibility is separate from engineering feasibility.** A candidate can be perfectly buildable in Rust and still be un-shippable because the *service's* terms forbid third-party clients (the Discord-user-client case) or the format/network is proprietary and hostile (WhatsApp, iMessage). **Every network/service candidate gets a ToS/legal verdict from the primary source (the service's own ToS/API policy), classified as: OPEN (third-party clients permitted), GRAY (discouraged/unclear), or WALLED (forbidden/proprietary — a documented dead-end, never listed as a working ship).** Do not hand-wave this — over-promising a "Discord client" that needs a ToS-violating user-token is exactly the dishonesty this axis prevents.

## ISC-1 — Python on LogansOS (the separate language question)
- **The path split:** CPython/MicroPython are **C + full-POSIX/libc** ⇒ the compat-island category we ratified *against* (round 1's REJECTED tier; the X11/GTK rejection). **RustPython** (pure-Rust Python 3, MIT) is the LogansOS-native path — a cap-native libneo client via OT-52's rung. Audit it firsthand: (a) is the **core VM** genuinely pure Rust, and which optional features drag `*-sys` (`ssl`/`zlib`/`hashlib`)? (b) the real **`no_std`/`std` boundary** — how much pure-computation Python runs with no OS (its WASM target is the evidence to check), and exactly which **stdlib modules** force the std-analog; (c) the **stdlib→libneo/NeoFS/caps mapping** — which modules (`os`/`io`/`open`/`time`) shim cleanly onto our syscall surface vs. which have no home (`subprocess`/`socket`/threads).
- **Tiers:** pure-computation Python (REPL on OT-57) = nearest-term; file/OS Python = the std-analog rung + per-module shims; net/subprocess Python = later/maybe-never for N=1.
- **The AI-native framing to evaluate:** Arthur running **sandboxed, capability-confined RustPython as a code-execution / action substrate** — an agent code-interpreter that structurally cannot exceed its granted caps. Is a cap-confined RustPython the right shape for Arthur's code-exec tool (vs. WASM per OT-44 H3)? Recommend.

## ISC-2 — the 8 categories (verdict each: tier + pure-Rust candidate AND best library route + purity-from-tree + license + maintenance + ToS-where-applicable + one-line verdict)
1. **Password manager** — *(PM prior: strongest fit)* — RustCrypto (AES-GCM/Argon2/ChaCha20Poly1305, pure Rust) over NeoFS + per-category encryption (OT-17). 2. **Archive manager** — pure-Rust `zip`/`tar`/`flate2`(miniz_oxide)/`ruzstd`/`lzma-rs`. **Trap to verify:** the *default* zstd/xz crate backends are C `*-sys` — confirm the pure-Rust decode/encode coverage per format (which formats are create+extract vs extract-only in pure Rust). T1/T2 shell over the libs.
3. **System utilities** — `uutils/coreutils` (pure-Rust coreutils, MIT), `ripgrep`/`fd`/`bottom`/`dust`/`procs`. Which are the **T1 shelf on OT-57**, which are **already Arthur/`neo>`-native** (superseded, don't ship duplicates), which pull `*-sys` (e.g. git-backed tools). 
4. **Media player** — *(round 1 covered — confirm + extend)* — `symphonia` (pure-Rust audio decode) + `rodio`; audio gated on the OT-46 voice-lane driver (same driver). **Video honestly:** pure-Rust video-decode state + GPU dependency (T3). Library-into-Workfield vs ported player.
5. **Office suite** — **split the ask:** (a) **format interop** (`docx-rs`/`calamine`/`umya-spreadsheet`/`pulldown-cmark` — mostly pure ZIP+XML; audit) = the load-bearing "don't be a dead-end when sent a `.docx`" requirement, a **library**; (b) **editing apps** — a markdown/rich-text editor via the Atrium text-engine is near-term; a **spreadsheet/presentation app is the deepest gap** (no shippable pure-Rust one — say so). A LibreOffice-equivalent is NOT day-1.
6. **Web browser** — **ELEVATED OUT to its own study, OT-61 (`Plans/DISPATCH-2026-07-12-web-browser-headline-research-prometheus.md`) — the PL ranked it the #1 day-1 app.** Do NOT cover it here beyond noting, for the shelf's sake, that the day-1 interim floor is a CPU HTML/md reader + Arthur-mediated fetch (the full two-path browser evaluation lives in OT-61).
7. **Chat / messaging aggregator** — **do NOT design a Ferdium-style webview aggregator** (it's a browser + N webviews = the browser gap, worse). Evaluate **native protocol clients on open protocols**, per-service with a ToS verdict: **Matrix** (`matrix-rust-sdk` + `vodozemac` E2E — the anchor; bridges do the aggregation natively; OPEN), **Telegram** (`grammers`, OPEN), **XMPP/IRC** (`xmpp-rs`/IRC crates, OPEN), **Signal** (`presage`/`libsignal`, GRAY), **Discord** (`serenity`/`twilight` are pure Rust but **bot-only**; a user client is **WALLED** by ToS), **WhatsApp/iMessage** (**WALLED**, proprietary). The AI-native framing to evaluate: **Arthur as the unified inbox** — all connected protocols flow into Arthur/a Workfield, each connection a scoped cap; is that the differentiated shape (same as email's library-behind-Arthur)?
