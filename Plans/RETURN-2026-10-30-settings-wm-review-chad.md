- **2 PASS - a cut selects a complete old or new setting, not fields from both records.** `settings-core/src/lib.rs:389` plans a write only to the other file with checked generation increment; select verifies each whole record independently. The WM writes and fsyncs that file through `desktop_session/login.rs:219`, compares its read-back with all expected bytes (`settings.rs:208`), and only then stores/applies the new record (`:228`). If a successful write's read-back fails, resync (`:250`) reselects the two copies as the next boot would, and applies that selected complete record. It does not merge fields from different copies. The host cut test (`settings-core/src/tests.rs:293`) checks every prefix truncation, every prefix overwrite of the inactive old record, and single-bit damage: old or complete new, with the active record intact. This is a one-inactive-copy-write durability model; it does not promise recovery if both copies are independently destroyed. The author reports the block-write/flush cut scenario passing; I did not rerun that QEMU campaign.
