## Findings

- **PASS — attached zone directory and row details.** `tz_page::attach` constructs the `Zones` implementation from `libneo::tz`; its shortlist resolves the setup-core `ZONES` names, search delegates to `tz::find_zone`, and each row combines the IANA name with the computed abbreviation and UTC offset (`userland/neo-init/src/desktop_session/setup.rs:287-325`; `userland/setup-core/src/lib.rs:59-71, 428-444`). The live `detail` path converts the pinned local RTC reading to the earlier UTC instant for an ambiguous time, then formats `utc_to_local`'s abbreviation and signed offset. Hand check against the host tz database at the gate instant `2026-11-01 05:57Z`: New York is `EDT, UTC-4` (id 105; generated rule is EST-5/EDT-4), and London is `GMT, UTC+0` after its 2026-10-25 fall-back (id 300). The corresponding zone-rule rows are in `userland/libneo/src/tz_table.rs` (New York line 116, London line 299). The row renderer displays the id's canonical zone name and computed detail (`userland/setup-core/src/lib.rs:428-444`).

- **PASS — search and Space behavior.** Printable input is sent as `Input::Char`; while the searchable Time zone page is active it updates the query and refreshes results. On other pages, `Char(' ')` maps to Choose, and the key adapter forwards Space as a character (`userland/setup-core/src/lib.rs:341-348, 463-491`; `userland/neo-init/src/desktop_session/setup.rs:409-418`). Host KATs assert `new y` narrows to New York, Space types on the page, and Space still chooses elsewhere (`userland/setup-core/src/tz_tests.rs:71-89, 238-250`).

- **FAIL — decline/refusal does not preserve the old zone.** Leaving a chosen zone emits exactly `Outcome::Confirm(id)`; `run` calls `tz_page::confirm`, then changes the page to review-only only after a successful confirm (`userland/setup-core/src/lib.rs:501-514`; `userland/neo-init/src/desktop_session/setup.rs:75-88, 363-375`). However, before the kernel confirm result is known, `clock::set_mode` writes `TimeZone`/`RtcLocal` and updates `scene.clock.zone`/`rtc_local` (`userland/neo-init/src/desktop_session.rs:8449-8457`). If `sys_clock_confirm_realtime` refuses (for example, `EALREADY` because another confirm won), `resolve` leaves the clock unconfirmed but does not restore the old mode (`userland/neo-init/src/desktop_session.rs:8343-8372`); the new selection can remain stored and displayed. There is no explicit user decline action on this page. The setup-core KAT only proves the page remains editable after a false result, not that the previous zone is retained (`userland/setup-core/src/tz_tests.rs:147-202`). `clock::set_mode` needs transactional behavior: retain old settings/mode and restore them when the clock confirm is not accepted. The success witness does require the New York confirm, confirmed UTC clock, EDT and New York summary (`tools/xtask/src/login_scenarios.rs:1985-2006`).

- **PASS — settings persistence and volatile store.** The confirm routes through `clock::set_mode`, which calls the checked `settings::set_wm` path for `TimeZone` and `RtcLocal`; the settings path commits, reads the written bytes back, and applies the resulting state (`userland/neo-init/src/desktop_session.rs:8449-8457`; `userland/neo-init/src/desktop_session/settings.rs:298-315, 418-439`). The S3 xtask asserts key 4 is New York id 105, key 5 is local RTC, zero refusals, and exactly two writes for the initial record plus zone update (`tools/xtask/src/login_scenarios.rs:1985-1995, 2020-2026`). On a volatile store, `commit` only updates the in-memory record and logs `writes=0` (`userland/neo-init/src/desktop_session/settings.rs:300-308`); the S2 volatile witness asserts the zero-write logs and rejects any `SETTINGS written` line (`tools/xtask/src/main.rs:21068-21100`). The S3 scenario itself is installed-store, not volatile.

- **PASS — scenario discriminates wrong zone or missing confirm.** The S3 key script types `new y`, chooses its match, then leaves the page (`tools/xtask/src/login_scenarios.rs:443-458`). Its required serial sequence checks the stored id, New York clock zone and offset, EDT, and confirm log; it also requires exactly one confirm (`tools/xtask/src/login_scenarios.rs:1985-2006, 2020-2026`). A wrong-zone result misses the id/name/offset assertions; a missing confirm misses the confirm/confirmed-clock assertions. Scenario registration is `login_setup_tz` (`tools/xtask/src/main.rs:3630-3641`).

- **PASS — off by default.** `neo-init` has `default = []`; `setup-menu` and `setup-tz` are opt-in features (`userland/neo-init/Cargo.toml:207, 225`). The normal build therefore does not compile the S3 page or enable its setup feature.
