# RETURN #107 — OT-87 R4.2 install bundle review

Reviewed merged commit `0d2608f9` (PR #165 squash; commit records the gated head relationship) against `Plans/DISPATCH-2026-10-27-ot87-r4.2-bundle-review-chad.md`. RAG health was healthy and the example semantic query returned results. Targeted verification passed: all 9 `install-bundle-logic-tests` and all 5 `xtask::esp_template_tests` passed. The real `cargo xtask install-bundle` command could not be run in this Windows worker because `LIMINE_DIR` is unset and `/home/neo/limine/BOOTX64.EFI` is absent; the existing reproducibility KAT and PR's recorded real-build evidence are cited below. No source changes were made. Overall: **FAIL** because `slot_map` accepts an overflowing directory-entry offset in unchecked builds instead of refusing the malformed map.

1. **Independent NEOINST1 oracles — FAIL (malformed slot-map offset overflows).** The bundle and slot-map fixtures are hand-laid independently of the writer (`tools/install-bundle-logic-tests/src/tests.rs:24-54,89-169`), and parser KATs reject damaged headers, runs, hashes and slot maps (`tests.rs:172-224,268-322`). But `slot_map` checks `dirent_offset % 32 == 0 && dirent_offset + 32 <= sector_size` using unchecked `u32` addition (`kernel/src/install_bundle_logic.rs:309-339`). Concrete valid-length slot-map input: sector size 512, one entry, zero reserved fields, path `slot/A/kernel`, extent `(first=100,sectors=10)`, directory sector 5, and `dirent_offset=0xffffffe0`. The offset is 32-aligned; the addition overflows. I reproduced the expression: checked arithmetic panics, while `-C overflow-checks=off` wraps the sum to zero and returns `entry_fits=true`. The Cargo profiles do not enable release overflow checks (`Cargo.toml:90-96`), so release can accept the malformed entry rather than return `BadSlotEntry`. Use checked addition (or compare by subtraction after bounding) and add this to the slot-map KAT. The standard 9 KATs pass but do not cover this value.

2. **ESP templates — PASS.** Both S=512 and S=4096 images are formatted FAT32 with 4 KiB clusters and fixed valid timestamps (`tools/xtask/src/esp_template.rs:94-131`); tests assert FAT32's minimum cluster count, correct paths/extents/directory entries, and the map read-back (`tools/xtask/src/esp_template_tests.rs:15-89`). The read-back is our own `geometry`/`list`/`chain`/`slot_entry` implementation, not fatfs (`esp_template.rs:177-223,273-315,404-430`), and it compares FAT copies and rejects non-contiguous chains; the explicit non-contiguous-chain KAT passes (`esp_template_tests.rs:93-158`). `Dockerfile:77-83` pins the controlled build environment to Limine `v8.6.0-binary`; the PR body reports byte comparison of BOOTX64.EFI against that Limine build and mtools inspection of both templates. `LIMINE_DIR` is overrideable, so a different local input deliberately changes the resulting bundle hash; the controlled Docker/CI path is pinned.

3. **Slot sizes — PASS for R4.2's template scope; R4.3 dependency noted.** Each slot reserves 72 MiB for the kernel and 44 MiB for each of four modules, 496 MiB total across both slots (`tools/xtask/src/esp_template.rs:36-43`). The fit KAT includes Limine and the padded config, leaves more than 8 MiB free, and checks the measured kernel/modules against at least 1.5× headroom (`tools/xtask/src/esp_template_tests.rs:163-190`); it passed. R4.2's bundle builder does not consume current kernel/module artifacts (`tools/xtask/src/install_bundle.rs:109-128`), so it cannot reject a future oversized binary. It also does not copy or truncate a deployment. The fail-closed size check belongs in the R4.3 slot writer before writes; THINK §7.1 defines a maximum-size extent writer and §7.2 records the current deployment budget (`docs/THINK-2026-10-27-ot87-installer.md:710-732,738-760`). This is a stage boundary, not a demonstrated R4.2 truncation.

4. **Bundle pin and reproducibility — PASS, with CLI rerun limitation.** `assemble` constructs the five ordered parts, verifies each part hash/length and slot map, expands sparse images against source bytes, and is deterministic for the same inputs (`tools/xtask/src/install_bundle.rs:28-89`). `check_staged` refuses an incorrect whole-bundle pin (`install_bundle.rs:95-105`). The reproducibility KAT assembles twice and compares bytes, accepts the correct pin in either case, and refuses changed bytes or a different seed (`tools/xtask/src/esp_template_tests.rs:194-224`); it passed. Actual CLI uses `LIMINE_DIR/BOOTX64.EFI` and a generated NeoFS seed (`install_bundle.rs:109-128`), so I could not rerun it without the pinned Limine binary in this environment. PR #165's Tests section records two identical real builds with bundle hash `f7b6f4fb…48f7401c`; the fixed FAT timestamp and deterministic seed construction show no time/path fields are embedded. The bundle hash is the SHA/BLAKE3 contract R4.3 compiles and checks.

5. **Vendoring — PASS.** `third_party/fatfs/LICENSE.txt` contains the MIT license and copyright; `VENDORED.md` records upstream URL and full commit `38b3a7950bf0e765e34286d1dfe76c519ee347e2`, manifest/source deltas, and maintenance path (`third_party/fatfs/VENDORED.md:1-27`). The workspace excludes the crate and only xtask depends on it; no kernel or userland dependency is added (`Cargo.toml:64-71`; `tools/xtask/Cargo.toml:20-28`). The vendored version and commit match THINK §11.2 (`docs/THINK-2026-10-27-ot87-installer.md:845-858`).
