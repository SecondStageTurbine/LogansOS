# RETURN: cross-family adversarial review of CP-41 (kernel MXCSR at entry)

**Reviewer:** Chad (Codex family)  
**Reviewed branch:** `origin/claude/eloquent-bell-8eu39r` at `2bc4132e`  
**Base:** `origin/main` at `57261d66`  
**Verdict:** **MERGE-WITH-NITS**

No merge-blocking finding survived re-verification. The entry-local save/reset/restore order is correct on the legacy FXSAVE stub and on the `xsave-fpu` stub's runtime FXSAVE and XSAVE paths. The user image is captured before the reset, Rust runs after the reset, and the saved image is restored before `iretq`. A timer/syscall body that context-switches does not break this: the per-thread context image may temporarily contain the kernel-default MXCSR, but resuming the suspended entry frame reaches its own final FXRSTOR/XRSTOR and restores the original user value.

## Findings

### N1 — Low: `new_current` describes a fuller x87 reset than it constructs

**Location:** `kernel/src/arch/x86_64/fpu.rs:109-125`

`FpuState::new_current()` says the image contains x87 state "as after `fninit`", but it starts with a live FXSAVE/XSAVE snapshot and overwrites only FCW, FSW, abridged FTW, and MXCSR. FOP/FIP/FDP and x87/SSE/AVX payload bytes remain from the creating context. Setting FTW to zero makes every x87 stack register empty, so the leftover payload and pointers cannot affect CP-41 kernel arithmetic; this is a wording/adjacent register-hygiene issue, not an MXCSR-entry defect.

The parallel CP-40 branch (`5238f494`) replaces creator snapshots with a constructed initial image and will conflict in this function. Resolve that integration in favor of CP-40's `new_initial()` while retaining CP-41's entry resets. Repro/inspection: compare the four writes at `fpu.rs:123-125` with the 512-byte architectural FXSAVE legacy region; only bytes 0..=4 and 24..=27 are rewritten.

## Required adversarial checks

1. **Entry coverage — pass.** I inventoried all five `global_asm!` owners (`context.rs`, `fpu.rs`, `idt.rs`, `syscall.rs`, `timer.rs`) and every `extern "x86-interrupt"` handler. Both syscall variants reset MXCSR at `syscall.rs:563` and `:646`; both timer variants do so at `timer.rs:134` and `:255`. `enable_sse()` installs the cold default on the BSP and every AP (`mod.rs:108-148`). The recoverable browser-runtime ring-3 page-fault kill path resets before it can switch away (`idt.rs:346-366`). New kernel/user thread images get default FCW/FSW/FTW/MXCSR (`fpu.rs:109-125`), and first-run threads restore that image under `xsave-fpu`. Other exception handlers either halt; the returning breakpoint handler contains only diagnostic/integer work and preserves the interrupted state. `swapgs_irq_entry` is correctly unchanged on this base: it neither saves FPU state nor schedules, and its TLB/reschedule/block/USB/accelerator bodies and their immediate completion drains contain no floating-point arithmetic. Loading 0x1F80 there would corrupt the interrupted user MXCSR. CP-38 must add the reset only after its IRQ FPU save.

2. **x87 decision — pass, with N1 above.** I built the `phase9-real-quant` CP-41 kernel and disassembled the 30,632,160-byte ELF with the toolchain's `llvm-objdump`. The complete set of mnemonics beginning with `f` was: `fninit` twice (BSP `_kernel_start`, AP `ap_entry`), `fnstcw` once (the test-only float probe), `fxsave` once, and `fxrstor` once. There was no compiler-generated x87 arithmetic in the kernel or linked `compiler_builtins`. The probe's `fnstcw` is the non-waiting form and executes no arithmetic. Skipping `fninit` in the hot stubs is safe for the reviewed configuration; any future x87 use must change this invariant.

3. **Save/reset/restore ordering — pass.** ELF disassembly confirms `syscall_entry` calls `fpu_save_area_asm`, then executes `ldmxcsr KERNEL_DEFAULT_MXCSR`, then calls `syscall_dispatch`, then calls `fpu_restore_area_asm`, and only then returns through `iretq`. `timer_isr_entry` has the same order around `timer_rust_handler`. In the non-feature assembly source, FXSAVE precedes the reset and FXRSTOR follows the Rust body. Standard-form XRSTOR is invoked with x87|SSE|AVX in RFBM; MXCSR is loaded whenever SSE or AVX is requested even if the saved `XSTATE_BV` marks the component initial. FXRSTOR always reloads the legacy MXCSR field. Thus a user value cannot reach the body and the kernel default cannot leak back to ring 3.

4. **Faults in the stub — pass.** `KERNEL_MXCSR=0x1F80` has no reserved bits and is accepted on every SSE-capable x86-64 CPU. The stack save areas are 16-byte aligned for FXSAVE and 64-byte aligned for XSAVE; the XSAVE size and RFBM mask come from CPUID/XCR0 and the buffer is cleared before XSAVE, so reserved header bytes cannot poison XRSTOR. A hostile live MXCSR with reserved bits cannot be established by ring 3: LDMXCSR/FXRSTOR/XRSTOR validate it when loaded. Sticky flags plus unmasked exceptions do not make FXSAVE/XSAVE or the restore itself deliver `#XM`; the exception is taken by a subsequent faulting SIMD operation. `fninit` is the non-waiting form, so a pending unmasked x87 exception cannot fault the cold reset. The page-fault cold reset intentionally discards the state of a thread that is about to be killed.

5. **Context switches — pass.** With `xsave-fpu`, `context_switch*` saves the live default-MXCSR kernel state into the outgoing per-thread image and restores the incoming image. If the switch occurs inside a syscall/timer frame, returning to that frame later performs the authoritative entry-local restore before user return. Without `xsave-fpu`, switches copy no FPU state: a first-run thread sees the kernel default loaded by boot or the timer entry; an already-suspended user thread resumes inside its own entry frame and restores its own stacked FXSAVE image. No path transfers one thread's MXCSR to another. The non-`xsave-fpu` design still has its pre-existing broader SIMD-register isolation limitation, outside CP-41.

6. **`FpuState::new_current()` edits — pass for CP-41, with N1.** FCW is at legacy offset 0, FSW at 2, abridged FTW at 4, and MXCSR at 24; the writes use those offsets. They do not touch the XSAVE header at 512, which was zeroed before XSAVE and then authored by the instruction. No caller needs a faithful live copy: all four callers construct a new execution context, while `adopt_current` is overwritten by the first switch-out before any restore. `SYS_THREAD_CREATE` and `SYS_SPAWN` now start with the default environment instead of accidental creator inheritance. That differs from POSIX `pthread_create`, but the native ABI does not promise POSIX fenv inheritance, and preserving the old behavior would also preserve the creator-snapshot register leak addressed by CP-40. The browser PAL/private pthread layer should document default-fenv creation if it exposes `fenv` later.

7. **Discriminator validity — pass, with stated coverage gap.** The ring-3 probe places `fldcw`, `ldmxcsr`, `syscall`, `stmxcsr`, and `fnstcw` in one inline-asm block, so user floating-point code cannot consume the hostile state before entry. The kernel uses `black_box` operands plus an explicit `sqrtss`, preventing constant folding of the arithmetic. It checks the inherited control bits, fourteen result bit patterns, and exact user MXCSR/FCW restoration. The kernel scenario also asserts the runtime save path, so `-cpu max` must use XSAVE and qemu64 must use the helper's FXSAVE fallback. QEMU TCG's lack of `#XM` delivery means the trap half is not dynamically proven, but observing MXCSR 0x1F80 before the first operation plus the hostile-state result oracle proves the masks/control state were installed. Real-silicon `#XM` remains a documented coverage gap, not a vacuous pass.

8. **Other structural checks — no additional finding.** `KERNEL_DEFAULT_MXCSR` is emitted as the intended RIP-relative memory operand; disassembly resolves both stubs to it. Return-value preservation across the helper calls is correct. The reset occurs after the FPU save, so it cannot alter the saved user image. The test syscall is feature-gated to `neo-test`. `git diff --check` and `cargo fmt --all -- --check` pass.
