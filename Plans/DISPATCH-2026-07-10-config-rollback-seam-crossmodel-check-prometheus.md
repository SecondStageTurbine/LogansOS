## The problem, self-contained (this is all the internal context you need)
Two future subsystems, each ratified in shape, must agree on one interaction:

- **The config store (subsystem A):** ONE typed, per-domain, capability-gated, file-backed key-value store under `/neofs/.arthur/config/`. Arthur, the `neo>` shell, and the future GUI are all *views* over this one store (no split-brain second registry). Owner-authored settings; the store is a *policy mirror*, never the authority (the kernel capability is). Today's `grants.json`/`stakes.json` are the conforming seed.
- **The update/rollback model (subsystem B):** never mutate the running system — build the next OS state as a complete verified artifact (a **deployment** = kernel + userland root + base config) *beside* the current one, flip a boot pointer, keep the previous deployment(s) bootable, bit-for-bit. Rollback = boot a previous deployment. This is the whole-system generalization of our kill-switch discipline.

**THE SEAM YOU MUST DESIGN:** when the owner rolls the *system* back to a previous deployment, **what happens to their config?** And conversely — how does changing/reverting a *setting* relate to changing/reverting a *system version*? Design the interaction from first principles + prior art; recommend a shape.

## ISCs — reason it out independently, then recommend
- **ISC-1 — where does config live relative to a deployment?** Inside the rolled artifact (travels with the deployment), beside it (separately versioned), or some split? Reason it; don't guess.
- **ISC-2 — the default behavior on a system rollback (the load-bearing UX call).** When the owner rolls the OS back, do their **settings survive**, or do they **revert with the system**? Justify from *owner intent* and from prior art — how do the immutable-OS systems actually handle user config across a rollback? (Ground firsthand: Fedora Silverblue/rpm-ostree's `/etc` handling and `/var`; openSUSE MicroOS/transactional-update's `/etc` overlay + snapshot semantics; and the cautionary case of an OS update that *destroyed* user data. Read these directly — **no summarizing fetch** for exact mechanics; a mangled claim here poisons the design.)
- **ISC-3 — the version-skew hazard.** A setting written against a *newer* config schema, when the owner rolls back to an *older* base that doesn't define that key. What is the safe behavior — reject? ignore? hold-inactive? crash? Pick one and justify (fail-safe, never fail-boot).
- **ISC-4 — are the two axes independent?** Is "roll back the system" separable from "roll back a setting," or are they coupled? If separable, what's the mechanism that keeps them independent?
- **ISC-5 — the cross-model payoff: what would a Claude-style analysis likely MISS?** This is the highest-value section. From your (different-model) vantage, name anything the "one store + reversible deltas + kill-switch discipline" framing might systematically over- or under-weight: a failure mode, a simpler alternative, a user-intent case, a security or crash-consistency hole, a complexity the Claude framing would rationalize away. Be adversarial to the obvious answer. If after honest analysis you *agree* with the obvious shape, say why it survives your scrutiny — that's a valid (and valuable) corroboration.
