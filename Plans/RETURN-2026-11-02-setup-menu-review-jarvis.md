# Relay 284: setup-menu THINK review

Reviewed design head: `a514ea631121a9f53f759d76af78c4ddd9a61d4e` (`origin/dexter/setup-menu-think`).
Compared implementation claims against `origin/main` head `c65ee28ee9bb978db6e69f4224a363e114752ff7`.

- **PASS — Security model (§4.1, §4.4).** The WM is the existing settings writer (`userland/neo-init/src/desktop_session/settings.rs:2-3,172-199,311-315`); client requests are checked against the settings-app identity and key policy (`:283-305`). The clock authority requirement is specified by the time-zone THINK (`docs/THINK-2026-11-02-time-zones.md:56-64`), and the proposed setup wizard runs before clients and uses the WM route. The confirm syscall is not implemented on this reviewed `main`; S3 must enforce the stated input-system-authority check. Existing installer calls likewise require the installer handle (`kernel/src/arch/x86_64/syscall.rs:9033-9072`).
- **FAIL — Screen readiness claims (§3).** Language and Keyboard are correctly marked hidden stubs; Comfort keys 1/2 exist and apply live (`userland/settings-core/src/lib.rs:72-85,112-137`; `userland/neo-init/src/desktop_session/settings.rs:356-360`). Time zone and Try/Install are correctly conditional on their future lanes. Network's “wired read-only works” overstates `main`: DHCP and link snapshots exist (`kernel/src/net/dhcpv4.rs:365-374`; `kernel/src/net/identity.rs:227-254`), but `main` has no per-interface status syscall (the design itself says so at §3 row and §3.3). S4 must land before a wizard can display wired status. Concrete input: on current `main`, boot with a CDC-ECM lease (`10.0.2.15`); no userland syscall can retrieve the link/lease for the page. Reword the row as “kernel state available; wizard status needs S4.”
- **PASS — Try vs Install persistence (§2.3, §2.4).** The document distinguishes volatile Try state, per-boot Install choices, restart-required cross-mode choices, and the v1 installed-first-boot record. The no-disk-write guarantee is explicit and has a whole-disk before/after oracle. It depends on S2 selecting `StoreMode::Volatile` before `settings::load`; current `settings::load` writes an initial record when none exists (`userland/neo-init/src/desktop_session/settings.rs:172-199`), so that ordering and the volatile write bypass are mandatory parts of the gate.
- **PASS — Rungs and kill-switches (§5).** Each S1–S7b rung names a scenario/oracle and a feature-off behavior; S1 pins the current desktop control, S2 pins the legacy record, and kernel-touching S4 calls out the broader gate. S1/S2 and later content dependencies are stated. The off-path claims are testable against the named controls.
- **FAIL — §6 falsifier already present (#2).** Until the final settings page exits, the design defers the one clock confirm (§2.2, §3.4). On `main`, action-log timestamps come directly from `CLOCK_REALTIME` (`userland/neo-init/src/desktop_session/action_log.rs:75-82`), while `CLOCK_REALTIME` is currently RTC local wall time without an offset (`kernel/src/arch/x86_64/syscall.rs:7374-7395`). Thus setup-page log records made before confirmation are interpreted as UTC and remain wrong after the clock is corrected. Concrete input: set `RtcLocal=1`, boot with the RTC at `2026-11-01 01:59` in `America/New_York`, then make a page choice before leaving the settings pages; its action-log timestamp uses the unconfirmed local value. S3 should either confirm before logging zone-dependent events (with a safe Back/change design), defer timestamping those events until final confirmation, or explicitly accept and test this limitation. Other §6 conditions are not established by current `main`; notably the DHCP client already stores its interface id (`kernel/src/net/dhcpv4.rs:85-93,238-245`), so a per-interface status snapshot can expose existing state rather than require new runtime bookkeeping.
