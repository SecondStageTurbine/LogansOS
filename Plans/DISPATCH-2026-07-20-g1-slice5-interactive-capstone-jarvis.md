## What Slice 5 is — the loop closes
Slices 1–4 built the pieces; **Slice 5 wires them into one live interactive loop and proves it end-to-end:**
> a real userland surface a user **types into**, on screen — keystroke → InputFocus routes to the focused client → the client renders the glyph into its `SharedPixelBuffer` → `commit` → the compositor composites the **damaged region** to the framebuffer → the typed character appears.

This is the "JC sits down and uses it" moment: the first genuinely *interactive* surface. Keep it minimal — a **text/workfield surface that echoes typed characters** (a real interactive surface, not a full app; the app shelf comes later). The point is the *loop*, proven, not a feature-complete editor.

## The two mechanisms Slice 5 adds
1. **The interactive client** — a userland surface (extend the Slice-2/3 `neo-worker` client pattern) that: creates a `WORKFIELD_ROOT`/`TEXT` surface (Slice 2), maps its `SharedPixelBuffer` RW (Slice 3), holds the `InputFocus` **RECEIVE** root (Slice 4 — the client owns RECEIVE, the compositor gets ACTIVATE-only; **the no-snoop inversion is load-bearing — reaffirm it, the compositor never sees a keystroke**), and on each received key event renders the glyph into its buffer + `commit`s.
2. **Damage/pacing (the Slice-5-proper mechanism).** On a keystroke the client marks a **damage rectangle** (the changed glyph cell), and the compositor recomposites **only the damaged region**, not the whole surface — bounded per-frame work. Prove: (a) a single keystroke damages exactly its cell (not the full surface), (b) the present is paced (no unbounded per-keystroke full-screen repaint). This is the efficiency layer that makes real interactivity viable and is the last G1-ladder mechanism.

## The falsifiable proof (Phase 1 — QEMU)
A QEMU scenario that: injects a known keystroke via the HID path → asserts it routes through `InputFocus` to the focused client (and **the compositor's channel carries no event byte** — the Slice-4 no-snoop property, re-asserted in the integrated loop) → the client renders the glyph → `commit` → the compositor composites the **damage rect** → **the framebuffer shows the exact glyph pixels at the expected cell** (assert the on-screen bytes, and assert the damage rect covered only that cell). A second keystroke advances the cursor cell. Falsifiable end-to-end: a break anywhere in the loop fails the on-screen pixel assertion.

## Kill-switch + byte-oracle + I-14 + CP-bank (required)
- **Kill-switch (Rule-1):** compositor/interactive-loop **off** ≡ the v1 console path bit-for-bit (extends the existing Slice-1/2 kill-switch; armed regression).
- **Byte-oracle (I-12):** if Slice 5 adds a **damage-rect** on-wire layout (or a commit-with-damage envelope), hand-lay a fixture; if it rides the existing Slice-2 `commit` verb, state that.
- **I-14:** the interactive client is a real app — a client fault (wild render, never-commits, floods keystrokes) is contained: bounded per-client input queue (Slice-4, already), bounded damage handling, no governance lock on the composite path; a misbehaving client degrades its own surface, never governance or other surfaces.
- **CP-bank (`docs/concurrency-pitfalls.md`):** the input→render→commit→composite loop crosses the HID-delivery (Slice-4) + present (Slice-1) seams; confirm no new IF-off spin, the damage/commit vs composite handshake is race-free (a commit racing a composite doesn't tear or read a half-rendered buffer — the Slice-1 fence/epoch discipline covers it; confirm), no CP-29/I-16 regression.
