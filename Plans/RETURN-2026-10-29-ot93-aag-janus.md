**Verdict: FAIL.** The Ready-in-syscall guard closes the reported rendezvous leak. It does not establish bounded termination of survivors, and process wait completion still precedes their termination. RAG health was healthy. This is a source/interleaving review; I did not rerun the author's QEMU sweep or independently reproduce its +50-frame control result.

1. **PASS — production `in_syscall` window.** `kernel/src/arch/x86_64/syscall.rs:605` masks IF at SYSCALL entry; both assembly variants reach `syscall_dispatch` without enabling it (`:753`, `:852`). `:983` enters the syscall before dispatching anything that can yield. `kernel/src/sched/scheduler.rs:1567` sets the flag under the local scheduler lock. `syscall.rs:1360` disables interrupts before `leave_syscall`; `scheduler.rs:1585` clears the flag and checks the process in the same critical section. Both returns actually use IRETQ (`syscall.rs:842`, `:945`); there is no separate production SYSRET path to miss. An IRQ cannot put the cleared tail into Ready before IRETQ. Ring-3 exception containment does not return (`kernel/src/arch/x86_64/idt.rs:621`); ring-0 faults halt. The explicit test-only exception is covered in item 6.

2. **FAIL F1 — an infallible wait can remain unbounded.** `kernel/src/sched/scheduler.rs:2099` has no killed/retiring check and no timeout. `kernel/src/drivers/block/virtio_blk.rs:825` retries queue submission indefinitely, and `:907` parks awaiting device completion without a deadline. Concrete interleaving: CPU 0 publishes the kill, completes its token/ready scans and the final token scan (`kernel/src/sched/process.rs:4317`, `:4343`, `:4431`). CPU 1 was running in a file-I/O syscall, so it survived. Its reschedule IPI interrupted ring 0 and performed no exit (`idt.rs:969`). CPU 1 subsequently submits I/O and parks at `virtio_blk.rs:907`; the device never posts a used entry. The thread never reaches `leave_syscall`, and no further scan or deadline wakes it. Its process anchor and kernel stack remain indefinitely. The same missing bound applies to the submission retry loop if an existing request never completes. Do not fix this by simply freeing a DMA buffer; cancellation must preserve device ownership until quiescence. A discriminator should hold completion past kill, then verify a specified bounded cancellation/quiescence result. This is a failed dispatch requirement even though device-wait cancellation was already limited on main.

3. **PASS — ordering of the refused user waits and the return check.** `process.rs:4317` publishes with AcqRel before the scans. `scheduler.rs:1546`, `:2037`, `:2175` check through the thread's own anchor while holding the scheduler lock used to publish a park: if a park checks clear first, the subsequent scan sees the parked thread; if the scan passed first, the check observes the published flag. The caller's endpoint/futex/wait-any guard remains held until the scheduler owns the blocked thread. `scheduler.rs:1617` scans after publication, releases all scheduler locks, then sends IPIs. A return check that ran first stays IF=0 through IRETQ; an ensuing IPI is handled in ring 3. The flag-before-`FORCED_ALIVE` increment gap ends before the scans/IPIs, so it does not defeat that argument. Migrating threads can miss a finite per-CPU pass as acknowledged in the PR; their next syscall/ring-3 tick still checks. This is not a bounded-exit proof for item 2.

4. **PASS — no new reaper lifetime hole for a spared thread.** `kernel/src/sched/thread.rs:235`, `:239` keep the process/Pmap anchors until `Thread::free`; ordinary user creation installs the anchor (`process.rs:3096`, `:3523`). The Ready scan excludes `in_syscall` (`scheduler.rs:319`, `:1527`). A boundary exit publishes its zombie with the scheduler lock held through the switch (`:1750`, `:1810`), and `reap` must acquire that lock before removing it (`:2856`). The lock releases on the new stack. Process deregistration therefore does not free the survivor's stack, Pmap, or join registry. In particular the raw join registry/done-word remains pinned by the calling thread's anchor (`process.rs:3595`). Retained resources in F1 are a liveness failure, not evidence that these anchors are absent.

5. **FAIL F2 — `sys_wait` can finish before the survivor leaves the kernel.** Concrete interleaving: a third process is already waiting on the victim; the victim is held Ready inside its send, as in the new discriminator; another process calls `terminate`. `kernel/src/sched/process.rs:4374` removes the registration, then `:4449` calls `complete_process_waiters(..., None)` and `:4455` publishes EXITED while the sender still has not resumed. `:2980` wakes the waiter with ESRCH immediately. A new wait also sees the removed registration and returns ESRCH (`:2816`). The survivor can still execute kernel code after this observable completion; the test itself releases its hold only at `:4476`. This does not create an anchor UAF (item 4), but fails the dispatch's wait-before-kernel-exit criterion. If ESRCH intentionally means only 'registration removed', document that weaker contract and provide a separate completion barrier; otherwise defer completion/removal until the last survivor has left. Join's refusal path returns ESRCH rather than looping (`:3655`); a raw done-word remains pinned by the joiner's process anchor. F1 can still prevent eventual physical reclamation.
