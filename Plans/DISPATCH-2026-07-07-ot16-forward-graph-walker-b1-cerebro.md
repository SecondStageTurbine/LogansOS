## Why B1 first, and why it's low-risk
`kernel/src/ai/forward_logic.rs` hardcodes the Qwen2 model-graph orchestration in ring 0 — a shift to any new architecture (the Gated-DeltaNet hybrid; a future model) is currently a *kernel patch* with `if qwen / if delta_net` branches (the Article 5.7 anti-pattern applied to model graphs). OT-16 makes the forward *graph* **data-driven from the `.neom`**: a new architecture becomes a new `.neom` schedule, not a kernel branch. B1 builds the walker and proves it is a **behavior-preserving refactor** — the ops are already proven/byte-oracled; the walker is a typed enum-dispatch table over them, NOT a graph VM (no ring-0 NN compiler; ANSPEC §19.2 / Article 6.6 line).

## ISCs (THINK §6.1 B1 decomposition)
- **ISC-1 — Layer-kind schedule data structure + `.neom` header section.** The `LayerSchedule { version, layer_count, layers: [LayerDescriptor] }` shape (THINK §1.2): an ordered typed table, `LayerKind::Qwen2AttentionFFN` the only variant B1 needs (the `GatedDeltaNetLinear` variant is *declared* for B2 but unimplemented — reject it at load in B1, don't stub-execute it). - **ISC-2 — The schedule walker** dispatching to the existing proven Qwen2 ops (`ai/ops/` — matmul/RMSNorm/RoPE/SwiGLU/softmax/attention stay compiled-in, untouched). The walker *replaces the hardcoded per-layer loop* with a walk over the schedule. Same ops, same order, driven by data.
- **ISC-3 — Load-time validation (the 7 invariants, THINK §2.2):** version gate, layer-count bounds (`0 < n <= MAX_LAYERS=128`), known-kinds-only, config consistency, weight-tensor presence, state budget, no-dynamic-control-flow. **A malformed/hostile schedule is REJECTED at load with a typed `ModelError`, never crashes ring 0** — validate once during `.neom` load, before any forward executes.
- **ISC-4 — The double kill-switch (D3 — the real acceptance test):**
  - **Kill-switch 1:** feature `ot16-graph-walker` **off** ≡ the exact current hardcoded `forward_layer_with_attention_output()` loop, bit-for-bit. No path changes.
  - **Kill-switch 2 (the load-bearing proof):** walker **on** + a Qwen2 schedule (24 × `Qwen2AttentionFFN`) ≡ hardcoded output, **byte-identical.** Host KAT: run hardcoded → capture bytes; run walker-with-equiv-schedule → capture bytes; byte-identical = pass, any diff = walker bug. The OT-30 top-1 parity oracle stays green (same model, same tokens).
- **ISC-5 — OT-34 threaded-matmul compatibility.** Threading is op-level, not schedule-level (THINK §4.2) — the walker dispatches to the *same* OT-34 deterministic column-partition matmul. Prove byte-identity through the walker at NEO_SMP=4 (the QEMU parity scenario), i.e. the OT-34 determinism guarantee survives the walk.

## Byte-oracle (MANDATORY — this defines an on-disk byte layout)
The new `.neom` schedule header section is an **on-disk byte layout** ⇒ the format/ABI standing rule fires: ship an **independent hand-laid-out byte example** of a small schedule (e.g. 2× `Qwen2AttentionFFN`) — the exact header bytes, hand-computed from the spec, asserted against independent of the writer/reader. Round-trip (`write_then_read == input`) is NOT sufficient alone (a writer+reader built from the same spec agree even when both are off-spec — the ADR-028 `.neom` v1 lesson). This is the **`.neom` format-version bump**, an **ADR-028-family change** (THINK §1.4 open item; §6.4 ratification point 2 — proceed with the byte oracle at B1). Name it in a new/amended ADR.

## Fault-containment note (I-14, inference-path kernel mechanism)
