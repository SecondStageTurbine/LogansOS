## The question (and the exact divergence to resolve)
Janus's cross-check flagged: *"Keep iced out of the compositor, but don't prematurely reject its permissive widget/layout/accessibility machinery for applications."* So: **do we adopt/adapt iced's widget-layout-a11y machinery to build our apps (password-manager GUI, browser chrome, the shelf), or build an own app-toolkit?** iced is **MIT** (permissive → adoptable), which is why it's not auto-rejected. The tension is *impedance*: iced assumes a hosted renderer (`wgpu`/`tiny-skia`) + a `winit` event loop, whereas our world is a **cap-native `#![no_std]` userland**, an **own-Vello renderer**, the **G1 surface protocol** (create/commit/damage), and **kernel-routed InputFocus** events. The spike answers whether iced's *core* rides our seam or fights it.

## The load-bearing feasibility claim to TEST (the PoC)
> **Can iced's renderer-neutral core (`iced_core` layout + widget tree) be driven by an OWN Vello backend rendering to a pixel buffer, fed by OUR event source — without dragging in iced's `wgpu`/`winit` shell?**

Build a **minimal offscreen PoC** (host, no OS integration needed to answer feasibility): implement (or stub) iced's renderer/backend seam with an own-Vello (or a trivial software rasterizer if Vello wiring is out of timebox) backend, lay out + render **one real widget** (e.g. a text field + a button — exactly what the password-manager unlock needs), and feed it **synthetic input events shaped like our `InputFocus`/`InputEventV1`** rather than winit events. Assert the pipeline produces the expected pixels. If the PoC proves infeasible within the timebox, the *reason it's infeasible* (where iced welds to wgpu/winit/std) is itself the deliverable — a negative result is a valid spike outcome.

## What the analysis must cover
1. **iced's layering** — is there a genuine renderer-neutral core (`iced_core` / the `Renderer` + `text::Renderer` traits) our own-Vello backend can implement, or is the widget set welded to `iced_wgpu`/`iced_tiny_skia`? How much of iced is the *shell* (winit/event-loop — which we'd replace with the G1 seam) vs the reusable *core* (layout algo, widget traits, `accesskit` a11y integration)?
2. **`std` dependence** — iced targets hosted OSes. How much of the *core* (layout, widget tree, a11y) is `std`-bound vs `no_std`-portable to our userland? What would porting cost?
3. **The event-loop impedance** — iced's runtime is `winit`-driven. Can its update/view/message loop be driven by our event source (kernel-routed input events + a commit-on-frame model) instead, or is the runtime too coupled to winit?
4. **Accessibility** — iced integrates `accesskit`. Is that machinery reusable? (a11y is a real need — the ratified WCAG-AAA floor — that we'd otherwise build from scratch; reusing iced+accesskit could be a large win.)
5. **The recommendation** — **adopt iced-core-over-our-seam** / **hybrid (borrow iced's layout algo + accesskit, own the widgets)** / **own-toolkit-from-scratch** — with the effort estimate + the risk of each, grounded in what the PoC actually showed.
