## ISCs — the buildable design (both of you answer ALL of these, from your own vantage)
- **ISC-1 — the protocol, concrete.** The actual surface/session verbs a client uses (create-surface, attach-buffer, commit, present, focus-request, destroy…) and their carrier: syscalls? the existing IPC primitives? What is a **kernel object** vs **userland compositor state**? Keep the kernel policy-free (Article 6.6 — mechanism only); the compositor is a userland process. Specify each verb's inputs/outputs/caps-required precisely enough to write the ABI doc from.
- **ISC-2 — the cap taxonomy made real.** Map SurfaceCap/BufferCap/InputFocusCap/PresentFenceCap/DecorationCap (+ CaptureCap absent-by-default) onto our **existing** capability system (I-15 file/handle caps, the derive/grant/revoke/attenuate graph): which are genuinely **new kernel cap kinds**, and which are conventions over existing caps? State the derivation rules (who mints a SurfaceCap; can a client attenuate a BufferCap; what does revoking an InputFocusCap do mid-frame) and the I-15 subset invariant per kind.
- **ISC-3 — buffers, zero-copy, damage.** Client-allocated buffers shared **by capability** (no dma-buf-style FD handshake): the allocation path, how a BufferCap grants the compositor read access without a copy, the commit/swap discipline (who owns the buffer when), **damage tracking** (per-surface damage rects → minimal recomposition work), and the software composition loop to the kernel framebuffer (the current fb primitives are the floor). State the memory-safety story (a client scribbling its own buffer mid-composite must corrupt only its own pixels, never the compositor).
- **ISC-4 — present pacing + honest liveness.** Frame pacing on the software path (what "vsync" means without display hardware timing — QEMU and bare-metal both), PresentFenceCap semantics (when a client may reuse a buffer), and the tie to **latency-is-beauty** + the measured Liveness Thread: present events are real measured events, never theater (no fake frame callbacks).
- **ISC-5 — input routing = the cap check.** Focus is a capability check — input-security and input-routing are ONE code path (the ratified line). The existing USB-HID cap-gated input path is the seed: how a key event routes to the focused surface's owner, what the InputFocusCap actually gates, focus transfer, and the no-snooping property (X11's global-input anti-pattern must be impossible *by construction*, not by policy).
- **ISC-6 — the seams, honest.** (a) **OT-22 multi-principal:** G1 ships single-principal, but the protocol must be **multi-principal-ready** — name exactly what changes when OT-22 opens (per-principal surface namespaces? cap provenance on input events?) so nothing needs a redesign. (b) **G0 → G1 migration:** G0 draws raw on the framebuffer with no compositor; how does the G0 Workfield become a composited surface with minimal rework (Chad's G0 spec deliberately named its regions like future surfaces — use that). (c) **The text engine:** a T0 text surface is a client buffer like any other — confirm the zero-copy path fits. (d) **I-14 (required):** the compositor is userland — enumerate what a compositor fault can and cannot touch (it must never stall/corrupt governance; the kernel framebuffer write path's containment; no governance lock on any composite path).
- **ISC-7 — kill-switch + build decomposition + forks.** Kill-switch: compositor-off ≡ today's raw console **bit-for-bit** (the v1 console path untouched when off — state the proof shape). Then the smallest-first build decomposition (slice 1 = ? — one surface, one client, composite-to-fb?) through full G1, each slice gated; and your honest forks + recommendation each (e.g. syscalls-vs-IPC as the carrier, scene-graph granularity, damage-rect vs full-repaint first slice, where DecorationCap lands in v1).
