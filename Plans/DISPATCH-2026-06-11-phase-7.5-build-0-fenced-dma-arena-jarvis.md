## 0. The decision this build makes
The lane is forbidden from granting any connectivity driver DMA until I-14(c)'s guard exists. This build ships the **(c1) half** of that guard — containment against *our own* errant descriptor programming, the realistic near-certain failure class of a from-scratch xHCI/NIC bring-up. A **fenced DMA arena**: a pre-registered physical region from which connectivity-driver DMA buffers are allocated, plus a **validation gate** at the descriptor-programming boundary that refuses any address not inside the arena before it can reach a device. This is the Linux restricted-DMA-pool / swiotlb pattern. It is a **strict overlay**: every DMA user already flows through `DmaBuffer`, so this is an arena-backed *allocation variant* + a validation function, not a refactor. **(c2) — the misbehaving device — is explicitly NOT addressed here; it is 7.5-V (VT-d).** Honesty in the ledger: this build closes I-14(c1), not I-14(c2).

## 1. The arena (minimal, fenced, kill-switchable)
- **A pre-registered arena region.** At init, reserve a bounded contiguous physical region (size configured; sufficient for the USB/NIC ring + buffer working set). Record `[base, base+len)` as the fence bounds.
- **Arena-backed allocation.** `DmaBuffer::alloc_in_arena(len)` (or an `arena: bool`/region parameter on the existing path — your call, minimal) allocates from the arena, not the general frame allocator. Connectivity drivers (7.5-A onward) use *only* this. Existing DMA users (GPU/NVMe/AHCI/virtio) are **untouched** — they keep `alloc_zeroed`, outside the arena, exactly as today.
- **The validation gate (the (c1) guard).** A checked boundary — `arena::validate(phys, len) -> Result<(), DmaFault>` — that every connectivity-driver DMA-address-into-a-descriptor passes through before the device sees it. It asserts `[phys, phys+len) ⊆ [base, base+len)`. The gate is the *one* path by which a connectivity driver hands an address to hardware (the `mint`-style single-gate discipline: a driver that skips it cannot reach the device). An address outside the arena = `DmaFault`, refused, never programmed.
- **Kill-switch (Rule 1, REQUIRED).** Arena-off (feature-disabled / not initialized) ⇒ behavior is **bit-for-bit today**: `DmaBuffer` allocates as it does now, no validation gate in the path, the full existing family unchanged. The arena is a strict superset — no existing DMA user changes behavior on or off.

## 2. ISCs
- **ISC-1 — The arena region + allocator.** Reserve the fenced region at init; arena-backed `DmaBuffer` allocation drawing from it; Drop returns frames to the arena (not the general allocator). Bounded, no leak (alloc==free at teardown — a balance check, the O1a precedent).
- **ISC-2 — The validation gate (pure-tier where possible).** `validate(phys, len)` is pure arithmetic over the fence bounds — put it in the host-testable tier and unit-test the truth table: fully-inside ✓, straddling-the-low-edge ✗, straddling-the-high-edge ✗, fully-outside ✗, zero-length, integer-overflow at the bounds (saturating). The kernel glue is the boundary wrapper that calls it on the descriptor-programming path.
- **ISC-3 — The single-gate property (the containment proof).** There must be **no path** by which a connectivity driver hands a DMA address to a device without passing `validate` — the gate is unbypassable by construction (a typed wrapper / the only public programming entry), the same way `mint` is the only way to get a tensor `Arc`. Document this as the I-14(c1) argument. (No connectivity driver exists yet, so this build establishes the gate and proves it with an adversarial test, ISC-5.)
- **ISC-4 — I-14(c1) ledger guard (REQUIRED — Rule 2, the deferred-guard now landing).** Update the I-14 row in `docs/complexity-governance.md`: **(c1) is now guarded** — name the arena + validation gate + its test as the running guard; **(c2) remains mandated-not-yet-proven**, guard ships at 7.5-V (VT-d). Update the audit-log line. This is the first half of I-14(c) moving from "mandated" to "proven."
- **ISC-5 — The adversarial gate test (the discriminator).** A test that programs DMA addresses through the gate: in-arena addresses pass and reach the (mock) device; **every out-of-arena address — including one pointing at governance/tensor memory — is refused with `DmaFault`** and never reaches the device. Assert a refusal counter (>0 in the attack path) and **0 escapes ever**. This is the (c1) containment, demonstrated.
- **ISC-6 — Standards.** Strict superset (arena-off ≡ today, ISC-1); SPDX; **no new `unsafe`** beyond what `DmaBuffer` already justifies (the arena reuses the existing frame/zeroing safety arguments — no new raw-pointer surface); `cargo fmt`; host suite (validation truth table + the adversarial gate test + the full existing DMA-user family: virtio-net/accel/NVMe/AHCI/virtio-blk regressions unchanged) green; `shard-coverage`; `clippy -D warnings`; builds on+off. **Open ANSPEC §10 (or the connectivity-spec section) "DMA isolation"** + **ADR-045** (the fenced arena: the (c1)/(c2) threat split, the arena, the validation gate, the single-gate property, the explicit deferral of (c2) to VT-d).

## 3. Gate (two-stage — host + QEMU, no OptiPlex)
Pure software; no hardware dependency, no driver (no blind-hardware run → no failure-mode/discriminator section beyond the adversarial test ISC-5).
- **Stage A (you):** builds (on+off); validation truth table + adversarial gate test + the existing DMA-user regressions green; clippy; fmt; shard-coverage; the kill-switch equivalence (arena-off ≡ today).
- **Stage B (QEMU):** the adversarial gate scenario — in-arena DMA reaches the mock device, out-of-arena (incl. an address aimed at governance memory) is refused with 0 escapes; existing DMA paths (virtio-net/blk in QEMU) unchanged.

## 4. Scope guard
The fenced arena + validation gate only. **Do NOT** build VT-d/IOMMU (that is **7.5-V**, the (c2) guard — and it must land before `iwlwifi`); **do NOT** build xHCI/USB or any driver (7.5-A onward — they consume this); **do NOT** move existing DMA users (GPU/NVMe/AHCI/virtio) into the arena (they keep today's path — the arena is for *connectivity* drivers); **do NOT** claim I-14(c2) containment (state plainly the arena stops our-errant-programming, not a misbehaving device); **do NOT** add a new lock primitive or `unsafe` surface; **do NOT** change *what* any op computes.

## 5. Merge (PM, on Stage-B PASS)
Close-gate: rebase onto current `main`, re-run Stage-A+B, push. PM `pm-merge-check` → `--ff-only` → `main`. Then **BUILD-7.5-A** (xHCI + USB core — the lane's first blind-hardware build, all DMA via this arena, opening with its own pre-seeded failure-mode bank: cycle bit, dequeue semantics, scratchpad, context size, IRQ-ack ordering; QEMU-xHCI green before any OptiPlex run). With 7.5-0, the lane has a contained DMA footing before a single driver touches hardware — the boundary built before the feature that needs it.
