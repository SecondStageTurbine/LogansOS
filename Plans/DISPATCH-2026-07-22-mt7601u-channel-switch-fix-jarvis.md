## The root cause (from Prometheus step 1 — read the full FINDINGS)
`Plans/RESEARCH-2026-07-22-mt7601u-channel-switch-trapmine-FINDINGS.md`:
- **The wedge is `MCU_CAL_BW`** (the bandwidth-calibration MCU command inside `set_bw_filter`), a firmware round-trip that crashes the MCU on certain channels (the LKML "mt7601u dies during channel switch" bug). It is **NOT** the channel-set itself (the RF/BBP freq-plan + LNA `RANDOM_WRITE`s are safe) and **NOT** the deferred/periodic calibration. Our `phy.rs:385-442` reproduces the exact wedging sequence (`set_bw_filter` → `mcu_calibrate(MCU_CAL_BW)` at ~423-424).
- **The warm failure is a stale MCU command queue after host reboot** — upstream's `load_firmware` fast-returns on `COM_REG0==1` with zero resync and only survives because `usb_reset_device()` flushes the device USB state machine on every probe; our bare-metal path has no equivalent, so orphaned seqnos + stale DMA descriptors persist → calibration times out.
- **Options A (boot-on-target-channel) and C (host-CSR channel-set) are DEAD** — don't attempt them (the freq-plan regs are MCU-internal, only reachable via MCU `RANDOM_WRITE`; the cold MCU boots on the blob's default channel). The fix is B + D(b).

## Scope — build exactly this (the two fixes)
1. **Fix 1 — skip `MCU_CAL_BW` on the FIRST targeted channel tune (Option B).** In the targeted-association path (`phy::set_channel` / the `run_configured_association` tune), on the **first** set of the operating channel, **skip `set_bw_filter` (the `MCU_CAL_BW` calls)**. The RF frequency plan, LNA gain, VCO cal, and TX power are still programmed — enough for RX + management-frame TX (auth/assoc). **Recalibrate after association succeeds** (upstream's `cal_work` pattern — run `MCU_CAL_BW`/the cal subset once the RF state is settled on the operating channel, when a crash is far less likely). Structure it so the *scan* path (which already skips deferred cal upstream) is unchanged, and the skip is scoped to the first targeted tune.
2. **Fix 2 — warm-path resync (Option D(b)).** In the firmware-load path (`load_firmware` / the resident-firmware branch), when firmware is already resident (`firmware_running()`/`COM_REG0==1`), **still run `fce_preload_setup` + vendor_reset before trusting it** (the pre-FW-register-setup from upstream `mcu.c:459-491` that resets FCE DMA state + flushes the MCU command queue) — instead of the current zero-resync fast-return. This brings a warm device back to known-good post-boot state without re-uploading the 45,412-byte blob.
