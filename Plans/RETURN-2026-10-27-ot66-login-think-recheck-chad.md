# RETURN #117 — OT-66 login/session THINK re-check

Reviewed `3c3939c5` (`docs/THINK-2026-10-27-ot66-login-session.md`), revision 2, against relay #117. RAG health was healthy and the dispatch query returned source pointers. This is a docs-only design re-check; no code or tests were changed or run. **Overall: FAIL** on items 2 and 5 below. Line references are from the reviewed tree unless otherwise noted.

1. **PASS — Item 2, Try and installed-disk exposure.** The threat table now says Try can read the attached installed disk, explains that read-only prevents writes rather than reads, states K1b only withholds the found-volume cap from Try clients, and correctly notes Try's neo-init still has root access and another boot image can read the files. It identifies encryption at rest as the confidentiality boundary and includes the installer/first-boot warning (`THINK:92`; first-boot and Try details `THINK:368-387`). This is complete and consistent with the stated no-encryption scope.

2. **FAIL — Item 3, model-load gate and K1 rights scope.** The cited `model_load_path` check does what the THINK says: under `cap-rooted-open`, it requires `RootDirCap` with `READ` before the model-source branches (`kernel/src/arch/x86_64/syscall.rs:2619-2626`; THINK:149-150). However, the THINK does not say K1 will check every fd-based directory operation against the attenuated handle's rights. K1b describes `open_at`, rights subset checks, and product call-site ports only (`THINK:151-153,406`). Janus F1 documents why this omission matters: readdir, mount and umount look up the backing `OpenFile` with empty required rights (`kernel/src/arch/x86_64/syscall.rs:6179,6264,6287`), then the VFS checks that backing object's rights (`kernel/src/fs/mod.rs:416-417,437-438,450-451`) rather than the derived handle's attenuated rights. Concrete input: derive/inherit a root directory handle advertising LOOKUP only, place it at a worker fd, and call `readdir(fd, valid_buffer, cursor=0)`; the operation can enumerate despite the handle lacking READDIR. A client handle lacking MOUNT can similarly call umount on an eligible child. K1's scope and close gate need to cover these consumers' effective handle rights.

3. **PASS — Item 4, NEOCRED1 copy-on-write and cut gate.** `commit_regular_write` writes newly reserved content blocks and a new inode, then updates the child entry (`kernel/src/fs/neofs/inode.rs:371-425`). `fsync_regular` drains the mount (`inode.rs:487-498`); cache roles order data, inode, root directory, free map, then superblock (`kernel/src/fs/neofs/cache.rs:29-37`). That supports the stated property that updating one credential file leaves the other file's inode/data untouched, while namespace and superblock publication remain copy-on-write (`THINK:223-244`). The proposed L1 gate injects a crash after every write and flush, reboots, checks that exactly one of old/new passwords is accepted, and compares the untouched file's bytes (`THINK:245-250`); this would discriminate a rewrite of the other file or loss of both valid records. The field ranges in the new layout end at byte 160 (offset 152 plus 8 reserved bytes; `THINK:201-220`), and the oracle cases listed at line 250 match the pair/torn-newer/below-floor cases. The literal oracle is specified as an L1 deliverable, not present in this design-only change, so its eventual bytes remain to be checked at that gate.

4. **PASS — Item 6, delay counter lifetime.** The counter is in neo-init memory; the login UI and verifier are in neo-init, and the document assigns the counter to neo-init if a restartable verifier is split out later (`THINK:259-266`). `kernel/src/main.rs:466-480` waits for neo-init to exit, reaps it, and returns to kernel-only mode; it does not respawn it. Thus a WM/login-screen state restart within neo-init retains the counter, and a process exit cannot provide a fresh login screen. Boot calls `spawn_neo_init` (`kernel/src/main.rs:973`), so the in-memory counter starts anew at boot as claimed.

5. **FAIL — Item 5, late-client lock gate.** The product contract is explicit: Locked composes only WM chrome, defers OP_BUSY, and gives a client spawned while locked no focus, input or pixels (`THINK:315-323`). The L2 close gate separately checks that a client's commit plus OP_BUSY does not change the frame digest, and that a client spawned while locked receives no input (`THINK:325-327,403`). It does not require the digest assertion to cover a client spawned while locked; the two checks can pass while a late client's commit leaks pixels. Concrete input: enter Locked, spawn a client and create its surface, then have it commit a unique visible pattern and send OP_BUSY; assert the before/after frame digest is identical and the client receives no input. Make that late-client draw part of the gate's digest scenario.

6. **PASS — §8 dependency chain under either revert.** The chain is explicit: K1a-0 → K1a → K1b, L3 depends on K1b, and the MVP lists K1b and L3 (`THINK:395-412`). The ledger and Janus RETURNs put both #166 and #168 under fix-forward to S4, with rollback of #168 then #166 if that misses (`Plans/LEDGER-2026-07-29-logansos-release-ledger.md:352-362`). If #166 is reverted, K1a and downstream K1b/L3 are blocked; if #168 is reverted, K1b/L3 are blocked. The declared prerequisites capture both cases, so no independent path is claimed and the MVP items must remain blocked until the chain is restored or fixed forward.
