## The claims that carry the decision (pressure-test each)
1. **THE RISKY ONE — the shader-compilation gap (where the ~2-4 pm estimate lives or dies).** §1.3 admits: "No shader compilation path beyond pre-compiled EU kernels." But Vello's backdrop-blur is a **WGSL compute shader**, not a hand-written EU kernel. So *something* must lower WGSL → Gen9 EU ISA at build or run time (naga front-end + a **Gen9 EU backend** that does not exist today). Is that EU-backend/shader-compiler inside the "minimal compute device, ~2-4 person-months" estimate, or is it the hidden monster that blows it up? Could Vello's specific shaders be pre-compiled offline once (bounding the problem), or does Vello's pipeline demand a general WGSL→EU compiler? **This is the crux — a wrong answer here invalidates the whole minimal-first effort claim.**
2. **The Vello ↔ wgpu coupling (your iced/Servo method, applied).** Vello's compute backend is normally driven *through wgpu*. The FINDINGS says we target "a minimal compute device that Vello can target directly" — is that real, or is Vello's scene→compute pipeline welded to `wgpu` types (device/queue/pipeline/bind-group) the same way iced was welded to `winit`/`cosmic-text` and Servo to `std`/winit? Can Vello emit its compute passes against *our* minimal device without dragging wgpu in, or does "minimal device" have to reimplement enough of the wgpu HAL surface that the saving evaporates? Is there a `vello_cpu` / software path that sidesteps the GPU-compute question entirely for the glass MVP (and if so, does that change the whole "GPU-API-first" ordering)?
3. **The Phase-6 reuse claim.** §1.1 lists a silicon-proven compute stack (EU dispatch, PPGTT, execlists, cross-tenant isolation). Is Vello's blur compute genuinely "the same hardware path" as the proven Add/Matmul/GELU kernels, or does a real graphics-shaped compute pass need hardware features the Phase-6 kernels never exercised (larger workgroups, shared local memory, barriers, samplers/image loads, multiple dispatch stages with dependencies)? Which proven gate actually covers Vello's compute shape, and which is extrapolation?
4. **The extension path to WebRender (is it a vertical add or a rewrite?).** The claim: the minimal compute device's resource/queue/fence model extends cleanly to the WebRender GL adapter (textures/render-targets/3D pipeline) without a rewrite. You measured Servo/WebRender's GPU assumptions in the browser cross-check — does WebRender actually sit on this substrate, or does "minimal-compute-first" defer (not solve) the hard graphics problem such that the browser still faces the ~9-14 pm wall later? Is the ordering honest, or does it just move the cost?
5. **I-14 on the compute device + no-contradiction.** §1.3 notes "No VT-d domain (identity-mapped GPU)." Compute buffers resolve via per-context PPGTT (silicon-proven cross-tenant fault). Is PPGTT isolation *sufficient* for I-14(c) on the compute path, or does compute DMA also need the VT-d domain (as scanout DMA needed the Slice-3 fence)? And does anything here contradict a ratified decision (OT-63 GpuSubmitCap/scanout-fence, the own-Vello glass direction, the Gen9 accel driver)?
