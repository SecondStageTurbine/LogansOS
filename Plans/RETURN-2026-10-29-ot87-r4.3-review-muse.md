# RETURN — relay #115: OT-87 R4.3, the installer's writes (PR #170)

Reviewer: Muse (Gwen), a separate model family, reviewing Claude-authored code. Pasted by the PL on 2026-10-29; banked
by the PM. Muse's text is summarised per item below, with its file:line anchors kept.

**Reviewed SHA:** `d72d4470` (#170's squash; batch 12b run `40787440872`, green). Scope: the installer's writes only.
`installer` is in no product image; Muse checked that `PRODUCT_IMAGE_KERNEL_FEATURES` has no `installer` and no
`neo-test*` entry.

1. **The only write path — PASS.**
   - **The write sites:**
     - `installer.rs:278` (`ClaimTarget::write` → `ClaimedWriter::write`, with the R4.1 pre/post checks, →
       `KernelTarget::write` → `GuardedDevice::claimed_write`, `mod.rs:517`);
     - `installer.rs:376` (`ClaimDevice::write_block`, for the W4/W5 NeoFS mounts through `PartitionDevice`);
     - the flushes at `:282` and `:360`.
   - `install_logic.rs` writes only through the `Target` and `Payload` traits.
   - `Prepared` (`:459ff`) seals the writer.
   - No installer code calls `GuardedDevice::write_block`, `get_device` or any raw device handle for the target.
   - **Scope notes, not failures:**
     - (a) A claim doesn't lock out a hypothetical concurrent writer on the plain guard path. None exists in the
       install flow, and a blank target arms nothing.
     - (b) `installer` implies `neofs-partition`, so on a Finish target the guard's partition claim arms the NeoFS
       extent. Only a hypothetical concurrent writer could use it.
2. **Zero reads of the boot medium — PASS, enforced by construction and measured by the scenario.**
   - **Construction:** the only device handles are built over the claim, and every payload byte comes from RAM (the
     bundle module, the Limine-loaded kernel file, the boot modules, the pinned leases).
   - **The boot medium can't be the target:** the claim's `BootDisk` refusal covers a boot GPT GUID
     (`installer.rs:170`), and otherwise a non-zero first MiB classifies as Foreign.
   - **Limitation:** the test-harness scenario leg couldn't be re-read, because the file is too large for the tool.
3. **Refusals write nothing — PASS.**
   - **Every row is decided in `preflight` before `install()`:**
     - too small;
     - `NoLayout`;
     - `NoFlush`;
     - `SectorSize`;
     - a foreign GPT, whether opaque or a valid Windows table;
     - a whole-disk filesystem;
     - Installed;
     - the bundle, module and model pins;
     - `SlotTooSmall`.
   - **No write happens before W1:** the first write anywhere is W1's backup array. A refused writer drops with
     `claimed` cleared (`install_claim.rs:185`).
   - **A nuance inherited from R4.1:** `Claim::read` doesn't check the media generation, but the first write's
     pre-check refuses before submission.
4. **Durability — PASS.**
   - `install_ordered` follows THINK §4.7 rules 2–4:
     - each payload step is write → flush → verify → flush → boundary;
     - each GPT copy is written array first, then header, each flushed and verified;
     - W6 clears INCOMPLETE backup first, then primary;
     - `Outcome::Installed` is reported only after W6's last flush.
   - A failed flush stops everything (`Failure::Flush`). That's stricter than "two failures end the session".
   - The cut model in `tools/install-state-logic-tests` proves the outcomes. Its named traces are present.
5. **The bundle pin — PASS.** `load_bundle` (`installer.rs:132`) runs first in `preflight`:
   - **It refuses before any claim or write:** `NoBundle`, `NoPin`, or `PinMismatch` (the BLAKE3 over the whole
     module).
   - **Then the part checks:** `installer_manifest` and `check_part`.
   - **The provenance check:** xtask's `install-bundle --check`.
6. **The written GPT passes the R3 validator as fixed by #172 — PASS** (checked against `5c65f2e5`).
   - `gpt_layout` writes two entries that touch but don't overlap: ESP `[m, 513m−1]` and NeoFS `[513m, E]`, with
     `E ≤ last_usable`.
   - Both entries lie inside `[2+a, l−a−1]`, and no partition touches metadata.
   - The CRCs match how the validator recomputes them.
7. **The Zenbook's internal disk can never be a target — PASS, on two independent layers.**
   - **Layer 1:** VMD/RST is never probed (`pci.rs:259–269`), so there's no device, row, token or claim.
   - **Layer 2:** R4.3 admits only Blank (Fresh) or Incomplete (Finish), and Windows classifies Foreign. There's no
     erase path, and `preflight` always takes a Fresh claim.
   - **Layer 3, for the boot medium:** `BootDisk`.
   - **Caveat:** `PROTECTED_SERIALS` is still empty (`install_claim.rs:32`). The VMD-lane rule is a process rule, not
     code. R4b erase will need the table.

**Overall verdict: PASS.** All seven items pass. The recorded limitations:
- the scenario leg (the boot-medium read counter) wasn't re-read;
- the R4.1 token-reuse-after-drop limitation is unchanged (it isn't a bypass);
- the protected-disk table is still empty, pending a VMD lane.
