This is **I-14(c2) for the GPU** (ADR-050 VT-d/IOMMU applied to the accel device), and — per Chad's ADR-077 cross-check amendment 5 — it is the physical boundary that **MUST precede any userland compute queue.** **Doubly-motivated: this is also the foundation the ratified gaming direction extends** (gaming = VT-d GPU passthrough to a microVM guest = this pattern at scale on a discrete GPU). ## Scope — what Slice 5 IS
1. **Narrow the iGPU's VT-d domain.** Today (ADR-077 §5.3): the iGPU is identity-VT-d-domained → PPGTT isolates GPU *contexts* from each other but NOT the device from host physical memory. Slice 5 moves the Gen9 accel device into a **translated VT-d domain (via the proven ADR-050 IOMMU infra)** that maps **ALL GPU-reachable allocations** — per Chad amendment 5: **ring, LRC, HWSP, state, kernel, CURBE, seqno, PPGTT page tables, AND the compute/scanout buffers** — and nothing else. A GPU DMA outside that domain **faults**, not silently scribbles governance/tensor memory.
2. **I-14(c2) proof (falsifiable).** A negative control: a GPU-issued DMA to an **out-of-domain physical address FAULTS** (the IOMMU rejects it) — the physical-memory analogue of the Slice-3 scanout-fence out-of-arena refusal. This closes the I-14(c) claim for the GPU that PPGTT alone could not (the gap Chad named).
3. **Still kernel-internal (amendment 4).** Slice 5 establishes the *boundary*; it does **not** add a userland compute queue (that's post-Slice-5). The point of Slice 5 is precisely to make a future userland queue *safe*.
4. **The gaming through-line (note, don't build).** This graphics-VT-d-domain-for-a-GPU pattern is what the ratified gaming passthrough-microVM extends (VT-d-passing a discrete AMD GPU to a confined guest). State how Slice 5 generalizes — proving the mechanism on the Gen9 iGPU de-risks the gaming Phase-0 spike — but **do NOT build gaming here.**
