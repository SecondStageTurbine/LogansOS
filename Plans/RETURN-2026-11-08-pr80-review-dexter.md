## #80.1 PASS — the channel is a typed handle, its transfers are bounded, and a closed peer is `EPIPE`

**The surface.** The PR adds `channel::try_recv` (`userland/neoplutarch-std-overlay/std/os_neoplutarch.rs:328-331`) and `std::os::neoplutarch::input` (`:334-376`), over the four new trampolines in the sanctioned overlay file (`userland/neoplutarch-std-overlay/std/neoplutarch_rt.rs:359-386`). `try_recv` is `SYS_TRY_RECV` (`kernel/src/arch/x86_64/syscall.rs:6224-6239`); `input::recv` is the fixed 8-byte `SYS_INPUT_FOCUS_RECV` (`:9135-9193`).

**Named: there is no ambient channel namespace.** A process can only name a channel it already holds a handle to; `channel::try_recv` takes a `RawHandle` (`os_neoplutarch.rs:329`), and the kernel resolves it through `ipc_lookup`, requiring the `RECV` right (`kernel/src/arch/x86_64/syscall.rs:6234-6237`). The scenario makes the naming explicit on the client side: it walks its own handle table, keeps exactly the `HandleKind::Channel` entries, and requires **exactly one** (`userland/browser-app/src/io_smoke.rs:67-76`); the launcher hands each process exactly one channel end plus the std fixture's runtime cap (`kernel/src/test_harness.rs:3236-3253`). A process that holds no channel gets `EBADF` from the lookup, not a name it can guess.

**Bounded: both directions carry a kernel-checked length.** `try_recv` passes `buf.len()` as the maximum (`os_neoplutarch.rs:329-330`); the kernel refuses a zero `max_len` and validates the user range (`kernel/src/arch/x86_64/syscall.rs:6228-6232`), and the handoff copies `min(sender_len, max_len)` (`kernel/src/ipc/mod.rs:301`). The scenario sends one byte into a four-byte buffer (`io_smoke.rs:78,84,100`). The input side is fixed-width by construction: `EVENT_LEN` is 8 (`os_neoplutarch.rs:346-347`), and the kernel rejects any `out_len` other than `INPUT_EVENT_V1_LEN` (`kernel/src/arch/x86_64/syscall.rs:9141-9143`). The input queue is also bounded per client (capacity 64) and by the live-route cap (32) (`kernel/src/atrium/focus.rs:34-43`), so a client that never drains its focus cannot grow an unbounded queue.

**A closed peer is an error, never a park.** Both receive paths test the peer's `EndpointState::Closed` before any blocking state: `recv` returns `EPIPE` (`kernel/src/ipc/mod.rs:258-260`) and `try_recv` returns `EPIPE` (`:315-318`); `try_recv` has no `block_current` arm at all, and its only handoff is the existing send-blocked one (`:293-323`). The std wrapper turns the negative errno into `io::Error` (`os_neoplutarch.rs:329-330`). The scenario's polling loop retries only `WouldBlock` and exits with `FAIL(4)` on every other error (`io_smoke.rs:86-97`), so a closed peer produces a deterministic failure, not a hang. The same is true of the peer: its blocking `recv`/`send` return `EPIPE` and it exits non-zero (`userland/browser-app/src/io_peer.rs:36-42`).

**Scope note (not a fail).** `browser_io_smoke` does not itself drive the closed-peer leg: the peer sends `W` and exits, and the smoke stops after taking it (`io_smoke.rs:84-100`). The closed-peer path is the pre-existing kernel path above, not a line this PR changes; the PR's own contribution is the std binding. If the PM wants a scenario witness for this API, a post-`W` `try_recv` expecting `BrokenPipe` would add it. The browser app's actual session/surface channels (two per client in A1a) are also not created by this PR: it is the std I/O surface under that app model, as the PR body says. The item is satisfied for the surface; the app loop is A1a.
