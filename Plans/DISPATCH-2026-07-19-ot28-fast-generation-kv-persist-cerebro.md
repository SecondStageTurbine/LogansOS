## The fix (one-line) and why it's low-risk
**Persist one KV cache across `sys_generate` steps and forward only the new token each step → O(N²)→O(N)** (~4 s/token → full reply in seconds on the same single-threaded bare-metal run).

**This is not new infrastructure — the pattern is already proven on `main`.** B3 (`0163ffc`) landed exactly this for the *inventory* path: `qwen_inventory::InventoryDecodeState` (`kernel/src/ai/qwen_inventory.rs:85`) prefills once, holds a persistent `Qwen2KvCacheSet` (`:93`) by value, and calls `advance()` (`:156`) per token — the incremental `next_logits_for_token` (`:205`) machinery and `Qwen2KvCacheSet`/`Qwen2KvCacheLayer` ALREADY EXIST and are AAG-clean. The bare-metal hardcoded path calls `crate::ai::generate::next_logits` instead, which has no persistent cache. **The task is to give the hardcoded `generate` path the same prefill-once + persistent-`Qwen2KvCacheSet` + advance-one-token structure the inventory path already uses** — reuse the existing cache type and incremental forward, don't invent a new one.

## Mandatory correctness gate (Rule-1 kill-switch + equivalence oracle)
A forward-path change is only safe if it's provably behavior-preserving:
1. **Bit-for-bit token identity.** The fast (KV-persist) path MUST produce **identical token ids** to the current O(N²) path on the small config — the equivalence oracle. This is the byte-oracle discipline applied to generation: the fast path is verified against the *independent* slow path, not against itself.
2. **Kill-switch (Rule-1).** Ship the fast path behind a feature/flag whose **disabled mode ≡ the current O(N²) path, bit-for-bit**, with the equivalence proven by an **armed, falsifiable** regression (fast≡slow token-identity), not a dormant assert. Complexity you can switch off is bounded.
3. **In-kernel QEMU token-identity KAT** on the small config — the fast≡slow proof runs in the gate (a host unit test of the cache logic is welcome too, but the *gate* proof is the QEMU KAT).

## Concurrency / pitfall-bank consultation (OT-62 — required, and it's short here)
Per the SMP-touching-dispatch rule, consult `docs/concurrency-pitfalls.md`. **This change adds NO cross-CPU / interrupt / lock / atomic / TLB / scheduler-wake code**: the persistent KV cache is **per-`sys_generate`-call owned state** (a stack-local `Qwen2KvCacheSet` of owned `Vec<f32>`), exactly like `InventoryDecodeState`, which the B3 concurrency lens confirmed is stack-local per-call with no shared-mutable/aliasing surface. So the cross-CPU CP classes are **N/A by construction** — state the guard (the cache never escapes the call; two concurrent `sys_generate` calls get independent stacks → independent heap caches). The one real correctness axis is **cache lifetime/coherence within the single call** (does the persisted cache at step N correctly hold exactly tokens `0..N`?), which the token-identity KAT proves.
