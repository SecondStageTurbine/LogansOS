## Why this exists
Our GUI is design-complete through G1 (paradigm → Atrium design language → text engine → G0 spec → the cross-model-validated G1 compositor design) — but it was designed largely from first principles + one lifted Wayland idea, and we **never systematically benchmarked it against the actual Rust GUI/compositor ecosystem**, nor mined the prior art for the **glass/frost/vibrancy** aesthetic the PL wants. This pass closes both gaps before we spend the kernel-object budget. It's the same discipline we apply to every driver: **mine the field's solved problems + traps before you build.**

**Hard MPL-hygiene rule (CLAUDE.md / OT-1):** read every project for **principle only**; **NEVER copy GPL/copyleft or otherwise-incompatible code** into our MPL-2.0 tree. **License is a first-class finding** — several candidates are copyleft (COSMIC is **GPL-3.0**; Slint is **GPL-or-commercial**) which forecloses code adoption entirely, vs permissive ones (iced/Smithay/egui/Vello/wgpu ≈ MIT/Apache) which could be *adapted*. Pull each license from the actual repo `LICENSE` file, not a summary — the license gates "reference-only vs adaptable."

## Scope A — the Rust GUI/compositor ecosystem benchmark (the original gap)
For each, produce: architecture in one paragraph, **license (from the LICENSE file)**, the **solved problem worth reference-lifting**, the **traps** they hit (pre-inoculation), and how it compares to OUR ratified design (cap-native surfaces, one kernel pixel-buffer, **kernel-routed input focus / no-snoop-by-construction**, userland compositor, kill-switch ≡ v1 console):
- **Redox OS Orbital** — ⭐ the closest analog on Earth: a Rust OS with its OWN from-scratch display server (`orbital`) + scheme-based IPC. Mine hardest: how it does surfaces, buffer sharing, input routing, and where it fell short (does it snoop? does it have our cap-native isolation, or did it settle for less?). Its mistakes are our pre-inoculation.
- **COSMIC** (System76): Smithay-based Wayland compositor (`cosmic-comp`) + **iced/libcosmic** retained-mode toolkit. **GPL-3.0.** Mine the *toolkit* architecture (iced's Elm-style retained model) and its compositor pacing/damage — but note we reject the Wayland stack itself (Linux graphics stack we don't have; userland client-isolation our kernel caps give for free).
- **Smithay** — Wayland-compositor building blocks in Rust (MIT). What primitives generalize; what's Wayland-protocol-specific (and thus N/A for us).
- **iced / Slint / egui** — the Rust retained/immediate-mode toolkit options (see Scope C). Licenses: iced MIT, **Slint GPL/commercial**, egui MIT/Apache.
- **Servo's compositor / WebRender + Vello** — GPU-accelerated 2D rendering in Rust (WebRender is the browser's path per OT-61; Vello is compute-shader 2D, Apache/MIT). Relevant because our glass/frost + browser both need a GPU 2D renderer — is there ONE renderer that serves the compositor AND the browser (shared OT-63 leverage)?

## Scope B — glass/frost/vibrancy materials (the PL's aesthetic — mine this deeply)
The PL wants **Mac-like frosted glass**. Find how it's really done and what it costs:
1. **How macOS does it** — `NSVisualEffectView` **materials** (sidebar / menu / hud / under-window etc.) + **vibrancy** (foreground color bleed-through) + the **backdrop-blur pipeline**: capture the backdrop behind the surface → downsample → blur (Gaussian, or the cheaper **dual-Kawase**) → tint/saturate → composite. Describe the pipeline concretely enough that our compositor could implement it.
2. **The GPU cost — LOAD-BEARING.** Real-time backdrop blur is a **per-frame GPU operation** (sample + multi-tap blur + composite, every frame, behind every glass surface). Quantify it (passes, bandwidth, why CPU blur is too slow at native res). **Does beautiful glass/frost effectively REQUIRE the GPU?** If yes (I expect yes), this makes **OT-63 (GPU/accel, Gen9 bring-up) a hard GUI prerequisite, not just a browser one** — state that conclusion explicitly and quantify what the Gen9 iGPU can sustain. What's the honest CPU-only fallback (static/precomputed blur, no live translucency, or solid panels)?
3. **The accessibility caveat — MANDATORY, do not skip.** Translucency/frost fights legibility and our ratified **WCAG-AAA contrast floors**. macOS ships **"Reduce Transparency"** precisely for this. A glass GUI MUST degrade to solid/high-contrast for legibility. State the rule: frost is a *material*, legibility is an *invariant* — the contrast floor wins, and a Reduce-Transparency kill-switch is required. (This dovetails with our kill-switch discipline.)
4. **The anti-pattern we already flagged:** macOS Tahoe/"Liquid-Glass" — the lesson was **enforced-sameness** (every icon into one rounded-rect), NOT the glass material itself. Confirm the distinction: we want the glass *material* + our **grammar-not-uniformity** rule (distinct silhouettes), not Tahoe's homogenization.

## Scope C — the retained-mode toolkit question (own vs adopt), now constrained by glass
Our OT-45 amendment chose "own-cap-native retained-mode" over egui in the abstract, but never picked a concrete rendering approach. **Glass/frost narrows it:** the renderer must support translucency + backdrop blur, which most simple/immediate-mode toolkits don't do well (it's a compositor+GPU concern). Evaluate: (a) **own retained-mode scene + a GPU blur pass** (via a lifted permissive 2D renderer — **Vello/wgpu**, Apache/MIT — reference-liftable), vs (b) **adapt a permissive toolkit** (iced MIT). Rule out the copyleft ones for adoption (Slint GPL, COSMIC/iced-vs-libcosmic licensing). Recommend, with the license + the glass-support + the cap-native-fit as the axes.

## Scope D — reconcile glass/frost with the Atrium design language
Does frosted glass **amend** Atrium (neon-as-meaning + ≥70% negative space + "the only shadow is the Undo Shadow" + Electric-Blue-as-light)? Explore the synthesis, don't just flag tension: **glass/frost as the MATERIAL substrate, the cap-surface trust-state (owned / tethered / denied / untrusted / undo-armed) expressed as the glass's tint/vibrancy/frost-density** — i.e. *security-as-the-beautiful-part, rendered in glass*. Note "depth via blur/translucency" is compatible with "the only *drop* shadow is the Undo Shadow." Output a proposed ADR-024/Atrium amendment sketch (PL ratifies later) — the glass material + how it carries trust-state + the Reduce-Transparency/contrast-floor invariant.
