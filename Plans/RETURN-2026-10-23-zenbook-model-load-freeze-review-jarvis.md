## Finding F1 — P2: the stack probe borrows arbitrary live physical RAM

**Location:** `kernel/src/test_harness.rs:37042`, `kernel/src/test_harness.rs:37047`.

`run_boot_model_load_stack` constructs an ordinary `&[u8]` starting at HHDM(1 MiB), extending to the real model's size, without reserving or initializing that range. Its safety comment proves only that the guest has RAM there and this routine reads it. It does not prove a single owned allocation, initialized contents, or that other kernel paths cannot change those bytes while BLAKE3 holds the reference. Those are requirements of [`slice::from_raw_parts`](https://doc.rust-lang.org/stable/core/slice/fn.from_raw_parts.html).

**Concrete input/interleaving:** run `boot_model_load_stack` in its configured 4 GiB QEMU guest (`tools/xtask/src/main.rs:8603`), with a valid low physical placement of the kernel image, for example at 2 MiB with its data/BSS inside the probe's largest range. The 485,489,152-byte hash then borrows the kernel's live data too. `run_checked` enables interrupts for the hash (`kernel/src/mm/inference_stack.rs:264`, `:360`). A timer interrupt writes the two non-`UnsafeCell` `TIMER_SCRATCH` words (`kernel/src/arch/x86_64/timer.rs:53`, `:201`, `:202`) inside that borrowed input. The shared reference's immutability contract is violated. The range also spans unrelated objects rather than a reserved input allocation. This is undefined behavior in the measurement, even if a particular build prints a plausible depth and reaches `PASS` at `kernel/src/test_harness.rs:37064`.

**Re-check:** traced the actual xsave timer arm, not only the non-xsave arm: this scenario enables `inference-stack` and hence `xsave-fpu` (`kernel/Cargo.toml:830`, `:858`). The xsave arm performs those writes too. Compared the probe with the inference stack's own reference construction: that mapping has exclusive ownership under `BUSY`, and is borrowed for prepare/scan only while the caller is off that stack (`kernel/src/mm/inference_stack.rs:200`, `:257`, `:271`). The probe has no equivalent ownership condition. This is a source-level counterexample; I did not run this guest or observe a particular incorrect numeric depth.

**Requested correction:** hash an exclusively owned, fully initialized buffer at each measured length, with test-only memory provisioning sufficient for the largest input. Preserve one `blake3::hash` call over the full input; replacing it with small streaming updates would measure a different stack path. Keep the guarded stack and the existing depth reporting, then repeat both optimization measurements. This finding concerns test evidence, not a demonstrated defect in the production preload.

## Nine-item checklist

### 1. Locks taken at IF=1 — PASS

**1a. Checked the boot ordering and all live execution classes.** The preload precedes both the scenario/userland dispatch and the product's `spawn_neo_init` (`kernel/src/main.rs:830`, `:833`, `:865`); the scheduler smoke cohort has exited and been reaped (`kernel/src/sched/mod.rs:127`, `:135`). `boot-neofs` is a synchronous mount on the boot thread before preload (`kernel/src/main.rs:797`). The possible virtio completion worker polls storage and yields, without entering the AI subsystem (`kernel/src/drivers/block/virtio_blk.rs:1531`). APs poll matmul work and yield (`kernel/src/sched/scheduler.rs:483`, `:496`); preload publishes no matmul job. No user syscall can run yet.

At this pinned SHA there is **no separately spawned USB port-service thread**. xHCI scans/enumerates ports synchronously during initialization (`kernel/src/drivers/usb/xhci.rs:743`), before the scheduler/preload sequence (`kernel/src/main.rs:713`, `:782`). I checked the USB sources and kernel thread spawn sites rather than assuming the diagnosis's description of a newer USB lane applied here. Its ISR drains bounded event state under IRQ-safe locks and atomics (`kernel/src/drivers/usb/xhci.rs:824`, `:827`, `:838`). Timer scheduling does not acquire AI locks (`kernel/src/arch/x86_64/timer.rs:336`, `:383`; `kernel/src/sched/scheduler.rs:865`). Thus no reachable CPU-0 IF=0 waiter can acquire the preload's `ARENA`, `DEDUP`, or sharing `REGISTRY` while its holder is suspended.

**1b. Checked the rest of the build's lock chain.** The weight path hashes/probes, registers residency, installs a slot, then publishes candidacy (`kernel/src/ai/model.rs:459`, `:479`, `:480`, `:481`). Additional plain locks are accelerator accounting `TABLE` (`kernel/src/drivers/accel/accounting.rs:160`), the accelerator device registry used by `default_home` (`kernel/src/ai/arena.rs:447`; `kernel/src/drivers/accel/mod.rs:395`, `:427`), and `TensorSlot` (`kernel/src/ai/reservation.rs:93`, `:431`). The same pre-userland exclusion applies; no mover is active. Sharing registry and dedup guards do not span the process reader scan (`kernel/src/ai/sharing.rs:112`, `:140`, `:227`). That scan masks interrupts around process/handle locks (`kernel/src/sched/process.rs:1632`).

Heap and frame allocation mask interrupts before locking (`kernel/src/mm/heap.rs:100`, `:120`; `kernel/src/mm/mod.rs:463`); tensor allocation copies after the frame guard drops (`kernel/src/ai/tensor.rs:428`, `:436`). Census releases the frame lock before logging (`kernel/src/mm/mod.rs:665`, `:674`). Serial UART locking masks interrupts (`kernel/src/drivers/console/serial.rs:115`), the durable log entry uses `try_lock` (`kernel/src/log/block_sink.rs:523`), and the boot console uses `try_lock` (`kernel/src/drivers/fb/progress.rs:179`). No newly exposed interrupt-on lock cycle was found. This proof depends on the existing placement before userland, not on `SwitchMutex` being generally IRQ-safe (`kernel/src/sync/switch_mutex.rs:180`).

### 2. Preemption on the boot thread — PASS

**2a.** The BSP scheduler adopts the boot context as an ordinary thread with `pid=KERNEL_PID`, its own FPU save state, and no owned replacement stack (`kernel/src/sched/scheduler.rs:555`, `:587`; `kernel/src/sched/thread.rs:343`, `:346`, `:356`). Rotation updates the per-CPU tid and saves/restores each thread's actual `rsp` and FPU state (`kernel/src/sched/scheduler.rs:895`, `:897`, `:917`). Timer ring-0 entry uses the interrupted RSP, so an interrupt on the inference stack resumes there (`kernel/src/arch/x86_64/timer.rs:218`, `:224`). No ring-3 transition occurs within this boot call. Owner publication masks interrupts around the `BUSY` CAS and tid/pid stores (`kernel/src/mm/inference_stack.rs:311`); the tid and pid remain those of the same boot thread when it resumes. The model's attribution is explicitly `KERNEL_PID`, independent of sampled current state (`kernel/src/boot_modules.rs:539`).

**2b.** No other production pre-userland thread invokes the inference stack. Even if a future caller arrives, it cannot acquire `BUSY` while this owner holds it: its CAS fails and `wait_round` yields with an interrupt window (`kernel/src/mm/inference_stack.rs:312`, `:341`, `:374`). Ownership spans prepare, execution, and scan, and is cleared only after those finish (`:257`, `:279`, `:348`). The non-cancellable kernel owner cannot be force-killed: pid 0 is refused by termination (`kernel/src/sched/process.rs:3027`), and `cancel_requested` excludes it (`kernel/src/mm/inference_stack.rs:286`).

### 4. Vocab ordering (B1c F8) — PASS

**4a.** Checked all four requested combinations against `compose`, not just the happy path. Product pins pair the same model/vocab basename (`kernel/src/boot_model_logic.rs:32`, `:64`, `:98`), and preload calls the same `find_verified` used by `/boot` lookup (`kernel/src/boot_modules.rs:527`, `:449`). ### 5. Error values — PASS

### 6. Stack measurement — FAIL (P2 F1, 6a); 6b PASS

**6a.** F1 above is the re-checked failing input. Separately, the watermark mechanism measures deepest **written** stack bytes from the dedicated stack's top, including stack-switch/callback and any interrupt frames that occurred, not a continuous minimum-RSP trace and not total syscall stack use (`kernel/src/mm/inference_stack_logic.rs:103`; `kernel/src/mm/inference_stack.rs:254`, `:427`). Prepare resets the fill for each call and the caller scans only after returning to its own stack, under `BUSY`. Thus a measured overwrite beyond 32 KiB is meaningful evidence of insufficient stack capacity once the input is made sound; a smaller measured depth alone is not proof that the whole syscall fits. The author's opt-0/opt-3 numbers were not independently reproduced in this review.

**6b.** With preload off, model hashing/build remain inside the IF=0 syscall on the same 32 KiB thread stack (`kernel/src/arch/x86_64/syscall.rs:2495`; `kernel/src/boot_modules.rs:343`, `:373`; `kernel/src/sched/thread.rs:57`). That is the previous execution path, with the separately intended BLAKE3 optimization change. Acceptable as the explicit rollback/kill-switch, **not as a fix for loading the full model with that switch off**. The author already states that opt 3 is only margin; no conclusion that 29,808 B makes the complete syscall safe is justified. Product `iso --with-model` enables preload (`tools/xtask/src/main.rs:6031`), as do product ELF checking (`:5852`) and the CI product-real-lm arm (`.github/workflows/ci.yml:799`).

### 7. Tick discriminator — PASS, with its scope stated

**7a.** The hook is inside `load_model` after successful verification and before build (`kernel/src/boot_modules.rs:369`). It samples actual IF, then measures tick/co-runner deltas during its spin; the positive case requires IF on, at least 20 ticks and nonzero co-runner execution (`kernel/src/test_harness.rs:37089`, `:37188`). A load held at IF=0 for that entire interval cannot pass. The co-runner is explicitly placed on CPU 0 and must have started before loading (`:37132`, `:37138`), so AP activity or work outside the interval cannot supply its delta.

**7b.** The park is representative of the long compute window's IF/preemption policy: both the actual hash and build lie within the same `run_checked` closure (`kernel/src/boot_modules.rs:538`; `kernel/src/mm/inference_stack.rs:264`, `:360`). It holds the inference stack and the model lease, but no transient arena/dedup/accounting lock. It therefore proves scheduling during the load, not the interrupt safety of every short critical section; item 1 supplies that separate source audit. It also does not reproduce the real model's memory pressure or timing.

**7c.** The control deliberately wraps the same loader in `without_interrupts` (`kernel/src/test_harness.rs:37165`). It requires successful load, execution of the hook, sampled IF off, and exactly zero deltas (`:37181`, `:37195`). Zero ticks/runs **alone are not unique to IF=0**: a masked/broken timer could produce them with IF on. This control disambiguates with the explicit IF sample, pre-started CPU-0 co-runner, and the earlier scheduler smoke test (`kernel/src/sched/mod.rs:101`). Neither the 20-tick park nor its control is evidence that the entire real hash/build has been dynamically exercised at silicon scale.

### 8. `poll_control` — PASS

**8a.** The protocol consumes `G` first and exactly one expected `M` next (`userland/neo-init/src/desktop_session.rs:1236`, `:1239`, `:2107`). Arthur's handoff remains after `M`. `sys_try_recv` invokes the same rights/lookup and IRQ discipline (`kernel/src/arch/x86_64/syscall.rs:5395`). `Channel::try_recv` copies and completes the same blocked sender as `recv`, and restores endpoint state unchanged on `EAGAIN` (`kernel/src/ipc/mod.rs:274`, `:291`, `:309`). Pointer ticks do not receive from the Arthur session (`userland/neo-init/src/desktop_session.rs:344`, `:3678`). There is no new byte-consuming or reordering path. Both old and new helpers assume a one-byte protocol message, not a general multi-byte stream.

**8b.** The EAGAIN loop returns to ring 3 with IF enabled and no kernel lock held; `spin_loop` does not mask interrupts (`userland/neo-init/src/desktop_session.rs:2108`). Timer scheduling rotates ready threads (`kernel/src/sched/scheduler.rs:1321`, `:1338`). Importantly, EAGAIN does not call `continue_current_after_receive` and cannot continually renew its handoff preemption deferral (`kernel/src/ipc/mod.rs:309`, `:659`; `kernel/src/sched/scheduler.rs:1480`). Arthur therefore continues to get CPU time. Like CP-59's other polling loops it spends CPU and can increase latency; it does not guarantee idle/park efficiency or let the WM monopolize CPU 0 indefinitely.

**8c.** Checked both rendezvous arrival orders: if Arthur sends before a poll, try-recv completes its blocked send; if it sends after EAGAIN, the next poll does so. No sender requires the WM to be `RecvBlocked` first (`kernel/src/ipc/mod.rs:200`, `:284`). Subsequent focus/intent/`D` ordering is retained (`userland/neo-init/src/desktop_session.rs:1247`, `:1252`, `:1260`). Without `desktop-pointer`, the helper directly uses the old blocking receive (`:2100`). Other handshake receives still block as before; this patch specifically covers the slow `G`-to-`M` load interval.
