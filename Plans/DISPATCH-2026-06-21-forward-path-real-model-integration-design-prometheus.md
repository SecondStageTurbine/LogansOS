## 2. The three confirmed gaps (the D-block to resolve)
- **D1 — Mixed-quant weights in the forward matmul (THE crux).** `forward_logic.rs` only does `matmul_q4_k_q8_k` (q4_K weights × q8_K activations). The real model's weight tensors are **mostly q5_0 (133) + q6_K (12) + q8_0 (13) + q4_K (12) + f32 (121)**. Options: **(A) per-tensor dequant-to-f32 then f32 matmul** — reuses the landed `gguf_dequant_logic` primitives, simplest, correct, but slower + more memory (a dequantized weight is 4–8× its quantized size; can't hold all of it dequantized at once → dequant-per-matmul, streaming); **(B) native `q5_0/q6_K/q8_0 × q8_K` matmul kernels** — fast + memory-lean like the existing q4_K path, but 3 new matmul kernels each needing a byte-oracle. **Recommend with rationale** (likely A first for *correctness on silicon*, B as a later perf slice — but you decide and justify; note the latency consequence in D5). Map which tensors are which type (attn/ffn/embed/norm) so the design knows the hot path.
- **D2 — Model config: data-driven from `.neom`, not hardcoded consts.** `QWEN25_05B_HIDDEN_SIZE=896` etc. are `const`. 0.5B happens to match, but the **dual-model decision (0.5B + 1.5B + `/model`)** means the config (layers, hidden, heads, kv-heads, head-dim, rope-theta, vocab, intermediate) **must come from the `.neom`/GGUF metadata** — else 1.5B is wrong. Design how the forward graph reads its `Qwen2LayerConfig` from the model object (the ANSPEC §19.2 data-driven-graph intent, scoped to *config*, not a full graph rewrite — OT-16 stays frozen otherwise). State what the `.neom`/sidecar must carry and where the importer (L1) already puts it (or a follow-on importer note if missing).
- **D3 — Real vocab/tokenizer wiring.** `neo-arthur` uses a hardcoded `BPE_VOCAB` fixture; the real **151 936-token vocab + 151 387 merges** live in the L1 sidecar. Design: load the sidecar at Arthur startup into `tokenizer_logic` (which already "accepts raw-source vocab + merge slices"), wire `conversation_logic`'s `tokenize`/`decode` over it, and handle **Qwen chat special tokens** (`<|im_start|>`/`<|im_end|>`/etc.) so a real conversation frames correctly. Userland-only (no kernel change).
- **D4 — Memory/residency at real scale.** 485 MB (0.5B) / ~1.1–1.3 GB (1.5B) resident vs the fixture. Audit the model-load/residency path (the slot arena, `sys_model_load`, L1's 2 GiB cap) for any limit at real scale; if option A (dequant-to-f32) streams, confirm the working-set bound. Surface any blocker as a dependency.
- **D5 — Latency honesty (set Stage-B expectations).** Estimate the real-model per-token latency on **CPU scalar `soft_f32`** (the forward ops aren't AVX2-bit-identical, so they run scalar) for 0.5B and 1.5B. This is the honest "how slow will talking to Arthur be" number — it justifies the `/model` 0.5B fallback and tells the PL what Stage-B will feel like. No over-claim; an order-of-magnitude estimate with the assumptions stated.
- **D6 — Slice plan + kill-switch.** Order the sub-builds (recommend: **F1** mixed-quant forward [kernel] → **F2** config-from-`.neom` [kernel] → **F3** real-vocab tokenizer [userland]), each **kill-switched default-off ≡ the fixture path bit-for-bit** (the `arthur_boots_thinking` fixture scenario must stay green throughout — the equality anchor). Mark which are kernel-touching (F1/F2) vs userland (F3). The end-state scenario: a real-`.neom` inference producing a sane token (the real-model analog of `arthur_boots_thinking`).
