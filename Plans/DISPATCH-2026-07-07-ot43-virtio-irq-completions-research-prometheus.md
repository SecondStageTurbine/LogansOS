## 1. What to determine (real source — Linux `drivers/block/virtio_blk.c` + `drivers/virtio/virtio_ring.c`, the virtio spec v1.x, rust-vmm/`vm-virtio`, Redox `virtio-blk`; byte-oracle-acquisition rule — read the actual source/spec, never a summarizing fetch)
- **A — Interrupt delivery: MSI-X vs legacy INTx for the virtqueue.** How virtio-blk requests a per-queue completion interrupt: MSI-X per-queue vector (the modern path) vs a shared legacy INTx with ISR-status readback. **Cross-reference OUR existing interrupt infrastructure** (read `kernel/src/arch/x86_64` IDT/APIC/MSI setup + how other devices — mt7601u, virtio-net if any — take interrupts) and state the minimal path: does our virtio-blk currently register ANY IRQ, or is it poll-only today? - **B — The used-ring notification/suppression handshake.** `VIRTIO_F_EVENT_IDX`, `VRING_AVAIL_F_NO_INTERRUPT` / `VRING_USED_F_NO_NOTIFY`, `used_event`/`avail_event` indices — the exact protocol so the device raises the completion interrupt when (and only when) we want it, without spurious storms or **missed interrupts** (the race where the device posts completion + suppresses the IRQ in the exact window the submitter checks-and-parks — the classic missed-notification bug). Cite the spec §2.7 ordering + barrier requirements and the memory fences required around avail/used index publication.
- **C — The ISR pattern.** What the used-ring interrupt handler actually does: read ISR status / ack the vector, drain the used-ring, retire completion(s), wake the parked submitter. The **ordering** (ack-before-drain vs drain-before-ack) and the **re-arm** (how it re-enables notifications after draining without missing a completion that landed during the drain). How Linux/Redox structure the top-half (ISR) vs any bottom-half.
- **D — Coexistence with our inline-poll + single-claim invariant (LOAD-BEARING).** In fix v2 there are now THREE potential retirers: the inline-poll submitter, the (retained?) polling worker, and the new ISR. All must retire through the **single `in_flight.take()` claim** (`virtio_blk.rs:841`, `claim_completion`). The FINDINGS must state how prior art keeps exactly-one-consumer under IRQ + poll racing (the ISR claims via the same path; a completion the inline-poll already took must make the ISR a no-op, and vice-versa). Does the polling worker get RETIRED entirely once the IRQ exists, or kept as a belt-and-suspenders backstop?
- **E — I-14 ISR-lock boundary (our governance constraint — flag for Jarvis's build).** Per I-14(a) and the I-14 ISR-lock boundary: the interrupt handler must take **NO** AI-governance lock (INFLIGHT/RECENCY/ARENA/reservation/TABLE) and must respect the OT-13 lock-order band. State what lock (if any) the used-ring drain needs (the device inner `SwitchMutex`) and whether taking it in ISR context is sound (can the ISR contend with a thread holding it? deadlock risk?) — this is the exact I-14 ISR-lock-boundary question and Jarvis's build will need the answer.
