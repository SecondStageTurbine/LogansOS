## The load-bearing claims to pressure-test (RATIFY / RATIFY-AFTER-AMENDMENT / REFUTE each)
Verify against the **same pinned upstream commits** Janus cited (Servo/Stylo/SpiderMonkey/WebRender/SWGL/gleam/surfman — check the FINDINGS for the exact hashes; raw-source, never WebFetch), and against our actual kernel/libneo code.

1. **THE HEADLINE — SWGL rasterizes directly into a confined `SharedPixelBuffer` with NO scanout authority.** Janus claims `swgl::Context` impls `gleam::gl::Gl` (`swgl_fns.rs:504`), takes a caller-owned framebuffer (`init_default_framebuffer`/`get_color_buffer`), writes **only virtual pixels**, and never touches the DMA arena / `GpuSubmitCap` / MMIO / scanout — so `Servo/WebRender → SWGL → confined SharedPixelBuffer → compositor` keeps the browser fully within OT-52's confinement (client-present still `scanout_authorized()`→EPERM, `buffer.rs:192-214`). **Is this REAL?** Does SWGL truly never require a physical/scanout path? Does the `AtriumSwglRenderingContext` seam actually let hardware GL swap in later without re-architecting? Any hidden requirement (a GL entry SWGL `unimplemented!`s that WebRender's browser profile actually calls — Janus flagged `swgl_fns.rs:978,1423,1498-1512,2292-2344`; is his "panic_on_gl_error + exercise every pinned shader" mitigation sufficient, or a latent release-refresh trap)?
2. **The host-closure verdict — "bounded native port, NOT a `no_std` strip, NOT a POSIX ABI."** Janus (converging with Chad) says the engine closure is intrinsically hosted+concurrent (Servo spawns constellation/script/paint/font/net threads; SpiderMonkey needs a native pthread/TLS port) → a `libstd` PAL + a private C++/libc++ subset **behind the browser bundle boundary**, forking ONLY the narrow provider seams. **Is the "behind the bundle boundary, no POSIX personality leaks to the ABI" containment actually holdable** — or does hosting `std` inevitably grow the Linux-compat island (the OT-44 trap)? Is Janus's guard (a checked surface manifest + "a new syscall-shaped compat entry needs its cap-provenance + negative gate in the same change") a real defense or wishful?
3. **The C0-C3 ladder — is it honest, or does it hide a monster** (the way the original "just strip `std`" framing hid the shader-compiler / hosted-engine reality)? C0 target+PAL skeleton → C1 threads/TLS/waits/VM-protect/W^X → C2 sealed handles+no-dial → C3 SpiderMonkey(no-JIT). **Is C0 really the gating first rung, or is there an EARLIER blocker?** Is any rung mis-ordered or under-scoped? Is "C3 SpiderMonkey interpreter-first" honest about the JIT-later cost, or is a no-JIT engine too slow to ever pass the modern-site battery (making C3 a false floor)?
4. **The gap table — are the LogansOS gaps correctly assessed?** Janus cites: userspace single-threaded, 16 MiB `sys_map_region` ceiling, no unmap/protect/reserve, no W^X, no user-thread lifecycle ABI (`libneo/src/lib.rs:1768-1900`, `kernel/src/sched/process.rs`). **Confirm each against the real code** — is anything he calls "Required/high" actually already present, or anything he under-rates actually a deep kernel change (new user-thread syscalls, VM-protect/W^X, per-process crash containment)? These become real kernel builds — are they correctly sized (in dependency-depth/cycles/gates, NOT calendar — restate any figure)?
5. **The confinement + crash-containment claim.** The browser gets **no dial cap** (C2), and a content-process crash/OOM must kill **only** that process (C3). Does our process/capability model actually deliver per-content-process crash containment, or is that a new invariant needing its own guard? Does "abort across the C++ boundary, don't unwind Rust through C++" hold on our target?
6. **The honest "no prototype — blocked on C0-C2." Is there a SMALLER first step that IS buildable now** (e.g. a piece of the C0 PAL skeleton, or a SWGL-into-SharedPixelBuffer smoke that doesn't need the full thread runtime), or is the precursor genuinely atomic? If there's a cheaper de-risking spike, name it.
