**Verdict:** FAIL: the simple failed-write path is fixed, but a write that lands before reporting failure and a failed rollback still violate the all-or-nothing guarantee.

## Section 377 checks

- **FAIL — failed/refused write preserves stored zone, RTC mode and live clock; partial update rolled back.** The two keys now form one settings record (`userland/neo-init/src/desktop_session/settings.rs:369-380`). `confirm_zone` waits for `store_zone` before asking the kernel, returns on store failure, and assigns the live zone/mode and redraws only after kernel acceptance (`userland/neo-init/src/desktop_session.rs:8511-8546`). A write rejected before any bytes land therefore leaves all three unchanged. Two remaining counterexamples prevent an all-or-nothing PASS:
  1. **Bytes land, but the write operation reports failure.** Start with defaults in `settings.a`, generation 1, then choose New York 105. Let the complete generation-2 record reach `settings.b`, but let `sys_fsync` return an error. `login::write_whole` returns false even though the record's bytes can be valid and readable (`userland/neo-init/src/desktop_session/login.rs:238-244`). `commit` then returns false without read-back, resync or rollback because `written` is false (`userland/neo-init/src/desktop_session/settings.rs:321-331`). `store_zone` reports failure and the live clock remains old, but the next load selects the valid higher-generation New York record (`userland/settings-core/src/lib.rs:449-465`; load at `userland/neo-init/src/desktop_session/settings.rs:275-279`). Choosing Etc/UTC with `rtc_local=false` from the default `rtc_local=true` similarly leaves a changed stored RTC mode. Writing the other file protects the previous record from corruption; it does not stop a fully landed failed operation from becoming the selected record. If the initial read-back fails after a successful write, the resync path can also adopt the new record and return success rather than roll it back (`settings.rs:329-331, 409-425`).
  2. **Kernel refusal followed by rollback-write failure.** Let `store_zone` successfully store New York in generation 2, then refuse the kernel confirm (the existing refusal control supplies EALREADY). Make the restore's write to `settings.a` fail before writing. `restore` leaves generation 2 in force and returns false (`userland/neo-init/src/desktop_session/settings.rs:393-406`); `confirm_zone` discards that result and returns `Ok(false)` with the old live zone/mode (`userland/neo-init/src/desktop_session.rs:8525-8534`). The new zone remains stored and can be confirmed on the next boot. The source explicitly documents this outcome at `settings.rs:393-395`. This is a partial transaction with no successful rollback, even though the two keys no longer use separate writes.

- **PASS — a test forces a write failure and checks preservation (source witness, narrow coverage).** `setup-tz-write-fail-test` arms `FAIL_NEXT_WRITE` in `store_zone` (`userland/neo-init/src/desktop_session/settings.rs:375-377`); `commit` consumes it and short-circuits the actual write (`settings.rs:317-321`). The registered `login_setup_tz_write_fail` scenario (`tools/xtask/src/main.rs:3662-3670`) requires the failed-write/store/skipped-confirm sequence and `confirmed=0`, rejects a stored-zone or refused-confirm line, then runs the shared unchanged-clock and reboot checks (`tools/xtask/src/login_scenarios.rs:2081-2113`). The shared witness rejects confirmed UTC/EDT and key-by-key application, requires only the initial settings write, and checks journal times retain the RTC basis (`login_scenarios.rs:1953-1991`). Boot 2 must select generation 1 from `a`, show `zone not set`, and remain unconfirmed (`login_scenarios.rs:1995-2017`): retaining that initial record also retains its default RTC mode. This covers the requested ordinary forced-write failure. It does not exercise partial/fully landed writes, failed read-back, or failed rollback. New York uses the same local-RTC mode as the defaults, so the test does not attempt an RTC-mode transition or directly compare the live RTC-mode field. The refusal scenario checks successful rollback to generation 3, not failure of rollback (`login_scenarios.rs:2049-2079`).
