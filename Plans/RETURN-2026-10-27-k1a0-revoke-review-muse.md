# RETURN — relay #108: K1a-0, closing two revoke escapes in the capability graph (PR #166)

Reviewer: Muse (Gwen), a separate model family, reviewing Claude-authored code. Files read from the repo at the reviewed SHA. Pasted by the PL on 2026-10-27; banked verbatim by the PM.

Reviewed SHA: `149d4a19` (PR head `7e15450c` plus a merge of main). Gate batch 9, run 40484657565, all green.

1. **The race is closed — PASS.** `revoke_handle` holds the global `CAP_GRAPH` ticket lock across both the iterative walk and the removal loop (`kernel/src/sched/process.rs:2005ff`, walk at 2040–2065, `forget` at the end), and every install re-checks the parent live under the same lock (`install_minted_locked`, `process.rs:1858ff`, returning `InstallCapError::ParentGone`). No interleaving lets an install land under a cap a concurrent revoke removes: the install either waits on the ticket lock and then finds the parent gone, or completes before the revoke starts and is then walked.
2. **Laundering is closed — PASS.** Close and exit both re-parent through `CapGraph::retire` (`process.rs:1729`, nearest non-dying ancestor, bounded walk, cycle returns None in `kernel/src/sched/cap_graph_logic.rs`): `close_handle` (`process.rs:1787ff`), `teardown` (`process.rs:1764ff`, drains handles and takes derivations before retiring), the terminate path (`process.rs:3715–3721`) and the natural reap path (`process.rs:2856–2858`) all retire under `CAP_GRAPH`. One precision note: in source order `retire_one` (`process.rs:1752`) drops the closing cap's own edge and then re-parents its children, rather than re-parenting first. The checklist's "before" holds as an observability property, not source order: the whole sequence runs inside one held `CAP_GRAPH` section, so no revoke, install, close or exit can observe a child pointing at a dropped edge. Revoking an ancestor therefore reaches every live descendant after any sequence of derive, grant, close and exit.
3. **Rights never widen — PASS.** Re-parenting mutates only the `Option<CapId>` parent field in `cap_graph_logic.rs`, never rights bits. Derive enforces `child_rights.is_subset_of(parent_rights)` (`process.rs:1934`); grant takes the three-way intersection source ∩ offered ∩ max (`process.rs:2319ff`). The KAT (`tools/cap-graph-logic-tests/src/lib.rs`, chain root 1→2→3→4→5 with narrowing rights) closes middle caps [2,3,4] in every subset and permutation, asserting ancestry preserved, rights monotone across a re-parent, and `revoke_set(1)` equal to all survivors. One pre-existing qualification, not introduced by this change: TCP accept installs a socket with full READ|WRITE|CLOSE rights under a READ|CLOSE listener (`kernel/src/arch/x86_64/syscall.rs` ~4882), and a GPU fence installs FENCE_WAIT|FENCE_QUERY under a QUEUE_SUBMIT queue cap (~7673). Those creations are not rights-subsets of their graph parent, but re-parenting grants no new bit (the rights field is untouched); it only preserves or strengthens revocation reachability. The "no holder gains a right" property holds.
4. **A dead parent refuses the install — PASS.** `install_cap` refuses a recipient with `exiting` set, and `install_minted_locked` returns `ParentGone` when the parent is gone from the recipient's table and from the cross-process live scan. Spawn **refuses**: `spawn_user` returns `SpawnError::ParentGone` when the parent is not live (`process.rs:2649–2656`), mapped to EBADF by `sys_spawn` (`syscall.rs:1766`; hook twin at `process.rs:2187`). The child never starts, so it cannot run without the cap. Safe either way; refusal is what the code does.
5. **The edge gate is real — PASS, with named misses.** The gate (`tools/cap-graph-logic-tests/src/lib.rs`, edge_gate module) scans every `.rs` under `kernel/src` except `test_harness.rs` for the mutation tokens `.insert(`, `.remove(`, `take(&mut`, `.values_mut(`, `.clear(`, `.retain(`, resolves the enclosing function, and asserts the `seen` set contains at least derive_handle/.insert, teardown/take and revoke_handle/.remove, so the gate is live, not vacuous. A straightforward planted rogue direct edit in a new function is caught. Sites it would miss, as the checklist asks: (a) a macro expanding to a derivations write (call site has the token, no mutation token; macro definition has the mutation, no token); (b) an alias under another variable name (`let m = &mut *proc.derivations.lock(); m.insert(...)` — only the literal name `derivations` is tracked, which is why the current code, which names its local `derivations`, is caught); (c) a helper in another module that receives the map and mutates it; (d) direct field reassignment of `derivations` (not in the mutation list); (e) anything inside exempted `test_harness.rs`. Follow-up, not a revert trigger: make `derivations` module-private with CapGraph-only accessors, which closes (a)–(d) by construction.
6. **The ADR-010 amendment — PASS.** `docs/ADR-010-capability-system-foundation.md:271–288` states the rule (nearest ancestor not also being removed), the lock order (Channel.state → CAP_GRAPH → PROCESSES → handles → derivations), and explicitly says Q4 survive-exit is unchanged: a donor's exit still kills nothing in its recipients. No existing guarantee changes. Minor wording note, same as item 2: the ADR says children are re-parented "before a cap's edge is removed," while the code removes the closing cap's own edge first under the lock; observationally equivalent, but the ADR sentence would be exact if it said "before any other operation can observe the removal."
7. **No new denial of service — PASS.** `CAP_GRAPH` is a FIFO ticket lock (`kernel/src/sync/ticket_mutex.rs`: fetch_add ticket, spin until serving; guard Drop increments serving with Release), so a revoke's wait is bounded by the lockers ahead of it, one critical section each (design comment, `process.rs:1661–1674`). No park or IPC wait under `CAP_GRAPH` was found: holders sit in `without_interrupts` sections taking only spin/SwitchMutex table locks; `complete_grant` does its tensor mint outside the interrupts-off block, and spawn drops the guard before pushing the thread.
8. **Test-only items stay out of the product — PASS.** `neo-test-cap-graph-revoke` and `neo-test-cap-graph-unlocked-control` are defined at `kernel/Cargo.toml:575` and `:579` as `["neo-test"]` derivatives; every hook is gated on them (`process.rs` lines 1769, 2060, 2074, 2095, 2859, 3730; `syscall.rs:385`, `:1231`); `PRODUCT_IMAGE_KERNEL_FEATURES` (`tools/xtask/src/main.rs:5251`) contains no `neo-test*` entry. Also noted: `install_cap` has a deliberately broken path under `neo-test-missing-cap-lock-negative` (`kernel/Cargo.toml:554–556`, defined as `[]` but named `neo-test-*` and absent from the product list) which inserts without `note_parent` — a test-only negative gate, not product code.
9. **Coverage — PASS, with a named gap.** The neo-init scenario `cap_graph_revoke` (`userland/neo-init/src/main.rs:6608ff`) runs 7 legs (race-derive, race-grant, race-spawn; close; exit; kill; share-close) and prints PASS only when the leaked-bitmask is 0; the `cap_graph_race` hook (`process.rs:2095ff`) proves `CAP_GRAPH` is held under the fix (try_lock check, LOCK_NOT_HELD = −1000) and, under the control, runs inside the window so the cap survives — i.e. the legs leak under the control, which is what makes the control a valid falsifier. The pass/leak behavior itself rests on the green gate run, not a re-execution here. Accept and fence are covered only through the shared `install_cap` path (leg 7 is a tensor share): that is sufficient for the mechanism, because accept and fence install through the same `install_cap` and their closes go through the same `close_handle` (e.g. socket close ~`syscall.rs:5419`, `sys_close` ~`syscall.rs:6308`), and teardown is universal. Named gap: there is no direct accept-leg or fence-leg in the scenario.

**Overall verdict: PASS.** All 9 items pass. The item 3 cross-type note, the item 5 gate misses, and the item 9 accept/fence gap are recorded limitations, not failures.
