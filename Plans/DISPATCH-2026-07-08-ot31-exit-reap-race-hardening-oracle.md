## The confirmed window (from the OT-49 AAG, verbatim mechanism)
`exit()` (`kernel/src/sched/scheduler.rs:1065`) → `rotate` drops the scheduler lock with the **zombie `Box` already pushed to `zombies`**, and the dying CPU **keeps executing on the zombie's stack** (`record_context_switch` + the context-switch asm's register pushes + `xsave` writing INTO the zombie `Box`) until the final `mov rsp`. In that ~6-instruction window, a **BSP `reap()` that locks, pops, and `Thread::free`s** the zombie frees a **stack/FPU area still in active use on another CPU** — a use-after-free of a live stack. Cross-CPU only, vanishingly narrow, reachable mainly via the neo-test AP-placement path; **byte-identical pre-OT-49** (OT-49 changed only *where* `next` comes from, not this ordering — so this is a *pre-existing* hazard OT-49 surfaced, not one it introduced).

## The fix (ISC-1) — the release-on-new-stack discipline the IPC paths already use
The IPC block paths (`scheduler.rs:865`, `:879`) release their locks via **`context_switch_with_release2`** — the lock byte is cleared **on the NEW stack, after `mov rsp`**, so no other CPU can observe the parked thread as reap-able/runnable until the switching CPU is fully off the old stack. **`exit()` must adopt the same discipline** so the zombie is not visible to `reap()` (not popped/freed) until the dying CPU has switched off the zombie's stack. Two equivalent shapes (pick the one that's cleanest against the current code — you know it best):
- **(a)** route `exit()`'s final switch through the `context_switch_with_release2` pattern (release the scheduler lock / publish the zombie on the new stack, after the register save + `mov rsp`), OR
- **(b)** **defer the zombie push** to `zombies` until after the stack switch — the reaper can't see (and therefore can't free) a zombie that isn't published until the dying CPU is off its stack.
Either closes the window: `reap()` can never `Thread::free` a stack that a CPU is still executing on.
