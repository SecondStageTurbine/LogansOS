## FINDING B (CONFIRMED, PM re-verified in code) — the compositor can read the focused client's events
The receive gate rejects a handle *bearing ACTIVATE*, but **nothing stops the compositor process from minting a RECEIVE-only sibling and reading the queue.** The chain, every link verified:
1. `full_input_focus_rights()` (`kernel/src/sched/process.rs:255`) = the **compositor root** cap: `ACTIVATE | RECEIVE` + **full meta (incl. DERIVE)**. Its own comment: *"the client leaf is the DERIVE-time attenuation to RECEIVE-only."* So the compositor holds RECEIVE **and** DERIVE.
2. `is_subset_of` (`process.rs:117`) permits `RECEIVE ⊆ (ACTIVATE|RECEIVE)`; `with_cap` for `InputFocus` (`process.rs:686`) returns a leaf holding **the same `Arc<InputFocus>` / same id**, rights attenuated only.
3. The receive gate (`kernel/src/arch/x86_64/syscall.rs:5312-5318`) admits any handle with `USE ∧ RECEIVE ∧ ¬ACTIVATE ∧ is_active` and pops the single per-id queue in `DELIVERY` (`focus.rs:100-110`). **Nothing binds that queue to the client process.**

**Exploit (all in code today):** compositor holds root → `sys_derive(root, meta=USE, semantic=RECEIVE)` → a RECEIVE-only leaf **in the compositor's own table**, same focus id → `sys_input_focus_activate(root)` → `sys_input_focus_recv(self_leaf)` passes the gate → pops the focused client's key/pointer bytes. The `!ACTIVATE` check is bypassed by one derive. **The compositor snoops keystrokes** — the exact property (Redox-Orbital / Wayland man-in-the-middle) this slice exists to eliminate.

## FINDING A (CONFIRMED) — the invariant is untested (delete the guard, all green)
The QEMU scenario `atrium_input_routing_scenario` (`test_harness.rs:25363`) exercises only raw kernel objects (`InputFocus::new/activate/route_event/try_recv/debug_queue_stats`) — it **never calls `sys_input_focus_recv_impl`, never constructs a cap handle.** Its "no-snoop discriminator" asserts `debug_queue_stats()==(0,0)` (a non-active focus has no queue) — strictly weaker than "the gate rejects a snooper." **You could delete the `!has_semantic(ACTIVATE)` guard at `syscall.rs:5315` and every gate stays green.** The dispatch's crown-jewel requirement — *"PROVE the compositor's channel never carries an event byte, a falsifiable assertion, not a claim"* — is unmet.

## The fix
1. **Invert the trust model so no-snoop is STRUCTURAL (the real fix).** The **client** owns the `InputFocus` and holds the **RECEIVE-bearing** cap; the **compositor** gets an **ACTIVATE-ONLY** derived leaf (no RECEIVE) — so the compositor can *transfer* focus but **structurally fails the RECEIVE gate** and can never consume the queue, with no cap it can derive to get there (you can't derive RECEIVE from an ACTIVATE-only parent — `is_subset_of` forbids it). Reconcile with the Slice-2 **focus-request** verb: the compositor's ACTIVATE-only cap is what the focus-request/policy flow already wants; the client receives its own events via its RECEIVE root. *(Alternative if inversion is infeasible: bind RECEIVE-consumption to the owning process on the receive path — a lineage/holder check so a same-id RECEIVE leaf in a foreign table is refused. Inversion is cleaner and by-construction; justify whichever you pick.)*
   **Acceptance criterion (hard):** the compositor process, using ANY cap it can hold or derive, **cannot read an event byte.**
2. **Arm the falsifiable no-snoop proof (mandatory — close Finding A).** A QEMU scenario (and/or host KAT over the cap logic) that: mints the compositor's cap + a client RECEIVE cap, activates focus, routes an event, and asserts **(a)** the client reads it, **(b)** the compositor — via its own cap AND via any leaf it can `derive` — gets **EPERM / EAGAIN and zero bytes**. The test MUST go **red if the guard (or the inversion) is removed.** That is the un-deletable proof the dispatch required.
