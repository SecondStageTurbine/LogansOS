## Lenses — REFUTE-default

**1. I-14 fault containment — the primary lens (all three vectors).**
- **(a) Lock isolation:** does any part of the eth0 path — `boot_eth0.rs`, the CDC-ECM RX/IRQ path, `boot_frame_eth0.rs` — acquire an AI-governance lock (`INFLIGHT`/`RECENCY`/`ARENA`/the reservation/`TABLE`)? It now runs **during boot**, potentially interleaved with governance init in a way no test scenario ever was. Check the *ordering*, not just the absence.
- **(b) Liveness:** the DHCP pump is bounded (`aa6c5b27` is literally "use bounded product DHCP pump budget") — **prove the bound**. 4 attempts × 750k pump passes: can any path spin unbounded, block boot, or monopolise a CPU if the dongle is present but wedged (enumerates, never completes a transfer)? A boot that hangs on a half-dead dongle is worse than one that has no network.
- **(c) DMA:** every RX/TX buffer must route through `dma_arena::fence(...)`. **`fence_refusals=0` on the successful run is weak evidence** — it is consistent with "everything was fenced and nothing was refused" *and* with "the counter was never incremented because the fence was never called." Jarvis's Slice-4 lens found exactly that shape one lane over: `accel_intel` **never calls `dma_arena::fence` at all**, so its `fence_refusals=0` measured nothing. **Reason from the code path, not the counter.** Name every buffer the device DMAs into, and the fence site for each. If any buffer is allocated outside the arena, that is a blocker regardless of what the run printed.

**2. Absent / hostile hardware — the case the hardware run could not test.** The non-functional bar for every 0.1 rung is *no hang or panic on absent hardware*. The proven run had a working dongle. Refute the rest: **no dongle at all**; a dongle that enumerates but never links; a **different** USB-Ethernet chip that matches the CDC-ECM class but is not an AX88179 (the vendor-specific native init — does it get applied to a device that can't take it?); a device that unplugs **mid-DHCP**; a DHCP server that answers with a malformed or hostile OFFER. Which of these panics, hangs, or reads out of bounds?

**3. Frame parsing / on-wire bytes.** The AX88179 prepends a vendor RX header. Parsing attacker-controllable bytes from the wire is the single highest-risk surface here. Are lengths validated **before** they are used as slice bounds? Is a packet count from the header trusted? Can a crafted or truncated frame cause an OOB read, an underflow in a length computation, or an infinite loop in the demux? **The frame parser is remote-attacker-reachable the moment we ship — treat it as such.** Note whether any byte-oracle/KAT covers the header layout independently of the writer/reader pair, or whether the only evidence is that a real dongle worked once.

**4. The kill-switch — `boot-eth0` OFF ≡ prior layer, bit-for-bit.** The feature is default-off, which is the right shape. Prove it holds: with `boot-eth0` disabled, is the boot path byte-identical to `main`'s — no residual call, no changed init ordering, no unconditional `boot_frame_eth0` dependency? **This is the exact failure the rung-5 AAG caught** — the compositor gained an *unconditional* `/neofs/.arthur/memory` dependency behind what looked like a gated build. Look for the same shape here: something outside the `cfg` that now assumes eth0 exists.

**5. Completeness — what the green gate and the silicon run each structurally cannot cover.** QEMU has no AX88179. The bare-metal run had exactly one dongle, one LAN, one DHCP server, one boot. Say precisely what is proven, what is merely *not disproven*, and what has **zero** coverage from either channel. In particular: is the `boot-eth0` path exercised by **any** gate scenario, or is it in the same never-compiled/never-run position OT-69 just proved for `mt7601u` and `accel-intel`? Check whether `boot-eth0` appears in Prometheus's new `feature-gated-coverage` matrix (landed `3f756daa`) — if it does not, say so; that is a real gap and a cheap fix.
