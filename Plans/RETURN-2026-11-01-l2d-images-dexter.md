## The answer in brief

1. **The decoder exists; the desktop path does not.** `userland/neo-image-decode` is host-only
   std on main (`src/lib.rs:17-24`), and `libneo` refuses its `image-decode` feature for
   `target_os = "none"` with a `compile_error!` (`libneo/src/lib.rs:26-32`). The WM/Atrium has
   no runtime image path: icons are build-time RGBA blobs
   (`neo-atrium/src/icons.rs:4-7`), client surfaces are opaque XRGB with no alpha and no
   scaling (`libneo/src/atrium_wm.rs:267-273,345-369`), and the only client layers are
   `ROLE_TEXT`/`ROLE_WORKFIELD_ROOT`.
2. **App icons are not the first build.** They already ship as BLAKE3-pinned 40×40 blobs,
   rasterised on the host (`icons.rs:29-33`; `neo-atrium/src/scene.rs:948-975`). Runtime PNG
   icons would either put a decoder in the WM (forbidden by the process rule) or require a new
   icon-supply protocol for no visible gain.
3. **A wallpaper is not the first build.** The design authority rejects the wallpaper-and-icons
   desktop (`docs/THINK-2026-07-08-gui-vision-cerebro.md:28`,
   `docs/THINK-2026-07-23-desktop-ux-SYNTHESIS.md:14`), and a full-screen client base layer is
   a compositor change: `Scene::compose` hardcodes the WM's `base` as layer 0
   (`desktop_session.rs:901-914`), and `compose_layers_xrgb8888` requires an opaque full-scene
   base (`atrium_wm.rs:311-336`).
4. **The browser `<img>` is later.** OT-61 C2.4 is scoped to the 152-crate stylo closure; the
   image/SVG stack is in the 828-crate layout closure
   (`docs/RESEARCH-2026-10-30-ot61-stylo-layout-closure.md:17,214`). Servo's loader already
   decodes in its own process; whether it uses our API or its own `image` crate is an OT-61
   integration decision.
5. **First build: a one-image viewer (`neo-view`) + a `no_std` PNG backend + `desktop_image_boot`.**
   The WM opens the path and lends a `USE`-only READ cap (the `permission.rs:226-238` pattern,
   not the raw root open), spawns the viewer with a 64 MiB frame budget
   (`libneo/src/lib.rs:1337-1360`), and never decodes. The viewer reads 4 KiB chunks
   (`MAX_FILE_IO`, `syscall.rs:1529`), sniffs/decode with a 16 MiB cap
   (`neo-image-decode/src/lib.rs:127-145,155-178`), flattens RGBA to opaque XRGB, creates its
   own G1 surface, and commits. The WM copies the committed rect with `SharedPixels::snapshot`
   (`atrium_wm.rs:244-264`) and composites it (`desktop_session.rs:888-1000`). The kernel
   never sees the encoded bytes and has no image parser.
6. **Memory has a hard enforcement, not just a table.** The per-image cap is 16 MiB (2048²);
   the viewer's frame budget is 64 MiB; `mem-quota` charges heap maps and G1 buffers to the
   process account (`kernel/src/mm/pmap.rs:793-840`,
   `kernel/src/atrium/buffer.rs:141-160`), so an over-budget decode fails with `ENOMEM` and the
   WM keeps the last frame. The WM total at 1920×1080 is ~35 MiB; the first viewer is
   ~6–8 MiB.
7. **Cache: build 1 caches nothing.** The G1 surface is the cache; once the viewer commits, the
   WM holds `client_copy` and the viewer can free the RGBA. Later, a per-process LRU cache
   keyed by path + encoded length + a 64-bit digest, in decoded bytes, with the visible image
   pinned; no WM cache, no kernel cache, no shared decode service. There is no `stat` on this
   target (`docs/THINK-2026-11-01-l1d-coreutils-on-logansos.md:25-29,84-86`), so a path alone
   is not a reliable key.
8. **The gate is end-to-end independent.** A new `desktop_image_boot` scenario reads
   `/neofs/images/first.png`, shows it in a 640×400 client, and the kernel compares the
   framebuffer against a fixture generated by `reference_png_rgba.py` (a from-spec Python PNG
   decoder) plus `scene_oracle.py` (a numpy scene renderer). The fixture is regenerated by
   `scripts/desktop/check_fixtures.sh`. The discriminators include a wrong-image digest, an
   over-cap refusal, the encoded cap, the `mem-quota` `ENOMEM` case, the WM dependency/symbol
   check, and the `desktop-image`-off kill-switch.

## Upstream re-check for the recommended OS backend

I checked `zune-png` at the same pinned `zune-image` commit the L2b RETURN recorded, by fetching
the raw files from that commit (no summarizing read):

| Item | Value |
|---|---|
| Repository | `https://github.com/etemesi254/zune-image` |
| Pinned commit | `2f9086b07cdf5a36621ce18f79d310f99b751de9` (2026-10-24, the L2b `zune-jpeg` pin) |
| Crate | `crates/zune-png`, package `zune-png` 0.5.2 |
| Licence | **MIT OR Apache-2.0 OR Zlib** (`crates/zune-png/Cargo.toml`) |
| `no_std` | `default = ["sse", "std"]`; with `default-features = false` it is `alloc`-based, and `zune-inflate` 0.2.0 is also `no_std`-capable |
| Extra dependency | `zune-inflate` 0.2.0 (same triple licence) and `simd-adler32` for the `zlib` feature |

The THINK's §9.3 recommends this over waiting for OT-61's std: it keeps the viewer `no_std`,
matches the existing `zune-jpeg` family, and lands without OT-61. The cost is a second inflate
implementation beside `miniz_oxide`, which the existing fuzzer should cover with a `zune-png`
target. The cross-decoder KAT must be runnable on the host (a `zune-backend` feature), not only
on the OS target.
