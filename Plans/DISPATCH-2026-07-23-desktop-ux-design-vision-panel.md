## Why now
Slice-6 landed — G1/atrium is LIVE on silicon (Milestone A: boot → G1 owns scanout → confined `ROLE_TEXT` client → USB-HID input via `InputFocus` → composited answer) with glass material wired. That is the desktop **foundation**. What's missing to be an *actual desktop*: **window management** (multi-window/z-order/move/focus/stack) and a **graphical shell** (wallpaper + launcher/dock — the owner's home surface). This panel designs that layer on the proven G1 seam. (No build slot is opened here — the eventual implementation is gated + waits for a runner slot; this produces its spec.)

## The design question (each of you, independently)
Design the **window-management + graphical-shell layer on top of the existing G1 compositor** — capability-native, minimal, OURS (NOT X11, NOT a Wayland clone; the OT-52 stance), and **beautiful** (OT-45 is co-designed with this, not bolted on). Cover:

1. **Window-management model.** Multi-surface z-order / stacking, focus, move/resize, minimize/close — as **compositor-owned policy**. The compositor already holds scanout authority + composites confined `SurfaceCap` surfaces; extend it to manage *many* surfaces with a stacking order and a focus stack. What is the WM a *principal* of, and how does it stay the sole holder of composition/stacking authority (no client reorders/snoops another's surface — the anti-X11 invariant)?
2. **The capability model for windows.** Each window = a `SurfaceCap` (already exists); the WM as a trusted principal that grants/revokes surface slots. How does a client request a window, get input focus, and present — WITHOUT gaining scanout or the ability to see/move peers' surfaces? Map to the existing `CLIENT_ROLE`/`COMPOSITOR_ROLE` split (`atrium/logic.rs`) + `InputFocus`. No new ambient authority.
3. **The graphical shell.** The owner's home surface — wallpaper, a launcher/dock, the desktop metaphor **as far as Article 1.5 / OT-26 allow** (we reject desktop-metaphor-as-primary; what IS the right primary for an AI-native OS where Arthur/agents are first-class?). This is the beauty surface — propose the visual language (glass material is live; how do WM chrome + shell use it?).
4. **Reuse vs. new (grounded).** What's REUSED (G1 compositor, `SurfaceCap`, `InputFocus`, `ROLE_TEXT`/`ROLE_WORKFIELD_ROOT`, the glass blur path, ADR-073 surface protocol) vs. what's NEW (z-order/stacking state, WM policy, focus-stack, shell chrome, a launcher-cap). Name the kernel vs. userland split (is the WM in-kernel-compositor policy or a trusted userland principal? — argue it).
5. **The slice ladder.** Break the build into gated slices (like the glass P1 / browser C ladders) — the smallest first rung that shows a second window + focus switch on G1, then up. Each slice's kill-switch + discriminator.
