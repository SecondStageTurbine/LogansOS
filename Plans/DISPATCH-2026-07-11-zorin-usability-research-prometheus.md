## The PL's prompt (verbatim — this is the acceptance bar)
> *"I've been calling Zorin OS one of the most usable Linux distributions on the market for some time. Zorin OS is the ideal distro for anyone coming from MacOS and/or Windows. Zorin OS is exactly what an operating system should be, be it open-source or proprietary. One reason Zorin OS stands above the rest is the ability to easily choose (or change) the layout so the UI is perfectly familiar. Zero learning curve is always good for usability. Another helpful feature comes by way of open-source app suggestions. If you download and attempt to install a Windows application, Zorin OS will suggest an open-source equivalent."*

**The PL's goal, verbatim in spirit: make LogansOS the OS someone someday writes about this way.** So the research question is NOT "what does Zorin do" as a catalog — it is **"what did Zorin do that EARNED each sentence of that paragraph, and what is the LogansOS-native way to earn the same sentences?"** (Locate and read the actual review firsthand — the register reads like Jack Wallen's ZDNet/Linux coverage of Zorin; find the real source, quote it exactly, and mine the reviewer's *criteria*, not just the praise.)

## The load-bearing tension (design the study around it, don't paper over it)
Zorin's headline mechanism — **mimic the familiar desktop layout** — is something LogansOS has **ratified against**: The Atrium is explicitly not a windows-icons-menus desktop, and borrowing another OS's visual identity is the anti-pattern our design language names (distinctness IS recognition). So a naive "copy the layout switcher" reading is worthless to us. The valuable reading is one level up: **Zorin's real insight is migration psychology — meet the user where they already are; make the first five minutes cost nothing; never punish a habit learned elsewhere.** The mechanism (layout mimicry) is Zorin's implementation for a desktop OS. **Your job: extract the principle, verify how the mechanism actually works, and transpose the principle to an OS whose primary interface is conversation** — where our claim to "zero learning curve" is stronger than mimicry can ever be: *everyone already knows how to talk.*

## ISCs
- **ISC-1 — the Zorin mechanism inventory, firsthand.** How each praised feature actually works, from primary sources (zorin.com, Zorin docs/blog, the shipped tooling's own documentation; no summarizing fetch for exact claims): **(a) Zorin Appearance** — what the layout switcher really changes (panel/dock/menu arrangement? behaviors? shortcuts?) and what it deliberately does NOT change (the uncanny-valley boundary); which layouts ship free vs Pro; **(b) the Windows-app detection** — how attempting to run/install a `.exe` is detected and how the open-source-alternative suggestion is produced (where the equivalence database lives, how it's maintained, what happens when there's no equivalent — the fall-through to Wine/Bottles); **(c) the arrival experience** — first-boot/onboarding (Zorin Tour?), defaults, preinstalled-vs-suggested software posture; **(d) the edition structure** (Core/Pro/Lite/Education) and what the paid tier actually sells. For each: what it is, what it costs Zorin to maintain, and which *sentence of the review* it earned.
- **ISC-2 — the migration psychology, separated from the mechanism.** State the transferable principles explicitly, each grounded in what you verified in ISC-1: meeting existing vocabulary/muscle-memory; the first-five-minutes cost; redirect-rather-than-reject when the user reaches for a foreign thing; familiarity as a *bridge* (a starting point that fades) vs familiarity as an *identity* (borrowed clothes forever). Which of these did Zorin get right, and where does the mimicry approach hit its ceiling (the app-compat disappointment when Wine can't run the thing the familiar UI implied it could; behavior-vs-appearance mismatch)?
- **ISC-3 — the transposition (the payoff section — spend the most here).** For each transferable principle, the LogansOS-native analog, grounded in our shipped/ratified substrate:
  - **The redirect pattern, generalized:** Zorin's "you tried a Windows app → here's the native equivalent" is *exactly* our shape: attempted-foreign-thing → suggested-native-way, stated kindly, never a dead end (the explain-never-vanish lens, already standing). Transpose it to: the user *speaks in Windows/macOS idiom* ("open Task Manager," "where's the Control Panel," "empty the Recycle Bin," drops a `.exe` on the machine) → **Arthur understands the foreign vocabulary as intent**, does the native thing, and gently names it ("that's `neo> ps` here, sir — I've opened it"). A **familiarity translation layer as knowledge in Arthur, not chrome in the UI.** Map it onto OT-26 (intent→Action), the OT-44 H2 catalog (the manifest-visible app catalog is our equivalence-database analog), and the butler register. What does the translation vocabulary need to cover, and where does it live (a curated mapping? the model's own knowledge, guarded by clarify-don't-guess)?
  - **The arrival moment:** Zorin wins the first five minutes with a familiar screen. Our first five minutes = the first conversation. What must Arthur's first-boot experience do so a Windows/macOS migrant feels *zero* learning curve — not because the screen looks like home, but because nothing needs to be learned to start? (Composes with the v1 console greeting, OT-46 persona, F1-F8.)
  - **The honest non-transposition:** say plainly which Zorin mechanism we do NOT adopt (layout mimicry of other OSes) and why (the Atrium's ratified identity; the Tahoe distinctness lesson; mimicry sets compat expectations a non-Windows OS structurally can't meet — the ReactOS-treadmill rhyme, already banked in OT-44).
- **ISC-4 — the anti-lessons (trap-mine the model).** Where Zorin's approach costs it: the uncanny-valley risk (looks like Windows ⇒ expected to *behave* like Windows ⇒ disappointment where it can't); mimicry as permanent identity vs bridge; the equivalence-suggestion DB's maintenance burden; the Pro-tier structure vs our standing ruling (**tiers are NEVER the brain axis** — verify what Zorin gates behind Pro and state what our analog must never gate). Each anti-lesson → the discriminator/rule that keeps us off the trap.
- **ISC-5 — the north-star artifact: write the review we want.** Draft **the one-paragraph review of LogansOS we are trying to earn**, in the register of the PL's quote — then, under it, the **mechanism checklist that earns each sentence** (which shipped/ratified/banked piece delivers it, and what's still missing). This turns "someone someday writes about us this way" into a falsifiable acceptance bar, the way F1-F8 did for the five-year-old test — outward-facing this time. Mark honestly which sentences we cannot yet earn and what build earns them.
