## What A3 is (and what it is NOT)
A1 = one read/nav action. A2 = one mutating action, made safe-to-be-wrong by OT-19. **A3 = a *sequence*** — "clean up my downloads folder and tell me what you removed" decomposes into read-dir → several deletes → a summary. Each step still runs the A1/A2 loop (constrained-decode → typed `Action` → `execute_action()` cap-check → result); A3 is the **orchestration layer** that threads results between steps, decides the next step, applies the OT-19 graduation **per step**, and reports the whole chain honestly.

**NOT** new substrate: reuse A1's decode (`SYS_GENERATE_MASKED`), `execute_action()`, A2's mutating grammar, OT-19's `reversibility_logic.rs`, OT-18 grants. **NOT** irreversible-external (NetSend stays an OT-18 restriction, out of scope). A3 is the loop + the multi-step safety composition + the report, not a new action vocabulary.

## The ratified substrate A3 orchestrates (all landed — reuse, don't rebuild)
- **A1/A2 agentic loop** (`agentic_action_logic.rs`): the single-step decode→Action→cap-check→result. A3 calls it in a loop, feeding each result back as context for the next step's constrained decode.
- **OT-19 reversibility** (`reversibility_logic.rs`): copy-before-write, tombstone-on-delete, one-session/10 MB-LRU undo window, `.arthur/stakes.json` policy, fail-safe confirm-before-destructive. A3's per-step mutating actions route through this exactly as A2 does — the undo window is **already session-scoped**, so a multi-step chain is already reversible step-by-step.
- **execute_action() cap-check** (I-15): the authority boundary, re-run **every step**.

## ISCs
- **ISC-1 — the multi-step loop (the core).** Given a goal, run an **interleaved observe→act loop** (ReAct-style, recommended over plan-all-upfront: robust to a weak model and to reality drifting from a pre-baked plan — and it lets clarify-don't-guess fire mid-chain): constrained-decode the *next* action given `(goal, results-so-far)`; execute it (through A1/A2's existing path); append the result to context; repeat until the model emits a terminal `done` action or a `clarify`. Constrained decode as A1 does — each step emits only a valid `Action`, `done`, or `clarify`. If you choose plan-then-execute instead, justify it and keep clarify-per-step.
- **ISC-2 — per-step OT-19 graduation (the load-bearing safety composition — the thing multi-step must NOT break).** The OT-19 confirm/undo graduation applies **per mutating step, never once for the chain.** A multi-step goal MUST NOT become a way to batch-approve destruction: a chain containing three irreversible-high-stakes deletes confirms **three times** (or per the stakes policy), not once at the top. Reversible steps obey silently + back up (undo available); irreversible-local + high-stakes surface-once + confirm — identical to A2, evaluated at each step. Reuse `reversibility_logic.rs`; add no new authority.
- **ISC-3 — bounded autonomy (runaway prevention).** The loop is **step-budgeted** (a hard max-steps ceiling; on hitting it, stop and report honestly, never silently truncate — cite what's done and what's left, in the butler register). This is the multi-step analogue of the kill-switch discipline: autonomy you can bound is safe autonomy.
- **ISC-4 — partial-failure + whole-chain reversibility semantics (the genuinely-new design point — get this right).** Define what happens when step *k* of *n* fails or is declined: A3 does **best-effort with an honest ledger** — it does NOT silently roll back completed steps, but because every completed mutating step is in the OT-19 session-undo window, the transcript reports "I did steps 1–2 (both undoable), stopped at step 3 because <reason>" and the owner can undo the chain via the existing session-undo. State the semantics explicitly; do NOT invent a hard cross-step transaction/DB — the honest report + the session-undo window IS the reversibility story. Prove the whole chain is undoable after a partial run.
- **ISC-5 — clarify-don't-guess, mid-chain (OT-26 D4).** As context accumulates the weak model can drift; any ambiguous step → `clarify` in the butler register, never a guessed destructive act. This is the primary recovery path and matters more in A3 than A1/A2 (more steps = more drift surface).
- **ISC-6 — close the banked A2 residual: the stakes-policy-on-a-reversible-path confirm.** OT-19's stakes policy can elevate a *normally-silent reversible* action to a confirm, but that path was reachable-yet-ungated after A2. **A3 ships a `.arthur/stakes.json` fixture that exercises it** — a multi-step scenario where a step is reversible but the user's stakes policy makes A3 surface-and-confirm it anyway (Arthur never judges stakes; the policy does — OT-19 D3). This is a required deliverable, not optional.
- **ISC-7 — the transcript surface + the duality gate.** The chain's report in the OT-46 **butler register**: honest, measured, names each step + its undoability ("Done — three files removed, all undoable, sir"). Run against the **F1-F8 five-year-old checklist** (`THINK-2026-07-07-usability-five-year-old-design.md`) AND the **S1-S8/T1-T4 duality gate** (`THINK-2026-07-08-poweruser-neo-shell-duality-design.md`): a multi-step goal's `neo>` equivalent is a pipeline/script — show the agentic multi-step path and the `neo>` power path coexist, and that A3 can do **nothing** `neo>`+caps couldn't (power-is-not-jailbreak; multi-step is not an escalation channel).
