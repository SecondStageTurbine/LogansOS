## Why you, why now
Cerebro's C1 design doc (`docs/RESEARCH-2026-07-22-ot61-c1-host-runtime-abi-design-FINDINGS.md`, on branch `codex/ot61-c1-host-runtime-cerebro`) freezes a **five-primitive ABI** on the claim that **`std::sys` and SpiderMonkey's pthread port converge** on the same POSIX/futex-shaped set — so "designing for one designs for both." The load-bearing simplification is: build **one** futex wait/wake and get *both* std's futex-mutex/condvar AND pthread's mutex/cond in userland; plus TLS-keys-over-a-single-FS.base-setter with **no loader `PT_TLS`**. That convergence was synthesized by a **Claude** seat from your SpiderMonkey findings (`docs/RESEARCH-2026-07-22-ot61-servo-host-closure-spike-FINDINGS.md §2`). **A same-family convergence is weak evidence** (shared priors, shared blind spots). You sourced the real SpiderMonkey needs — so you are the right lens to falsify the force-fit. **C1.0 (VM+clock) is already ratified and building** — this review does NOT block it; it gates the **C1.1 (futex+thread) / C1.2 (TLS)** freeze, which is where the convergence risk lives.

## The job — REFUTE, don't ratify (default-to-suspicious)
Read the doc. For each of the three convergence-dependent primitives, **try to find a real consumer need the frozen ABI does NOT serve** — a concrete `std` or SpiderMonkey requirement (cite file:line from the engine source / rust-src you already have) that would force a C1 redo if discovered after the syscalls exist. Specific refutation targets (attack these, add your own):

1. **P1 futex convergence.** "One `futex_wait`/`futex_wake` → both sync layers in userland." Refute: does SpiderMonkey's `Mutex_posix.cpp`/`ConditionVariable_posix.cpp` (or std's futex mutex/condvar) need a semantic the bare Linux-subset futex can't give **without a kernel change** — e.g. a cond-var **monotonic-vs-realtime deadline attr**, `PTHREAD_PROCESS_SHARED`, robust/PI mutexes, requeue, or a wake-fairness guarantee? Is "spurious wake permitted" actually tolerated by **both** call sites?
2. **P2 thread ABI** (`create/join/detach/exit/yield/setname/self`, stack+guard at creation). Refute: does pthread / the GC need something **not** in the seven syscalls? Specifically — **SpiderMonkey's GC stack-scan (`NativeStack.cpp`) needs the thread's stack base+extent**; the doc says stack bounds are "provided at creation" — **does the ABI actually expose stack base+size *back to the running thread*** for the conservative GC scan, or only accept them at spawn? Also: `pthread_cancel`, per-thread `errno`, detach-state-at-create vs. separate `detach`, TLS-installed-before-first-user-code ordering.
3. **P3 TLS (the highest-risk force-fit).** The doc keeps the kernel tiny — **one FS.base setter, userland keys, loader stays PT_LOAD-only (no `PT_TLS`).** Refute hard: **does std or SpiderMonkey use *native* `#[thread_local]` / `__thread` / `MOZ_THREAD_LOCAL` (the compiler-emitted, FS-relative-at-fixed-offset TLS model)** rather than only runtime `pthread_key`? If so, the compiler emits FS-relative accesses against a `PT_TLS` image the loader is declared **not** to build — a real gap the userland-key scheme does **not** cover. Confirm from the actual engine + rust-src whether native TLS is in the no-JIT interpreter path. Also: does the userland destructor layer run the **POSIX iterated-destructor passes** (`PTHREAD_DESTRUCTOR_ITERATIONS`) both consumers may rely on?
4. **(bonus) P5 W^X / no-JIT.** The A1 JIT deferral is correct in principle — but refute the *premise*: does SpiderMonkey **no-JIT interpreter** truly never allocate executable memory (baseline ICs, wasm baseline, regexp JIT, trampolines)? If the interpreter still needs a W+X or RX-codegen path, "C1 introduces no W^X-violating path" is understated. Cite the source.
