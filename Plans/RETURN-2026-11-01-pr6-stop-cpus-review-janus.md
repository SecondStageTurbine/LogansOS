Reviewed PR #6 head `3212ad13a9800172952be4a50da734c852c2676e`, fetched from `pull/6/head`; compared with `origin/main` at `26b59b7184776b2ca5a34d269cc74b63eb7c5f03`. All source line numbers below refer to the reviewed head. Overall: FAIL.

1. FAIL — an in-flight shootdown is not drained before the shutdown CPU becomes unserviceable (CP-64). `kernel/src/acpi/shutdown.rs:238` disables interrupts before broadcasting STOP; `kernel/src/arch/x86_64/cpu_stop.rs:74` waits 100 ms before sending NMIs. Neither withdraws shootdown readiness nor synchronizes with the sender lock. Concrete interleaving: at SMP=2, CPU 0 enters K4 and executes CLI; CPU 1, already in an IF=0 shootdown sender, publishes a request targeting CPU 0. CPU 1 cannot take STOP, and CPU 0 cannot acknowledge the shootdown. The sender panics after its 50 ms deadline (`kernel/src/mm/tlb_shootdown.rs:21`, `kernel/src/mm/tlb_shootdown.rs:378`), before K4's NMI escalation. The existing safe transition drains senders under their lock before CLI and withdrawing readiness (`kernel/src/mm/tlb_shootdown.rs:64`); K4 does not use that protocol. Ordinary interrupt handlers and IRQ-safe lock holders defer STOP until IF permits it, or are interrupted by the NMI; the park handlers themselves take no shared lock (`kernel/src/arch/x86_64/cpu_stop.rs:100`, `kernel/src/arch/x86_64/cpu_stop.rs:113`). That ordinary case does not establish safety for the overlapping shootdown.

2. FAIL — acknowledgements are published, but K5/K7 proceed even when some never arrive. Release stores at `kernel/src/arch/x86_64/cpu_stop.rs:125` pair with Acquire loads at `kernel/src/arch/x86_64/cpu_stop.rs:96`. The second wait's result is discarded at `kernel/src/arch/x86_64/cpu_stop.rs:78`; remaining CPUs become `holdouts`, and `kernel/src/acpi/shutdown.rs:239` merely prints that mask before continuing. Concrete input: four registered CPUs, CPUs 1 and 2 acknowledge STOP, CPU 3 acknowledges neither STOP nor NMI. A host probe of the actual stop-loop source returned `targets=0xe, parked_by_ipi=0x6, parked_by_nmi=0, holdouts=0x8` after two waits. This violates the single-CPU assumptions in `kernel/src/arch/x86_64/ioapic.rs:117` and `kernel/src/drivers/console/serial.rs:39`. A concrete deadlock variant is an AP holding SERIAL when an earlier NMI enters before STOPPING, then self-deadlocking in `dump` (`kernel/src/arch/x86_64/idt.rs:1183`, `kernel/src/arch/x86_64/idt.rs:600`): NMI blocking prevents the later stop NMI, and K4's next print waits forever on SERIAL (`kernel/src/drivers/console/serial.rs:143`). With another AP acknowledged by NMI, forcing SERIAL open can instead overlap an unparked owner. Timeout must select a path safe with live holdouts, rather than assuming they stopped. The nominal two 100 ms waits also depend on a running PM timer (`kernel/src/acpi/power.rs:144`, `kernel/src/acpi/power_logic.rs:253`): a constant-zero timer and no acknowledgements never reach escalation. A probe aborted that actual PM-wait loop after 1,000,000 identical reads; there is no independent fallback deadline.

3. FAIL — K5 masks I/O APIC entries and the shutdown CPU's LAPIC timer, but does not mask MSI/MSI-X. `kernel/src/acpi/shutdown.rs:248` calls only timer disarm and `MaskPlan::mask_all`; `kernel/src/arch/x86_64/ioapic.rs:120` sets each redirection entry's mask bit, and `kernel/src/arch/x86_64/lapic_timer.rs:309` masks/stops the local timer, including its TSC deadline. No PCI interrupt-disable or MSI-X table masking is called. Concrete input: enable xHCI MSI (`kernel/src/drivers/usb/xhci.rs:741`) or NVMe MSI-X (`kernel/src/drivers/block/nvme.rs:251`), request shutdown, then inject a device event after K5. MSI remains enabled/unmasked (`kernel/src/drivers/pci.rs:793`, `kernel/src/drivers/pci.rs:822`) and bypasses the I/O APIC. If shutdown runs on an AP, the programmed destination is the now-stopped BSP (`kernel/src/arch/x86_64/apic.rs:295`); otherwise the interrupt can remain pending at the shutdown CPU. The stop-before-mask order does not deprive the implemented K4/K7 waits of a needed device IRQ: those waits poll ports with IF=0 (`kernel/src/acpi/power.rs:418`). That narrower ordering property does not satisfy source masking. Missing MADT also silently skips I/O APIC masking (`kernel/src/acpi/shutdown.rs:235`, `kernel/src/acpi/shutdown.rs:250`). The new gate checks the presence of a K5 log marker, not actual MSI masks or a valid I/O APIC count (`tools/xtask/src/main.rs:9768`).

4. FAIL — literal feature-off binary identity; PASS for preserving the previous shutdown sequence. The new shutdown call/module, STOP vector, NMI hook, output mode, and masking code are feature-gated (`kernel/src/acpi/shutdown.rs:173`, `kernel/src/arch/x86_64/mod.rs:23`, `kernel/src/arch/x86_64/idt.rs:226`, `kernel/src/arch/x86_64/idt.rs:1186`, `kernel/src/drivers/console/serial.rs:140`). However, `kernel/src/arch/x86_64/apic.rs:240` unconditionally replaces the existing fixed-IPI implementation with a call to a new helper. Concrete build input on both the PR and its parent `07d7f6ef9651a143191e2aa8b525713b3fc3bf16`: from `kernel/`, `cargo rustc -Zjson-target-spec --features power-clean --bin kernel -- -C debuginfo=0 --emit=asm` (no `power-stop-cpus`). Both builds passed. In the parent, `send_fixed_ipi` begins with a 72-byte stack allocation and calls `lapic_id_for_cpu`; at the PR head it pushes one register, ORs `0x4000` into the vector, and calls `send_ipi_low`. Thus generated instructions differ even with debug information disabled. The same ICR bits are ultimately sent, so this is a literal identity failure, not evidence of a changed feature-off shutdown outcome. Preserve the old helper under the feature-off configuration if literal identity is required.
