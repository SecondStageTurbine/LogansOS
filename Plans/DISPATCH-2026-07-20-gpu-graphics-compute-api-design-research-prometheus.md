# DISPATCH: GPU graphics/compute API — design + prior-art research (glass-first) → Prometheus

**Date:** 2026-07-20
**From:** PM (Claude)
**To:** Prometheus (research seat, cross-model from the Claude PM)
**Status:** DISPATCHED — **pure research/design, NO-GATE** (a FINDINGS/design doc). PL-ratified 2026-07-20 as **the next major GPU lane** after Chad's browser cross-check (`docs/RESEARCH-2026-07-20-ot61-browser-crosscheck-FINDINGS.md`) established that a **GPU graphics/compute API is the shared prerequisite for BOTH glass and the browser** — OT-63 so far is the *display* path (present/flip/scanout-fence); WebRender needs a GL/wgpu-class device we don't have, and glass's Vello backdrop-blur is a GPU *compute* pass that needs the same substrate. This pass designs that substrate. **Glass is the nearer-term payoff, so scope glass-first.**

## The framing
**Design a cap-native GPU graphics/compute API on the Intel Gen9 iGPU, scoped so its FIRST deliverable unblocks glass (Vello backdrop-blur as a GPU compute pass), with the fuller graphics surface (render targets for WebRender) as the stated longer target.** Build on what exists — do NOT design from scratch:
- **Phase-6 Gen9 GPU compute** (ADR-032 `docs/ADR-032-phase-6-intel-gen9-gpu-compute-driver.md`, the BUILD-4a bring-up, `RESEARCH-2026-06-08-gen9-execlist-lrc-bringup.md`): execlists/LRC, GGTT/PPGTT, ring submission — the compute-submission foundation likely already exists in-tree (`kernel/src/accel/` / `intel_gen9_ppgtt.rs`). Inventory it FIRST.
- **OT-63 display path** (merged): present backend, `GpuSubmitCap` (the cap that gates GPU submit — the graphics API's authorization primitive), scanout-DMA fence (I-14(c)).

## What the research must answer
1. **Inventory the Phase-6 Gen9 compute foundation** — what's already in-tree (execlist submission, PPGTT, EU dispatch, any compute-shader path)? What did BUILD-4a actually prove on silicon vs QEMU? This is the base; the API is the layer above it. (RAG/grep the `accel/` tree.)
2. **What does Vello's compute backend minimally require?** Vello renders via GPU compute shaders (its `wgpu`/compute pipeline). To run Vello's blur/scene compute on Gen9, what's the minimal device contract — a compute pipeline (shader module + bind groups), storage/uniform buffers, dispatch, a fence/completion (we have present-fence + GpuSubmitCap)? Map Vello's requirements onto a **minimal Gen9 compute device**, NOT a full wgpu implementation.
3. **The API-shape decision (load-bearing):** a **full wgpu-class device/queue/pipeline API** (large, serves WebRender later) vs a **minimal compute-first device** (serves Vello/glass now, extends to graphics later). Recommend, with the effort/risk of each and how the minimal path extends to the WebRender needs without a rewrite. (This is the analogue of the browser engine decision — get it right.)
4. **The Gen9 hardware surface** — what the Gen9 render/compute engine (EUs, the command streamer, MEDIA/COMPUTE pipelines, the ISA) exposes for compute dispatch; the shader compilation path (do we need an EU shader compiler, or can Vello's shaders be pre-compiled / is there an existing path?). Prior art: Intel PRM Vol for Gen9 compute, Mesa/i915 for **principle only (GPL — no code lift)**, how other Rust GPU stacks target Intel.
5. **The cap-native GPU device model** — the graphics/compute device is cap-bounded: `GpuSubmitCap` gates submit (Slice-2, merged), the scanout/render DMA is fenced (Slice-3, in flight), I-14 containment holds (a GPU shader fault can't reach governance/tensor memory — the IOMMU/fence story). State how the API preserves I-14.
6. **The build ladder** — staged from the Phase-6 base to glass: Gen9 compute device → Vello compute backend → glass backdrop-blur → (later) render targets → WebRender. What's the MVP (glass blur running on the iGPU) and the honest effort to it.
