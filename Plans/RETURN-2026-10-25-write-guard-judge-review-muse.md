The verdict below covers the guard change itself.

1. The judgement runs exactly once per device — PASS.
kernel/src/drivers/block/mod.rs:233-245: arming() returns the completed value from arming.get() if present; otherwise only the caller that wins the judging compare-and-swap (line 239) enters call_once (line 242). Every other caller goes to wait_for_judgement(). The flag and the Once are per device (mod.rs:109-116), so no path runs judge() twice or skips it on the normal path. Observation, not a fail: if judge() panicked, judging is never cleared, so no path could re-run or complete the judgement and waiters would loop on arming.get(). The failure direction is fail-closed (no write proceeds), judge()'s paths are fallible-safe, and allocation failure is the only panic vector.

2. No write before the decision — PASS.
mod.rs:372-376 (submit) and mod.rs:391-396 (write_block) both gate on write_allowed() → arming() before any inner call. A caller arriving mid-judgement loses the CAS and waits in wait_for_judgement() (mod.rs:248-259), which loops on arming.get() until the decision exists. Reads, flushes, and geometry pass through without arming, and none of them writes data. The test-only raw-write path (mod.rs:467-476) gates on write_range_allowed() the same way.

3. Refusals still hold — PASS.
mod.rs:284-299: a write outside every armed extent is refused, with the first refusal logged (only when claims are non-empty). write_guard_logic.rs fails closed when the judgement itself fails: an unreadable LBA 0 gives opaque-unreadable (:301), an unbelievable GPT gives opaque-gpt-invalid (:357), and a bad MBR gives opaque-mbr-invalid (:360); GPT copies validate header CRC32 (:468) and entry-array CRC32 (:504); a blank-start read error is not blank (:554-568). The no-marker refusal is logged at judgement time (mod.rs:308-336). PR #120 did not touch any of these paths.

4. The judgement itself reads, never writes — PASS.
write_guard_logic.rs:570-571 (judge(), documented "Reads only") calls only disk.read() across the NEOFS copies, log header, scratch sector, partition table, and blank-start probes. GuardReader (mod.rs:172-220) implements only Disk::read, via read_block calls in 64 KiB chunks. The only write-like functions in the logic file build in-memory buffers (sealing/provisioning helpers) and never touch the device.

5. The interrupts-on wait is safe for every caller — PASS.
Checked against the lock audit, not just its summary. No caller holds an interrupt-safe or ISR-taken lock at arming(): the cache's lock is scoped to the snapshot and released before write_fs_block (cache.rs:559-571); the sink's install() does its first write with no lock held and sets SINK only after it returns (block_sink.rs:144-166), so sink paths holding SINK can only exist after the judgement and take the arming.get() fast path; writes_allowed() and guard_allows_raw_write() drop REGISTRY before arming (mod.rs:402-407, mod.rs:467-476); write_block/submit hold no locks. NeoFS SwitchMutexes (entries, metadata, record, inode_block) may be held, but no ISR takes them. The caller's interrupt state is restored before the inner device is used: with_interrupts_enabled saves the prior state and restores it in a Drop guard (kernel/src/arch/x86_64/mod.rs:478-501), and the wait loop breaks inside that closure (mod.rs:251-258). On virtio the window adds nothing — the same chains already turn interrupts on in the io_gate acquire under the same locks. On AHCI/NVMe the window is new, but the hazard it could expose (a preemptible entries holder with an IF=0 spinner on the same CPU) already exists on main without this change, and the old IF=0 spin with entries held was the deadlock this PR fixes. The follow-up (wrapping the NeoFS bodies of sys_fsync, sys_open, and sys_readdir interrupts-on) has since landed on main as #121 and closes that residual window; it is not part of #120's verdict.

6. The test-only items stay out of the product — PASS.
The judge pause hook and wait counters are all under neo-test-block-write-guard (mod.rs:124-168); the spin-control wait is under neo-test-write-guard-judge-spin-control with the normal wait under not(...) (mod.rs:261-269); the guard-off judge() is under neo-test-block-write-guard-control with a compile_error! for bare-metal, product, and fb-progress-console builds (mod.rs:339, mod.rs:505-515). All three features derive from neo-test (kernel/Cargo.toml:797-803). PRODUCT_IMAGE_KERNEL_FEATURES (tools/xtask/src/main.rs:4879-4938) contains no neo-test feature, and the product build adds only hwp-performance (:4940-4955); CI's image-kernel-build uses the same function.

7. Coverage — PASS.
The block_write_guard judge-contention leg (kernel/src/test_harness.rs:19193-19238) holds the judgement's first read for 20 ticks, then asks for the same judgement with interrupts off, and fails if the waiter spun with interrupts off (:19232), if it did not wait at all (:19235, guarding against a vacuous pass), or if it got the wrong judgement (:19238). It is skipped under the guard-off control, whose judgement reads nothing. The NOTE's falsification result stands: the spin control hung on all 4 attempts, and the fixed branch ran 0 hangs in 12. Gaps the gate does not cover, named: AHCI/NVMe on real hardware (the gate runs QEMU virtio-blk only); the judge-panic path (fail-closed, liveness only, see item 1); multi-waiter contention (one waiter exercises the shared loop, so the mechanism is covered but N-waiter behavior is not directly exercised); and the sink-install lock ordering, which is covered by the audit rather than a gate leg.

Overall verdict: PASS.
