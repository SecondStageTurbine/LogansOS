The CP-86 claim about the lifetime of a running sibling's own address space and thread is sound.
The known, disclosed CP-86 liveness gap remains: it also permits a running kernel-side joiner to
park after the drain. This is the concrete item-2 failure below, not a claim of premature memory
freeing. C1.3b must be checked separately; a later fix is not credited to this pinned commit.

1. **PASS — CP-86 own-process/thread memory lifetime.**
   User Thread objects own `Arc<Pmap>` and `Arc<Process>` (`kernel/src/sched/thread.rs:98`, `:123`);
   user constructors attach them (`:483`, `:558`). `Thread::free` releases them at `:227` through
   `:235`. `scheduler::exit` keeps the scheduler lock across the stack switch
   (`kernel/src/sched/scheduler.rs:1601`, `:1661`), and the BSP reaper takes that same lock before
   popping a zombie (`:2649` onward). Thus it cannot free the exiting kernel stack before the CPU
   leaves it; a remote Running sibling is not a zombie at all. `process.rs:587` decrements the
   registry's live count only at reap; `:2474`, `:2493` defer natural process teardown until the
   last thread. exit_group/fault retirement set flags and drain siblings, retaining PROCESSES
   registration (`:2890` onward). `wait_for_exit_abi` consumes completion or parks, and does not
   remove a target Process (`:1952`). External terminate can remove registration earlier (`:3175`
   onward), but a surviving Thread's own two Arcs still prevent its Process/Pmap destruction.
   A live sibling therefore retains its own user mappings, Process allocation and kernel stack.
   This is a static lifetime check, not a proof about every other raw-pointer syscall in the kernel.

2. **FAIL — a joiner can park after the retirement purge.**
   With `browser-runtime` on and `wait-multiplex` off (valid feature configuration;
   `kernel/Cargo.toml:390`, `:413`), process P has W on CPU 0 and J on CPU 1, possible after IPC
   migration. J enters `thread_join_for_current(W)`, sees W's done-word zero and claims its record
   (`process.rs:2635`, `:2672` onward), then pauses before `futex::wait_on_key` at `:2700`.
   W calls SYS_EXIT: `retire_process_from_current_thread` marks P exiting, purges futex entries,
   and drains ready/token slots (`process.rs:2890` through `:2924`). J is Running and absent from
   those stores. W exits and is reaped; the reaper's fault-killing branch scans IPC and sys_wait
   stores, but generic token re-draining is conditional on `wait-multiplex` (`:2461` through `:2471`).
   J now enters `futex::wait_on_key` (`kernel/src/sched/futex.rs:146`): the queue-guard recheck tests
   only the done-word (`process.rs:2702`); there is no exiting check. It installs an infinite
   waiter/token after the purge. SYS_EXIT did not call `thread_exit_current` to set W's done-word.
   J never wakes, live remains nonzero, and P's parent's sys_wait never completes.

   This schedule is checked statically against both sides of the locks; no forced QEMU schedule
   is claimed. It is a concrete late-park symptom of the disclosed CP-86 Running-at-drain gap,
   whose planned repair already mentions futex refusal. Existing parked siblings are extracted
   once under their owning locks; a token already taken by a racing waker is generation-checked
   at scheduler ownership transfer. A Ready -> Running winner can still escape the scans. The
   unconditional checklist statement that no joiner parks after the drain is false at this SHA.
