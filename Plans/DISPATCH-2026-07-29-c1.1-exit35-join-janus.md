## The question
**What makes `h.join()` return non-`Ok(0)` for a normally-exiting `parked_waiter`, intermittently, with no forced teardown in play?** Trace the plain path: waiter woken → returns from `sys_futex_wait` → thread body returns 0 → exit → zombify → reap → joiner collects status. Specific angles:
1. **Join-vs-exit race on status collection** — can the joiner attach *after* the target has already exited and been reaped, so the status is gone (ESRCH/EINVAL) rather than `Ok(0)`? Is there a window where a reaped-but-not-yet-collected status is dropped?
2. **Ordering of done-word store vs status publication** — is the collected status published before/after the join wake, and can a joiner observe the wake but not yet the status?
3. **Multiple joiners / repeated join** — check 7 joins 3 handles in sequence; can an earlier join's reap disturb a later handle?
4. **Does the libneo `neo-test` feature gating change the userland thread/join code path** (feature unification reaching `neo-worker`/`neo-init`)? This is the unexamined half of the regression window.

## RESULT (Janus, 2026-07-30) — **HOLDS**: the plain join/reap path is race-free
Every interleaving closes under the `Process.threads` registry lock, verified with file:line:
- exit publishes `exit_code` → `done` → `done_word.store(1, Release)` under the registry lock (`process.rs:2461`); join claims the record under the **same** lock before parking (`:2523`); reap marks reaped and removes only if `detached || collected`, same lock (`:561`); join's final collect holds the lock, removing if already reaped else marking collected (`:2573`); the syscall wrapper returns success only once the encoded tag is present (`syscall.rs:5140`).
- **join-before-reap** → `collected=true`, later reap removes. **reap-before-join** → `reaped=true`, record retained, later join removes. **exit-while-join-claiming** → serialized by `Process.threads`. No interleaving makes a normally-exiting `parked_waiter` return non-`Ok(0)`.

**Two-way split, resolved by inspection (no gate runs needed):** `937550a3` **changes no kernel join/reap code.** Its libneo half only gates `SYS_FUTEX_QUEUE_LEN`; its negative-control rewrite is *defined* before check 7 but **not executed until after the check-7 joins**, so it cannot cause a check-7 failure in the same pass. ⇒ `937550a3` is **surfacing timing/layout, not introducing a runtime path** before the failure. Attribution therefore resolves to neither half of that window as a *cause* — the defect is elsewhere and timing-exposed.

**Separate real finding (track, do not fix here):** the already-done fast path returns status **without setting `join_claimed`**, so two late joins can both collect before reap — a **POSIX single-joiner violation**. Not the exit-35 cause; logged as a follow-on.
