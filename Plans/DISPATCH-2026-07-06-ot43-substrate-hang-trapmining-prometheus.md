## 0. The prime suspect (from the OT-43 AAG on Jarvis's instrumentation — start here)
The submit path parks the calling thread via `sched::block_current_with_token_and_guard` **while holding BOTH the per-CPU scheduler lock AND the virtio inner `SwitchMutex`, interrupts off (IF=0), mid-context-switch, before `notify_queue`**; the single-in-flight virtio-blk completion is retired by a **separate completion-worker kthread** that **wakes the parked submitter cross-CPU via `wake_thread_token`**. That park-while-holding-lock + cross-CPU-wake handoff is the textbook shape for **lost-wakeup** and **lock-ordering** hangs. The scenario reaches: CSPRNG init → BEGIN → NeoFS RW mount → neo-init spawn → user-process spawn → **hang with repeated virtio-blk completions**. Mine the documented patterns for THIS shape.

## 1. What to mine (real sources — the byte-oracle-acquisition rule: read actual driver/kernel source + issue trackers, never a summarizing fetch)
- **A — Wake/park race (lost wakeup).** The canonical "block_current then a completion wakes it" hazard: wake delivered *before* the waiter finishes parking (token published late), or the wake token consumed by the wrong generation. Prior art: Linux `blk-mq` completion vs `blk_mq_request_started`, the classic `prepare_to_wait`/`schedule` ordering rule (wait-queue add BEFORE releasing the lock that the waker takes), condvar "lost wakeup" literature, seL4/Redox/Theseus block-driver park/wake. For each: the **exact ordering invariant** that prevents it, and the **observable signature** (parked forever while the device shows the op *completed* — matches our "repeated virtio-blk completions" symptom).
- **B — Lock-ordering / deadlock under IF=0.** Parking while holding the scheduler lock + a device mutex, with a cross-CPU waker that must take the same scheduler lock: can the waker spin forever on a lock the parked thread never releases (or releases in the wrong order)? Prior art: virtio-blk driver locking in Linux/BSD/rust-vmm, the "never sleep/park holding a spinlock" rule and where it's violated, priority-inversion/convoy on the completion path.
- **C — virtio-blk single-in-flight specifics.** Our device is single-in-flight by design. Mine virtio-blk / virtio-queue gotchas: **used-ring notification suppression** (`VIRTQ_USED_F_NO_NOTIFY` / `VRING_AVAIL_F_NO_INTERRUPT`), missed-notification races (submitter checks used-ring emptiness and parks in the exact window the device posts completion + suppresses the notify), memory-barrier requirements around avail/used index publication (the `virtio` spec §2.7 ordering), and the TCG-vs-hardware timing differences that make this intermittent under emulation.
- **D — Spawn/IPC hand-off.** The hang is *post-spawn*. Mine lost-wakeup patterns in a process-spawn → first-run → IPC-rendezvous hand-off where the parent waits on a child that blocks on I/O that never wakes. Does the spawn path itself park on a token the same way? Cross-reference our own OT-13 lock-order band + I-14.
- **E — Why intermittent / contention-sensitive.** It passed Oracle's consolidation gate (14:04) but hung all retries of Cerebro's gate; shard reshuffling shifts timing. Mine: what makes lost-wakeup/notification races *timing-dependent* (the window is a few instructions; contention widens it) — this explains why it's a flake not a hard failure, and predicts the fix makes it deterministic-green.
