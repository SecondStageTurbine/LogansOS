## The one-sentence result

The systems that serve both audiences do it with **one substrate wearing two (or N) views, where the user — never the system — chooses when to go deeper, the default never overrides intent, and opening the power path never degrades the safe posture.** Every verified mechanism below is an instance of that sentence; every verified anti-pattern is a violation of it.

## The six verified principles (P1–P6), each with its LogansOS mapping

### P1 — One config substrate, two views (never two systems)
macOS's `defaults` system: per-app typed key-value domains (plists) underlie BOTH the GUI preference panels AND settings with no GUI exposure at all — the beginner GUI and the power-user CLI are **two views over the same store**, not separate systems (macos-defaults.com, 3-0). The GUI user and the terminal user are editing the same truth; depth is *more keys visible*, not *a different mechanism*.
**LogansOS mapping (the biggest new substrate decision this research surfaces):** when LogansOS grows real configuration, it must be **ONE typed, capability-gated config store** that Arthur (conversation), `neo>` (deterministic commands), and any future GUI all read and write. No hidden second registry, no "Arthur's settings" vs "system settings." Arthur saying *"I've turned that off, sir"* and `neo> config get` must provably show the same key. **Bank as a design decision needing PL ratification when the first config surface builds** (today's config surface is small — grants.json/stakes.json already follow the pattern: files Arthur mediates but the owner can read raw).

### P2 — Adaptable beats adaptive; stable beats self-morphing (measured, not opinion)
Findlater & McGrenere's controlled study (CHI 2004, 27 subjects, split menus): a **static menu beat a system-driven adaptive menu** on speed (3-0); a **user-controlled adaptable menu beat the adaptive one** (2-1); and **most users preferred the adaptable** — control over automation (3-0). Silent, system-driven UI adaptation measurably *degrades* performance and is disliked; explicit user-driven customization wins.
**LogansOS mapping:** the OS surface **never auto-morphs**. Arthur may *suggest* ("you use this daily — want a shortcut?"), but the transcript grammar, `neo>` command set, and any visual layout stay stable unless the owner explicitly changes them. This is also a vindication of a call we already made: OT-19 D3 puts stakes policy in a **user-set file** Arthur applies mechanically — adaptable, not adaptive — and the reversal of that (Arthur silently adjusting its own friction thresholds from observed behavior) is now evidence-backed as an anti-pattern, not just a governance worry.

### P3 — Layered interfaces with user-controlled promotion (the HCI canon)
Shneiderman's multi-layer interface design: novices start at a reduced-feature **layer 1** and **move up by their own choice** when ready — one system serving novice→expert without forking the product (ACM 957205.957206, both claims 3-0). Apple codifies the same at the vendor level: essentials always visible, advanced functionality hidden by default behind disclosure — and applies it at the **OS-substrate** level: the system-wide Save sheet ships collapsed with a disclosure button expanding to full filesystem navigation — **one dialog, two audiences, a stateful escape hatch, not two UIs** (Apple HIG, both 3-0).
**LogansOS mapping:** our two-layer structure is already right — **the transcript IS layer 1, `neo>` IS the higher layer** — and this literature says the load-bearing part is the *promotion affordance*: the layer-2 door must be visible-but-quiet from layer 1 (Arthur mentioning "you can also do this yourself with `neo> …`" is our disclosure button; the first-boot greeting names both layers). Rule for every future surface: when a surface has a simple and a full form, ship ONE surface with a disclosure state, never two parallel surfaces.

### P4 — The default may never override user intent; transparency over silent substitution
The verified anti-pattern, in the wild: Ubuntu 20.04's `chromium` APT package is an **empty shell that silently installs snapd and fetches from Canonical's store** — the distributor overriding the user's chosen mechanism at the package-manager layer; Mint called it a "backdoor" (Mint blog + LWN, all 3-0). Mint's counter is **substrate-level, not policy prose**: APT is configured to *forbid* snapd by default — while the escape hatch stays documented and available (install it yourself if you want it) — and Mint's own empty chromium package **explains why it's empty and where to get the real thing** instead of silently substituting (3-0 ×3).
**LogansOS mapping:** we're structurally ahead — **install-is-data (OT-44 H2) makes silent substitution impossible by construction** (no install step executes vendor code, the bundle is verified-then-placed as data). This research adds the *transparency* half as a named rule: **when LogansOS declines or can't do what was asked, it explains and points at the path — never silently redirects.** That's a butler-register obligation (OT-46) AND an H2 pipeline requirement: the catalog shows the caps manifest *before* download; a rejected bundle gets a stated reason, not a vanish.

### P5 — Opening the power path must not degrade the safe posture (the ChromeOS lesson)
ChromeOS exposes its full-Linux escape hatch (Crostini) as an **ordinary Settings toggle, explicitly WITHOUT developer mode** — no scary verified-boot-off screen; enabling depth does not weaken the appliance posture (3-0). The power path is **architecturally contained**: the VM is the declared security boundary, everything inside is untrusted (2-1), and the base image under it is **immutable** — dm-verity, signed, read-only — so the power environment structurally cannot mutate the substrate it runs on (3-0).
**LogansOS mapping:** this is our capability model wearing a different vendor's clothes, and it's worth stating as a standing invariant: **the power path is a capability tenant, not a jailbreak.** `neo>`, the SDK, third-party bundles, future dev tooling — all run capability-bounded on the same kernel with **no "developer mode" that turns protections off.** Depth on LogansOS is *more granted capabilities*, never *fewer enforced invariants*. (The contrast case is the classic anti-pattern: making power users disable security to get power — that trains the most capable users to run the least protected systems.)

### P6 — Resource tiers as named editions with a sane default and honest trade-offs
Mint ships three editions along a features-vs-footprint axis (Cinnamon full / MATE traditional-faster / Xfce lightest), tells the undecided **"start with Cinnamon"** (killing the beginner's paradox of choice), and states each lighter edition's trade-off plainly — fewer features, slower development, in exchange for old-hardware speed (installation guide, 3-0 ×3).
**LogansOS mapping — CORRECTED BY PL RULING (2026-07-08): the brain is NEVER the tier axis.** The PM's first draft mapped editions onto brain sizes (0.5B/1.5B/3B); the PL rejected it: **the brain should always, always be the best possible brain available** — it is the core value proposition of an AI-native OS, not a footprint knob. A "lite brain edition" would ship a worse *Arthur*, which is shipping a worse *product* (the Mint analogy fails there: Xfce trades chrome, not competence). So: the OS auto-selects the best brain the machine can actually run (a hardware-fit floor is an engineering constraint, not a user-facing edition), and Mint's editions pattern — named tiers, honest one-line trade-offs, a sane default for the undecided — applies only to **non-brain axes** if we ever need them (visual/console feature profiles, optional subsystems, logging depth). Never make a beginner choose; never hide a choice from a power user; never offer intelligence as the thing you give up.

## What we already have vs. what this adds

**Already structurally ours (validated, not new):** no telemetry by design; install-is-data (P4's hard half); capability-bounded depth (P5); user-set policy over model judgment (P2, via OT-19 D3); transcript + `neo>` two-layer (P3's skeleton).
**New, actionable, banked:**
1. **The unified config store decision (P1)** — one typed capability-gated store, Arthur/`neo>`/GUI as views. Needs PL ratification when the first real config surface builds. → propose as a new OT row.
2. **The never-adaptive surface rule (P2)** — a standing design lens on every Arthur/console/GUI build: suggest, never silently rearrange.
3. **The promotion-affordance rule (P3)** — layer-2 visible-but-quiet from layer 1; one surface with disclosure states, never two parallel surfaces.
4. **The explain-never-vanish rule (P4)** — H2 catalog/reject surfaces + butler strings.
5. **The power-is-not-a-jailbreak invariant (P5)** — stated once, enforced forever by the capability model; belongs next to Article 29.3 in spirit.
6. **Editions with a named default (P6)** — folds into OT-44/first-boot **only on non-brain axes** (PL ruling: the brain is always the best the machine can run, never a tier).

## Immutable-substrate addendum — P7, the update/recovery model (re-verified 2026-07-08, all 5 claims against upstream doc source)

The strongest single lesson of the study, and the one that answers the PL's *update-model + recovery/rollback* axis directly. **Two independent implementations converge on one substrate move:** never mutate the running system — build the next system state as a **complete, verifiable artifact beside the current one, flip a pointer at boot, keep the old state bootable.**
- **Fedora Silverblue / rpm-ostree / libostree (VERIFIED):** root + `/usr` mounted **read-only** ("it never changes as it is used"; stated goal "more stable, less prone to bugs"); `rpm-ostree upgrade` builds a **new deployment offline, applied at reboot**, keeping ≥2 bootable deployments; libostree: *"if the system crashes or you pull the power, you will have either the old system, or the new one"*; rollback = pick the previous entry at the boot menu or `rpm-ostree rollback`. The power path is the **same ledger**: layered packages are **recorded reversible deltas on the pristine base** ("preserves rollback and the transactional model"), and `rpm-ostree reset`/`uninstall` returns to "a pristine, known state."
- **openSUSE MicroOS / transactional-update (VERIFIED, independent impl):** same pattern on **btrfs snapshots** — "creates a new snapshot before performing any update," atomic ("either the unmodified old state or the new state is active … not possible to have a running system in an intermediate state"), `rollback` via snapper.
- **Honest trade-off (VERIFIED):** activation requires a **reboot**; layering is expected to be **sparing**; software that straddles `/usr`+`/var` or drops into `/opt` "will over time cause drift." The immutability buys unbreakability at the cost of the mutable-`/usr` workflow.

**P7 — the OS-image rollback net is ONE mechanism serving both audiences.** The beginner gets unbreakability **as a default** (read-only base, every change power-loss-safe and reversible from the boot menu — no user care required); the power user gets depth through the **same** recorded-delta ledger, so *"undo my customizations"* and *"undo a bad update"* are the **same operation**, not two subsystems. This is the exact contrary of Windows's P4/registry failure (mutate-in-place, damage-at-your-own-risk, a pulled update that already deleted files).

**LogansOS mapping — this is our kill-switch discipline, promoted from per-feature to whole-system.** Our kill-switch invariant is *"disabled ≡ the previous layer, bit-for-bit"*; the OS-image analog is *"the previous deployment is kept and bootable, bit-for-bit."* Reversibility enforced by the **substrate** (immutable base + atomic pointer-flip + recorded layers), never by user care — which is precisely why one mechanism can be both the beginner's safety net and the expert's escape hatch. We already have the philosophical pieces (kill-switch per feature; OT-19 per-action undo; install-is-data so an install is a reversible data placement); what we do **not** yet have is the **whole-system A/B deployment + atomic-boot-flip + kept-bootable-previous** substrate that would make a *bad update or a bad config* recoverable by the same reflex. **Bank as a design direction for the update model (see OT-51).** Reinforces, doesn't duplicate: OT-19 undoes an *action*, this rolls back a *system version*.
