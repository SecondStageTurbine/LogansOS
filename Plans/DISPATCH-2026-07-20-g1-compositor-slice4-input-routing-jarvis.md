HID driver path ⇒ I-14 fault-containment analysis required.** Slice 4 of the ratified G1 ladder (`docs/THINK-2026-07-10-g1-compositor-SYNTHESIS.md` §2). **This is the Milestone-A interactivity payoff** — the step that turns "a composited surface on screen" into "a surface you can *type into*."

## What Slice 4 is
Slice 2 shipped the **focus-request verb + the compositor's focus *policy* hook** (the compositor decides who *should* have focus) but explicitly **not HID routing**. Slice 1 (merged) shipped the **`InputFocus` kernel object + atomic route transfer + the leaf gate** (`kernel/src/atrium/focus.rs`: `activate`/`deactivate`/`is_active` over the single `ACTIVE_INPUT_FOCUS` word). Its own doc says: *"the fd-0 takeover and HID delivery arrive with the G1 input slice."* **Slice 4 is that delivery:** wire the actual keyboard + mouse event stream so it reaches **only the client whose `InputFocus` leaf is the active route**, gated by the existing `is_active()` comparison — and **the compositor never sees the event bytes.**

## The crown-jewel invariant — NO-SNOOP (the whole reason we're not X11/Orbital)
**Input security and input routing are the same comparison (SYNTHESIS §2).** The compositor holds the root `ACTIVATE` cap and *decides* focus (it calls the route transfer); it does **NOT** sit in the event path. HID events flow **kernel → focused client**, never through the compositor. This is the property Qubes validated as *necessary* (`docs/RESEARCH-2026-07-20-qubes-prior-art-FINDINGS.md` §1.3/T5) and that Redox Orbital and Wayland both *lack* (their compositor is a man-in-the-middle on every keystroke). **Slice 4 must PROVE the compositor's channel never carries an event byte** — a falsifiable scenario assertion, not a claim. This is the highest-value line in the slice.

## What to build
1. **HID delivery through the focus gate.** Route keyboard (`drivers/usb/hid_keyboard`) and mouse (Oracle's merged USB pointer) events to the client holding the active `InputFocus` leaf. The client consumes via its leaf cap (`RECEIVE` right, gated by `is_active()`); a non-focused client's poll returns nothing. The current direct sink (`syscall.rs:4321` `hid_keyboard::try_read_byte()` on the console read path) becomes the **kill-switch-off** baseline (see below).
2. **Atomic focus handoff (no cross-handoff leakage).** When the compositor transfers the route (Slice 1's single-swap `activate`), input redirects atomically: the previously-focused client stops receiving *before* the new one starts — no event delivered to the wrong surface across the swap. Slice 1's `swap(AcqRel)` gives you the atomicity; Slice 4 proves no event straddles it.
3. **Bounded per-client input queue (I-14(b)).** A focused client that stops draining its input must NOT stall the kernel HID path or other clients — bounded queue, drop-oldest (or documented backpressure) when full, never an unbounded grow and never a spin. State the bound.
4. **The O2 focus-indicator signal (from the Qubes pass — bake it in, don't render it).** The compositor draws the focus indicator from its *own* `activate` decision (it knows what it activated), **never by observing events** — so surfacing "who has focus" to the user needs zero event-snooping. Slice 4 must ensure the compositor has this signal without a path to the bytes. (The actual glass focus-ring *rendering* is a later GUI slice; Slice 4 provides the honest signal + the guarantee it needs no event visibility.)

**Scope boundary — do NOT touch:** buffer *lifetime* mechanics (**Slice 3**); damage/pacing (**Slice 5**); `present()`/the present-fence (**Cerebro's OT-63 lane**); the visual focus-ring rendering polish (**later GUI slice** — Slice 4 is the *signal + routing*, not the pixels). Slice 4 is the HID *delivery + no-snoop guarantee + focus handoff* only.

## Kill-switch (Rule-1) — mandatory
Input-routing-**off** ≡ **today's behavior bit-for-bit**: the direct `hid_keyboard::try_read_byte()` console/Arthur read path, unchanged (Arthur reads the keyboard directly, as on the last bare-metal run where the PL typed "Arthur"/"Hello World"). With the feature **on**, input routes through the `InputFocus` gate to the focused client. Ship the disabled mode + an **armed regression** proving disabled ≡ the current direct-read path (unit-test equality where expressible), not asserted.

## Byte-oracle (I-12) — the input event is an on-wire layout
The event struct delivered kernel→client (key event: keycode/modifiers/press-release; pointer event: dx/dy/buttons) is a byte layout crossing the syscall boundary ⇒ a **hand-laid byte fixture** per event kind, asserted independently of the writer+reader (mirror the Slice-2/Rung-0 byte-oracles). Include a key-event fixture and a pointer-event fixture.

## I-14 fault-containment analysis (HID driver path — required section)
- **(a) Lock isolation:** the HID delivery path (IRQ → route lookup → enqueue to focused client) acquires **NO** AI-governance lock (`INFLIGHT`/`RECENCY`/`ARENA`/reservation/`TABLE`). Assert it (grep-checkable + the route read is the existing single-atomic `is_active()`).
- **(b) Liveness degradation:** a client monopolizing/ignoring its input queue degrades to drop-oldest on its own bounded queue — governance and other clients stay live (never a stall). This is the I-14(b) backstop for the input path.
- **(c) Memory isolation:** Slice 4 introduces **no new DMA** — it routes events from the *existing* USB HID path; state this (no new device-initiated DMA buffer, so I-14(c) fence is N-A for the new code, and the existing HID DMA is unchanged).

## CP-bank consultation (interrupt/HID-touching — required section)
Consult `docs/concurrency-pitfalls.md`. `focus.rs` already did the consultation for the **route word** (CP-11 Release/Acquire publish/observe; CP-12 monotonic non-reused ids; CP-13 single aligned u64, no torn read). Slice 4 adds the **delivery queue + the HID-IRQ→enqueue path** — state, for each class it touches: the ISR-context enqueue vs client-context dequeue (CP-14/15/16 interrupt-wake-race — does a blocked reader wake correctly + lock-free/IF-safe?), the SPSC/MPSC discipline on the queue, and that the HID ISR takes no lock that a syscall-context path also holds (lock-ordering). New pitfalls learned on the gate get added back to the bank.
