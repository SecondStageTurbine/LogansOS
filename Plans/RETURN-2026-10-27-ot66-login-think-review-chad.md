# RETURN #98 — OT-66 login/session THINK cross-family review

Reviewed `d49acd0f` (`docs/THINK-2026-10-27-ot66-login-session.md`) against `Plans/DISPATCH-2026-10-27-ot66-login-think-review-chad.md`. RAG health was healthy and the dispatch's semantic query returned results. No code changes were made. Overall: **FAIL**. This is a design review: the issues below are omissions in the proposed contract, not claims of demonstrated production data loss or credential disclosure. Recommend keeping the design/rungs open until the listed guarantees are made explicit; post-merge, revert-first on a confirmed failure rather than repairing code in this review.

1. **What exists today — PASS.** The design correctly identifies ambient name-based `sys_spawn` (`docs/THINK-2026-10-27-ot66-login-session.md:55`; `kernel/src/arch/x86_64/syscall.rs:1630-1700`), `open_root_temporary` as the root-form ambient open (`THINK:56`; `kernel/src/fs/mod.rs:1188-1203`), and kernel-agnostic user accounts (`THINK:87-95`). It labels `userland/vault-core` a password vault and reuses only its Argon2id floor (`THINK:68-70`; `userland/vault-core/src/lib.rs:13,97`).

2. **Threat table and missing threats — FAIL (scoped omission).** The listed claims are bounded honestly: keyboard protection is conditional on L1, file isolation on K1, process-spawn policy on K2, and offline disk access remains unprotected because there is no encryption at rest (`THINK:72-84,412-416`). However, the design does not identify the specific Try threat: a person booting the supplied Try system with the installed disk attached may read files from that disk. §7 says the disk is mounted read-only and the installed account is not used (`THINK:325-330`); read-only and skipping login do not establish confidentiality. This is an explicit missing threat statement, even though the broad “disk … booted from another OS” row and no-encryption caveat already bound the general offline case. The design needs to say whether Try exposes installed files and what protects them; this review does not claim it exposes verifier plaintext or that arbitrary credential bytes are returned to a client.

3. **K1/K2 and ambient syscall gaps — FAIL.** The proposed product-call-site port and SpawnCap gate address `sys_open` and `sys_spawn` as described (`THINK:117-130,344-347`). But `SYS_MODEL_LOAD` independently accepts a path and opens NeoFS through `fs::open_root_temporary` (`kernel/src/arch/x86_64/syscall.rs:2519-2538,2563-2609`). K1's stated scope lists product open call sites and `open_at`, but does not mention converting or gating this path (`THINK:133-139,360-366`). This leaves a path-based, capability-free filesystem lookup after the named rungs unless deliberately covered by the K1 port. It is an ambient open path; the review does not infer that malformed model input yields credential plaintext. Other globally callable syscalls such as `SYS_GETRANDOM`, `SYS_CLOCK_GETTIME`, and `SYS_SCHED_YIELD` remain ambient but do not themselves grant file or spawn authority (`syscall.rs:243-245,137,157`). `sys_mount` is directory-handle-based (`syscall.rs:6114-6133`). The intended `open_at` must still permit relative opens through a granted directory cap; the security boundary is removal of ambient root opens, not denial of every path open.

   The test-only root-grant design itself is appropriately layered: feature implication, compile-time forbidden combinations and xtask refusal in accepted spellings, with the write-guard-control precedent (`THINK:373-388`; `kernel/src/drivers/block/mod.rs:499-515`; `tools/xtask/src/main.rs:5205-5225`).

4. **NEOCRED1 — FAIL (crash guarantee unspecified).** The two slots share one 4 KiB NeoFS block, and the update rewrites the complete file while preserving the newer slot and replacing the older one (`THINK:174-216`). The document explicitly leaves open whether that block overwrite can tear. NeoFS's COW path commits the new inode/root after writing new content (`kernel/src/fs/neofs/inode.rs:236-290`); `fsync` drains data, inode, root, and later roles in order and flushes only after draining (`kernel/src/fs/neofs/inode.rs:352-363`; `kernel/src/fs/neofs/cache.rs:29-37,560-604`). The existing overwrite-recovery scenario injects before superblock publication (`kernel/src/test_harness.rs:30071-30112`), so it does not establish the design's stronger promise that power loss can never leave both slots invalid under all device/torn-write behaviors. COW can preserve the previous file until publication, so this is a missing durability guarantee, not confirmed runtime corruption. The hand-laid byte oracle is committed as an L1 deliverable and the Argon2id floor is specified (`THINK:193-205,344-345`; `userland/vault-core/src/policy.rs:18-32`): PASS for those subchecks.

5. **Lock screen — PASS, with an exclusivity condition.** The design gives the WM the lock focus, says client receive roots fail the kernel focus-id comparison, routes pointer to WM, routes SAKs to the WM latch, and says only the lock surface is composited (`THINK:262-277`; `kernel/src/atrium/focus.rs:195-210,584-600`; `kernel/src/atrium/sak_logic.rs:20-31`). This is sufficient if lock mode suppresses all client-owned surfaces and decorations, including the existing WM-rendered Arthur busy emblem (`userland/neo-init/src/desktop_session.rs:5177-5184`), and newly created clients remain outside the input route until unlock. The design's “only the lock surface” must be enforced as that exclusive compositor state; neither OP_BUSY nor a late client should add visible pixels or receive input while locked.

6. **Wrong-password delay — FAIL.** The growing delay is bounded and does not permanently lock out the owner, but its counter is explicitly in memory and only said to reset at boot (`THINK:219-230`). There is no specified storage/scope that survives restarting the WM or login screen. A user can reach the delay, restart that process, and try again at the first-attempt rate. Put the bounded counter in a supervisor/state owner that survives those restarts (while retaining the stated boot reset) and say so.

7. **Fit with OT-87 — PASS.** First-boot account creation occurs on the installed writable system; Try has no account/login and leaves persistence absent or read-only (`THINK:318-330`), consistent with the referenced installer design's R5.

8. **Rung ladder — PASS.** L0–L5 provide dependencies, close gates, kill-switches, and no calendar estimates; K1/K2 identify cap-model work, pitfall-bank/cross-family review and Muse routing (`THINK:338-369`; security routing `THINK:371-389`).

9. **Prior art — PASS.** The survey records license, last-commit date and SHA where verified; the blocked Fuchsia license/date/status details are explicitly marked unverified. It states that nothing is vendored and limits GPL/AGPL material to design principles (`THINK:391-412`).
