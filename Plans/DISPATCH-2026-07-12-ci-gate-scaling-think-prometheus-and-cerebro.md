## The problem (measured, not hypothetical)
The 4-shard QEMU gate has been outgrown by its own suite. The fresh evidence (the B3 gate saga, 2026-07-11/12 — runs `29168424137` and `29174345628`, plus the CI patch on `codex/ot16-b3-qwen35-deltanet-bringup-jarvis` @ `82f33270`, which will merge with B3 and is your incoming baseline):
- ~240+ scenarios across 4 shards under TCG (pure emulation), with the new **honest interactive prompt-driver** raising true per-scenario cost.
- At the old 70-min shard ceiling, cold-cache shards had completed only **14–16 of 60–69 scenarios — all passing** — when GitHub killed them. The ceilings died of suite growth, not failures.
- Jarvis's evidence-based patch (the baseline you start from): host 30→**60 min** (measured 24–26 cold), QEMU shards 70→**240 min**, **staging** (manual/nightly QEMU waits on a green host job), an xtask regression test pinning the invariants, per-scenario timeouts untouched (hangs still fail fast).
- Fleet: ~3 self-hosted runners today (all WSL boxes); the 4th box (Ryzen M75q-1) is procured but not yet racked.

**The PM's framing, which both THINKs must confront: 240 minutes is a correct *measurement*, not a sustainable *policy*.** A full gate now occupies the fleet for ~4 hours; two staggered kernel gates ≈ a working day. The suite will keep growing (every build adds scenarios, and the standing rule FORBIDS pruning: *gate discriminators are never removed as test-only weight — they are paid-down debt and stay armed permanently*). So the answer must scale coverage, not shed it.

## ISCs (both answer ALL, independently)
- **ISC-1 — the cost model, from real data.** Build the honest cost model from primary evidence (the cited run logs; per-scenario serial timings; the xtask shard partition): per-scenario cost distribution (which scenarios dominate — the interactive/real-brain tier?), cold-vs-warm-cache split (how much of the 4 hours is *rebuilding the dev image and dependency graph* vs *running scenarios*), the TCG multiplier, and the growth rate (scenarios added per feature build, historically). Every later recommendation must trace to this model.
- **ISC-2 — the tiered gate (the core design).** Design the split between a **merge-blocking tier** and a **full tier** (the nightly `schedule` trigger already exists). The load-bearing constraints: (a) the *criterion* for tier membership must be principled and reviewable, never vibes — e.g. a standing core (boot/caps/governance invariants + every I-14 discriminator) plus an **impacted-area selection** (the shard/scenario subset covering the kernel areas the diff touches)? Deterministic and auditable — no silently-dropped coverage; (b) **everything stays armed somewhere** — the full suite runs nightly at minimum (the anti-rot rule); (c) **no misleading green** — a green merge-tier must be honestly labeled as tier coverage, and the merge report says which tier ran.
- **ISC-3 — the escaped-defect contract (the governance half — this is what the PL ratifies).** If the merge tier is a subset, a defect can land on `main` and only redden the nightly. Define the contract: what a green merge-tier *means*; what happens when nightly goes red on main (**revert-first vs bounded fix-forward window? who owns it?**); how the escaped defect's scenario gets promoted into the merge tier (the feedback loop). This is a change to what "merged" means — state it precisely enough for PL ratification.
- **ISC-4 — parallelism + fleet.** Shard rebalance (4→N; the partition is xtask-owned and cost-weighted partitioning is possible — the coverage-complete+disjoint check already exists); the 4th box's role and per-runner-label guard thresholds; whether shard count should scale with the fleet automatically. What does the fleet need to hold the merge tier under a target (state a target — e.g. merge tier ≤ 45 min end-to-end?) as the suite doubles.
- **ISC-5 — the warm-cache levers (minutes without touching coverage).** The measured cold cost was dominated by image/dependency rebuilds. Evaluate: persistent per-runner caches, a prebuilt dev image pulled instead of rebuilt, cargo cache strategy, staging's already-landed win. Cheap infra minutes first, policy second.
- **ISC-6 — rollout + guards.** Introduce the policy without a flag-day: sequencing, the xtask workflow-invariant regression tests extended to pin the tier definitions (Jarvis's precedent), and the kill-switch framing (the full-gate-on-every-kernel-merge behavior must remain one revert away).
- **ISC-7 — honest forks + recommendation.** The genuine forks (tier criterion shape; revert-first vs fix-forward; target ceiling for the merge tier; shard count; whether `workflow_dispatch` keeps a full-gate option per-merge for high-blast-radius changes — I'd expect yes) with your recommendation and reasons. The merge-gate contract (ISC-3) is explicitly a **PL ratification** item.
