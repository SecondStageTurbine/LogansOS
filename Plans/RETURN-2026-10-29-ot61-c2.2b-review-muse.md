# RETURN — relay #163: #205 `3bcc2f99`, OT-61 C2.2b, the per-account object budget: containment

Reviewed SHA: `3bcc2f99`. Reviewer model: Muse (Gwen), reviewing Claude-authored code. Pasted back by the PL on
2026-10-29 and banked by the PM verbatim. The PL verified item 1's FAIL chain locally: `SYS_BUFFER_MAP`
(`syscall.rs:7862`) maps via `map_borrowed_region`, which pushes one pin per map into `borrowed_pins`
(`pmap.rs:1011`) with no object charge and no count limit in the path.

Scope: containment only, behind `obj-quota` (the browser lane, in no product image). Accounting logic
`kernel/src/mm/mem_account_logic.rs`; weights and charge points `kernel/src/sched/process.rs`; thread release
`kernel/src/sched/thread.rs`; the two syscall handlers `kernel/src/arch/x86_64/syscall.rs`. All paths are
`kernel/src/` unless noted.

1. Can a budgeted process create kernel objects past its budget by any path? — FAIL.
   The charged surface is complete — every handle install into a budgeted table goes through `charge_next` with no
   fallible step before the install: `install_cap` (`sched/process.rs:2571`), `install_cap_excluding` (`:2609`),
   `derive_handle` (`:2645`), `derive_net_dial_cap` (`:2703`), and the spawn inherit loop (`:3428`).
   `HandleTable.entries` is private, so these are the exhaustive install paths, and every syscall install site goes
   through `install_cap` (`arch/x86_64/syscall.rs:1953, 2041, 2056, 2318, 2368, 2598, 2608, 2636, 3034, 3680, 5045,
   5089`). The weights cover the full queue bounds they rely on: UDP enqueue refuses past 16 datagrams of at most 2048
   bytes (`net/socket.rs:235`, `MAX_DATAGRAM` at `:22`), and the SOCKET weight includes 16 × (2048 + 64); TCP receive
   refuses past 64 KiB (`net/tcp.rs:908`), and the TCP_SOCKET weight includes twice that. Spawn is charged to the
   parent before anything is allocated (`sched/process.rs:3597`), thread create likewise (`:3904`).
   But one path is uncharged and unbounded, so the budget can be exceeded:
   * `SYS_BUFFER_MAP` (`arch/x86_64/syscall.rs:7862`) pushes one pin `Arc` per map into `Pmap.borrowed_pins`
     (`mm/pmap.rs:1011`), kept until the Pmap drops, with no object charge and no count limit — the only bounds are VA
     space and the (frame-charged, not object-charged) page tables.
   * Concrete input: a child spawned via `SYS_SPAWN_BUDGETED2` with `obj_bytes = 65536` and `frame_bytes = 0`,
     holding one buffer handle, calls `SYS_BUFFER_MAP` on that buffer in a loop 5000 times. Each map adds one 16-byte
     fat-pointer slot to `borrowed_pins`; at capacity 8192 the Vec alone holds 131,072 heap bytes — past the
     65,536-byte budget — while `obj_used` is unchanged and no `ENOMEM` is ever returned. (An `Arc` clone allocates
     nothing, so the Vec slots are the heap cost; 4097 maps already exceed the budget.)
   * Note: the design doc names buffer-map pins as deferred to a second build
     (`docs/DESIGN-2026-10-29-ot61-c2.2b-object-budget.md` §13). The gap is known, but the checklist as written asks
     "by any path" without carving pins out, and the code as written fails that question on this path.
   * Observation, not the FAIL basis: `SYS_TENSOR_WRITE`/`SYS_TENSOR_CREATE` copy a user-chosen length into a heap
     `Vec` before any size check (design §6.1, already reported to the PM as a separate lane) — likewise uncharged,
     but a panic bug rather than a budget-accounting path.
2. Can a child's object budget exceed its parent's, or be created out of nothing? — PASS.
   * Every child account is the caller's account or a child of it: plain spawn shares the caller's account
     (`sched/process.rs:3515`, `spawn_user_in` with `caller_mem_account()` at `:3534`), and budgeted spawn nests under
     it (`spawn_user_by_name_budgeted2` at `:3612` via `child_with_obj_limit` at `mm/mem_account_logic.rs:96`, which
     stores the parent `Arc` strongly, so the chain can never be freed from under a charge).
   * A v1 frame-budgeted child gets `obj_limit = UNLIMITED` of its own, but it still charges the parent's object
     counter through the chain walk, so it cannot escape a budgeted parent that way either.
   * Observation, stated plainly: the code does NOT clamp a child's limits to the parent's — a parent with `obj_limit`
     64 KiB can spawn a child with `obj_limit` `UNLIMITED`, so the child's nominal limit can exceed its parent's.
     Containment still holds, because `charge_obj` (`mm/mem_account_logic.rs:193`) charges every level of the chain
     with a CAS and rolls back on refusal: the child's effective consumption is capped at the parent's limit
     regardless of its own larger value. The larger value is unenforceable, not an escape. "Created out of nothing" is
     impossible: the only fallback to the root account is for kernel or fixture callers in `caller_mem_account`,
     never for a user spawner.
3. Is each charge released exactly once (exit, kill, failed spawn, revoke)? — PASS.
   * Handles: the weight is recorded per slot by `record_weight` (`sched/process.rs:1459`, which takes `pending`), and
     released by `release_weight` (`:1629`, which takes the slot's weight) at `remove` (`:1796`), the `obj-quota`
     `remove_cap_ids` (`:1865`), `drain` (`:1885`), and `HandleTable`'s `Drop` (`:1470`). Taking zeroes the slot, so a
     second release is a no-op (`release_obj(0)` returns early), a remove of an already-empty slot releases nothing,
     and `Detached`'s drop releases only tensor/net counts, never object weights — no double-release path exists.
   * Spawn: the parent's `SPAWN` charge is moved into the child's `obj_spawn` on success (`sched/process.rs:3604`) and
     released when the child's `Process` drops (the `ObjCharge` field drop, `mm/mem_account_logic.rs:271`); on any
     spawn failure the local charge drops in `spawn_user_in`. The exit-before-attach race releases exactly once either
     way: reaped before attach means `get(pid)` fails and the local charge drops; attached means the later `Process`
     drop releases it.
   * Thread: the charge is attached with `set_obj_charge` before the thread is placed, and `Thread::free`
     (`sched/thread.rs:239`) — the single release point, since the slab never runs `Drop` — clears it on every path
     (registry-insert failure, place failure, reap). The spawn's first thread carries no separate charge (it is inside
     the `SPAWN` weight), so its `free` correctly releases nothing.
   * Exit/kill: the reap path drains the table through cap-graph teardown (`sched/process.rs:2454`, reached from
     `on_thread_reap` at `:3722`), and the `Process` drop releases the spawn charge.
   * Note: exit-code entries and buffer-map pins are uncharged (pins are item 1's FAIL). Exit-code entries are
     indirectly bounded — each one requires a child spawn, and each spawn charges the parent ~33 KiB — so they cannot
     accumulate past the parent's budget the way pins can.
4. Can one process read or change another's usage through `SYS_MEM_INFO` v2? — PASS.
   * `sys_mem_info_v2_impl` (`arch/x86_64/syscall.rs:7348`) takes only the caller's output pointer — there is no pid,
     handle, or target argument. It resolves the account from `current_process_for_syscall`, i.e. the caller's own
     Pmap account (falling back to the root account only for kernel callers), validates the caller's buffer, and
     copies out exactly 48 bytes: the caller's own `obj_used`/`obj_limit` plus the v1 fields.
   * There is no write path to any limit in the handler; the record is read-only. The system-wide frames field is
     v1's pre-existing aggregate, not another process's usage, and a process that shares an account (an unbudgeted
     child) sees that shared account's counters by design, not a private counter belonging to someone else.

Overall verdict: FAIL, on item 1 only — the uncharged, unbounded buffer-map pin vector lets a budgeted process grow
heap past its object budget with no trip. Items 2, 3 and 4 pass: the chain walk caps effective child budgets, every
charged object releases exactly once on every teardown path, and `SYS_MEM_INFO` v2 reports only the caller's own
account.

Muse's note for the PM: #163 item 1 is a FAIL on the pin vector even though the design doc names pins as deferred to a
second build — the dispatch checklist asks "by any path" without carving pins out, and the bypass is concrete. Item 2's
nominal-limit observation (no clamping of child limits) was kept as an observation, not a FAIL, because the chain walk
makes the larger value unenforceable.
