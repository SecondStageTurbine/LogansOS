# RETURN: OT-90 P3a clean shutdown review, relay #199

Reviewer: Chad. Reviewed PR #246, head `821f2e69107f2c5d98488b10ef64ee8591630f05`, against `origin/main` and the OT-90 P2 review.

1. **PASS — flush sequence and progress bound.** `kernel/src/acpi/shutdown.rs:86-113` runs K1, then K2 for each mounted filesystem, logs the aggregate result, flushes the log sink (K3), and only then invokes P2's S5 or reset path. K1 gives process termination/reaping 200 timer ticks (2 s at 100 Hz; `shutdown.rs:34-35, 124-150`). Each writable NeoFS mount freezes new mutations and waits up to 500 ticks for in-flight writers, then drains in passes of at most 64 blocks and gives up after 500 ticks without a drained block (`kernel/src/fs/neofs/inode.rs:265-286`, `kernel/src/fs/neofs/cache.rs:361-401`). A completed drain uses the existing barrier ordering; errors/remaining dirty blocks are reported unclean and shutdown continues. This is a no-progress bound, not a total-time bound when progress continues.

2. **FAIL — a stuck block request can still hang shutdown forever.** The K2 deadline is checked only after `drain_pass` returns (`kernel/src/fs/neofs/cache.rs:375-399`). A write or flush that parks waiting for a device completion never returns to that check; for example, a Virtio device that accepts the request but never signals completion. The writeback worker can also already be parked in such I/O when K2 pauses it, and `stop_writeback_worker` calls `handle.join()` without a timeout (`kernel/src/fs/neofs/cache.rs:583-598`). Thus there is no forced fallback for a stuck device wait, despite the per-mount no-progress fallback for a pass that returns. The existing `ot90_straggler_forced` leg covers a user process only: it spawns a blocked worker (`kernel/src/test_harness.rs:39081-39097`), and xtask requires K1's termination marker before S5 and rejects a zero termination count (`tools/xtask/src/main.rs:9360-9377`). No device-stall scenario supplies a corresponding negative control for the missing I/O fallback. Concrete failing input: a dirty NeoFS block on a device whose write/flush request never completes; the shutdown thread remains in the synchronous request wait and never reaches K3 or power-off.

3. **PASS — shutdown writes remain behind the block write guard.** K2 drains through the mount's `BlockDevice`; the guarded wrapper checks each write in both `submit` and `write_block` before forwarding (`kernel/src/drivers/block/mod.rs:471-512`). This covers cache drains and NeoFS large-write direct block writes. Flush forwarding alone does not write data. No shutdown path bypasses the guard to write a forbidden disk.

4. **PASS — feature only, default off.** `power-clean` is declared as `power-control`-dependent and is not added to `PRODUCT_IMAGE_KERNEL_FEATURES` (`kernel/Cargo.toml:369-375`; `tools/xtask/src/main.rs`, `PRODUCT_IMAGE_KERNEL_FEATURES`). Its kernel paths are cfg-gated. With `power-clean` off, the existing P2 behavior remains; with `power-control` also off, the shutdown module and P2 path are absent as before. No image-A pairing assertion is needed while this remains feature-only.

Review is source-based; no QEMU run or dynamic stuck-device injection was performed.
