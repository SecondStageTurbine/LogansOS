# RETURN: relay 287, PR #60 clock/RTC review — Janus

Reviewed head: `c05deffba6fbef7ba14536e4fdfbb1647e5c6f51`.
Review branch: `codex/pr60-review-janus`, from `origin/main` at `b90540e4f21d9aad27ab18fcf08eb7e7ff792cf9`.
Verdict: **FAIL**. Checklist follows the dispatch's four requirements; references are to the reviewed head.

- **PASS — 1, initial state and authority.** `kernel/src/arch/x86_64/rtc.rs:56` initializes confirmation to 0; `rtc.rs:78` refuses confirmation without a seeded epoch. `kernel/src/arch/x86_64/syscall.rs:7416` checks the existing input-system authority before changing anything. `kernel/src/sched/process.rs:2150` requires the InputSystem handle, USE, and SYSTEM rights. An ordinary client gets EPERM; invalid RTC fallback remains unconfirmed and gets EAGAIN.

- **PASS — 1, write-once, bounds, and publication.** `kernel/src/arch/x86_64/rtc.rs:81` claims confirmation with compare-exchange; `rtc.rs:87` validates the arithmetic and releases the claim on refusal. `kernel/src/arch/x86_64/rtc_logic.rs:266` bounds the offset to ±86400 seconds and uses checked arithmetic. `rtc.rs:91` stores the base before publishing confirmation with Release; `rtc.rs:101` reads confirmation with Acquire. A reader that observes confirmed and subsequently reads realtime sees the corrected base. The base is one atomic u64; monotonic remains independent at `kernel/src/arch/x86_64/syscall.rs:7397`. CP-11/CP-17 publication and CP-13 base atomicity hold for that protocol. A host harness using the extracted production functions confirmed that an invalid offset permits a later valid call, 16 concurrent valid calls have exactly one winner, and a subsequent call is refused. Existing consumers' missing status handling is covered below.

- **FAIL — 1, correcting RTC mode leaves other consumers on the wrong confirmed clock.** `userland/neo-init/src/desktop_session.rs:6292` reconstructs an RTC reading using the original confirmation offset; `desktop_session.rs:6317` keeps subsequent corrections exclusively in WM state. Concrete input: an RTC actually holding `2026-11-02T06:29:00Z`, default `RtcLocal=1`, then `timezone America/New_York`, then `rtc utc`. The first command confirms offset -18000. The second corrects Home to `1:29 AM EST`, but kernel realtime remains `1793618940` (11:29 UTC), with status 1, instead of `1793600940` (06:29 UTC). The action log and Home now disagree by five hours about the instant. The THINK specifies write-once and contains no WM-only replacement of the system UTC contract. A mode correction needs an explicit reboot requirement or an approved mechanism that corrects the system clock for every consumer.

- **FAIL — 2, action-log timestamps have no confirmation flag.** `userland/neo-init/src/desktop_session/action_log.rs:81` reads raw realtime without status; `action_log.rs:152` and `action_log.rs:186` persist it unchanged. `userland/action-log-core/src/lib.rs:94` has no confirmation field, and `lib.rs:122` still writes all reserved bytes as zero. Concrete input: local RTC `2026-11-02 01:29`, no zone, append an action record, then enter `timezone America/New_York` and append another. The first timestamp is local/unconfirmed; the next is UTC, approximately five hours greater despite negligible elapsed time. Neither record distinguishes its time basis, contrary to THINK §2.7. After confirmation the ordinary timestamp arithmetic is UTC, but that does not identify earlier records.

- **FAIL — 2, Home reinterprets already confirmed UTC when changing zones or reapplying a setting.** `userland/neo-init/src/desktop_session.rs:6292`, `desktop_session.rs:6293`, and `desktop_session.rs:6317` rerun RTC interpretation even when status is already confirmed; `desktop_session.rs:6221` then applies that private skew before zone conversion. Concrete input: local RTC `2026-11-02 01:29`, `timezone America/New_York`, then `timezone Australia/Sydney`. Kernel UTC is correctly 06:29, but Home shows `1:29 AM AEDT`; it should show `5:29 PM AEDT`. The computed private skew is -57600 seconds. Another input: boot New York at `2026-11-01 01:00` local, confirm the earlier fold instant (05:00 UTC), wait until 06:30 UTC, then reenter the unchanged `timezone America/New_York`. Before the command Home correctly shows `1:30 AM EST`; afterwards it shows `2:30 AM EST` because resolve installs a +3600-second skew. Ordinary minute refresh with zero skew does cross DST correctly. Once confirmed, changing the display zone must convert the existing UTC instant rather than reinterpret it as another RTC reading.

- **FAIL — 2, the wall-clock probe still assumes the old RTC contract.** `userland/neo-init/src/main.rs:2536` rejects a base movement exceeding one tick, while `main.rs:2577` requires the raw pinned RTC time `5:48 PM`. It never reads confirmation status. Concrete input: pinned local RTC `2026-10-21T17:48:00`, confirmed with offset -14400 before the probe. Correct UTC is 21:48; the production probe returns 9, reporting that the boot time is not the pinned RTC's. Confirmation during its sample loop instead trips the base-moved check. The existing unconfirmed probe scenario can still pass; it does not verify the post-confirmation contract.

- **PASS — 3, invalid timezone input cannot alter settings.** `userland/libneo/src/tz.rs:330` resolves only compiled canonical names, aliases, or a unique complete city name. `userland/neo-init/src/desktop_session.rs:6046` calls set_mode only for Ok; the Err branch at `desktop_session.rs:6058` only builds suggestions. `userland/settings-core/src/lib.rs:131` rejects IDs outside TZ_ZONE_COUNT, and `lib.rs:228` checks before copying/changing Settings. TimeZone and RtcLocal are WM-only at `lib.rs:143`. Inputs `timezone atlantis`, `timezone york`, and an out-of-range numeric settings value leave settings unchanged; aliases and case-insensitive full names are accepted.

- **PASS — 4, kernel kill-switch.** With rtc-offset absent, `kernel/src/arch/x86_64/syscall.rs:7426` and `syscall.rs:7440` return ENOSYS for the new calls. The existing realtime calculation at `syscall.rs:7402` and seeded-base read at `kernel/src/arch/x86_64/rtc.rs:105` retain OT-85 arithmetic; the confirmation state and writer are compiled out.

- **FAIL — 4, Home does not restore today's behavior when the kernel feature is off.** `userland/neo-init/src/desktop_session.rs:6298` turns ENOSYS into an unconfirmed status instead of taking the old display path; `desktop_session.rs:6248` unconditionally adds the unconfirmed marker. Concrete input: desktop-clock userland, rtc-epoch kernel with rtc-offset disabled, default settings, RTC `2026-11-02 01:29`. Today's readout is `1:29 AM`; this head produces `1:29 AM (zone not set)`. Supplying a zone still activates the WM-only conversion after ENOSYS. Kernel arithmetic is preserved, but the full clock feature's off behavior is not.

- **PASS — available host validation.** At the reviewed head, `cargo test -p rtc-logic-tests -p tz-logic-tests -p settings-core --offline`: 30 RTC, 11 timezone, and 12 settings tests passed (53 total). Additional temporary host harnesses extracted the production RTC confirmation functions, Home State/resolve/local functions, and wallclock probe, with syscall/logging substitutes; they reproduced the concrete Home/kernel divergences and probe return code above. These are host checks, not a boot test. QEMU is unavailable on this worker, so no QEMU confirmation, authority, feature-off control, or four-shard gate result is claimed.
