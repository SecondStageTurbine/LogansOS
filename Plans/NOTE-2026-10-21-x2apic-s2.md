# NOTE: x2APIC support (CP-68): trap-mining, failure bank, audit (S2)

**Lane:** a real-silicon boot failure (PL, the B1 product ISO on a modern laptop, `main` `a21967a7`).
**Branch:** `claude/x2apic-support`.
**Pitfall:** **CP-68**, "kernel assumes xAPIC on firmware-locked x2APIC silicon". ADR-013:991 deferred
x2APIC; this is that debt.

## 1. The failure, restated

Limine panicked before the kernel ran: `PANIC: smp: Kernel does not support x2APIC, but machine requires
it`. The kernel's MP request had `flags = 0`. Limine's protocol (raw `PROTOCOL.md`, MP feature): *"if
firmware has already enabled x2APIC and bit 0 is clear, the bootloader will try to disable x2APIC before
handoff. If the MP request is present and x2APIC cannot be disabled, the bootloader will fail to boot the
executable."* That laptop's firmware keeps x2APIC on.

## 2. Sources (read for principle; no code copied)

- **Limine `PROTOCOL.md`**, pulled raw (`curl` of the upstream file):
  - Request flag bit 0 asks to "enable x2APIC, if possible".
  - Response `flags` bit 0 says "x2APIC has been enabled".
  - `lapic_id` is the MADT's Local APIC ID, 32 bits.
  - Base revision 5+: Limine sets SVR to `0x1FF`, masks the LVTs, and disables VT-d DMA translation and
    interrupt remapping.
- **The `limine` 0.6.3 crate** (`src/mp/x86_64.rs`): `MP_FLAG_X2APIC = 1 << 0`; `MpRespData { flags:
  u32, bsp_lapic_id: u32, .. }`.
- **Intel SDM Vol. 3A, ch. 11 ("Advanced Programmable Interrupt Controller"), x2APIC sections:**
  - The register-to-MSR map: `0x800 + (offset >> 4)`.
  - The 64-bit ICR with a 32-bit destination; ICR-high (`0x831`) does not exist.
  - No delivery-status bit in x2APIC mode.
  - A non-zero EOI write faults.
  - The mode-transition state machine: x2APIC → xAPIC directly is illegal (#GP); only x2APIC → disabled
    → xAPIC is.
  - WRMSR to the x2APIC ICR is not serializing.
- **OSDev wiki**, "APIC" / "x2APIC": the same map, and the note that the MMIO window is not used in x2APIC
  mode.

## 3. Failure-mode bank (each with its discriminator)

| # | Trap | Guard in this build | Discriminator |
|---|---|---|---|
| F1 | Clearing `X2APIC_ENABLE` while in x2APIC (x2APIC → xAPIC without disable) is #GP. The old `init_local_apic` did exactly that. | In x2APIC mode `IA32_APIC_BASE` is never written. | `x2apic_smp_ipi` boots in x2APIC; a #GP would be a fault line before `apic: mode=`. |
| F2 | A stale xAPIC MMIO mapping still in use: in x2APIC mode the MMIO window is not decoded, so writes vanish (an EOI or IPI is silently lost). | `read_reg`/`write_reg` route by the resolved mode, and no MMIO page is mapped in x2APIC. | A lost EOI wedges the vector: the second shootdown round times out (`timeouts>0`, then the deadline panic). A lost IPI fails `x2apic_reschedule_ipi_lost cpu=N`. |
| F3 | An x2APIC MSR access while actually in xAPIC is #GP. | The mode comes from the BSP's `IA32_APIC_BASE` (`resolve_mode`), not the bootloader's report alone. A mismatch is logged. | `apic: mode MISMATCH ...` on serial. |
| F4 | ICR format errors: writing `0x831` (#GP), an 8-bit destination in x2APIC (wrong CPU), the destination in the wrong half. | One 64-bit write of `x2apic_icr(dest, low)`; host KATs pin the encoding to SDM values. | `tools/apic-logic-tests`; `x2apic_reschedule_ipi_lost` names the CPU that missed. |
| F5 | The x2APIC ICR WRMSR is not serializing, so the target can take the IPI before the sender's stores are visible (stale shootdown payload, missed queued work). | `mfence; lfence` before the ICR write. | Hard to provoke under TCG. This is a review invariant, named in the Codex dispatch. |
| F6 | Destination-mode mismatch: x2APIC logical mode uses the read-only cluster LDR, so code that assumed flat logical mode would misroute. | Physical destination mode only (ICR bit 11 = 0), as before. | Review: no LDR/DFR writes exist. |
| F7 | An MSI destination above 255 without interrupt remapping. The 8-bit field truncates, so 256 aliases APIC 0. | `msi_address_for_bsp` refuses. `configure_msi*` returns false, which callers already treat as "no MSI" (NVMe errors out, xHCI polls). Named serial line. | `apic: MSI REFUSED: BSP lapic_id=N ...`. |
| F8 | MSI hard-wired to APIC ID 0 (`0xFEE0_0000`) whatever the BSP is. A BSP whose ID is not 0 gets device interrupts on another CPU or on none. Pre-existing, not x2APIC-specific. | The MSI address now targets the BSP's registered ID. | `x2apic_smp_ipi` asserts BSP-0 gives `0xfee00000` (the old constant). A non-zero BSP shows in `apic: cpu=0 lapic_id=`. |
| F9 | Mixed modes across CPUs: an AP left in xAPIC while the BSP is in x2APIC (firmware oddity), or the reverse. | `init_local_x2apic` halts an AP whose MSR is not in x2APIC, with a named line. | `apic: cpu=N ... is NOT in x2APIC mode ... halting this CPU`, then the AP ready-barrier degrade line. |
| F10 | A non-zero EOI write in x2APIC is #GP. | `end_of_interrupt` writes 0. | A #GP from any IRQ handler would show immediately. |

## 4. Expected next-layer failures on the laptop (blind-hardware discipline)

The PL's laptop run is the acceptance proof. QEMU cannot model firmware-locked x2APIC, only "x2APIC
available". These are the most likely ways the next boot still fails even if this fix is right:

1. **No working legacy PIC / PIT path.** The kernel tick is PIC IRQ0 on the BSP. Many modern laptops ship
   without a usable 8259/PIT, or with the HPET legacy-replacement route off.
   - Discriminator: serial reaches `apic: mode=x2APIC` and the AP bring-up, then time stops (no scheduler
     progress or tick-driven lines).
   - Fix shape: an LAPIC- or HPET-based tick. That is a separate, larger lane.
2. **An APIC ID above 255.** Some many-core parts number IDs sparsely.
   - Discriminator: the `smp: starting cpu_id=.. lapic_id=..` lines. IPIs handle it (32-bit ICR). MSI
     refuses only if the BSP's own ID is above 255.
3. **Interrupt remapping expected by firmware.** Limine (rev 5+) turns VT-d interrupt remapping off.
   x2APIC with IDs ≤ 255 works without it.
   - Discriminator: the MSI REFUSED line, or a device that never interrupts (NVMe probe error / xHCI
     falling back to polling).
4. **Serial.** A laptop may have no legacy COM port, so the boot log may need the NVMe log sink (runbook)
   instead.

## 5. 32-bit LAPIC ID audit

- `apic::LAPIC_IDS`, `register_lapic_id`, `lapic_id_for_cpu`, `smp::bring_up_aps` and `MpInfo::lapic_id`
  are `u32` throughout. No narrowing exists.
- **IPI destination.** The xAPIC ICR masks to 8 bits, which is architectural: xAPIC IDs are 8-bit. The
  x2APIC ICR carries all 32 bits.
- **MSI/MSI-X.** `drivers::pci::configure_msi_fixed_vector` / `configure_msix_fixed_vector` are the only
  constructors. Every driver (NVMe, virtio-blk, virtio-accel, xHCI, AHCI) goes through them. No other
  `0xFEE…` address is built anywhere (grep).
- **No other APIC register access.** The IOAPIC is unused; the LAPIC timer is test-only, through the same
  `write_reg`.

## 6. Pitfall-bank consultation (introduce / guard / N-A)

| CP | Class | This change |
|---|---|---|
| CP-4 | Shooting down a CPU not running your space | N-A: the target set is unchanged. |
| CP-5 | Freed page-table teardown flush | N-A. |
| CP-6 | INVLPG / CR3 ordering | N-A. |
| CP-7 | ACK before EOI in the IPI handler | Guarded, unchanged: the handlers are the same; only the EOI write's register path differs. |
| CP-8 | Shootdown to a not-yet-ready CPU | Guarded, unchanged: the ready mask is the same. In x2APIC an AP that halts in F9 never marks itself ready. |
| CP-9 | Store→load reordering, missing fence | **Introduced and guarded:** the x2APIC ICR WRMSR is not serializing, where the xAPIC MMIO store was ordered. `mfence; lfence` (F5). |
| CP-15 / CP-21 | EOI-only reschedule IPI | N-A: same handler and semantics. |
| CP-22 / CP-23 | IPI lost at `sti; hlt` / MWAIT | N-A: idle is unchanged. |
| CP-27 | Reschedule IPI to an AP still in init | Guarded, unchanged. |
| CP-64 | A long `IF=0` section on a shootdown-ready CPU | N-A. |
| **CP-68** | New: xAPIC assumed on firmware-locked x2APIC silicon | Introduced as the bank entry; guarded by this build. |

## 7. Coverage and the kill-switch

- **Existing gate scenarios still take the xAPIC path.** Measured locally (QEMU 8.2): `smp_same_cpu_ipc`
  on `qemu64` and `kernel_rng_selftest` on `-cpu max` both log `apic: mode=xAPIC` and pass. QEMU 8.2's TCG
  cannot emulate x2APIC at all ("TCG doesn't support requested feature: x2apic"). CI's image builds QEMU
  10.2.3, where it can, so `x2apic_smp_ipi` asks for `-cpu max,+x2apic` there.
- **Measured on QEMU 10.2.3 (built locally from the CI tag).** Plain `-cpu max` also comes up in x2APIC
  under CP-68, so **every `-cpu max` gate scenario runs in x2APIC mode on CI after this merges**:
  - all 32 (the desktop session set, `product_integration` with both boots, the Arthur memory set,
    XSAVE/MXCSR, vault, https) passed in the guest in x2APIC;
  - the `qemu64` scenarios stay xAPIC (`smp_same_cpu_ipc`, `wait_any_core`, `token_park_teardown_churn`
    all pass, `mode=xAPIC`).
  - Two desktop scenarios once failed xtask's ordered serial post-check after passing in the guest. That
    is serial interleaving, written up separately in `Plans/NOTE-2026-10-21-serial-line-interleave-s2.md`
    (one cause is pre-existing by construction; the other is unproven and being measured A/B).
- **The kill-switch is `xapic-only`.** It restores the pre-CP-68 request (flags 0), so the xAPIC branch
  of every function is today's code. The host KATs pin `xapic_icr` and `msi_address(0)` to the old
  encodings byte for byte.
- **Behaviour change on the OptiPlex (for the PM).** Requesting x2APIC means Limine enables it on any CPU
  that supports it. The OptiPlex and M710q CPUs do, so after this merges they run in x2APIC mode too,
  where they ran xAPIC before. It is the same code path the laptop needs, but it changes the proven B1
  acceptance machine. A re-run of the OptiPlex acceptance boot is recommended. Building with
  `xapic-only` restores the old behaviour there if needed.
