## 1. Expected failure modes + discriminators (the standing blind-run section — pre-seeded from your forensics)
- **FM-1 — userland livelock in the M2/M3 encrypted write path** (whole-file-rewrite / write-ahead nonce / truncate-backed rewrite loop re-trying forever — would explain endless virtio-blk traffic). *Discriminator:* per-step progress breadcrumbs in the encrypted-memory test binary (one serial line per test step, numbered) — the hang then names the exact step; plus a write-attempt counter breadcrumb (same step repeating = livelock, distinct steps = slow-but-alive).
- **FM-2 — kernel FS / virtio-blk completion race under stretched timing** (a completion consumed twice / a request re-submitted — "repeated completions" is suggestive). *Discriminator:* breadcrumb the block-request submit/complete with a request ID or sector — the log then shows whether the SAME request loops (kernel resubmission bug) or NEW requests flow (userland loop, see FM-1).
- **FM-3 — scheduler / IPC lost-wakeup on the spawn hand-off** (user process spawned but never runs, or blocks forever on an IPC the parent already answered; init waits forever). *Discriminator:* a first-instruction breadcrumb from the spawned test process + a breadcrumb on what neo-init is blocked in — "spawned but first-instruction never printed" (scheduler) vs "test process alive but IPC-blocked" (rendezvous) are then distinguishable at a glance.
- **FM-4 — harness-side serial stall** (unlikely — virtio-blk lines keep flowing, so the guest and the serial path are alive; include only to rule out). *Discriminator:* the timestamped breadcrumbs above make guest-side liveness explicit.
