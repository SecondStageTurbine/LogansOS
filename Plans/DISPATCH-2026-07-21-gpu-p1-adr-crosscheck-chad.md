## The claims that carry the ADR (pressure-test each)
1. **The blur kernel spec + its byte oracle (effect closure).** ADR-077 specifies a separable Gaussian blur over linear XRGB8888 (r=8, Q16 integer weights, clamp-to-edge, two-pass H→mid→V, 32×8 workgroups, **no SLM**) with a hand-computed 8×8 byte oracle. Pressure-test: (a) is the **byte oracle genuinely independent + correct** (raw-recompute it yourself — the exact-bytes rule; a wrong oracle passes a wrong kernel green)? (b) Is a separable two-pass blur **actually implementable with no shared-local-memory** on Gen9, or does the mid-buffer/neighbor-gather quietly need SLM (which would move it into the untested-silicon-shape bucket)? (c) Does **Q16 fixed-point actually yield the claimed bit-for-bit GPU ≡ CPU-floor kill-switch equality**, or can rounding diverge between the EU and the CPU reference?
2. **The minimal cap ABI is sufficient.** `Handle::GpuCompute` + `GPU_COMPUTE_ENABLE`, reusing the `GpuSubmitCap`/`authority_allows` pattern; buffers via `DeviceStorage`/`alloc_in_arena`; fence via `DispatchToken`/deadline-bounded wait. Is that ABI **actually enough to run this kernel** (bind two buffers + blur params + dispatch geometry + completion), or does it omit something the blur needs? Is the **kill-switch equality provable** (disabled ≡ CPU floor bit-for-bit), or is there a GPU-on path that produces different bytes?
3. **The I-14(c) sequencing — YOUR load-bearing finding, verify it's discharged.** ADR-077 adopts your catch: the graphics **VT-d / fenced-physical-DMA boundary must precede any userland compute queue** (PPGTT isolates contexts, not host physical memory), with a **manifest-only kernel-trusted blur allowed as a risk-accepted stage before it**. Verify: (a) is a kernel-trusted blur running *before* the physical fence genuinely safe as a bounded bring-up stage, or does even that path's DMA need the fence first? (b) Does the ADR keep the **userland** compute queue strictly behind the fence? (c) Is the risk-acceptance scoped and reversible (kill-switch), not a permanent hole?
4. **The silicon-shape delta is complete + honest (gate 4).** ADR-077 lists the new hardware shape this one kernel introduces vs. Phase-6 (2-D `GPGPU_WALKER`, SIMD32 multi-group occupancy, dependent two-pass inter-dispatch coherence via `PIPE_CONTROL` flush + MOCS). Is that the **complete** list, or does the blur need something Phase-6 never proved that the ADR missed — and is `PIPE_CONTROL` + MOCS actually **sufficient for the two-pass cache coherence** (the H-pass output must be visible to the V-pass read), or is there a flush/visibility gap? Cross-check claim 1's "no SLM/barriers/atomics/images."
5. **The build ladder, the ocloc/Linux-host reality, and no-contradiction.** 6 slices: CPU floor → compute ABI (kill-switch off) → pinned kernel via **ocloc** → UHD 630 silicon gate → VT-d narrowing → wire to G1. (a) Does the ladder correctly use the **proven ocloc/OpenCL-C path** and NOT reintroduce the WGSL→EU compiler monster (your P2 finding)? (b) **Practical gap check:** your P2 spike found the ocloc container is **Linux-only** — does the ladder account for a Linux host to compile the kernel, or does it assume the Windows dev box? (c) Any contradiction with OT-63 (`GpuSubmitCap`/scanout-fence), ADR-032 (Phase-6), or the ratified glass direction?
