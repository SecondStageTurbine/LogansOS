RAG healthy. **FAIL for the claim that no long-lived caller accumulates pins; charge serialization and lifetime pass with the partial-map qualification below.** No production changes.

- **1 PASS - charge and publication are serialized.** `kernel/src/mm/pmap.rs:1016` takes IRQ-safe inner, then borrowed_pins (`:1018`); cap check, `ObjCharge::new` (`:1032`), cursor reservation and pin push (`:1057`) all occur before inner is released. `lock_inner` returns `IrqSafeGuard` (`:538`, `:556`). Two CPUs on one Pmap cannot both use a stale pin count or cursor. Across Pmaps sharing an account, hierarchical checked CAS (`kernel/src/mm/mem_account_logic.rs:193`) arbitrates the budget. Under obj-quota every published pin is a tuple owning its charge (`pmap.rs:137`); no alternative pin push exists.
- **2 PASS for exactly-once lifetime accounting; error release is not always immediate.** After charging but before the push, cursor overflow/user-half errors (`kernel/src/mm/pmap.rs:1041`, `:1044`) drop the local tuple and return its charge. After the push, a map_user_locked error (`:1062`) intentionally leaves the pin, charge and cursor range in the Pmap until drop: earlier borrowed PTEs may already exist. Releasing that pin on the error without removing/shooting down the PTEs would be wrong. Thus a literal demand to roll back every failed map immediately is not met; this is the documented pre-existing bounded partial-map policy, now correctly charged. No independent release path can double-return it: ObjCharge is not Clone and its Drop releases its stored bytes once (`mem_account_logic.rs:249`, `:271`). Pmap's drop clears its page tables, shoots down before freeing (`pmap.rs:1242`), then automatic field drops release the pin tuples. Mid-syscall force-kill cannot strand a newly created charge on a raw-freed stack: creation through transfer to the Pmap is IF-off; the syscall does not park (`kernel/src/arch/x86_64/syscall.rs:7977`). Kill after publication leaves ownership with the Pmap until teardown.
- **3 PASS for cap/budget refusals, with the same partial-map distinction.** `MAX_BORROWED_PINS=1024` is gated only by atrium-compositor-g1 (`kernel/src/mm/pmap.rs:126`), and its check is outside cfg(obj-quota) at `:1019`. Full cap returns before charge, cursor movement or PTE changes. Refused budget returns at `:1037`, before cursor movement (`:1047`) and push (`:1057`); account rollback leaves no persistent counter change. Both errors become ENOMEM through the syscall's Pmap error fallback. An OutOfFrames failure later in the map loop can retain state as item 2 explains; do not generalize the state-free claim to every Pmap error. Concrete distinction: exhaust intermediate-table frames on page N of a multi-page map; the already-published pin/charge stays until Pmap drop, so such a failed attempt consumes one cap entry.
- **4 FAIL (P2) - desktop Home repeatedly maps into its long-lived WM.** `userland/neo-init/src/desktop_session.rs:1135` loops Home -> `arthur_session` (`:1146`) -> Home (`:1158`) without replacing the WM Pmap. Every session receives a fresh Arthur buffer and maps it read-only (`:1238`, `:1257`). The comment itself says this mapping is never unmapped (`:1261`). Fixed WM planes also consume pins at startup (`:121`, `:292`). Concrete input: boot desktop-home, launch Arthur, close it back to Home, and repeat in the same desktop session until the cumulative successful maps reach 1024 (or a configured object budget refuses earlier). The next compositor-role map returns ENOMEM, arthur_session returns 15 (`:1259`), and the outer WM loop exits on that code (`:1155`). Thus these are not all session-start mappings, and absence of a libneo munmap wrapper does not establish absence of accumulation. Additional per-launch mappings can reach the limit sooner. This is a source call-path counterexample, not a 1024-launch QEMU reproduction; existing frame/VA retention may hit a different resource limit earlier on a small-memory machine. Add a repeated Home/Arthur lifecycle leg and choose an explicit reuse/unmap/retirement policy.
